## Скрапперы

Скрапперы отвечают за сбор данных. Core не знает, что такое ютуб или любой другой источник: он получает только record: универсальные поля (ссылка на источник, дата публикации, дата скраппинга и т. п.) и `metadata` со специфичными для источника данными.

Каждый скраппер создаётся пользователем в его кабинете, регистрируется в core с собственным scraper_id и owner и после создания поднимает свой сайт настройки. Это пользовательский компонент; администратор управляет учётными записями, а не создаёт скрапперы за пользователей. Владелец сам определяет публикацию, устройство и доступ к сайту: может открыть его в интернете, оставить без входа или задать свои логин и пароль. Сессия core и доступ системного администратора на этот сайт не обязательны; местный логин admin не даёт административных прав в core. Независимо от сайта core принимает данные только с действующими полномочиями зарегистрированного скраппера и подставляет его owner.

Каждый скраппер обязан заполнить source_id, source_url и trust_level записи и привести source_url к каноническому виду. Core аутентифицирует scraper_id, подставляет owner из регистрации и проверяет неотрицательный целочисленный trust_level. Уникальный ключ — (owner, source_id, source_url). Одинаковые материалы разных владельцев принимаются как независимые записи, включая отдельные файлы и обработку; совпадение URL не открывает чужую копию. Source_id обозначает тип источника (youtube, telegram), а не идентификатор экземпляра скраппера.

Уровень доверия назначает скраппер по настройкам своего сайта при формировании записи. Он сохраняется вместе с записью в локальной очереди, чтобы повторная отправка использовала то же значение. Повторная отправка существующей записи этого owner не меняет её trust_level. Владелец может отдельно изменить уровень своей записи в кабинете core. Скраппер не выбирает другого owner и не получает доступ к поиску или служебным очередям балансировщика.

Скрапперы сами отвечают за целостность данных: если получить запись целиком не удалось (например, нет интернета), она в core не отправляется. Пустую запись (без текста и без файлов) скраппер тоже не отправляет; если core всё же отклонил запись как пустую (HTTP 422), скраппер пишет это в лог и удаляет запись из очереди.

#### Отправка в core

Все запросы содержат `X-Scraper-ID: <scraper_id>` и `Authorization: Bearer <секрет скраппера>`. Лимит файла — `GET /api/limits`; проверка записи — `GET /api/records/status?source_id=...&source_url=...` или `GET /api/records/{record_id}/status`; отправка — `POST /api/records` (`multipart/form-data`: JSON-часть `record`, затем бинарные части `files`). Точные поля и ответы — в [HTTP API](../api.md).

Каждый скраппер держит очередь отправки в core (SQLite, FIFO, персистентна) и папку с файлами записей, ожидающих отправки. В core одновременно находится не больше K незавершённых записей скраппера (K задаётся в конфиге скраппера): пока core разбирает следующую запись, GPU обрабатывает задачи предыдущих.

1. Пока незавершённых записей меньше K, скраппер отправляет следующую запись из начала очереди через `POST /api/records`. Core регистрирует её, сохраняет файлы и сразу отвечает `202`, не дожидаясь разбора (см. Core, 3.1).
2. Скраппер периодически вызывает `GET /api/records/{record_id}/status` для отправленных записей. Любая проверка существования или статуса в core ограничена owner его регистрации, в том числе по ID и по source_id/source_url; чужая копия даёт тот же ответ unknown, что отсутствующая. Пока запись в обработке (processing), она и её файлы остаются в очереди и в папке.
3. Когда core отвечает `done` или `error`, скраппер удаляет запись из очереди и её файлы из папки, освобождая место для следующей.
4. Если core отвечает `unknown` (записи нет: например, core упал при приёме), запись отправляется заново.

#### Файлы больше `max_file_size`

Размер каждого файла не должен превышать `max_file_size` core (значение отдаётся по API core, по умолчанию около 15 ГБ). Запись, в которой хотя бы один файл больше, в core не отправляется целиком: скраппер удаляет скачанное и заносит её в свою SQLite-таблицу «пропущено по размеру». Размер проверяется до скачивания, если источник его сообщает, и после скачивания. Перед добавлением записи в очередь скраппер сверяется и с этой таблицей, поэтому сканеры не скачивают такую запись повторно на каждом проходе. Для Telegram это почти недостижимо: лимит файлов там 2–4 ГБ.

#### Записи с ошибкой и повторная отправка

Когда core отвечает error, скраппер удаляет запись из своей очереди и папки с файлами и повторно её не отправляет: запись остаётся в core в статусе error. Перезапуска нет; запись можно удалить в кабинете core или через API с проверкой прав (Core, 6 и 11.5). После удаления своей копии core отвечает на неё unknown, даже если у другого пользователя есть такой материал. Скраппер отправит её заново, только если снова встретит.

Ограничение: снова встречают запись только режимы, которые на каждом проходе пересканируют источник целиком, — сканеры каналов, плейлистов и истории YouTube. Сканеры Telegram читают только сообщения после `last_message_id`, а Telegram-бот скраппера YouTube принимает ссылку один раз, поэтому сами удалённую запись не пришлют: ссылку нужно заново отправить боту вручную. Для сканеров Telegram это открытый вопрос (Core, 10).
