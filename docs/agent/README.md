## Агент

Приложение агента предоставляет пользователю ИИ-поиск, ручной поиск и Telegram-бот. Они могут входить в один монолит и разворачиваться в одном контейнере. При этом каждый режим — отдельный зарегистрированный агент со своим agent_id, owner и trust_level на сервере core (Core, 11). Для веб-интерфейса и Telegram режимы регистрируются отдельно, если используются оба интерфейса; ИИ-поиск и ручной поиск не делят одну регистрацию.

Каждый зарегистрированный agent_id является отдельным источником задач для балансировщика. Его очереди транскрибации, OCR и эмбеддингов отделены от очередей других режимов и пользователей, а результаты возвращаются только инициировавшему запрос режиму. Общий контейнер и адрес допустимы: API маршрутизирует служебный вызов по несекретному task_source_id регистрации (Core, 4.2). Core хранит реестр агентов и их права, но не их задачи. Все агенты равноприоритетны и выше core. Единственный балансировщик получает актуальные источники из core; приложение агента не создаёт балансировщики и не задаёт свой приоритет. За поиском и чтением каждый режим обращается к core с agent_id и автоматически выданным core token. Core проверяет эту пару и отклоняет запросы без любого из двух значений или при их несоответствии.

### Главный веб-интерфейс

Веб-интерфейс — основная точка входа в пользовательское приложение агента. Владелец может менять его, публиковать в интернете и сам задавать доступ: открытый сайт либо собственные логины и пароли, в том числе admin. Сессия core на сайте агента не обязательна; местные роли не дают прав в core. Создание агентов, назначение их прав и управление пользователями выполняются в отдельном кабинете core под его аутентификацией (Core, 6 и 11).

Приложение хранит agent_id и token на серверной стороне и использует их при обращениях к core. Посетитель сайта получает те возможности, которые открыл ему владелец; публичный интерфейс не расширяет owner и trust_level зарегистрированного агента. Настройки, история и результаты локального приложения управляются владельцем сайта. Core обеспечивает изоляцию своих данных независимо от устройства интерфейса, включая обращения по прямому ID. Из приложения доступны разделы:

- **ИИ-агент** — диалог на естественном языке: ИИ-агент сам составляет поисковые запросы, читает найденное и формирует ответ со ссылками на источники.
- **Ручной поиск** — пользователь сам задаёт запрос и фильтры, просматривает результаты и открывает найденные данные без участия LLM.
- **Telegram-бот** — просмотр состояния, включение и выключение бота. Выбранное состояние сохраняется между перезапусками контейнера. Выключение бота прекращает приём новых запросов из Telegram; веб-интерфейс и оба режима поиска в нём продолжают работать.

### Telegram-бот

Бот — встроенный интерфейс того же приложения. В Telegram пользователь может выбрать **поиск через ИИ-агента** или **ручной поиск**. Оба режима используют ту же реализацию поиска и контракт API core, что и веб-интерфейс, но каждый обращается со своим agent_id и использует свою область очередей. Какие Telegram-аккаунты могут пользоваться ботом, определяет владелец приложения. Выбор режима выбирает настроенную для него регистрацию; приложение обращается к core с её agent_id и token. Вне зависимости от доступа к боту core проверяет полномочия этой регистрации.

В режиме ИИ-агента бот принимает запрос, проводит поиск через ИИ-агента и возвращает ответ со ссылками. В ручном режиме бот позволяет задать поисковый запрос и фильтры, перейти к следующей странице результатов и открыть найденный объект. Переключение режимов доступно в интерфейсе бота.

### Ручной поиск

Веб-интерфейс предоставляет форму поиска, а бот — диалог и кнопки для задания тех же условий. Пользователь выбирает тип искомого объекта, фильтры и сортировку. Доступные поля и операции определяются через `GET /api/search/schema`. Для поиска по смыслу можно указать семантический запрос; его эмбеддинг агент получает через свою очередь и балансировщик. Поиск только по фильтрам эмбеддинга не требует.

Приложение преобразует выбранные условия в JSON-тело `POST /api/search`, показывает результаты со ссылками на источники и поддерживает постраничную выдачу. Через `POST /api/read` пользователь может открыть метаданные, дочерние объекты и сохранённый текст. LLM в ручном режиме не вызывается: пользователь получает найденные данные без сгенерированного ответа.

### Цикл обработки запроса через ИИ-агента

1. Пользователь вводит запрос в веб-интерфейсе или отправляет сообщение боту. Например, в Telegram можно отправить голосовое сообщение.
2. Если нужна транскрибация, приложение кладёт задачу в очередь выбранного agent_id. Все агенты имеют одинаковый приоритет выше core: при следующем запросе `GET /api/task-sources/{task_source_id}/check_tasks` балансировщик может вытеснить работу core. Другой агент с равным приоритетом не вытесняется; порядок при равенстве задаётся по ID.
3. Приложение запускает ИИ-агента с текстом запроса. Тяжёлые задачи, которые понадобятся дальше (эмбеддинг запроса для семантического поиска, OCR присланной картинки), также ставятся в очередь того же agent_id.
4. ИИ-агент ищет ответ с помощью инструментов (см. ниже).
5. Приложение возвращает ответ со ссылками в тот интерфейс, из которого пришёл запрос.

### API поиска и инструменты ИИ-агента

Оба режима поиска используют HTTP API core: `GET /api/search/schema`, `POST /api/search`, `POST /api/read`. Каждый запрос содержит `X-Agent-ID: <agent_id>` и `Authorization: Bearer <token агента>` выбранного режима. В режиме ИИ-агента параметры инструментов составляет LLM, а приложение выполняет HTTP-запросы; в ручном режиме приложение собирает параметры по условиям пользователя. Заголовки, параметры и примеры ответов закреплены в [HTTP API](../api.md). Произвольных SQL, Python, выражений и команд оболочки в этом языке нет. Приложение проверяет вызов и передаёт запрос в API core; доступов и паролей БД у модели и приложения нет. Поисковый API отделён от API приёма записей, очередей и административных операций; через него агент выполняет только поиск и чтение. Для удаления своей записи есть отдельная операция DELETE /api/records/{record_id} с обязательной серверной проверкой owner и trust_level (Core, 11.5); она не позволяет менять уровни доверия, пользователей или регистрации.

#### Что действительно можно прочитать

В БД остаются дерево объектов, их поля и метаданные, текст chunk'ов и эмбеддинги. Содержимое text читается из его chunk'ов в порядке `ord`; отдельной полной копии текста нет. Границы chunk'ов сохраняются в ответе: инструмент не обещает восстановить исходное форматирование документа.

Изображения photo, аудиодорожки audio и отрендеренные страницы не хранятся долговременно. Наличие строки element или fragment не означает наличие готового медиафайла. После завершения обработки `task_storage` очищается, и инструменты агента его не используют. Долговременно хранится исходный file, из которого потенциально можно заново извлечь данные по `meta` (Core, 3.3).

Обязательных `get_fragment` с рендерингом и `get_element` с возвратом медиа нет. В первой версии агент читает сохранённый текст и метаданные и даёт ссылку на источник. Повторное извлечение медиа из исходника — отдельная возможность на будущее: она потребует поддержки конкретного формата и ограничений на вычисления. Примеры извлечения в Core, 3.3 описывают механизм, а не обязательные инструменты агента.

#### `GET /api/search/schema` — узнать доступные поля

Необязательные query-параметры: `target` (тип объекта), `source_id` (источник). Без них возвращается вся схема. Ответ `200` содержит версию схемы языка, типы объектов, доступные поля, связи, типы значений, операции фильтрации и пределы запросов. Можно запросить описание целиком либо для конкретного типа объекта и источника. Метаданные источников и форматов описываются здесь же, а не зашиваются в промпт агента.

Поиск доступен по разрешённым схемой полям выбранного объекта и его предков, включая `record.metadata` и `file/fragment/element/text.meta`. Числовые массивы эмбеддингов не выдаются и не используются как обычные фильтры: для них есть семантический поиск; `embed_model` доступен как обычное поле. Поля record.owner, record.scrapper и record.trust_level описаны в схеме, но условия на них только сужают уже разрешённую область. Таблицы пользователей и регистраций агентов через search/read недоступны. Доступ к полям не даёт доступа к служебным таблицам задач, путям файловой системы или секретам. Метаданные схемы не включают значения из записей других пользователей.

Для JSONB путь задаётся массивом ключей, например `{"scope":"record","path":["metadata","chat_id"]}`. Зарегистрированные пути имеют тип в `schema`. Незарегистрированный путь тоже можно проверить на существование или сравнить с явно типизированным значением; это не возможность передать SQL. Отсутствующий ключ, JSON null и SQL NULL различаются отдельными операциями. Неподходящие типы не приводятся молча.

#### `POST /api/search` — поиск с фильтрами по всему пути к record

Параметры JSON-тела (обязателен только `target`):

- `target`: какой тип возвращать — `record`, `file`, `fragment`, `element`, `text` или `chunk`.
- `query`: необязательный объект с обязательными полями `embedding` (числовой вектор) и `embed_model` (имя модели). Текстовая строка вместо объекта не принимается. Агент получает эмбеддинг через собственную очередь и балансировщик и передаёт в core вектор и имя модели. Поиск идёт по совместимым эмбеддингам chunk'ов; другие модели не смешиваются. Если подходящего индекса нет, возвращается явная ошибка.
- `where`: дерево условий `all`, `any`, `not` и сравнений полей. Пустое условие означает отсутствие дополнительных фильтров.
- `select`: какие поля выбранного объекта и его предков вернуть. Обязательные идентификаторы и происхождение результата добавляются core.
- `order_by`: массив объектов с `scope`, `path`, `direction` (`asc` или `desc`), для fragment-предка также точная `depth`; для семантического поиска по умолчанию сначала самые близкие результаты.
- `limit`, `cursor`: размер страницы и непрозрачный курсор продолжения. По умолчанию `limit = 20`, `cursor = null`; верхние пределы задаёт core и публикует в `GET /api/search/schema`.

Без `query` инструмент выполняет обычную выборку по условиям и не требует эмбеддинга: например, «последние сообщения автора», «все PDF за неделю», «соседние chunk'и этого текста». Относительные даты агент переводит в абсолютные границы с учётом часового пояса пользователя; в core уходят даты со смещением UTC.

**Области полей (`scope`).** `self` — выбранный объект; остальные имена обозначают объекты на его фактическом пути вверх: `text`, `element`, `fragment`, `file`, `record`. Например, у chunk результата OCR путь проходит через text, photo, его fragment и file до record. У chunk собственного текста записи есть только text и record; отсутствующие связи не выдумываются. Несуществующая для типа связь — ошибка схемы; допустимая, но отсутствующая у конкретного объекта связь не удовлетворяет сравнению, кроме явной проверки отсутствия.

`fragment` обозначает ближайший fragment, включая сам объект, если `target = fragment`. Для вложенности есть условие `ancestor_fragment`: оно требует существования одного fragment выше ближайшего, удовлетворяющего вложенному `where`. Все сравнения внутри такого условия относятся к одному предку, а не к разным страницам или уровням. Можно указать точную глубину от ближайшего fragment (1 — его родитель). В результатах возвращается упорядоченный путь fragment с идентификаторами и запрошенными метаданными.

Поддерживаются равенство и неравенство, сравнение чисел и дат, принадлежность списку, буквальное вхождение подстроки, проверки NULL и наличия ключа, операции над JSON-массивами. Точный набор для каждого типа описан в `schema`; произвольных функций, регулярных выражений или SQL-фрагментов нет. Сортировка по предкам fragment требует точной глубины, чтобы поле имело однозначное значение.

Пример HTTP-тела: найти текстовые chunk'и из PDF, опубликованных в Telegram за октябрь, на странице с определённой меткой. Вектор в примере сокращён до трёх чисел; реальный запрос передаёт 2048 значений эмбеддинга текста «как работает asyncio», полученного через очередь агента. Ключ `page` здесь условный: использовать его можно, если он описан для этого формата в `schema`.

```json
{
  "target": "chunk",
  "query": {
    "embed_model": "Qwen3-VL-Embedding-2B",
    "embedding": [0.12, -0.34, 0.56]
  },
  "where": {
    "all": [
      {"scope": "record", "path": ["source_id"], "op": "eq", "value": "telegram"},
      {"scope": "record", "path": ["source_created_at"], "op": "gte", "value": "2026-10-01T00:00:00+03:00"},
      {"scope": "record", "path": ["source_created_at"], "op": "lt", "value": "2026-11-01T00:00:00+03:00"},
      {"scope": "file", "path": ["mime"], "op": "eq", "value": "application/pdf"},
      {"scope": "fragment", "path": ["meta", "page"], "op": "eq", "value_type": "integer", "value": 3}
    ]
  },
  "select": [
    {"scope": "self", "path": ["text"]},
    {"scope": "record", "path": ["title"]},
    {"scope": "file", "path": ["name"]},
    {"scope": "fragment", "path": ["meta"]}
  ],
  "limit": 20
}
```

**Семантика совпадения.** Если задан `query`, сначала условия проверяются на каждом кандидате chunk и его пути вверх, затем выполняется семантический поиск среди подходящих кандидатов. Для `target`, отличного от chunk, результат поднимается до выбранного объекта. Фильтры на `self` относятся к этому объекту. Поля ниже выбранного объекта в `where` недоступны: для условия на element нужно искать element или chunk, а не record. Если у одного объекта совпали несколько chunk'ов, он возвращается один раз, оценка — лучшая из оценок его подходящих chunk'ов. Ответ включает ограниченный список chunk'ов, подтверждающих совпадение. Дедупликация выполняется до применения лимита результата, чтобы одна большая запись не занимала всю страницу.

**Ответ `200`.** `items`, `next_cursor`, `schema_version`, `truncated`. Каждый результат содержит свой тип и ID, `record_id`, доступные ID объектов на пути, выбранные поля и сведения для ссылки: `source_id`, `source_url`, заголовок/автор/дата, доступная позиция в файле из метаданных. При семантическом поиске добавляются `score` (оценка близости) и `matches` (найденные chunk'и). Картинка без текста возвращается как совпадение по изображению с метаданными, а не как придуманное текстовое описание. Оценка близости не является вероятностью правильного ответа.

Обычная выборка имеет стабильную сортировку с ID в конце для разрешения равенств. При семантическом поиске core сохраняет ограниченную выдачу на время жизни курсора: продолжение не должно заново ранжировать первую страницу. При исчерпании бюджета или приблизительном поиске core явно сообщает, что выдача может быть неполной; отсутствие результатов не доказывает отсутствие данных. Истёкший курсор возвращает ошибку, после которой агент запускает поиск заново.

#### `POST /api/read` — дочитать найденное

JSON-тело: обязательные `target` (тип объекта), `id`, `mode` (`metadata`, `children` или `text`); необязательные `select` для metadata, `limit` (по умолчанию 20), `cursor` (по умолчанию null). Ответ `200` содержит `schema_version`, `items`, `next_cursor`, `truncated`. Читает только данные БД:

- `metadata` — поля объекта и путь предков, с той же схемой `select`, что у `search`.
- `children` — страница непосредственных детей в порядке дерева: у record — собственный text, затем file по `ord`; у file и fragment — fragment по `ord` либо содержащийся text/element; у photo/audio — существующий результирующий text; у text — chunk по `ord`. Служебные task не возвращаются. Равенства разрешаются по ID.
- `text` — сохранённые текстовые chunk'и объекта или его поддерева, с ID и границами каждого chunk, типом текста (собственный, извлечённый, OCR, транскрипция) и позицией в исходнике, если она известна. Обход следует тому же порядку дерева. Пустой ответ означает отсутствие сохранённого текста; OCR и транскрипция повторно не запускаются. Chunk-картинка текста не имеет; сохранённый OCR нужно читать через его photo или соответствующий text.

Все режимы имеют ограничения на число объектов и объём текста. Так агент может расширить контекст найденного chunk, прочитать соседние куски через `search` по `text_id` и `ord`, просмотреть структуру файла или постепенно прочитать запись целиком. Лимит одного вызова не означает молчаливого обрезания: ответ содержит курсор и признак усечения.

#### Границы доступа и выполнение

- Поиск и чтение доступны только для record в `done`. Условия пользователя этого не отменяют: фильтр готовности core добавляет самостоятельно ко всем операциям, включая чтение по ID. Внутри записи доступны метаданные сохранившегося file в `error`, но его содержимое отсутствует; упавший собственный text также не имеет chunk'ов.
- Core аутентифицирует отдельную регистрацию agent_id и сам добавляет record.owner = agent.owner и record.trust_level < agent.trust_level до поиска, ранжирования, подсчётов и чтения. Равные уровни доступа не дают. Owner и уровень из тела запроса не считаются полномочиями. То же условие проверяется при чтении по ID, переходе по курсору и выдаче из кеша; чужой или недоступный ID не отличим от отсутствующего. Роль администратора у владельца не расширяет права его агента (Core, 11).
- Core разбирает JSON в типизированное дерево запроса. Типы объектов, связи, поля, операции и сортировки выбираются из схемы; значения и JSON-пути передаются параметрами. Неизвестные конструкции отклоняются. Фильтрация строк по наличию слов `DROP` или `DELETE` не используется: эти слова могут быть обычным искомым текстом.
- Поисковые запросы выполняются отдельной ролью БД с чтением разрешённых таблиц/представлений, без владения объектами, прав записи, создания объектов, перехода к привилегированным ролям и выполнения опасных функций. Вызовы проходят в транзакциях только для чтения. Учётные данные приёма записей и административных операций не используются для поиска.
- Core ограничивает глубину и число условий, размер списков и строк, время выполнения, число одновременно выполняемых запросов, размер страницы и ответа. Приложение агента ограничивает число вызовов и общий бюджет одного пользовательского запроса. Произвольные JOIN, рекурсивный SQL и функции агент задать не может.
- Ошибки имеют машинный код и краткое объяснение: неверное поле/тип/операция, превышение лимита, истёкший курсор, недоступная модель эмбеддингов. Ответы не раскрывают SQL, внутренние пути и секреты. Содержимое найденных записей считается данными, а не инструкциями агенту и не может менять его права.

### Формат ответа ИИ-агента

В веб-интерфейсе ответ отображается в диалоге, в Telegram приходит одним сообщением: сам ответ на вопрос и список ссылок на источники. Ссылки берутся из `source_url` записей (record), на которых основан ответ. Для записей с псевдоссылкой `tg://chat/…` (личные диалоги и обычные группы Telegram) вместо ссылки показываются название чата и дата сообщения. Если найдены только метаданные или совпадение по картинке без доступного текста, ИИ-агент прямо сообщает об этом и не выдаёт догадку за прочитанное содержимое.
