## Балансировщик

### Состояние реализации

В репозитории реализованы конфигурация балансировщика и отдельные воркеры
`transcribe` и `embed`. Демон балансировщика, HTTP-вызовы, загрузка входов, управление
очередью и процессами пока не реализованы. Разделы ниже о циклах, вытеснении
и HTTP описывают проектируемое поведение. Фактические протоколы `transcribe`
и `embed` зафиксированы в разделе «Контракт запуска воркера» и README воркеров.

### Назначение и конфигурация

Настройки загружаются через `from src.balancer.config.config import Config`
и `Config.from_yaml("/path/to/config.yaml")`. Из готового словаря конфигурация
создаётся через `Config.from_dict(data)`. Зависимость PyYAML указана в
`src/balancer/config/requirements.txt`. Ошибки чтения и проверки вызывают `ConfigError`.
Все параметры обязательны; неизвестные поля запрещены. YAML читается стандартным
`yaml.safe_load`: при повторении ключа используется последнее значение.
Сейчас `from_dict` проверяет строку `temp_dir`, но не передаёт её в объект:
используется значение поля по умолчанию `MAIN_DIR / "tmp"`, где `MAIN_DIR` —
каталог запускаемого Python-файла. Параметра `base_dir` нет. Это текущее
ограничение реализации; загрузка конфига не создаёт каталоги и не запускает процессы. Перед запуском замените `token` в примере
на реальный. Конфиги воркеров читаются и проверяются самими воркерами;
балансировщик их не загружает.

Балансировщик — демон, который получает задачи из core, собирает пачки и запускает воркеры `transcribe`, `ocr`, `embed`. В каждый момент на GPU работает один процесс воркера. Очередь пачек и состояние выполнения хранятся в памяти; для transcribe/OCR входы скачиваются во временные локальные файлы. Для embed новый протокол предусматривает передачу текста и base64 в памяти; этот путь в балансировщике ещё предстоит реализовать.

Конфигурация: адрес core, постоянный `balancer_id`, служебный token, интервал между стартами циклов получения задач `delay`, пауза между циклами проверки `check_delay`, интервал повторов HTTP-запросов, таймаут HTTP-запроса, каталог временных файлов. `delay` и `check_delay` — отдельные независимые параметры с разными правилами отсчёта, описанными ниже; интервал повторов HTTP также задаётся отдельно. Пороги — конечные неотрицательные числа в единицах `complexity`, возвращаемой core для соответствующего типа.

Для балансировщика `task_source_id` — непрозрачный ID источника. Список источников, приоритеты и наличие задач приходят из API. Балансировщик применяет их одинаково ко всем источникам и типам, без зашитых значений приоритетов и исключений по ID. Политика приоритетов, устройство очередей и расчёт сложности принадлежат [core](../core/04_tasks_and_queues.md).

### Цикл получения задач

При запуске балансировщика первый цикл получения задач начинать сразу. Каждый цикл набирает не более одной пачки и включает её загрузку, выполнение и отправку всех результатов или ошибок. Цикл выполняется так:

1. Вызвать общий `POST /api/task-sources/reset` и дождаться подтверждения: он снимает все взятые задачи всех источников и типов. До успешного reset к следующим шагам не переходить.
2. Получить `GET /api/task-sources` и отсортировать источники по убыванию `priority`, при равенстве — по `task_source_id` в лексикографическом порядке.
3. Обходить источники в этом порядке. Для каждого источника отсортировать очереди по убыванию их приоритета, при равенстве — по имени типа в лексикографическом порядке.
4. Обходить очереди источника. Если `has_tasks = false`, перейти к следующей очереди. Если задачи есть, набрать и выполнить одну пачку по правилам ниже. После завершения пачки и подтверждения всех её `/result` и `/fail` завершить текущий цикл получения задач. К той же очереди или оставшимся очередям и источникам в этом цикле не возвращаться.
5. Пока пачка не набрана, после исчерпания очередей источника переходить к следующему источнику. Если все источники пройдены и пачки нет, завершить цикл без запуска воркера и проверок.

Снимок не гарантирует выдачу задачи: окончательный ответ даёт `/claim`. Пустой claim до набора первой задачи означает переход к следующей очереди; если уже набрана непустая пачка, выполнить её и завершить цикл после подтверждения всех результатов или ошибок. Новые источники попадают в работу через следующий снимок, отдельных reset или инициализации для них нет.

Для каждого цикла запоминать `started_at` по монотонным часам непосредственно перед первым вызовом reset. После полного завершения цикла следующий запуск разрешён, когда с `started_at` прошло не меньше `delay`: оставшееся ожидание равно `max(0, started_at + delay - now)`. Время набора, загрузки, работы воркера и подтверждения результатов или ошибок входит в этот интервал. Следующий цикл всегда начинается с общего reset и нового снимка источников.

Например, при `delay = 20 с` цикл, начавшийся в `0 с` и закончившийся в `1 с`, оставляет `19 с` ожидания: следующий стартует в `20 с`. Если он закончился в `3600 с`, следующий стартует сразу в `3600 с`. Это же правило действует для цикла без задач и после прерывания, в том числе вытеснения или потери ответа claim. Одновременно выполняется только один цикл получения задач; пропущенные за время долгой работы интервалы не создают очередь запусков.

Пока выполнение выключено администратором в интерфейсе балансировщика, новые пачки не набирать; уже запущенная пачка завершается и передаёт результат.

### Набор и выполнение пачки

В цикле получения задач набирать одну пачку одного типа от одного источника:

1. Последовательно вызывать `/claim`, добавляя задачу и её `complexity` в сумму. Входы на этом этапе не скачивать.
2. Остановить набор, когда сумма достигла или превысила X либо `/claim` вернул `{"tasks":[]}`. Последняя взятая задача входит в пачку целиком. Пустую пачку не запускать.
3. Одновременно запустить GET всех входов пачки по их `input.url` с теми же служебными заголовками. Дождаться завершения всех загрузок и только затем запустить воркер по контракту ниже. Ответ `404` на вход исключает задачу из пачки; `/fail` для неё не отправляется. Если пачка опустела, завершить текущий цикл получения задач без запуска воркера и проверок.
4. На время работы воркера запустить параллельные циклы проверки по правилам ниже. При штатном завершении воркера остановить проверки, получить и проверить результат всей пачки, отправить его через `/result` и дождаться подтверждения. После подтверждения всех результатов или ошибок и очистки входов завершить текущий цикл получения задач. Пока отправка не подтверждена, цикл остаётся незавершённым; новые задачи не брать.
5. Удалить локальные входы после подтверждения `/result` или `/fail`, отмены работы либо исключения задачи из пачки. После перезапуска удалить оставшиеся временные файлы предыдущего запуска.

### Сбой воркера

Если воркер завершился с ошибкой на пачке из k > 1 задач, записать WARNING и заменить её в локальной очереди k пачками по одной задаче, сохранив порядок. Уже скачанные входы использовать повторно. Каждую успешную одиночную задачу немедленно отправлять через `/result`.

При падении одиночной задачи отправить `/fail`; дальнейших запусков для неё нет. `error.attempts` — число запусков воркера с этой задачей после последнего claim: 1 для исходной одиночной пачки, 2 после падения общей пачки и одиночного запуска. Сетевые повторы и принудительное завершение при вытеснении в это число не входят.

Все одиночные пачки после разделения относятся к исходной пачке и выполняются в том же цикле получения задач, без новых claim и reset. Этот цикл завершается только после обработки всей локальной очереди, подтверждения всех `/result` и `/fail` и очистки входов. Пауза `delay` между одиночными запусками не применяется.

### Цикл проверки и вытеснение

Циклы проверки запускать только после набора непустой пачки в текущем цикле получения задач, параллельно с работой её воркера. Во время reset, получения начального снимка, набора и загрузки входов, отправки результатов и ожидания следующего цикла получения задач проверки не выполнять. Для одиночных пачек после разделения проверки также работают только во время соответствующего воркера.

Первый проверочный обход начинать сразу после запуска воркера. После завершения каждого обхода выждать `check_delay` и, если воркер ещё работает, начать следующий: `next_check_start = check_finished_at + check_delay`. Длительность самой проверки в паузу не входит. Например, проверка, начавшаяся в `0 с` и закончившаяся в `1 с`, при `check_delay = 20 с` допускает следующий старт в `21 с`; если она закончилась в `3600 с`, следующий старт — в `3620 с`. Проверки не перекрываются. Завершение воркера отменяет ожидание и дальнейшие проверки.

Таймеры независимы: проверки не меняют `started_at` цикла получения задач, а `delay` не определяет частоту проверок. Каждый проверочный обход выполняется так:

1. Получить свежий `GET /api/task-sources`.
2. Отсортировать источники и очереди точно так же, как в цикле получения задач.
3. Обходить источники и их очереди, пропуская пустые. Остановиться на первом источнике, у которого найдена очередь с `has_tasks = true`. Если такого источника нет, закончить проверку до следующего интервала.
4. Сравнить приоритет найденного источника с текущим — приоритетом источника, с которым была выбрана исполняемая пачка. Если найденный приоритет не больше текущего, закончить проверку до следующего интервала.
5. Если приоритет строго больше, завершить воркер сигналом `SIGKILL` и прервать текущий цикл получения задач. Дождаться завершения воркера и старого цикла, отбросить частичный результат, очистить очередь пачек и входы отменённой работы. Затем запустить новый цикл получения задач по правилу `delay` от старта прерванного цикла; он начнётся с общего reset.

Цикл проверки не вызывает reset и claim, не скачивает входы и не запускает воркеры. Он только читает снимок и определяет необходимость вытеснения. При равенстве приоритетов вытеснения нет; приоритеты очередей определяют порядок их обхода, но сами по себе не прерывают работу. Новый reset выполняется только после остановки старого цикла и воркера; старый цикл не должен отправлять результаты или брать задачи после этого reset. Подтверждённые результаты и ошибки сохраняются.

### Сеть и перезапуск

При недоступности core приостановить набор. Уже загруженная пачка может завершиться; результат хранить до восстановления связи. Вытеснение по устаревшему снимку не выполнять. Ошибка скачивания — повод повторить GET, а не запускать воркер или отправлять `/fail`.

Поведение при ошибках HTTP и потере ответа определено в контракте ниже. Перед возобновлением claim после восстановления связи обновлять список источников.

Воркер запускать из главного потока как дочерний процесс с `prctl(PR_SET_PDEATHSIG, SIGKILL)`: он должен завершаться при гибели балансировщика. После установки сигнала проверять, что родитель ещё тот же, чтобы закрыть гонку с его завершением. После перезапуска локальная работа не восстанавливается: начать цикл получения задач с общего reset, затем запросить источники.

### HTTP-контракт с core

Это полное описание исходящих HTTP-вызовов балансировщика. Все пути относятся к адресу core из конфигурации. В каждом запросе, включая скачивание входа:

```http
X-Balancer-ID: <balancer_id>
Authorization: Bearer <token балансировщика>
```

Все POST передают JSON с `Content-Type: application/json`. GET не имеют тела и query-параметров. Все поля в примерах обязательны, если явно не указано обратное. `balancer_id` в теле должен совпадать с заголовком. ID источника и задачи — непустые строки; при подстановке в URL каждый ID кодируется как один сегмент пути.

#### `GET /api/task-sources`

Ответ `200`, `Content-Type: application/json`:

```json
{
  "items": [
    {
      "task_source_id": "<ID источника>",
      "priority": 10,
      "queues": {
        "transcribe": {"has_tasks": true, "priority": 0},
        "ocr": {"has_tasks": false, "priority": 5},
        "embed": {"has_tasks": true, "priority": 5}
      }
    }
  ]
}
```

`items` — полный список без пагинации, может быть пустым; ID источников уникальны. `queues` содержит все три типа, в том числе пустые. `has_tasks` — boolean, наличие ожидающих задач на момент ответа. Оба уровня `priority` — конечные числа: большее значение означает больший приоритет; допустимы отрицательные значения и равенства. Значения в примере не задают политику или значения по умолчанию. Порядок элементов ответа не задаёт порядок обработки.

#### `POST /api/task-sources/{task_source_id}/claim`

Тело:

```json
{"type":"transcribe","balancer_id":"<balancer_id>"}
```

`type` — `transcribe`, `ocr` или `embed`. Ответ `200`, JSON с массивом `tasks` длиной 0 или 1:

```json
{
  "tasks": [
    {
      "task_id": "<ID задачи>",
      "type": "transcribe",
      "complexity": 12.5,
      "input": {
        "url": "/api/task-sources/<ID источника>/tasks/<ID задачи>/input",
        "mime": "audio/flac"
      }
    }
  ]
}
```

Пустая очередь: `{"tasks":[]}`. Параметра `limit` нет. `type` выданной задачи совпадает с запрошенным. `complexity` — конечное неотрицательное число; балансировщик использует его как готовую оценку и не пересчитывает по данным. `input.url` — путь на том же core, ведущий к эндпоинту скачивания этой задачи; `input.mime` — строка MIME. Входного содержимого в claim нет.

Успешная выдача резервирует задачу за этим балансировщиком; резервирование может быть отменено на стороне core, что проверяется при последующих вызовах. Если ответ потерян, неизвестно, была ли задача взята: отбросить набранную пачку и начать новый цикл получения задач с общего reset. Простой повтор claim может взять другую задачу и не восстанавливает потерянную выдачу.

#### `GET /api/task-sources/{task_source_id}/tasks/{task_id}/input`

Вызывать по `input.url`, полученному в claim. Ответ `200` — байты входа, `Content-Type` равен `input.mime`. Для текстового embed — UTF-8 с `text/plain; charset=utf-8`; остальные входы сохраняются как бинарные данные. Вход доступен только пока задача зарезервирована за этим балансировщиком. `404 task_not_available` означает, что вход уже недоступен; такую задачу исключить из пачки.

#### `POST /api/task-sources/{task_source_id}/result`

Тело для `transcribe` и `ocr`:

```json
{
  "balancer_id": "<balancer_id>",
  "results": [{"task_id": "<ID задачи>", "payload": {"text": "Полученный текст"}}]
}
```

`results` — непустой массив результатов задач одного источника. `payload.text` — строка; пустая строка допустима и является успешным результатом.

Для `embed` каждый элемент имеет следующий вид:

```json
{
  "task_id": "<ID задачи>",
  "payload": {"embed_model": "<имя модели>", "embedding": [0.12, -0.34, 0.56]}
}
```

`embed_model` — непустая строка с фактическим именем модели воркера; `embedding` — непустой массив конечных чисел полной размерности этой модели. В примере вектор сокращён. Балансировщик передаёт значения воркера без подмены модели или преобразования вектора.

Ответ `204 No Content`, без тела, после фиксации всех результатов. Результаты фиксируются по отдельности: если запрос оборвался, часть могла сохраниться. Повторять всё то же тело безопасно: удалённые, отменённые и уже завершённые задачи игнорируются. Существующая задача другого источника или другого исполнителя отклоняется с `404 task_not_available` без изменения этой задачи.

#### `POST /api/task-sources/{task_source_id}/fail`

Тело:

```json
{
  "balancer_id": "<balancer_id>",
  "task_ids": ["<ID задачи>"],
  "error": {
    "message": "CUDA out of memory",
    "attempts": 2,
    "worker": "transcribe",
    "model": "<имя модели>"
  }
}
```

`task_ids` — непустой массив, `error.message` — непустая строка, `error.attempts` — положительное целое. `error.worker` и `error.model` — необязательные строки. Балансировщик отправляет одну упавшую одиночную задачу за вызов.

Ответ `204 No Content`, без тела, после фиксации ошибки. Правила игнорирования устаревших задач, отклонения чужих задач и повторной отправки те же, что у `/result`. `/fail` завершает задачу ошибкой; для отмены и повторного выполнения используется `/reset`.

#### `POST /api/task-sources/reset`

Тело:

```json
{"balancer_id":"<balancer_id>"}
```

Источник в пути, теле или query не передаётся. Ответ `204 No Content`, без тела, после коммита: все задачи всех источников и типов в `processing` возвращены в `wait`, `taken_at` и `taken_by` очищены. Фильтра по источнику или прежнему `taken_by` нет; `balancer_id` в теле служит только проверке совпадения с авторизацией. Задачи в остальных статусах не меняются. Пустой набор также даёт `204`; повтор безопасен. Пока reset не подтверждён, не получать список источников для нового прохода и не брать задачи.

Для удалённого источника `/result` и `/fail` игнорируют поздние сообщения и возвращают `204`. Claim и скачивание входа удалённого источника возвращают `404 task_source_not_found`. Для неизвестного ID источника все операции с этим ID в пути возвращают `404 task_source_not_found`. Общий reset от существования отдельных источников не зависит.

#### Ошибки и повторы

Ошибки core имеют `Content-Type: application/json` и тело:

```json
{"error":{"code":"invalid_request","message":"Описание ошибки"}}
```

| Ответ / ситуация | Действие балансировщика |
|---|---|
| `400 invalid_request` — `balancer_id` в теле не совпал с заголовком; `422 invalid_request` — неверные поля, тип задачи или payload | Записать ошибку протокола и приостановить выполнение до исправления. Не повторять неизменённый запрос и не отправлять `/fail` из-за HTTP-ошибки |
| `401 unauthorized` — неверные полномочия; `403 forbidden` — нет права на операцию | Приостановить выполнение до исправления конфигурации/полномочий |
| `404 task_source_not_found` — источник неизвестен либо удалён для claim/input | Отменить локальную работу этого источника, обновить список; не продолжать claim по старому снимку |
| `404 task_not_available` при скачивании входа | Исключить задачу из пачки |
| `404 task_not_available` при result/fail | Записать нарушение контракта владения задачей и приостановить выполнение до исправления |
| `5xx`, обрыв связи, таймаут, неполный ответ | Подождать интервал повторов. GET повторить; result/fail повторить с тем же телом; reset повторить до подтверждения. При потере ответа claim начать новый цикл получения задач с общего reset |

При неизвестном результате result/fail не делать reset и не брать новую работу до подтверждения отправки. Неверный успешный ответ (некорректный JSON, отсутствующие поля, неподходящие значения) — ошибка протокола; для claim перед продолжением также требуется reset, поскольку резервирование могло состояться.

### Контракт запуска воркера

Контракт реализованного `transcribe`: [README воркера](../../src/balancer/workers/transcribe/README.md)
описывает фактическое поведение. Код находится в `workers/transcribe/src/`.
Реализован также [воркер embed](../../src/balancer/workers/embed/README.md). Он принимает один JSON-массив
`[{"task_id": "1", "text": "Текст"}, {"task_id": "2", "image": "<base64>"}]`
и возвращает `{"embed_model": "Qwen3-VL-Embedding-2B", "embeddings": {"1": [0.12], "2": [0.34]}}`.
Векторы здесь сокращены: реально каждый содержит 2048 чисел. У задачи ровно одно
из полей `text` (до 2000 символов с пробелами) и `image` (base64 без data URI).
Входные файлы, MIME и тип задачи ему не передаются; данные обрабатываются в памяти.
Имя модели возвращается один раз на пачку. Текстовые и графические внутренние
батчи разделены. Адаптер результата к HTTP `/result` пока не реализован.
Воркер `ocr` пока не реализован. HTTP-контракт core выше остаётся отдельным интерфейсом.

Далее описан контракт `transcribe`, который использует локальные файлы.

`transcribe` запускается напрямую, без shell, с обязательным `--config`:

```text
<python воркера> <каталог воркера>/src/main.py --config <путь к config.yaml>
```

Конфиг содержит ровно `model`, `device`, `compute_type`, `language`. Все поля
обязательны, значений по умолчанию нет; `language: null` — автоопределение.
Модель выбирает конфиг самого воркера. Конфиг балансировщика его не загружает.
Относительный путь к YAML считается от рабочего каталога процесса.

В stdin передаётся один JSON-массив UTF-8, после записи stdin закрывается:

```json
[
  {"task_id": "<ID задачи>", "path": "/tmp/balancer/batch/input-1"}
]
```

Массив непустой, каждая задача содержит ровно `task_id` и `path`. ID — непустые
уникальные строки; воркер не проверяет формат UUID. Для core это ID `task`
(для embed — `chunk`) либо самостоятельной задачи агента. `path` — абсолютный
путь к полностью скачанному существующему локальному файлу. `type`, `input`,
`mime`, адрес core и HTTP-полномочия воркеру не передаются. Файлы воркер не удаляет.
Балансировщик должен заранее скачать входы и выбрать воркер по типу задачи;
формирование имён временных файлов пока не реализовано.

Вся пачка проверяется до загрузки модели. `Batch.transcribe(config)` загружает
модель один раз, последовательно вызывает `Task.transcribe(model, language)`
и сохраняет словарь `task_id → text` в `batch.results`. Текст каждой задачи
сохраняется в `task.text`. Оба метода возвращают `None`.

Успех: код завершения `0`, затем `Batch.write()` печатает один JSON-объект в stdout:

```json
{"<ID задачи>": "[00:01:10] Сегодня мы поговорим про нейросети.\n[00:01:15] Рассмотрим, как работают эмбеддинги."}
```

Каждый непустой сегмент Whisper получает новую строку и таймкод начала
`[ЧЧ:ММ:СС]` относительно входного файла, доли секунды отбрасываются.
Внутренние пробельные символы схлопываются в один пробел. Сегмент модели
не обязательно соответствует одному предложению. Без речи возвращается `""`.
Хранилище допускает `None`/JSON `null`, но текущий успешный путь записывает строки.
В stdout нет обёрток `results` и `payload`.

Чтобы отправить такой результат в HTTP `/result`, балансировщику потребуется
преобразовать словарь в `results: [{"task_id": id, "payload": {"text": text}}]`
и добавить `balancer_id`. Это преобразование пока не реализовано. HTTP-контракт
выше допускает только строковый `payload.text`, политика обработки `null`
балансировщиком пока не определена.

Ошибки валидации разделены на `ConfigError`, `TaskError`, `BatchError`.
Ошибка конфига, входа, модели или распознавания даёт код `1` и сообщение
`transcribe: <описание>` в stderr, без частичного JSON в stdout. Ошибки CLI дают
код `2` от argparse. Python-диагностика библиотек перенаправляется в stderr;
прямой нативный вывод этим механизмом не перехватывается.

Сопоставление результатов выполняется по ID, по одному ключу на входную задачу.
Балансировщику предстоит читать stdout и stderr параллельно и проверять результат.
Ненулевой код, сигнал, неполный или некорректный ответ считаются падением пачки.
Разделение на одиночные задачи, `/fail` и вытеснение через `/reset` относятся
к описанному выше проекту балансировщика; сам воркер их не выполняет.
