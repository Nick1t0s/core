## Балансировщик

### Компоненты и связь с core

- **Балансировщик** — единственный отдельный демон выполнения тяжёлых задач. Его постоянный `balancer_id`, служебный token и адрес core задаются при настройке сервера. Пользователи не создают балансировщики. Состояние выполнения демон хранит только в памяти.
- **Три воркера-утилиты**: транскрибация, OCR, эмбеддинги. На одном GPU в каждый момент работает один воркер. Он запускается процессом на каждую пачку.
- **Все очереди находятся в core.** Логические источники — сам core и каждый зарегистрированный агент. У каждого источника три очереди. Скрапперы отправляют записи только в core; задачи обработки их записей попадают в собственные очереди core. Агент отправляет самостоятельные задачи и получает результаты через core, в отдельных очередях своего `agent_id`.
- `task_source_id` — несекретный ID логического источника: `agent_id` либо постоянный служебный ID core. Это не `record.source_id` (`youtube`, `telegram`).

Балансировщик обращается только к core. Во всех запросах передаёт `X-Balancer-ID: <balancer_id>` и `Authorization: Bearer <token балансировщика>`. Core проверяет эту пару; ID в JSON, если есть, должен совпадать с заголовком. Одни служебные полномочия покрывают все очереди, но не поиск и администрирование. Адресов и отдельных токенов источников нет; агентам не требуется входящее API для балансировщика.

### HTTP-запросы

Все пути относятся к адресу core из конфига:

| Эндпоинт | Назначение |
|---|---|
| `GET /api/task-sources` | Единый JSON: список `task_source_id`, приоритет каждого источника и для каждого типа `has_tasks` и приоритет очереди |
| `POST /api/task-sources/{task_source_id}/claim` | `type`, `balancer_id`; одна задача с `task_id`, `type`, `complexity`, `input.url`, `input.mime` либо пустой `tasks` |
| `GET /api/task-sources/{task_source_id}/tasks/{task_id}/input` | Входные байты, в том числе текстовый embed в UTF-8 |
| `POST /api/task-sources/{task_source_id}/result` | Зафиксировать результаты пачки в core |
| `POST /api/task-sources/{task_source_id}/fail` | Зафиксировать ошибку задачи в core |
| `POST /api/task-sources/{task_source_id}/reset` | Вернуть задачи выбранного источника, взятые этим балансировщиком, в `wait` |

Форматы — в [HTTP API](../api.md). `GET /api/task-sources` объединяет перечень и проверку очередей: отдельных запросов `check_tasks` и версии реестра нет. Наличие задач — снимок на момент ответа, окончательную выдачу определяет `claim`.

### Обновление источников

При запуске, в начале каждого прохода и каждого цикла проверки во время выполнения пачки балансировщик получает `GET /api/task-sources`. Новый агент появляется в списке без перезапуска и сначала проходит `reset`; до успешного reset его задачи не берутся. Удалённый агент исключается из списка. Статического списка агентов в конфиге нет.

При недоступности core новые пачки не набираются. Уже загруженная пачка может выполниться; результат передаётся в core после восстановления связи. До успешной отправки результата или ошибки новая работа не начинается; повторная отправка уже зафиксированных результатов безопасна (задачи вне `processing` игнорируются). Перед следующим claim список обновляется.

### Воркеры

- Воркер не принимает входящих соединений и HTTP-сервера не имеет. Балансировщик скачивает файлы по `input.url`, запускает воркер как процесс и передаёт пачку с данными; воркер возвращает балансировщику результаты всей пачки целиком, а балансировщик отправляет их в core (`POST /api/task-sources/{task_source_id}/result`).
- Процесс запускается на каждую пачку, поэтому модель каждый раз заново загружается в видеопамять. Это принято: когда задач много, пачка набирается полной и загрузка окупается, а когда задач мало, лишние секунды не важны.
- Так как входящих соединений нет, вытеснение (см. ниже) реализуется через завершение процесса воркера.
- Воркер — дочерний процесс балансировщика и не переживает его, как daemon-поток не переживает главный: при запуске воркеру ставится `prctl(PR_SET_PDEATHSIG, SIGKILL)`, и ОС убивает воркер, как только умирает балансировщик. Запускать воркер нужно из главного потока балансировщика: сигнал привязан к потоку, который породил процесс.
- В **админке балансировщика**, доступной администратору, можно управлять тем, выполняются ли сейчас задачи: пока выполнение выключено, балансировщик новые пачки не набирает.

### Приоритеты и проход

Core возвращает приоритеты источников и очередей в `GET /api/task-sources`. Все агенты равноприоритетны и строго выше core; пользователь не меняет приоритет своего агента. По умолчанию `transcribe = 3`, `ocr = 2`, `embed = 1`. Trust_level на выполнение не влияет.

Балансировщик обходит источники по убыванию приоритета, при равенстве — по `task_source_id`. Внутри источника обходит типы по убыванию приоритета очереди, при равенстве — по имени типа. Очередь обрабатывается до опустошения или вытеснения более приоритетным источником. Затем начинается следующий тип, источник и новый проход. Когда все очереди пусты, демон ждёт заданный в конфиге интервал.

### Сложность и набор пачки

Сложность вычисляет core по входным данным и отдаёт числом `complexity` вместе с каждым claim. Агенты и скрапперы сложность не передают. Балансировщик только складывает значения. Единицы зависят от типа: минуты аудио для транскрибации, число символов для текстового embed. Метрики OCR и изображений для embed, точные формулы и крайние случаи будут определены отдельно. Порог X задаётся в конфиге балансировщика отдельно для каждого типа в соответствующих единицах; нормализация разных входов одного типа относится к расчёту core.

1. Когда очередь пачек пуста, балансировщик набирает одну пачку одного типа от одного источника. Каждый claim атомарно переводит одну задачу из `wait` в `processing` и возвращает метаданные со сложностью. Скачивания на этом этапе нет.
2. После добавления каждой задачи суммируется `complexity`. Набор прекращается, когда сумма строго больше X либо claim вернул пустой `tasks`. При равенстве набор продолжается, превысившая порог задача входит в пачку. Пустая пачка не запускается.
3. Только после завершения набора скачиваются входные данные задач пачки из core по `input.url`. Это одинаково для аудио, изображений и текста: текстовый embed передаётся байтами UTF-8 с MIME `text/plain; charset=utf-8`, в claim содержимого нет.
4. После загрузки запускается воркер. Успешные результаты всей пачки отправляются в core, затем начинается набор следующей пачки.

`processing` включает период набора и загрузки, а не только работу GPU. Ошибка связи при загрузке не считается падением воркера: до получения данных он не запускается, загрузка повторяется после восстановления связи. Если задача удалена или возвращена в очередь и GET вернул `404`, она исключается из пачки; пустая пачка не запускается.

### Очередь пачек и сбой воркера

Очередь пачек — обычная Queue в памяти балансировщика. Если воркер упал на пачке из k > 1 задач, в лог пишется WARNING, а вместо неё ставятся k пачек по одной задаче. Уже загруженные данные используются повторно. Каждая успешная одиночная задача отправляется в core сразу; если падает одиночная задача, core получает `/fail` с сообщением и числом запусков. Дальнейших повторов нет.

Таким образом ошибка остаётся только у задачи, которая падает и в одиночку. Для задач дерева core выполняет цикл очистки, для самостоятельной задачи агента сохраняет `error`, который получит агент. Ошибка не равна вытеснению и не возвращает задачу в `wait`.

### Сканирование и вытеснение

Параллельно с работой воркера выполняются циклы проверки с периодом из конфига. Каждый цикл делает один `GET /api/task-sources`. Если хотя бы у одного источника со строго большим приоритетом появилась непустая очередь:

1. воркер убивается (KILL), частичные результаты выбрасываются;
2. очередь пачек и локальные входные данные отменённой работы очищаются;
3. через core вызывается `reset` текущего `task_source_id`: все задачи, взятые этим балансировщиком у этого источника, возвращаются в `wait`;
4. после успешного reset начинается новый проход с самого приоритетного источника.

Уже зафиксированные результаты и ошибки сохраняются. Равноприоритетные агенты друг друга не вытесняют. Появление более приоритетного типа внутри текущего источника не прерывает работу: он обрабатывается в следующем проходе. При недоступности core вытеснение по устаревшим сведениям не выполняется.

### Перезапуск

Воркеры завершаются вместе с балансировщиком средствами ОС. Очередь пачек, скачанные для неё данные и незавершённые результаты теряются; зафиксированное в core сохраняется.

При старте балансировщик получает список из core и выполняет reset каждого источника. Без списка и успешного reset собственных очередей core работа не начинается; для агента неуспешный reset повторяется на каждом проходе, его задачи до успеха не берутся. После этого проход начинается с самого приоритетного источника, возвращённые задачи выполняются с нуля.

Постоянный `balancer_id` позволяет вернуть задачи после перезапуска. Возврата по таймауту нет: зависший балансировщик перезапускают. Core при своём старте возвращает все незавершённые задачи всех источников в `wait` (Core, 4.5).
