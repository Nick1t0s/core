## Балансировщик

### Назначение и конфигурация

Балансировщик — демон, который получает задачи из core, собирает пачки и запускает воркеры `transcribe`, `ocr`, `embed`. В каждый момент на GPU работает один процесс воркера. Очередь пачек и состояние выполнения хранятся в памяти; входы скачиваются во временные локальные файлы.

Конфигурация: адрес core, постоянный `balancer_id`, служебный token, команда запуска каждого воркера (массив argv), порог пачки X для каждого типа, интервалы проверки очередей, ожидания при пустых очередях и повторов HTTP-запросов, таймаут HTTP-запроса, каталог временных файлов. Пороги — конечные неотрицательные числа в единицах `complexity`, возвращаемой core для соответствующего типа.

Для балансировщика `task_source_id` — непрозрачный ID источника. Список источников, приоритеты и наличие задач приходят из API. Балансировщик применяет их одинаково ко всем источникам и типам, без зашитых значений приоритетов и исключений по ID. Политика приоритетов, устройство очередей и расчёт сложности принадлежат [core](../core/04_tasks_and_queues.md).

### Источники и порядок выполнения

1. При запуске, в начале каждого прохода и каждого цикла проверки во время работы воркера получать `GET /api/task-sources`.
2. Каждый впервые обнаруженный источник инициализировать через `/reset`. До успешного ответа его задачи не брать; неуспешную инициализацию повторять на следующих проходах. Это правило одинаково для всех источников. Источники, исчезнувшие из снимка, исключать из обхода; вновь появившийся источник инициализировать заново.
3. Обходить источники по убыванию `priority`, при равенстве — по `task_source_id` в лексикографическом порядке. Внутри источника обходить типы по убыванию приоритета очереди, при равенстве — по имени типа в лексикографическом порядке.
4. Брать задачи только из очередей с `has_tasks = true`. Выбранную очередь обрабатывать до пустого `/claim` или вытеснения. Затем переходить к следующему типу, источнику и новому проходу. Снимок не гарантирует выдачу задачи: окончательный ответ даёт `/claim`.
5. Если все доступные очереди пусты, ждать интервал из конфигурации. Пока выполнение выключено администратором в интерфейсе балансировщика, новые пачки не набирать; уже запущенная пачка завершается и передаёт результат.

### Набор и выполнение пачки

Когда локальная очередь пачек пуста, набирать одну пачку одного типа от одного источника:

1. Последовательно вызывать `/claim`, добавляя задачу и её `complexity` в сумму. Входы на этом этапе не скачивать.
2. Остановить набор, когда сумма строго больше X либо `/claim` вернул `{"tasks":[]}`. При равенстве продолжать; превысившая порог задача входит в пачку. Пустую пачку не запускать.
3. Скачать каждый вход через GET по `input.url` с теми же служебными заголовками. После полного скачивания всех входов запустить воркер по контракту ниже. Ответ `404` на вход исключает задачу из пачки; `/fail` для неё не отправляется. Если пачка опустела, перейти к новому проходу.
4. Получить и проверить результат всей пачки, отправить его через `/result`. До подтверждения результатов или ошибки следующую пачку не запускать и новые задачи не брать.
5. Удалить локальные входы после подтверждения `/result` или `/fail`, отмены работы либо исключения задачи из пачки. После перезапуска удалить оставшиеся временные файлы предыдущего запуска.

### Сбой воркера

Если воркер завершился с ошибкой на пачке из k > 1 задач, записать WARNING и заменить её в локальной очереди k пачками по одной задаче, сохранив порядок. Уже скачанные входы использовать повторно. Каждую успешную одиночную задачу немедленно отправлять через `/result`.

При падении одиночной задачи отправить `/fail`; дальнейших запусков для неё нет. `error.attempts` — число запусков воркера с этой задачей после последнего claim: 1 для исходной одиночной пачки, 2 после падения общей пачки и одиночного запуска. Сетевые повторы и принудительное завершение при вытеснении в это число не входят.

### Проверка и вытеснение

Параллельно с работой воркера с заданным интервалом получать свежий снимок источников. Если у инициализированного источника со строго большим приоритетом есть непустая очередь:

1. Завершить процесс воркера сигналом `SIGKILL`, дождаться его завершения, отбросить частичный результат.
2. Очистить локальную очередь пачек и входы отменённой работы.
3. Вызвать `/reset` текущего источника и дождаться успешного ответа.
4. Обновить снимок и начать новый проход.

Сравнивать приоритеты источников по свежему снимку, включая приоритет выполняемого источника. При равенстве вытеснения нет. Более высокий приоритет другого типа внутри того же источника текущую работу не прерывает: тип будет выбран в следующем проходе. Если текущий источник исчез из снимка, отменить его локальную работу и начать новый проход. Подтверждённые результаты и ошибки повторно не отправлять.

### Сеть и перезапуск

При недоступности core приостановить набор. Уже загруженная пачка может завершиться; результат хранить до восстановления связи. Вытеснение по устаревшему снимку не выполнять. Ошибка скачивания — повод повторить GET, а не запускать воркер или отправлять `/fail`.

Поведение при ошибках HTTP и потере ответа определено в контракте ниже. Перед возобновлением claim после восстановления связи обновлять список источников.

Воркер запускать из главного потока как дочерний процесс с `prctl(PR_SET_PDEATHSIG, SIGKILL)`: он должен завершаться при гибели балансировщика. После установки сигнала проверять, что родитель ещё тот же, чтобы закрыть гонку с его завершением. После перезапуска локальная работа не восстанавливается: получить список источников и заново пройти их инициализацию через `/reset`.

### HTTP-контракт с core

Это полное описание исходящих HTTP-вызовов балансировщика. Все пути относятся к адресу core из конфигурации. В каждом запросе, включая скачивание входа:

```http
X-Balancer-ID: <balancer_id>
Authorization: Bearer <token балансировщика>
```

Все POST передают JSON с `Content-Type: application/json`. GET не имеют тела и query-параметров. Все поля в примерах обязательны, если явно не указано обратное. `balancer_id` в теле должен совпадать с заголовком. ID источника и задачи — непустые строки; при подстановке в URL каждый ID кодируется как один сегмент пути.

#### `GET /api/task-sources`

Ответ `200`, `Content-Type: application/json`:

```json
{
  "items": [
    {
      "task_source_id": "<ID источника>",
      "priority": 10,
      "queues": {
        "transcribe": {"has_tasks": true, "priority": 0},
        "ocr": {"has_tasks": false, "priority": 5},
        "embed": {"has_tasks": true, "priority": 5}
      }
    }
  ]
}
```

`items` — полный список без пагинации, может быть пустым; ID источников уникальны. `queues` содержит все три типа, в том числе пустые. `has_tasks` — boolean, наличие ожидающих задач на момент ответа. Оба уровня `priority` — конечные числа: большее значение означает больший приоритет; допустимы отрицательные значения и равенства. Значения в примере не задают политику или значения по умолчанию. Порядок элементов ответа не задаёт порядок обработки.

#### `POST /api/task-sources/{task_source_id}/claim`

Тело:

```json
{"type":"transcribe","balancer_id":"<balancer_id>"}
```

`type` — `transcribe`, `ocr` или `embed`. Ответ `200`, JSON с массивом `tasks` длиной 0 или 1:

```json
{
  "tasks": [
    {
      "task_id": "<ID задачи>",
      "type": "transcribe",
      "complexity": 12.5,
      "input": {
        "url": "/api/task-sources/<ID источника>/tasks/<ID задачи>/input",
        "mime": "audio/flac"
      }
    }
  ]
}
```

Пустая очередь: `{"tasks":[]}`. Параметра `limit` нет. `type` выданной задачи совпадает с запрошенным. `complexity` — конечное неотрицательное число; балансировщик использует его как готовую оценку и не пересчитывает по данным. `input.url` — путь на том же core, ведущий к эндпоинту скачивания этой задачи; `input.mime` — строка MIME. Входного содержимого в claim нет.

Успешная выдача резервирует задачу за этим балансировщиком; резервирование может быть отменено на стороне core, что проверяется при последующих вызовах. Если ответ потерян, неизвестно, была ли задача взята: перед продолжением отбросить набранную пачку и выполнить `/reset` этого источника. Простой повтор claim может взять другую задачу и не восстанавливает потерянную выдачу.

#### `GET /api/task-sources/{task_source_id}/tasks/{task_id}/input`

Вызывать по `input.url`, полученному в claim. Ответ `200` — байты входа, `Content-Type` равен `input.mime`. Для текстового embed — UTF-8 с `text/plain; charset=utf-8`; остальные входы сохраняются как бинарные данные. Вход доступен только пока задача зарезервирована за этим балансировщиком. `404 task_not_available` означает, что вход уже недоступен; такую задачу исключить из пачки.

#### `POST /api/task-sources/{task_source_id}/result`

Тело для `transcribe` и `ocr`:

```json
{
  "balancer_id": "<balancer_id>",
  "results": [{"task_id": "<ID задачи>", "payload": {"text": "Полученный текст"}}]
}
```

`results` — непустой массив результатов задач одного источника. `payload.text` — строка; пустая строка допустима и является успешным результатом.

Для `embed` каждый элемент имеет следующий вид:

```json
{
  "task_id": "<ID задачи>",
  "payload": {"embed_model": "<имя модели>", "embedding": [0.12, -0.34, 0.56]}
}
```

`embed_model` — непустая строка с фактическим именем модели воркера; `embedding` — непустой массив конечных чисел полной размерности этой модели. В примере вектор сокращён. Балансировщик передаёт значения воркера без подмены модели или преобразования вектора.

Ответ `204 No Content`, без тела, после фиксации всех результатов. Результаты фиксируются по отдельности: если запрос оборвался, часть могла сохраниться. Повторять всё то же тело безопасно: удалённые, отменённые и уже завершённые задачи игнорируются. Существующая задача другого источника или другого исполнителя отклоняется с `404 task_not_available` без изменения этой задачи.

#### `POST /api/task-sources/{task_source_id}/fail`

Тело:

```json
{
  "balancer_id": "<balancer_id>",
  "task_ids": ["<ID задачи>"],
  "error": {
    "message": "CUDA out of memory",
    "attempts": 2,
    "worker": "transcribe",
    "model": "<имя модели>"
  }
}
```

`task_ids` — непустой массив, `error.message` — непустая строка, `error.attempts` — положительное целое. `error.worker` и `error.model` — необязательные строки. Балансировщик отправляет одну упавшую одиночную задачу за вызов.

Ответ `204 No Content`, без тела, после фиксации ошибки. Правила игнорирования устаревших задач, отклонения чужих задач и повторной отправки те же, что у `/result`. `/fail` завершает задачу ошибкой; для отмены и повторного выполнения используется `/reset`.

#### `POST /api/task-sources/{task_source_id}/reset`

Тело:

```json
{"balancer_id":"<balancer_id>"}
```

Ответ `204 No Content`, без тела. Все незавершённые задачи указанного источника, зарезервированные за этим балансировщиком, вновь доступны для claim. Завершённые задачи не меняются. Повтор безопасен; пока reset не подтверждён, новые задачи этого источника не брать.

Для удалённого источника `/result` и `/fail` игнорируют поздние сообщения, `/reset` ничего не меняет; все три возвращают `204`. Claim и скачивание входа удалённого источника возвращают `404 task_source_not_found`. Для неизвестного ID источника все операции возвращают `404 task_source_not_found`.

#### Ошибки и повторы

Ошибки core имеют `Content-Type: application/json` и тело:

```json
{"error":{"code":"invalid_request","message":"Описание ошибки"}}
```

| Ответ / ситуация | Действие балансировщика |
|---|---|
| `400 invalid_request` — `balancer_id` в теле не совпал с заголовком; `422 invalid_request` — неверные поля, тип задачи или payload | Записать ошибку протокола и приостановить выполнение до исправления. Не повторять неизменённый запрос и не отправлять `/fail` из-за HTTP-ошибки |
| `401 unauthorized` — неверные полномочия; `403 forbidden` — нет права на операцию | Приостановить выполнение до исправления конфигурации/полномочий |
| `404 task_source_not_found` — источник неизвестен либо удалён для claim/input | Отменить локальную работу этого источника, обновить список; не продолжать claim по старому снимку |
| `404 task_not_available` при скачивании входа | Исключить задачу из пачки |
| `404 task_not_available` при result/fail | Записать нарушение контракта владения задачей и приостановить выполнение до исправления |
| `5xx`, обрыв связи, таймаут, неполный ответ | Подождать интервал повторов. GET повторить; result/fail повторить с тем же телом; reset повторить до подтверждения. Для claim сначала выполнить reset источника, как описано выше |

При неизвестном результате result/fail не делать reset и не брать новую работу до подтверждения отправки. Неверный успешный ответ (некорректный JSON, отсутствующие поля, неподходящие значения) — ошибка протокола; для claim перед продолжением также требуется reset, поскольку резервирование могло состояться.

### Контракт запуска воркера

У воркеров нет HTTP API. Балансировщик запускает команду выбранного типа из конфигурации без shell, передаёт один JSON-документ UTF-8 в stdin и закрывает stdin:

```json
{
  "type": "transcribe",
  "tasks": [
    {"task_id": "<ID задачи>", "input": {"path": "/tmp/balancer/batch/input-1", "mime": "audio/flac"}}
  ]
}
```

Все поля обязательны. `tasks` — непустая пачка одного типа и источника, ID уникальны. `input.path` — абсолютный путь к полностью скачанному локальному файлу, доступному воркеру для чтения; `input.mime` берётся из claim. Текстовые входы также передаются файлом. Воркеру не передаются HTTP-полномочия и адрес core.

Успех: код завершения 0 и один JSON-документ UTF-8 в stdout:

```json
{"results":[{"task_id":"<ID задачи>","payload":{"text":"Полученный текст"}}]}
```

`payload` имеет формат `/result` для выбранного типа. На каждую входную задачу должен быть ровно один результат; посторонние ID, пропуски и дубликаты запрещены. Порядок результатов произвольный, сопоставление — по `task_id`. Логи идут только в stderr; stdout читается параллельно с stderr, чтобы процесс не блокировался на заполненной трубе.

Ненулевой код завершения, сигнал, неполный или некорректный ответ означают падение всей пачки. Частичные результаты не принимаются. Сообщение для `/fail` формируется из причины завершения и stderr; имя воркера и известное имя модели передаются необязательными полями. Принудительное завершение при вытеснении обрабатывается как отмена через `/reset`.
