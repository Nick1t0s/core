## Балансировщик

### Компоненты

- **Балансировщик** — единственный отдельный демон для всей системы. Пользователи не могут создавать балансировщики. Его balancer_id и отдельные служебные полномочия задаются при настройке сервера; одного знания balancer_id для доступа к API недостаточно. Состояния не хранит: после перезапуска начинает набирать задачи заново (см. «Перезапуск»). Источники записывают balancer_id во взятые задачи (Core, 4.2).
- **Три воркера-утилиты**: транскрибация, OCR, эмбеддинги. Балансировщик запускает воркер с пачкой задач, воркер завершается после её выполнения.
- **Один GPU**: в каждый момент работает ровно один воркер.
- **Источники задач** — core и каждый зарегистрированный agent_id. Актуальный реестр, адреса API и приоритеты балансировщик получает из core через GET /api/task-sources (Core, 11.6), а не из собственного списка в конфиге. Источник определяется task_source_id: для агента это несекретный agent_id его регистрации; для core — постоянный служебный ID. Один адрес может обслуживать несколько источников, тогда вызовы маршрутизируются по task_source_id. Очереди живут в источниках (в core это SQL-запрос к таблицам задач). У балансировщика есть только очередь пачек в памяти — набранная, но ещё не выполненная работа (см. «Очередь пачек и сбой воркера»).

### HTTP-запросы

Реестр — `GET /api/task-sources` в core с `X-Balancer-ID: <balancer_id>` и `Authorization: Bearer <token балансировщика для core>`. Из ответа берутся `version`, `items`, а для каждого источника — `task_source_id`, `task_endpoint`, `priority`, `enabled`, `draining`, `token`.

К `task_endpoint` добавляются пути:

| Эндпоинт | Запрос | Ответ |
|---|---|---|
| `GET /api/task-sources/{task_source_id}/check_tasks` | Без тела | Наличие задач по трём типам |
| `POST /api/task-sources/{task_source_id}/claim` | JSON: `type`, `limit`, `balancer_id` | `tasks`: ID, тип и входные данные либо путь скачивания |
| `GET /api/task-sources/{task_source_id}/tasks/{task_id}/input` | Без тела | Бинарные данные задачи |
| `POST /api/task-sources/{task_source_id}/result` | JSON: `balancer_id`, `results` с `task_id`, `payload` | `204` после коммита |
| `POST /api/task-sources/{task_source_id}/fail` | JSON: `balancer_id`, `task_ids`, `error` | `204` после коммита |
| `POST /api/task-sources/{task_source_id}/reset` | JSON: `balancer_id` | `204` после возврата задач |

Во всех запросах к очередям и при скачивании файлов передаются `X-Balancer-ID: <balancer_id>` и `Authorization: Bearer <token этого источника>`. ID в JSON должен совпадать с заголовком. Token регистрации автоматически генерируется core при создании; ID задаётся при настройке и сохраняется при перевыпуске token. Аудио и картинки скачиваются до запуска воркера; текст приходит в `input.text`. Полные форматы — в [HTTP API](../api.md).

### Обновление источников

Реестр запрашивается при старте, перед каждым проходом и периодически во время выполнения пачки, вместе со сканированием очередей. Он содержит версию и состояние источников. Новый агент обнаруживается без перезапуска балансировщика и сначала проходит `POST /api/task-sources/{task_source_id}/reset`. Отключённые агенты и агенты заблокированных пользователей не получают новые задачи на GPU. Если отключён текущий источник, воркер останавливается, очередь пачек очищается, а задачи возвращаются служебным reset; недоступный reset повторяется после восстановления источника. Core сохраняет сведения об отключённых и удаляемых источниках до возврата взятых задач, чтобы они не потерялись при перезапуске балансировщика.

При недоступности core новые пачки не набираются по устаревшему реестру. Текущую пачку можно завершить и передать результат её источнику. После восстановления core реестр обновляется до следующего claim. В конфиге остаются адрес core, служебные полномочия, balancer_id и параметры выполнения, но не перечень пользовательских агентов.

### Воркеры

- Воркер не принимает входящих соединений и HTTP-сервера не имеет. Балансировщик скачивает файлы по `input.url`, запускает воркер как процесс и передаёт пачку с данными; воркер возвращает балансировщику результаты всей пачки целиком, а балансировщик отправляет их источнику (`POST /api/task-sources/{task_source_id}/result`).
- Процесс запускается на каждую пачку, поэтому модель каждый раз заново загружается в видеопамять. Это принято: когда задач много, пачка набирается полной и загрузка окупается, а когда задач мало, лишние секунды не важны.
- Так как входящих соединений нет, вытеснение (см. ниже) реализуется через завершение процесса воркера.
- Воркер — дочерний процесс балансировщика и не переживает его, как daemon-поток не переживает главный: при запуске воркеру ставится `prctl(PR_SET_PDEATHSIG, SIGKILL)`, и ОС убивает воркер, как только умирает балансировщик. Запускать воркер нужно из главного потока балансировщика: сигнал привязан к потоку, который породил процесс.
- В **админке балансировщика**, доступной администратору, можно управлять тем, выполняются ли сейчас задачи: пока выполнение выключено, балансировщик новые пачки не набирает.

### Приоритеты

- У каждой очереди есть внутренний приоритет (по умолчанию транскрибация — 3, OCR — 2, эмбеддинги — 1).
- Все агенты имеют одинаковый приоритет, строго выше приоритета core. Пользователь не может менять приоритет своего агента.
- Одинаковые приоритеты допустимы и среди источников, и среди очередей. Равенство источников разрешается по task_source_id, очередей — по имени типа. Trust_level на приоритет выполнения не влияет.

### Проход балансировщика

Проход — это обход всех активных источников по убыванию приоритета и затем по task_source_id, а внутри каждого источника — обход его очередей по убыванию приоритета и затем по имени типа. Очередная очередь источника обрабатывается через очередь пачек (см. ниже), пока она не опустеет; затем балансировщик переходит к следующей очереди и следующему источнику.

После обхода всех источников начинается новый проход. Если все очереди пусты, балансировщик ждёт и повторяет проход (интервал задаётся в конфиге). Так как более приоритетные источники обходятся первыми, они вычищаются раньше остальных.

### Очередь пачек и сбой воркера

Внутри балансировщика — очередь пачек (обычная Queue в памяти). Очередь источника обрабатывается так:

1. Если очередь пачек пуста, создаётся одна пачка: балансировщик вызывает `POST /api/task-sources/{task_source_id}/claim` и добавляет задачи в эту пачку, пока в ней меньше N задач (размер пачки задаётся в конфиге для каждого типа) и пока источник их отдаёт. В источнике задачи переходят из `wait` в `processing`; отдельно уведомлять источник не нужно. Если источник ничего не отдал, очередь источника пуста.
2. Пачка из головы очереди пачек отправляется на воркер.
3. Воркер завершился успешно → результаты всей пачки отправляются источнику (`POST /api/task-sources/{task_source_id}/result`), и балансировщик возвращается к шагу 1.
4. Воркер упал на пачке из k > 1 задач (OOM, неправильный файл, непредвиденная ошибка) → в лог пишется WARNING, и вместо этой пачки в очередь кладутся k пачек по одной задаче. Воркер запускается на каждую по очереди, пока очередь пачек не опустеет; результат каждой успешной отправляется источнику сразу после её запуска.
5. Упала пачка из одной задачи → источнику отправляется `POST /api/task-sources/{task_source_id}/fail` для этой задачи: текст ошибки и число запусков (см. Core, 4.2). Повторов нет. Ошибка — не то же самое, что вытеснение: упавшая задача в очередь не возвращается.

Так ошибку получает только задача, которая валит воркер и в одиночку, а остальные задачи упавшей пачки выполняются до конца. Цена — модель загружается заново на каждую задачу, но только для упавшей пачки.

### Сканирование и вытеснение

Параллельно с выполнением пачки балансировщик постоянно (период задаётся в конфиге) обновляет реестр core и вызывает `GET /api/task-sources/{task_source_id}/check_tasks` у всех источников со строго большим приоритетом, чем текущий. Этот GET только проверяет, есть ли задачи, и ничего не выдаёт. При выполнении core таким источником может быть любой агент, включая недавно зарегистрированный. Если у более приоритетного **источника** появилась задача:

1. воркер убивается (KILL), независимо от того, сколько он успел сделать; частичные результаты выбрасываются;
2. очередь пачек очищается;
3. у текущего источника вызывается `POST /api/task-sources/{task_source_id}/reset` — тот же вызов, что и при старте: все задачи, взятые этим балансировщиком, переходят из `processing` в `wait`. Результаты и ошибки, уже отправленные источнику, остаются;
4. текущий проход завершается и запускается новый, который начнётся с самого приоритетного источника.

Очередь отпускается только в двух случаях:

- она опустела;
- появилась задача более приоритетного источника.

Равноприоритетные агенты не вытесняют друг друга, независимо от порядка их ID. Если более приоритетная очередь появилась внутри того же источника, ничего не происходит: проход продолжается, а эта задача будет обработана в следующем проходе.


### Перезапуск

Перезапуск — это когда процесс балансировщика завершился и запущен снова: упал сам, его убила ОС (например, по OOM), перезагрузился сервер, его перезапустили вручную (например, при зависании) или обновили версию. Падение самого балансировщика — редкое событие: тяжёлая работа и почти все сбои происходят в воркерах.

Что происходит:

1. **Воркеры завершаются вместе с балансировщиком** средствами ОС (`PR_SET_PDEATHSIG`, cgroup сервиса, см. «Воркеры»). Двух воркеров на одном GPU и результатов, которые некому отправить, не бывает.
2. **Теряется всё, что в памяти:** очередь пачек и работа текущего воркера. Результаты и ошибки, уже отправленные источникам (`result`, `fail`), там закоммичены и не теряются.
3. **При старте** балансировщик получает реестр из core и вызывает `POST /api/task-sources/{task_source_id}/reset` у каждого известного источника, включая отключённые источники с незавершённым возвратом задач: задачи, которые он взял до перезапуска, возвращаются в wait. Пока reset у агента не прошёл, задачи из него не берутся; вызов повторяется на каждом проходе. Без полученного реестра и успешного reset самого core балансировщик не начинает работу.
4. После этого начинается проход с самого приоритетного источника. Задачи, которые были на воркере, выполняются заново с нуля.

`balancer_id` задаётся в конфиге и постоянен: если бы он менялся при каждом старте, балансировщик не смог бы вернуть задачи, взятые до перезапуска.

Возврата задач по таймауту нет: если балансировщик завис, его перезапускают, и дальше всё идёт по тем же шагам.
