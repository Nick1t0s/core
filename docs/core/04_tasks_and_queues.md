### 4. Задачи и очереди

#### 4.1. Очереди

Три очереди core соответствуют типам задач:

| Очередь (`type`) | Листья |
|---|---|
| `transcribe` | `task` с типом `transcribe` в статусе `wait` |
| `ocr` | `task` с типом `ocr` в статусе `wait` |
| `embed` | `chunk` в статусе `wait` |

Задача находится «в очереди», если `status = 'wait'`, и «на воркере», если `status = 'processing'` (тогда заполнены `taken_at` и `taken_by`). Отдельных структур очередей нет: очередь — это SQL-запрос к `task` или `chunk` в статусе `wait`. Порядок внутри очереди — FIFO по `created_at`.

Для балансировщика core — один источник задач (см. «Термины»): очередей для конкретных `record.source_id` (`youtube`, `telegram`) не существует, и балансировщик их не различает. Кроме собственных очередей, core хранит отдельные очереди каждого агента. Все приоритеты и наличие задач балансировщик получает одним запросом к core: все агенты равноприоритетны и выше core (см. 11.6).

#### 4.2. Централизованное API задач

Единственный балансировщик обращается только к core. Во всех запросах передаются `X-Balancer-ID` и один служебный token в `Authorization: Bearer`. Core проверяет пару по регистрации балансировщика; `balancer_id` в JSON должен совпадать с заголовком. Поисковых и административных прав этот token не даёт.

`task_source_id` в пути выбирает логический источник внутри core: собственные задачи обработки записей либо задачи отдельного `agent_id`. У каждого агента три изолированные очереди. Агенты отправляют входные данные в core и получают оттуда результаты под своими ID/token; скрапперы по-прежнему отправляют только записи, задачи по ним создаёт сам core в своих очередях.

| Эндпоинт | Действие |
|---|---|
| `GET /api/task-sources` | Единый снимок всех источников: ID, приоритет источника и для каждого типа `has_tasks` (`EXISTS` задач в `wait`) и приоритет очереди. Включает пустые очереди. Ничего не выдаёт и не изменяет; заменяет отдельные проверки `check_tasks` |
| `POST /api/task-sources/{task_source_id}/claim` | Обязательные `type`, `balancer_id`. Атомарно берёт одну задачу выбранного источника и типа по FIFO (`created_at`, при равенстве ID), переводит из `wait` в `processing`, ставит `taken_at`, `taken_by`. Для PostgreSQL — выбор с `FOR UPDATE SKIP LOCKED LIMIT 1` и UPDATE в одной транзакции. Ответ `200`: `tasks` с одной задачей (`task_id`, `type`, `complexity`, `input.url`, `input.mime`) либо пустой массив. Содержимого входа в ответе нет |
| `GET /api/task-sources/{task_source_id}/tasks/{task_id}/input` | Входные байты с MIME из claim; для текстового embed — UTF-8, `text/plain; charset=utf-8`. Только задача выбранного источника в `processing` с `taken_by` аутентифицированного балансировщика; иначе `404` |
| `POST /api/task-sources/{task_source_id}/result` | `balancer_id`, массив `results` (`task_id`, `payload`). Для OCR и транскрибации `payload.text`, для embed — `embedding` и `embed_model`. Каждая задача фиксируется своей транзакцией, для задач дерева — вместе с циклом готовности (4.3). Для агентских задач сохраняется результат, доступный только инициировавшей регистрации. `204` после всех коммитов |
| `POST /api/task-sources/{task_source_id}/fail` | `balancer_id`, непустой `task_ids`, `error` с `message`, `attempts`, необязательными `worker`, `model`. Для задач дерева выполняет цикл очистки (2.6), для самостоятельной задачи агента сохраняет `error`. `204` после фиксации; это не возврат в `wait` |
| `POST /api/task-sources/{task_source_id}/reset` | `balancer_id`. Возвращает все задачи выбранного источника в `processing` с этим `taken_by` в `wait`, очищает `taken_at`, `taken_by`. `204`. Применяется при старте, подключении источника и вытеснении; не считается ошибкой |

Core вычисляет сложность по входным данным до выдачи claim; агент и скраппер её не задают. `complexity` — конечное неотрицательное число в единицах типа: минуты для аудио, символы для текстового embed. Метрики OCR и изображений для embed, точные формулы и крайние случаи пока открыты. Балансировщик суммирует сложность до превышения порога X либо опустошения очереди. Только после набора пачки он скачивает входы и запускает воркер. Статус `processing` включает набор и загрузку пачки.

Для собственных очередей `task_id` — ID task либо chunk (embed); для агента — ID самостоятельной задачи в core. Агентские задачи не привязаны к record и не создают дерево. Формат отправки и чтения результата агентом — в [HTTP API](../api.md). Операции claim, result, fail и reset изолированы по `task_source_id`; переданный ID задачи другого источника отклоняется без изменения задачи. Доступ к существующей задаче другого балансировщика также отклоняется.

Данные собственных задач дерева читаются из `task_storage`, текст chunk — из БД и выдаётся как байты. Если до выдачи обнаружено отсутствие необходимого файла, core после фиксации claim отдельной транзакцией завершает этот лист ошибкой `stage = task_storage` (2.6) и пробует следующую задачу той же очереди; ответ по-прежнему содержит не более одной задачи. Для самостоятельной задачи агента отсутствие входа фиксируется как её `error`, без цикла очистки дерева. Если файл пропал между claim и загрузкой, core также фиксирует ошибку и возвращает `404`; задача исключается из пачки.

Операции result и fail над удалённой задачей или задачей вне `processing` игнорируются; поэтому повторная отправка после потери ответа безопасна. Reset затрагивает только указанный источник. Возвращённая задача вновь ожидает выполнения, завершённая ошибкой — нет.

#### 4.3. Обработка результата собственных задач core

Результат каждой задачи фиксируется **одной транзакцией вместе со всеми порождёнными записями и циклом готовности** (см. 2.6). Коммит происходит до ответа балансировщику, поэтому не бывает момента, когда задача завершена, а её дети ещё не созданы или её предки не пересчитаны.

**Эмбеддинг** (лист chunk): записываются `embed` и `embed_model`, chunk → `done`.

**Транскрибация** (лист `task_transcribe` под audio):

1. `task_transcribe` → `done`.
2. Если транскрипция непуста, создаётся text (`kind` = `task_result`) — ребёнок audio — со статусом `processing`. Текст сразу режется на chunk'и (дети text, статус `wait`, `embed` пуст).
3. Если транскрипция пуста, text не создаётся.

**OCR** (лист `task_ocr` под photo): то же самое, text становится ребёнком photo. Если OCR не вернул текст, text не создаётся; это не ошибка.

Пока созданные chunk'и не получат эмбеддинги, audio (или photo) остаётся в `processing`.

#### 4.4. OCR

OCR обязателен для каждой photo, в том числе для каждого кадра видео: `task_ocr` создаётся всегда, без настроек и политик. Photo с пустым результатом OCR завершается, не имея text.

#### 4.5. Восстановление после сбоев

Возврат задач, взятых в работу:

- **При старте core** все самостоятельные задачи агентов и все листья собственных задач в статусе `processing` возвращаются в очередь: `status = 'wait'`, `taken_at` и `taken_by` = `NULL`. Так обрабатывается падение core, в том числе при фиксации результата. Если балансировщик потом пришлёт результат по такой задаче, он будет проигнорирован (задача уже не в `processing`), а сама задача выполнится заново.
- **При старте балансировщика** он вызывает `POST /api/task-sources/{task_source_id}/reset` (см. 4.2): возвращаются задачи, которые взял именно он; балансировщик состояния не хранит и набирает задачи заново.

Возврата по таймауту нет: длинная транскрибация законно идёт часами, и таймаут срабатывал бы посреди нормальной работы. Если балансировщик завис, его перезапускают, и при старте он сам возвращает свои задачи через `POST /api/task-sources/{task_source_id}/reset`.

При старте core:

1. удаляет записи в `parsing` вместе с их каталогами (см. 3.2) — до того, как начать принимать новые записи;
2. возвращает самостоятельные задачи агентов и все листья из `processing` в `wait` — до того, как начать отвечать балансировщику;
3. запускает цикл очистки по таймеру (см. 2.8) и очистку хранилищ (см. 3.3); дальше они работают по своим таймерам.

Проверки и ремонта дерева нет: операция над листом и весь вызванный ею цикл фиксируются одной транзакцией (2.6), поэтому падение core не оставляет дерево наполовину пересчитанным.
