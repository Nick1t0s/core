### 4. Задачи и очереди

#### 4.1. Очереди

Три очереди core соответствуют типам задач:

| Очередь (`type`) | Листья |
|---|---|
| `transcribe` | `task` с типом `transcribe` в статусе `wait` |
| `ocr` | `task` с типом `ocr` в статусе `wait` |
| `embed` | `chunk` в статусе `wait` |

Задача находится «в очереди», если `status = 'wait'`, и «на воркере», если `status = 'processing'` (тогда заполнены `taken_at` и `taken_by`). Отдельных структур очередей нет: очередь — это SQL-запрос к `task` или `chunk` в статусе `wait`. Порядок внутри очереди — FIFO по `created_at`.

Для балансировщика core — один источник задач (см. «Термины»): очередей для конкретных `record.source_id` (`youtube`, `telegram`) не существует, и балансировщик их не различает. Кроме собственных очередей, core хранит отдельные очереди каждого агента. Все приоритеты и наличие задач балансировщик получает одним запросом к core. Политика приоритетов — в 11.6.

#### 4.2. Централизованное API задач

Полный HTTP-контракт для реализации сервера и клиента находится в [ТЗ балансировщика](../balancer/README.md#http-контракт-с-core). Правила служебной регистрации и приоритетов — в 11.6. Здесь описано, как core обслуживает эти вызовы.

`task_source_id` выбирает собственные задачи обработки записей либо задачи отдельного `agent_id`. У каждого агента три изолированные очереди. Агенты отправляют входные данные в core и получают оттуда результаты под своими ID/token; скрапперы отправляют только записи, задачи по ним создаёт сам core.

| Операция | Обязанность core |
|---|---|
| Снимок источников (`GET /api/task-sources`) | Включить все источники и все три типа очередей, в том числе пустые; `has_tasks` вычислить как `EXISTS` задач в `wait`. Ничего не резервировать |
| Claim | Атомарно взять одну задачу выбранного источника и типа по FIFO (`created_at`, при равенстве ID), перевести из `wait` в `processing`, заполнить `taken_at`, `taken_by`. Для PostgreSQL — `FOR UPDATE SKIP LOCKED LIMIT 1` и UPDATE в одной транзакции |
| Выдача входа | Проверить источник, `processing` и `taken_by`; выдать подготовленные байты. Чужой или недоступный вход не выдавать |
| Result | Каждую задачу зафиксировать своей транзакцией, для задач дерева — вместе с циклом готовности (4.3). Для агентских задач сохранить результат в области инициировавшей регистрации. Ответить после всех коммитов |
| Fail | Для задач дерева выполнить цикл очистки (2.6), для самостоятельной задачи агента сохранить `error`. Ответить после фиксации; не возвращать задачу в `wait` |
| Общий reset | Одной транзакцией вернуть все задачи всех источников и типов из `processing` в `wait`, очистить `taken_at`, `taken_by`. Фильтра по источнику или `taken_by` нет. Остальные статусы не менять; ответить после коммита |

Core вычисляет сложность по входным данным до выдачи claim; агент и скраппер её не задают. `complexity` — конечное неотрицательное число в единицах типа: минуты для аудио, символы для текстового embed. Метрики OCR и изображений для embed, точные формулы и крайние случаи пока открыты. Нормализация разных входов одного типа относится к расчёту core; порог пачки в конфигурации балансировщика должен использовать те же единицы. Статус `processing` включает набор и загрузку пачки.

Для собственных очередей `task_id` — ID task либо chunk (embed); для агента — ID самостоятельной задачи в core. Агентские задачи не привязаны к record и не создают дерево. Формат отправки и чтения результата агентом — в [HTTP API](../api.md). Операции claim, выдачи входа, result и fail изолированы по `task_source_id`; переданный ID задачи другого источника отклоняется без изменения задачи. Доступ к существующей задаче другого балансировщика также отклоняется. Reset общий, `task_source_id` не принимает. Коды ошибок заданы HTTP-контрактом.

Данные собственных задач дерева читаются из `task_storage`, текст chunk — из БД и выдаётся как байты. Если до выдачи обнаружено отсутствие необходимого файла, core после фиксации claim отдельной транзакцией завершает этот лист ошибкой `stage = task_storage` (2.6) и пробует следующую задачу той же очереди; ответ по-прежнему содержит не более одной задачи. Для самостоятельной задачи агента отсутствие входа фиксируется как её `error`, без цикла очистки дерева. Если файл пропал между claim и загрузкой, core также фиксирует ошибку и возвращает `404`; задача исключается из пачки.

Операции result и fail над удалённой задачей или задачей вне `processing` игнорируются; поэтому повторная отправка после потери ответа безопасна. Общий reset снимает все взятые задачи, включая самостоятельные задачи агентов. Возвращённая задача вновь ожидает выполнения, завершённая ошибкой — нет.

#### 4.3. Обработка результата собственных задач core

Результат каждой задачи фиксируется **одной транзакцией вместе со всеми порождёнными записями и циклом готовности** (см. 2.6). Коммит происходит до ответа балансировщику, поэтому не бывает момента, когда задача завершена, а её дети ещё не созданы или её предки не пересчитаны.

**Эмбеддинг** (лист chunk): записываются `embed` и `embed_model`, chunk → `done`.

**Транскрибация** (лист `task_transcribe` под audio):

1. `task_transcribe` → `done`.
2. Если транскрипция непуста, создаётся text (`kind` = `task_result`) — ребёнок audio — со статусом `processing`. Текст сразу режется на chunk'и (дети text, статус `wait`, `embed` пуст).
3. Если транскрипция пуста, text не создаётся.

**OCR** (лист `task_ocr` под photo): то же самое, text становится ребёнком photo. Если OCR не вернул текст, text не создаётся; это не ошибка.

Пока созданные chunk'и не получат эмбеддинги, audio (или photo) остаётся в `processing`.

#### 4.4. OCR

OCR обязателен для каждой photo, в том числе для каждого кадра видео: `task_ocr` создаётся всегда, без настроек и политик. Photo с пустым результатом OCR завершается, не имея text.

#### 4.5. Восстановление после сбоев

Возврат задач, взятых в работу:

- **При старте core** все самостоятельные задачи агентов и все листья собственных задач в статусе `processing` возвращаются в очередь: `status = 'wait'`, `taken_at` и `taken_by` = `NULL`. Так обрабатывается падение core, в том числе при фиксации результата. Если балансировщик потом пришлёт результат по такой задаче, он будет проигнорирован (задача уже не в `processing`), а сама задача выполнится заново.
- **При старте балансировщика** он вызывает общий `POST /api/task-sources/reset` (см. 4.2): все взятые задачи всех источников возвращаются в очередь; балансировщик состояния не хранит и набирает задачи заново. Тот же вызов начинает каждый новый цикл получения задач, в том числе после завершения пачки или вытеснения. Момент следующего старта определяется интервалом от начала предыдущего цикла по [правилам балансировщика](../balancer/README.md#цикл-получения-задач).

Возврата по таймауту нет: длинная транскрибация законно идёт часами, и таймаут срабатывал бы посреди нормальной работы. Если балансировщик завис, его перезапускают, и при старте он снимает все взятые задачи через `POST /api/task-sources/reset`.

При старте core:

1. удаляет записи в `parsing` вместе с их каталогами (см. 3.2) — до того, как начать принимать новые записи;
2. возвращает самостоятельные задачи агентов и все листья из `processing` в `wait` — до того, как начать отвечать балансировщику;
3. запускает цикл очистки по таймеру (см. 2.8) и очистку хранилищ (см. 3.3); дальше они работают по своим таймерам.

Проверки и ремонта дерева нет: операция над листом и весь вызванный ею цикл фиксируются одной транзакцией (2.6), поэтому падение core не оставляет дерево наполовину пересчитанным.
