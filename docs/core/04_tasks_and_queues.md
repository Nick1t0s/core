### 4. Задачи и очереди

#### 4.1. Очереди

Три очереди core соответствуют типам задач:

| Очередь (`type`) | Листья |
|---|---|
| `transcribe` | `task` с типом `transcribe` в статусе `wait` |
| `ocr` | `task` с типом `ocr` в статусе `wait` |
| `embed` | `chunk` в статусе `wait` |

Задача находится «в очереди», если `status = 'wait'`, и «на воркере», если `status = 'processing'` (тогда заполнены `taken_at` и `taken_by`). Отдельных структур очередей нет: очередь — это SQL-запрос к `task` или `chunk` в статусе `wait`. Порядок внутри очереди — FIFO по `created_at`.

Для балансировщика core — один источник задач (см. «Термины»): очередей для конкретных `record.source` (`youtube`, `telegram`) не существует, и балансировщик их не различает. Приоритеты очередей и источников задач хранит и применяет балансировщик, core их не знает.

#### 4.2. API источника задач

Балансировщик работает с каждым источником задач (core и клиентами) по одному и тому же API. Источник задач определяется адресом IP:PORT: балансировщик знает, чья задача, потому что сам отправил запрос на этот адрес. Источник, в свою очередь, знает, какой балансировщик взял задачу: `claim` передаёт `balancer_id` (постоянный идентификатор из конфига балансировщика), и источник записывает его в лист (`taken_by`). Core реализует API так:

| Операция | Действие |
|---|---|
| `claim(type, limit, balancer_id)` | `type` — `transcribe`, `ocr` или `embed`. Атомарно берёт до `limit` следующих задач очереди, переводит их из `wait` в `processing`, ставит `taken_at` и `taken_by = balancer_id`. Реализуется как `UPDATE … SET status = 'processing', taken_at = now(), taken_by = :balancer_id WHERE id IN (SELECT … WHERE status = 'wait' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT :limit) RETURNING …`. Возвращает пачку: для каждой задачи `task_id` и данные для воркера (аудио, картинку или текст chunk'а); аудио и картинку core читает из `task_storage` по `element_id`, текст chunk'а берёт из БД. Если для какой-то задачи файла в `task_storage` нет, core после коммита `claim` отдельной транзакцией выполняет `fail` этого листа со `stage = task_storage` (цикл очистки по 2.6) и добирает пачку следующими задачами той же очереди; балансировщик этого не видит. Пустой ответ — очередь пуста |
| `result([(task_id, payload)])` | Принимает результаты пачки (см. 4.3). Каждая задача вместе со своим циклом готовности фиксируется своей транзакцией; ответ приходит после коммита всех |
| `fail(task_ids, error)` | Задача упала и в пачке, и в одиночку (см. «Балансировщик»), поэтому обычно приходит ровно один `task_id`. Для каждого листа — цикл очистки по 2.6, своей транзакцией. `error` — структура: текст ошибки (`message`), число запусков (`attempts`), по желанию воркер и модель; из неё и из дерева core собирает снимок ошибки (2.7) |
| `check_tasks()` | Для каждого типа очереди — есть ли в ней задачи в `wait` (`EXISTS` по частичным индексам очередей). Задачи не выдаёт и ничего не меняет. Балансировщик опрашивает его, чтобы решить, нужно ли вытеснение |
| `reset(balancer_id)` | Все листья в `processing` с `taken_by = balancer_id` → `wait`, `taken_at` и `taken_by` = `NULL`. Балансировщик вызывает его при своём старте (задачи, взятые до перезапуска, он уже не выполнит) и при вытеснении (вернуть задачи из очищенной очереди пачек). Ошибкой это не считается |

`task_id` — идентификатор `task` либо chunk (для очереди `embed`).

Возвращённая и завершившаяся ошибкой задачи — разные события: возвращённую (`reset`) кладём обратно в очередь (`wait`), а ошибка запускает цикл очистки — file переходит в `error` и всё под ним удаляется, либо, если упал собственный text, удаляются его chunk'и, а ошибка пишется в record (2.4, 2.6). Любая операция над объектом, которого уже нет или который не в `processing`, игнорируется и не считается ошибкой.

#### 4.3. Обработка результата

Результат каждой задачи фиксируется **одной транзакцией вместе со всеми порождёнными записями и циклом готовности** (см. 2.6). Коммит происходит до ответа балансировщику, поэтому не бывает момента, когда задача завершена, а её дети ещё не созданы или её предки не пересчитаны.

**Эмбеддинг** (лист chunk): записываются `embed` и `embed_model`, chunk → `done`.

**Транскрибация** (лист `task_transcribe` под audio):

1. `task_transcribe` → `done`.
2. Если транскрипция непуста, создаётся text (`kind` = `task_result`) — ребёнок audio — со статусом `processing`. Текст сразу режется на chunk'и (дети text, статус `wait`, `embed` пуст).
3. Если транскрипция пуста, text не создаётся.

**OCR** (лист `task_ocr` под photo): то же самое, text становится ребёнком photo. Если OCR не вернул текст, text не создаётся; это не ошибка.

Пока созданные chunk'и не получат эмбеддинги, audio (или photo) остаётся в `processing`.

#### 4.4. OCR

OCR обязателен для каждой photo, в том числе для каждого кадра видео: `task_ocr` создаётся всегда, без настроек и политик. Photo с пустым результатом OCR завершается, не имея text.

#### 4.5. Восстановление после сбоев

Возврат задач, взятых в работу:

- **При старте core** все листья в статусе `processing` возвращаются в очередь: `status = 'wait'`, `taken_at` и `taken_by` = `NULL`. Так обрабатывается падение core, в том числе при фиксации результата. Если балансировщик потом пришлёт результат по такой задаче, он будет проигнорирован (задача уже не в `processing`), а сама задача выполнится заново.
- **При старте балансировщика** он вызывает `reset(balancer_id)` (см. 4.2): возвращаются задачи, которые взял именно он; балансировщик состояния не хранит и набирает задачи заново.

Возврата по таймауту нет: длинная транскрибация законно идёт часами, и таймаут срабатывал бы посреди нормальной работы. Если балансировщик завис, его перезапускают, и при старте он сам возвращает свои задачи через `reset(balancer_id)`.

При старте core:

1. удаляет записи в `parsing` вместе с их каталогами (см. 3.2) — до того, как начать принимать новые записи;
2. возвращает все листья из `processing` в `wait` — до того, как начать отвечать балансировщику;
3. запускает цикл очистки по таймеру (см. 2.8) и очистку хранилищ (см. 3.3); дальше они работают по своим таймерам.

Проверки и ремонта дерева нет: операция над листом и весь вызванный ею цикл фиксируются одной транзакцией (2.6), поэтому падение core не оставляет дерево наполовину пересчитанным.
