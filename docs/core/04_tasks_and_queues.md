### 4. Задачи и очереди

#### 4.1. Очереди

Три очереди core соответствуют типам задач:

| Очередь (`type`) | Листья |
|---|---|
| `transcribe` | `task` с типом `transcribe` в статусе `wait` |
| `ocr` | `task` с типом `ocr` в статусе `wait` |
| `embed` | `chunk` в статусе `wait` |

Задача находится «в очереди», если `status = 'wait'`, и «на воркере», если `status = 'processing'` (тогда заполнены `taken_at` и `taken_by`). Отдельных структур очередей нет: очередь — это SQL-запрос к `task` или `chunk` в статусе `wait`. Порядок внутри очереди — FIFO по `created_at`.

Для балансировщика core — один источник задач (см. «Термины»): очередей для конкретных `record.source_id` (`youtube`, `telegram`) не существует, и балансировщик их не различает. Приоритеты очередей применяет балансировщик. Приоритеты источников он получает из реестра core: все агенты равноприоритетны и выше core (см. 11.6).

#### 4.2. API источника задач

Единственный балансировщик работает с каждым источником задач (core и зарегистрированными режимами агентов) по одному и тому же API. Он получает task_source_id и адрес API из реестра core (11.6). Источник определяется task_source_id; одного IP:PORT недостаточно, потому что разные agent_id могут обслуживаться одним контейнером. В каждом запросе передаются `X-Balancer-ID: <balancer_id>` и `Authorization: Bearer <token этого источника>`; token приходит из реестра core и принимается только для выбранного task_source_id. Пользователи, агенты и скрапперы не могут вызывать служебное API балансировщика. Источник, в свою очередь, знает, какой балансировщик взял задачу: `claim` передаёт `balancer_id` (постоянный идентификатор из конфига балансировщика), и источник записывает его в лист (`taken_by`). Все пути ниже добавляются к `task_endpoint`. JSON-параметры, заголовки, ответы и примеры закреплены в [HTTP API](../api.md). Core реализует эндпоинты так:

| Эндпоинт | Действие |
|---|---|
| `POST /api/task-sources/{task_source_id}/claim` | JSON: обязательные `type`, `balancer_id`; параметра `limit` нет. `type` — `transcribe`, `ocr` или `embed`. Если очередь не пуста, атомарно берёт ровно одну следующую задачу, переводит её из `wait` в `processing`, ставит `taken_at` и `taken_by = balancer_id`. Реализуется как `UPDATE … SET status = 'processing', taken_at = now(), taken_by = :balancer_id WHERE id IN (SELECT … WHERE status = 'wait' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING …`. Ответ `200`, объект с массивом `tasks` из одной задачи (или пустым, если очередь пуста): у задачи `task_id`, `type`, `input`. Для текста `input.text` берётся из БД, для аудио и картинки выдаются `input.url` и `input.mime`; данные скачиваются отдельным GET из `task_storage` по `element_id` до запуска воркера. Если для выбранной задачи файла в `task_storage` нет, core после коммита `claim` отдельной транзакцией выполняет `fail` этого листа со `stage = task_storage` (цикл очистки по 2.6) и берёт следующую задачу той же очереди, пока не найдёт задачу с доступными данными или очередь не опустеет; балансировщик этого не видит. Один ответ всё равно содержит не более одной задачи; пачку собирает балансировщик по суммарной сложности. Ответ `{"tasks":[]}` — очередь пуста |
| `POST /api/task-sources/{task_source_id}/result` | JSON: `balancer_id`, массив `results` из объектов с `task_id` и `payload`. Для OCR и транскрибации payload содержит `text`, для эмбеддинга — `embedding` и `embed_model`. Принимает результаты пачки (см. 4.3). Каждая задача вместе со своим циклом готовности фиксируется своей транзакцией; ответ `204` приходит после коммита всех |
| `POST /api/task-sources/{task_source_id}/fail` | JSON: `balancer_id`, непустой `task_ids`, `error`. Ответ `204` после фиксации ошибок. Задача упала и в пачке, и в одиночку (см. «Балансировщик»), поэтому обычно приходит ровно один `task_id`. Для каждого листа — цикл очистки по 2.6, своей транзакцией. `error` — структура: текст ошибки (`message`), число запусков (`attempts`), по желанию воркер и модель; из неё и из дерева core собирает снимок ошибки (2.7) |
| `GET /api/task-sources/{task_source_id}/check_tasks` | Без тела и query-параметров. Ответ `200`: `{"transcribe":true,"ocr":false,"embed":true}` — для каждого типа очереди есть ли в ней задачи в `wait` (`EXISTS` по частичным индексам очередей). Задачи не выдаёт и ничего не меняет. Балансировщик опрашивает его, чтобы решить, нужно ли вытеснение |
| `POST /api/task-sources/{task_source_id}/reset` | JSON: обязательный `balancer_id`. Ответ `204`. Все листья в `processing` с `taken_by = balancer_id` → `wait`, `taken_at` и `taken_by` = `NULL`. Балансировщик вызывает его при своём старте (задачи, взятые до перезапуска, он уже не выполнит) и при вытеснении (вернуть задачи из очищенной очереди пачек). Ошибкой это не считается |
| `GET /api/task-sources/{task_source_id}/tasks/{task_id}/input` | Без тела. Возвращает бинарный файл с `Content-Type` из `input.mime`. Только для задачи выбранного источника в `processing`, взятой балансировщиком из token; иначе `404`. |

`task_id` — идентификатор task либо chunk (для очереди embed). В агентском приложении каждый режим имеет отдельный agent_id и собственную область очередей: claim, result, fail, check_tasks и reset работают только в выбранном task_source_id. Задачи и результаты не переходят между режимами или владельцами. Сам core остаётся одним служебным источником задач по записям всех пользователей; служебный доступ к этим задачам не даёт балансировщику поисковых или административных прав.

`POST /api/task-sources/{task_source_id}/result` и `POST /api/task-sources/{task_source_id}/fail` принимаются только для задач, выданных аутентифицированному балансировщику этим источником. Значение balancer_id в заголовке проверяется по служебной регистрации и должно совпадать с ID в теле запроса, если он там есть; передача одного balancer_id без действующего token доступа не даёт.

Возвращённая и завершившаяся ошибкой задачи — разные события: возвращённую (`reset`) кладём обратно в очередь (`wait`), а ошибка запускает цикл очистки — file переходит в `error` и всё под ним удаляется, либо, если упал собственный text, удаляются его chunk'и, а ошибка пишется в record (2.4, 2.6). Любая операция над объектом, которого уже нет или который не в `processing`, игнорируется и не считается ошибкой.

#### 4.3. Обработка результата

Результат каждой задачи фиксируется **одной транзакцией вместе со всеми порождёнными записями и циклом готовности** (см. 2.6). Коммит происходит до ответа балансировщику, поэтому не бывает момента, когда задача завершена, а её дети ещё не созданы или её предки не пересчитаны.

**Эмбеддинг** (лист chunk): записываются `embed` и `embed_model`, chunk → `done`.

**Транскрибация** (лист `task_transcribe` под audio):

1. `task_transcribe` → `done`.
2. Если транскрипция непуста, создаётся text (`kind` = `task_result`) — ребёнок audio — со статусом `processing`. Текст сразу режется на chunk'и (дети text, статус `wait`, `embed` пуст).
3. Если транскрипция пуста, text не создаётся.

**OCR** (лист `task_ocr` под photo): то же самое, text становится ребёнком photo. Если OCR не вернул текст, text не создаётся; это не ошибка.

Пока созданные chunk'и не получат эмбеддинги, audio (или photo) остаётся в `processing`.

#### 4.4. OCR

OCR обязателен для каждой photo, в том числе для каждого кадра видео: `task_ocr` создаётся всегда, без настроек и политик. Photo с пустым результатом OCR завершается, не имея text.

#### 4.5. Восстановление после сбоев

Возврат задач, взятых в работу:

- **При старте core** все листья в статусе `processing` возвращаются в очередь: `status = 'wait'`, `taken_at` и `taken_by` = `NULL`. Так обрабатывается падение core, в том числе при фиксации результата. Если балансировщик потом пришлёт результат по такой задаче, он будет проигнорирован (задача уже не в `processing`), а сама задача выполнится заново.
- **При старте балансировщика** он вызывает `POST /api/task-sources/{task_source_id}/reset` (см. 4.2): возвращаются задачи, которые взял именно он; балансировщик состояния не хранит и набирает задачи заново.

Возврата по таймауту нет: длинная транскрибация законно идёт часами, и таймаут срабатывал бы посреди нормальной работы. Если балансировщик завис, его перезапускают, и при старте он сам возвращает свои задачи через `POST /api/task-sources/{task_source_id}/reset`.

При старте core:

1. удаляет записи в `parsing` вместе с их каталогами (см. 3.2) — до того, как начать принимать новые записи;
2. возвращает все листья из `processing` в `wait` — до того, как начать отвечать балансировщику;
3. запускает цикл очистки по таймеру (см. 2.8) и очистку хранилищ (см. 3.3); дальше они работают по своим таймерам.

Проверки и ремонта дерева нет: операция над листом и весь вызванный ею цикл фиксируются одной транзакцией (2.6), поэтому падение core не оставляет дерево наполовину пересчитанным.
