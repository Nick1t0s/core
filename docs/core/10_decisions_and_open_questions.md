### 10. Принятые решения и открытые вопросы

Решения, принятые при составлении ТЗ:

1. Разбор записи до коммита дерева выполняет сам core, в фоне, после ответа скрапперу (разбиение PDF и Word на страницы и листы, определение кадров и аудио видео, нарезка текста); это не GPU-работа и в очереди балансировщика не входит. Кадры, аудио и рендер страниц для задач извлекаются при разборе и кладутся во временный `task_storage` (см. 3.3); запросы агента строят их из исходного файла по `meta` той же функцией извлечения.
2. Граница ошибки — file (для листьев внутри файла), а не element: лучше открыто потерять файл целиком, чем незаметно терять его части. Для листьев собственного text записи граница — record: в него пишется ошибка, но статус record не меняется. Ошибку обрабатывает цикл очистки: вверх до границы с сообщением, вниз по слоям, удаление снизу вверх — одной транзакцией; упавшее не дорабатывается (иначе работа GPU тратится на то, что нельзя найти). Для отладки остаются исходный файл и снимок ошибки (2.7). Цикл очистки по таймеру — только страховка (2.8).
3. Record становится `error`, только если все его дети (собственный text, если есть, и все file) в `error` (2.5); иначе `done`. Пустая запись не принимается (3.1), а упавший разбор записи даёт дерево из пустышек (3.5), так что других случаев `error` у record нет. Запись доступна в поиске агенту, только когда она в done, owner совпадает и record.trust_level < agent.trust_level (5, 11).
4. OCR обязателен для каждой photo, в том числе для каждого кадра видео. Кадры берутся каждые i секунд и не дедуплицируются: каждый кадр и эмбеддится, и отправляется на OCR.
5. Одна аудиодорожка файла — один element audio и одна задача транскрибации; длинное аудио на части не режется. Принятое следствие: при вытеснении (см. «Балансировщик») прогресс длинной транскрибации теряется целиком, и при активных агентах обработка записей core может откладываться. Равноприоритетные агенты друг друга не вытесняют.
6. `registered_at` — момент приёма записи (вставки record в `parsing`).
7. Параметры нарезки текста: максимум x символов на chunk, границы по абзацам и предложениям, перекрытие настраивается (по умолчанию 0).
8. Шаг кадров i, период очистки хранилищ, период цикла очистки по таймеру и формат материалов в `task_storage` — параметры конфигурации.
9. Element хранится в двух таблицах: photo и audio — в `element`, text-элементы — в `text`. Так text как результат OCR, транскрибации, собственный текст записи и text-элемент фрагмента лежат в одной таблице; колонка `kind` различает их, ссылки `record_id`, `fragment_id`, `element_id` согласованы с ней.
10. Операция над листом и вызванный ею цикл (готовности или очистки) фиксируются одной транзакцией с блокировкой file (или собственного text записи) и record (2.6), поэтому проверка и ремонт дерева не нужны.
11. Статус `wait` есть только у листьев-задач (chunk, `task_transcribe`, `task_ocr`); у контейнеров «ожидания» нет, они с момента создания `processing` (record — `parsing`, пока идёт разбор).
12. `task_storage`: один файл на element, создаётся при разборе до коммита дерева, живёт до завершения record и удаляется очисткой хранилищ целым каталогом записи; очистка хранилищ только читает БД. Пропажа файла — ошибка задачи, заново данные не извлекаются. Лимита размера нет: объём ограничен K незавершёнными записями на скраппер. Для фото, которое само является файлом, копия всё равно делается: выигрыш от ссылки на исходник минимален.
13. Пути файлов выводятся из идентификаторов, поэтому `record_id` и `file_id` выдаются core при приёме (record сразу вставляется в `parsing`) и в БД нет ни путей, ни хэшей файлов: изменения записей не отслеживаются.
14. Приём асинхронный: core отвечает `202` после сохранения исходных файлов и разбирает запись в фоне; отдельной таблицы состояния приёма нет, её роль играет record в статусе `parsing`. Core работает в одном экземпляре, поэтому при старте все записи в `parsing` считаются прерванными. Для нескольких экземпляров core понадобится heartbeat разбора.
15. Источник задач определяется task_source_id (core или отдельный agent_id), все очереди обслуживает API core (4.2). Core — один источник: record.source_id и владельцев записей балансировщик внутри него не различает. Задачи и результаты агента хранятся в его отдельной области очередей в core. Балансировщик обращается только к core с едиными служебными полномочиями; список источников, наличие задач и приоритеты получает одним запросом (11.6).
16. Балансировщик работает пачками на одном GPU: в каждый момент выполняется ровно один воркер, процесс воркера запускается на каждую пачку. Упавшая пачка разбивается на пачки по одной задаче, `fail` получает только задача, упавшая в одиночку; ретраев нет. Состояние балансировщик не хранит, воркеры завершаются вместе с ним средствами ОС; при старте и при вытеснении он вызывает `POST /api/task-sources/{task_source_id}/reset` и так возвращает только свои задачи. Возврата задач по таймауту нет (4.5).
17. Ручного перезапуска нет. Запись можно удалить в кабинете core или через API (6, 11.5); при вызове агентом обязательны совпадение owner и record.trust_level < agent.trust_level. После удаления скраппер отправит запись заново, если встретит.
18. Эмбеддинги хранятся в `halfvec(2048)` с индексом HNSW (7).
19. Скраппер держит в core до K незавершённых записей. Запись с файлом больше `max_file_size` (по умолчанию около 15 ГБ) в core не отправляется и заносится в таблицу пропущенных по размеру у скраппера.
20. Доступ аутентифицируется и в локальной сети: в core люди входят по логину и паролю, агенты, скрапперы и балансировщик предъявляют постоянный ID и отдельный token, автоматически генерируемый core при создании регистрации. Внешняя регистрация закрыта, открыта или требует одноразового приглашения по выбору администратора. Администратор имеет доступ ко всему и управляет пользователями; пользователь создаёт свои агенты и скрапперы (11).
21. Приложение агента может оставаться одним монолитом в контейнере: веб-интерфейс, ИИ-поиск, ручной поиск и Telegram-бот. Каждый режим регистрируется отдельно со своим agent_id, owner, trust_level и областью очередей, даже при общем сервере приложения. Core и балансировщик разворачиваются отдельно.
22. У record один owner и один trust_level; уникальность — (owner, source_id, source_url). Материалы разных владельцев дублируются полностью. Таблицы связи многие ко многим и поля owners нет.
23. Балансировщик один, пользователи не могут создавать его экземпляры через API. Все агенты равноприоритетны и выше core; равенства разрешаются по ID. Внутренние приоритеты очередей также могут совпадать; для них равенства разрешаются по имени типа.
24. Owner и trust_level агента подставляет core из своей регистрации. Равенство уровней не даёт доступа; агенты не могут менять свои полномочия. Административная роль владельца не передаётся агенту.
25. Сайты агентов и скрапперов пользователь размещает и защищает по своему усмотрению, включая публикацию в интернете и собственные логины/пароли. Сессия core для этих сайтов не обязательна; локальный admin не даёт прав в core. Agent_id — постоянный несекретный ID, совпадающий с task_source_id; core проверяет пару agent_id/token при каждом вызове API агента. Record.scrapper хранит scrapper_id первоначального скраппера и заполняется core; повторная отправка его не меняет.
26. Удаление record допустимо в любом статусе при проверке прав, удаляет его дерево и задачи и согласовано с фоновым разбором. Данные других владельцев не затрагиваются (11.5).

27. Сложность вычисляет core и возвращает в claim вместе с метаданными задачи. Балансировщик суммирует её и только после набора пачки скачивает входные данные, включая текстовый embed как байты UTF-8. Агенты и скрапперы сложность не передают.

Открытые вопросы:

1. **Повторная отправка из Telegram.** Сканер каналов и чатов читает только сообщения после `last_message_id`, поэтому удалённую вручную запись сам не пришлёт. Есть идея на каждом проходе брать все id сообщений группы или чата и сверять их с core; пока не решено.
2. **Поиск** (раздел 5) в разработке.
3. **Сложность задач.** Формулы, метрики OCR и изображений для embed, приведение входов одного типа к единицам его порога и крайние случаи будут определены отдельно. Принятые единицы: минуты аудио и число символов для текстового embed.
4. **Самостоятельные задачи агентов.** Сроки хранения входов и результатов, квоты, удаление и очистка будут определены отдельно. Эти задачи хранятся отдельно от дерева record.
