### 11. Пользователи, регистрация и доступ

#### 11.1. Учётные записи и роли

Клиент — пользователь core, управляющий своими агентами и скрапперами. Его учётная запись хранится в app_user; каждый из его агентов хранится отдельной строкой agent с owner = app_user.id. Один клиент может владеть несколькими агентами. Далее термины «клиент» и «пользователь core» означают одну сущность.

Core хранит пользователей и аутентифицирует вход по логину и паролю. Телефон и электронная почта для создания пользователя и входа не нужны. Логин уникален с учётом единого правила нормализации регистра; пароль хранится только как стойкий хеш с солью. Первый администратор создаётся при первоначальной настройке сервера, а не через открытую регистрацию.

- **Администратор** имеет доступ ко всем данным и управляет пользователями: создаёт и блокирует учётные записи, сбрасывает пароли, управляет внешней регистрацией и приглашениями. Административный интерфейс не создаёт пользовательские агенты и скрапперы. Если администратору нужны собственные источники, он создаёт их через пользовательский раздел в своей учётной записи.
- **Пользователь** видит только собственные записи и настройки, создаёт своих агентов и скрапперы на своём сайте. Совпадение уровней доверия у разных пользователей не связывает их права.

Административный доступ — отдельное право сессии человека. Агент администратора подчиняется тем же проверкам owner и trust_level, что любой другой агент; роль владельца не даёт агенту обхода ограничений. Блокировка пользователя делает недействительными его сессии и полномочия агентов и скрапперов. Существующие записи при блокировке сохраняются.

#### 11.2. Внешняя регистрация и приглашения

Администратор выбирает один из трёх режимов `registration_mode`:

| Режим | Создание учётной записи |
|---|---|
| `closed` | Только администратором; внешняя регистрация выключена |
| `open` | Любой посетитель задаёт логин и пароль |
| `invite` | Посетитель задаёт логин, пароль и одноразовый код приглашения |

По умолчанию регистрация закрыта. Внешняя регистрация всегда создаёт обычного пользователя; роль из запроса не принимается. Администратор может создавать пользователей при любом режиме, без кода.

Коды создаёт администратор; код непредсказуем, показывается при выдаче, на сервере хранится его хеш. Код можно отозвать. В режиме `invite` проверка кода, создание пользователя и отметка об использовании фиксируются одной транзакцией с блокировкой приглашения: из двух одновременных регистраций с одним кодом успешна только одна. При ошибке создания пользователя код не расходуется. Режим регистрации проверяется сервером в той же операции, а не только в форме сайта. Смена режима не удаляет существующих пользователей.

#### 11.3. Регистрация агентов и скрапперов

Пользователь создаёт агент через свой сайт. Каждый режим работы имеет отдельную регистрацию и собственный `agent_id`; общий контейнер не означает общих полномочий. Для веб-интерфейса и Telegram режимы регистрируются отдельно, если используются оба интерфейса. Например, ИИ-поиск в веб-интерфейсе и ручной поиск в боте могут иметь разные уровни доверия.

Для агентов, скрапперов и единственного балансировщика действует единая схема: постоянный несекретный ID и отдельный секретный `token`. ID задаётся при создании регистрации и далее не меняется: `agent_id` и `scrapper_id` — UUID, задаваемые владельцем в запросе создания, `balancer_id` задаётся администратором при настройке сервера. ID уникален в пределах своего типа во всём core, в том числе среди удалённых регистраций; повторное использование запрещено. Конфликт ID возвращает `409 Conflict` без сведений о владельце.

Core автоматически генерирует token при создании регистрации: 256 случайных бит криптографического генератора в текстовом виде. Пользователь не задаёт token. Token показывается при выдаче, core хранит только его хеш. Перевыпуск создаёт новый token и сразу отзывает прежний, не меняя ID, owner, права и привязки задач или записей. Токены компонентов используются только на серверной стороне и не попадают в публичные HTML, клиентский JavaScript, URL или логи.

В каждом запросе компонент передаёт свой ID в заголовке `X-Agent-ID`, `X-Scrapper-ID` или `X-Balancer-ID`, а token — в `Authorization: Bearer <token>`. Для API очередей дополнительно используется отдельный token выбранного источника (11.6). Сервер проверяет пару ID/token, активность регистрации и её допустимые операции. Удалённая регистрация не может быть включена или получить новый token; её ID сохраняется для запрета повторного использования. Отсутствие любого из двух значений, неверный token или token другой регистрации даёт `401`. Одного ID недостаточно.

Core хранит в agent `agent_id`, `token_hash`, owner (ID пользователя), mode, trust_level, адрес API очередей task_endpoint и состояние enabled. Owner определяется по сессии при создании и далее не меняется. Владелец меняет уровень доверия своих агентов, отключает их и перевыпускает token. Агент не может менять свою регистрацию, owner или trust_level. По проверенной паре agent_id/token core определяет owner, trust_level и допустимые операции при каждом запросе; переданные клиентом owner, trust_level и фильтры эти права не расширяют. Отдельный пароль агента не требуется.

Сайты агентов и скрапперов принадлежат пользователю: он может менять их, публиковать в интернете, открывать без входа или назначать любые собственные логины и пароли, включая admin. Core не требует на этих сайтах своей сессии, своей формы входа или обязательного доступа системного администратора. Локальный логин admin не даёт административных прав в core. Кабинет и административный сайт самого core остаются под его аутентификацией. Посетители открытого сайта агента могут пользоваться предоставленными владельцем возможностями, но каждый запрос приложения к core всё равно ограничен зарегистрированным агентом и его правами; публичность сайта этих прав не меняет.

Скраппер также создаётся пользователем через его сайт и имеет отдельные `scrapper_id` и `token`. Core хранит owner и состояние скраппера. После создания экземпляр скраппера поднимает собственный сайт для настройки источников, режимов, очередей и уровня доверия отправляемых записей. Публикацию сайта и правила входа на него определяет владелец, независимо от входа в core. Скраппер назначает `trust_level` своим записям при отправке; owner и `scrapper = scrapper_id` core подставляет из проверенной регистрации скраппера. Скраппер не получает поисковые права агента и не может записывать данные от имени другого владельца.

#### 11.4. Владение записью и уровни доверия

Каждая запись имеет ровно одного владельца. В таблицу record добавляются три обязательных поля:

| Поле | Значение |
|---|---|
| `owner` | Внешний ключ на пользователя |
| `trust_level` | Уровень доверия записи, назначенный скраппером владельца |
| `scrapper` | UUID скраппера, впервые добавившего запись: ссылка на scraper.scrapper_id; core заполняет из проверенной регистрации |

Уникальный ключ записи — `(owner, source_id, source_url)`. `source_id` — имя источника (`youtube`, `telegram`), в прежней версии ТЗ поле называлось `source`. Owner записи и скраппера не меняется после создания. Одинаковый материал у разных пользователей хранится отдельными record с отдельными деревьями, файлами, статусами, задачами и уровнями доверия. Между пользователями дедупликации нет; таблицы связи многие ко многим и поля `owners` нет. Поле scrapper неизменно и имеет того же owner, что запись. Повторная отправка внутри одного владельца, включая отправку другим скраппером, не обновляет существующую запись, в том числе её trust_level и scrapper. Удаление скраппера отзывает token и скрывает регистрацию из активных списков, но сохраняет строку регистрации и её ID для ссылок record.scrapper; записи не удаляются. Поле scrapper хранит происхождение и не добавляет ограничений к существующим правилам доступа по owner и trust_level.

Уровни — неотрицательные целые числа; большее значение агента даёт доступ к большему диапазону записей своего владельца. Уровни разных пользователей между собой не сравниваются. Владелец может менять trust_level своей записи через кабинет; агент не может менять уровни записей, собственные права или владельца.

Для запроса агента core сам добавляет обязательное условие:

```sql
record.owner = :authenticated_agent_owner
AND record.trust_level < :authenticated_agent_trust_level
```

Оба параметра получены core из аутентифицированной регистрации агента. Сравнение строгое: при равных уровнях доступа нет. Например, при уровне агента 5 доступны записи его владельца с уровнями 0–4, но не 5; агент уровня 0 не получает ни одной записи. Запись другого пользователя недоступна при любом её уровне.

Условие применяется до поиска, ранжирования, подсчётов, лимитов и формирования ответа ко всем объектам через их record: к `search`, `read`, чтению по ID, дереву, файлам и возможному будущему извлечению медиа. Для поиска и чтения содержимого дополнительно обязательно `record.status = 'done'`. Пользовательский кабинет показывает собственные записи всех статусов; сессия владельца позволяет управлять своими записями и их уровнями. Агенту такое право сессии не передаётся.

Хранилища исходников и task_storage не публикуются как открытые каталоги: файл выдаётся только через авторизованную операцию core. Знание record_id, file_id или пути не заменяет проверку доступа.

Курсоры, кеши и сохранённая выдача разделяются по agent_id и владельцу; секретный token в них не раскрывается. На каждой странице core снова проверяет действующие права и принадлежность записей: снижение уровня агента, повышение уровня записи, удаление записи или отзыв доступа не позволяют дочитать старую выдачу. Недоступный ID возвращает тот же ответ, что отсутствующий; поля, ошибки, счётчики и ссылки не раскрывают чужие записи.

#### 11.5. Удаление записи у себя

Core предоставляет операцию `DELETE /api/records/{record_id}`. При вызове агентом удаляется record, только если его owner совпадает с owner агента, а текущий `record.trust_level` строго меньше текущего уровня агента. Проверка полномочий и удаление выполняются одной транзакцией с согласованными блокировками регистрации агента и record: изменение уровней не даёт обойти проверку. Передать другого owner нельзя. Операция доступна для записи в любом статусе; фильтр `done` относится к поиску и чтению, а не к удалению.

Дерево и задачи удаляются каскадом, каталоги исходных файлов и task_storage удаляет очистка хранилищ. Поздние результаты удалённых задач игнорируются. Фоновый приём и разбор синхронизируются с удалением по record_id: после коммита удаления они не могут повторно создать дерево или файлы удалённой записи. Копии материала других пользователей не затрагиваются. Повторное удаление не раскрывает, существовала ли чужая запись. Владелец может выполнить удаление из своего кабинета без посредничества агента; администратор — для любой записи.

Повторная отправка скраппером после удаления считается новым добавлением для владельца с новым record_id; правила повторного сканирования описаны в разделе «Скрапперы».

#### 11.6. Единственный балансировщик и реестр источников

Балансировщик в системе один; его служебная регистрация и полномочия задаются при настройке сервера. Пользовательские API не позволяют создавать балансировщики или получать их полномочия. Знание balancer_id не заменяет служебную аутентификацию.

Core предоставляет только балансировщику `GET /api/task-sources`: версию реестра, сам core и все зарегистрированные агенты с полями `task_source_id`, `task_endpoint`, `priority`, `enabled`, `draining`, `token`. Запрос содержит `X-Balancer-ID: <balancer_id>` и `Authorization: Bearer <token балансировщика для core>`; ответ `200` — объект `version`, `items`. `token` — отдельный секрет очередей выбранного task_source_id, не token агента для поиска. Точные запросы и ответы — в [HTTP API](../api.md). Активны только включённые агенты незаблокированных пользователей. Отключённые и удаляемые источники со взятыми задачами остаются в ответе для служебного reset (`draining = true`), но новые задачи из них не берутся. Для агента task_source_id — несекретный agent_id его регистрации; для core используется отдельный постоянный ID. Это идентификатор очередей, а не record.source_id (`youtube`, `telegram`). Реестр не содержит паролей пользователей или токенов агентов для поиска. Доступ балансировщика к очередям аутентифицируется отдельными служебными полномочиями, которые не дают права пользовательского поиска и администрирования. Служебный reset доступен и для отключённого агента; блокировка его пользовательских полномочий возврату задач не мешает.

Core и каждый agent_id являются отдельными источниками, даже если несколько режимов обслуживает один контейнер по одному адресу. API очередей маршрутизирует запрос по task_source_id; очереди, claim, result, fail и reset одного режима не затрагивают другой. Общая реализация и общие процессы допустимы, общие полномочия и выдача результатов между владельцами — нет.

Служебные полномочия для вызова очередей привязаны к конкретному task_source_id. Секрет доступа балансировщика к core не передаётся на адреса пользовательских агентов; полномочия для одного источника не принимаются другим. Реестр возвращает `token` для очередей каждого источника; балансировщик передаёт свой `X-Balancer-ID` и этот token в `Authorization: Bearer <token>` только на соответствующий task_endpoint. Этот token не является пользовательским токеном агента и не даёт доступа к поиску или кабинету.

Балансировщик получает реестр при запуске, перед каждым проходом и при периодическом опросе во время работы; при изменении версии обновляет источники. Статического списка агентов в его конфиге нет. Новый источник сначала проходит `POST /api/task-sources/{task_source_id}/reset`, затем допускается к работе. При отключении текущего источника воркер останавливается, набранные пачки отбрасываются, задачи возвращаются через служебный reset. Источник не удаляется окончательно из реестра служебного обслуживания до возврата его взятых задач; это позволяет завершить reset после временной недоступности.

Версия реестра меняется при создании, отключении и удалении агента, изменении его адреса и блокировке владельца. Источник с новым адресом проходит reset перед первым claim по этому адресу.

Все агенты имеют одинаковый приоритет, строго выше core; создать себе более приоритетный источник пользователь не может. При равенстве приоритетов порядок задаётся по task_source_id. Равноприоритетный источник не вытесняет текущий. Подробности обхода и вытеснения — в разделе «Балансировщик».

Если core недоступен, балансировщик не набирает новые пачки по устаревшему списку; уже выполняемую пачку может завершить и передать её результат. После восстановления он обновляет реестр до следующего claim. При запуске без полученного реестра и успешного reset самого core работа не начинается.

#### 11.7. Проверяемые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Два пользователя прислали одинаковые source_id/source_url | Два record с разными owner, ID, деревьями, файлами и независимой обработкой |
| Повторная отправка той же ссылки тем же владельцем с другим trust_level | Существующая запись не меняется; новая не создаётся |
| Агент уровня 5 обращается к собственным записям уровней 4 и 5 | Первая доступна, вторая недоступна для поиска, чтения и удаления |
| Агент с любым уровнем передал чужой ID или подставил owner/trust_level в запрос | Чужие данные не выдаются и не удаляются; полномочия не меняются |
| После первой страницы понизили уровень агента, повысили уровень записи или отозвали доступ | Следующая страница и кеш не выдают ставшие недоступными данные |
| Запись удалили во время приёма, разбора или выполнения задачи | Дерево не восстанавливается, поздний результат игнорируется, файлы удаляет очистка |
| Две регистрации одновременно используют один код | Ровно одна успешна; ошибка создания пользователя не расходует код |
| Создали новый режим агента в работающей системе | Он появляется в реестре без перезапуска балансировщика, имеет отдельный agent_id и проходит reset до claim |
| При работе агента появились задачи другого агента того же приоритета | Вытеснения нет; при следующем обходе равенство разрешается по ID |
| Владелец опубликовал сайт агента без входа или с локальным логином admin | Посетители используют возможности этого сайта; запросы к core ограничены его зарегистрированными агентами, локальный admin не даёт прав администратора core |
| Запрос к API агента в core не содержит действующего agent_id | Доступ отклонён независимо от публикации сайта и локального входа на нём |
| Пользователь вызвал административное API или API балансировщика | Доступ отклонён; регистрация администратором или балансировщиком через пользовательский запрос невозможна |
