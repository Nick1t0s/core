### 9. Инварианты

1. Дерево записи появляется в БД целиком одной транзакцией; до этого record находится в `parsing` и детей не имеет; частичных деревьев не бывает.
2. Каждый контейнер имеет хотя бы одного ребёнка; исключение — record в `parsing`, file в `error` и собственный text в `error` (их дети удалены циклом очистки, или это пустышки разбора).
3. Задачи привязаны только к листьям (chunk, `task_transcribe`, `task_ocr`).
4. Результат задачи фиксируется вместе со всеми порождёнными записями одной транзакцией и коммитится до ответа балансировщику.
5. Каждый photo имеет ровно один chunk-картинку и ровно один `task_ocr` (пока его file не в `error`).
6. Контейнер внутри file (или собственный text записи) `done` только если все его дети `done`; ошибка любого листа внутри file делает ошибочным file, а всё под ним в той же транзакции уходит в `error` и удаляется.
7. Статус `wait` бывает только у chunk, `task_transcribe` и `task_ocr`; у остальных объектов его нет.
8. Операция над листом и весь вызванный ею цикл (готовности или очистки) — один коммит.
9. Record в `error` тогда и только тогда, когда все его дети (собственный text, если есть, и все file) в `error`. Ошибка file или собственного text статус record не меняет; ошибка собственного text пишется в `error` записи.
10. Терминальный статус (`done`, `error`) не меняется; перезапуска обработки нет. Авторизованное удаление записи доступно в любом статусе (6, 11.5).
11. Тройка `(owner, source_id, source_url)` уникальна и обязательна. У record ровно один owner и собственный trust_level; одинаковые материалы разных владельцев — независимые записи.
12. Долговременно core хранит только исходные файлы: либо исходный файл, либо ничего. Исходный файл хранится, пока существует record. Данные для задач лежат во временном `task_storage` и удаляются очисткой хранилищ целым каталогом записи, когда record завершён (`done`, `error`) или его нет в БД.
13. К моменту, когда задачи появились в очередях, их данные уже лежат в `task_storage` (файлы создаются до коммита дерева).
14. Статус `parsing` бывает только у record. Запись в `parsing` существует, только пока core её принимает и разбирает; при старте core все такие записи удаляются.
15. Агенту в поиске и чтении доступны только record в done с owner этого агента и record.trust_level строго меньше agent.trust_level. Полномочия core определяет по аутентифицированной регистрации, а не по параметрам запроса.
16. Record в `error` имеет хотя бы одного ребёнка, и все его дети — file в `error` и собственный text в `error`, без детей.
17. После старта core и до первого `claim` ни одного листа в `processing` нет.
18. Строки в `error` ниже границы (fragment, element, text, кроме собственного text записи, chunk, task) не переживают коммит цикла очистки.
19. Лист в `processing` всегда помечен балансировщиком, который его взял (`taken_by`); лист в `wait` не помечен.
20. Каждый режим агента имеет собственный зарегистрированный agent_id, owner, trust_level и область очередей; общая реализация не объединяет права.
21. Балансировщик один, его нельзя создать через пользовательские API. Реестр источников он получает из core; все агенты имеют равный приоритет выше core, равенства разрешаются по ID.
22. Удаление агентом возможно только для собственного owner при record.trust_level < agent.trust_level; дерево и задачи удаляются вместе с записью, копии других владельцев не затрагиваются.
23. Одно приглашение создаёт не более одного пользователя; регистрация и погашение кода атомарны. Внешняя регистрация никогда не выдаёт роль администратора.
