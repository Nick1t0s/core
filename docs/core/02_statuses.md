### 2. Статусы

#### 2.1. Значения статусов

**Листья chunk, task_transcribe, task_ocr** имеют четыре статуса:

| Статус | Значение |
|---|---|
| `wait` | Задача ждёт взятия: лежит в очереди, `taken_at` и `taken_by` пусты |
| `processing` | Задача в работе: её взял балансировщик, `taken_at` и `taken_by` заполнены |
| `done` | Задача успешно завершена |
| `error` | Задача завершена с ошибкой; существует только внутри транзакции цикла очистки (см. 2.6) |

**Остальные объекты дерева** (record, file, fragment, element, text) имеют три статуса (у record есть ещё четвёртый, см. ниже); `wait` у них не бывает:

| Статус | Значение |
|---|---|
| `processing` | Объект не завершён: не завершены его дети |
| `done` | Объект успешно завершён |
| `error` | Объект завершён с ошибкой. Надолго в `error` остаются только file, record и собственный text записи; остальные строки в `error` удаляются в той же транзакции цикла очистки (см. 2.6) |

У **record** есть ещё четвёртый статус — `parsing`: запись принята, core сохраняет её исходные файлы или разбирает её; детей у record в этом статусе нет. Переходы record:

- `parsing → processing` — коммит дерева (см. 3.1);
- `parsing → error` — разбор записи упал: коммитится дерево из пустышек в `error`, и проверка готовности в той же транзакции переводит record в `error` (см. 3.5, 2.5);
- `processing → done` — нет детей в `processing`, и хотя бы один ребёнок в `done` (см. 2.5);
- `processing → error` — нет детей в `processing`, и все дети (собственный text, если есть, и все file) в `error` (см. 2.5).

Других путей в `error` у record нет: ошибка собственного text пишется в record, но его статус не меняет (см. 2.4), а пустая запись не принимается (см. 3.1).

Если core упал во время приёма или разбора, record в `parsing` удаляется при старте (см. 3.2).

`done` и `error` — терминальные: после перехода статус не меняется. Запись в `error` можно только удалить вручную (см. 6).

Переходы листьев: `wait → processing` (claim), `processing → done` (result), `processing → error` (fail, цикл очистки), `processing → wait` (`reset(balancer_id)`, возврат при старте core, см. 4.2, 4.5). Кроме того, цикл очистки на пути вниз переводит в `error` все листья под границей в любом статусе (см. 2.6).

#### 2.2. Вся работа сидит в листьях

Задачи воркеров привязаны только к листьям:

- эмбеддинг — chunk в статусе `wait` или `processing`;
- транскрибация — лист `task_transcribe`;
- OCR — лист `task_ocr`.

Все остальные объекты (record, file, fragment, audio, photo, text) не имеют собственной работы и являются контейнерами. Это закрывает проблему «пустого успеха»: у audio до завершения транскрибации всегда есть ребёнок `task_transcribe` не в статусе `done`, у photo — `task_ocr`, поэтому проверка «все дети готовы» не может ошибочно пометить контейнер готовым. Никаких дополнительных флагов «готов к обработке» не нужно.

#### 2.3. Правило готовности

Контейнер внутри file (или собственный text записи) готов, когда число его готовых детей равно числу всех его детей, то есть когда у него нет ни одного ребёнка не в статусе `done`. Правило одинаково для всех контейнеров, включая «листовые» fragment (у которых единственный ребёнок — element): особых случаев нет.

#### 2.4. Граница ошибки и ошибки

- **Ошибка листа внутри file** (в любом fragment, element или text этого файла) делает ошибочным этот file. Граница — file: в него пишутся текст ошибки и снимок (см. 2.7), а всё, что под ним, в той же транзакции уходит в `error` и удаляется циклом очистки (см. 2.6).
- Граница — file, а не element: лучше открыто потерять файл целиком, чем незаметно терять его части.
- **Ошибка листа собственного text записи** (chunk этого text) делает ошибочным этот text: он переходит в `error`, его chunk'и удаляются, а текст ошибки и снимок пишутся в record — для собственного text границей служит record. Статус record при этом не меняется: файлы записи обрабатываются дальше.
- На статус record ошибки file и собственного text сами по себе не влияют. Record становится `error`, только если все его дети в `error` (см. 2.5).
- Ошибка воркера всегда серьёзная: сбои воркера (OOM, неправильный файл и т. п.) обрабатывает балансировщик, разбивая упавшую пачку на пачки по одной задаче; `fail` приходит в core только по задаче, которая упала и в одиночку (см. «Балансировщик»).

#### 2.5. Готовность record

Record переходит в терминальный статус, когда у него нет ни одного ребёнка (file или собственного text) в `processing`. Тогда:

- если все дети в `error` (собственный text, если он есть, и все file), `status` = `error`: в `error` пишется «все дети завершились ошибкой», в `error_detail` — сводка `{"stage": "children", "text": …, "files": [{"id": …, "error": …}]}`, где `text` — снимок ошибки собственного text, который уже лежал в record (если text был), а `files` — список упавших file; полные снимки ошибок file остаются у самих file;
- иначе (хотя бы один ребёнок в `done`) `status` = `done`;
- в обоих случаях `processed_at` = текущий момент.

Это единственный случай `error` у record. Записи без детей не бывает: пустая запись не принимается (см. 3.1), а если разбор записи упал, все её дети записываются пустышками в `error` (см. 3.5).

Проверка выполняется только для record в `processing`: record в `parsing` детей ещё не имеет и ею не затрагивается. Она запускается из цикла готовности и цикла очистки (см. 2.6), а также сразу в транзакции коммита дерева (см. 3.1), в том числе дерева из пустышек (см. 3.5): если при разборе ни одного листа не появилось, циклов не будет, и без этой проверки record навсегда остался бы в `processing`.

У записи в `done` есть хотя бы один ребёнок в `done`; отдельные file в `error` и упавший собственный text (его ошибка лежит в `error` самой записи) у неё бывают. Искать в ней при этом может быть нечего: например, у file с беззвучным аудио нет ни одного chunk'а.

У record в `error` все дети — границы в `error` без детей: file в `error` и собственный text в `error` (если он был).

#### 2.6. Обновление статусов: цикл готовности и цикл очистки

Статусы chunk и task (листья) меняются только по операциям API источника (см. 4.2), при восстановлении (см. 4.5) и циклом очистки: `claim` переводит лист из `wait` в `processing`, `result` — в `done`, `fail` — в `error`, `reset(balancer_id)` возвращает в `wait`. Статусы всех остальных объектов (element, fragment, text, file, record) вычисляют два цикла:

- **цикл готовности** распространяет `done` вверх по дереву; его запускает результат задачи (`result`);
- **цикл очистки** распространяет ошибку вверх до границы, затем `error` вниз по слоям и удаляет всё, что в `error` ниже границы; его запускает ошибка задачи (`fail` от балансировщика или `fail`, который core выполняет сам, если для задачи нет файла в `task_storage`, см. 4.2), а также таймер (см. 2.8).

**Правило циклов:** операция над листом (`result` или `fail`) и весь вызванный ею цикл — одна транзакция с одним коммитом. Состояний, когда лист уже завершён, а его предки ещё не пересчитаны, или когда под ошибочной границей остались строки, в БД не бывает.

**Блокировки.** Транзакция первым делом блокирует строку своей единицы блокировки — file или собственного text записи (`SELECT … FOR UPDATE`). Её находят по внешним ключам: у element и fragment есть `file_id`, у text — `fragment_id` (или `kind = 'record'`, тогда единица блокировки — сам text). Строка record блокируется в конце: перед проверкой готовности record, а в цикле очистки собственного text — перед записью ошибки в record.

Зачем это нужно. Без блокировки два последних соседа (например, два последних chunk одного text), завершившиеся одновременно в двух транзакциях, видят друг друга ещё в `processing`: чужая транзакция не закоммичена. Ни одна из них не переводит родителя в `done`, и он зависает навсегда. С блокировкой транзакции внутри одного file идут по очереди, и вторая видит коммит первой (в PostgreSQL на уровне READ COMMITTED каждый запрос видит всё, что закоммичено до его начала). Блокировка record нужна по той же причине: одновременно могут завершиться разные дети одной записи.

Порядок блокировок всегда один — строка единицы (file или собственного text записи), затем record, — и каждой транзакции нужна ровно одна единица, поэтому взаимных блокировок нет. Операции, которые трогают только лист (`claim`, `reset`, возврат при старте core), file и text не блокируют; `claim` выбирает строки с `FOR UPDATE SKIP LOCKED` и не ждёт транзакцию цикла. Цена: результаты внутри одного file фиксируются последовательно, но каждая транзакция занимает миллисекунды, и это не узкое место.

**Цикл готовности.** В транзакции результата листа (см. 4.3):

1. Лист → `done`.
2. Проверяется родитель: если у него нет ни одного ребёнка не в `done` (для record — ни одного в `processing`), он переводится в `done` (`finished_at = now()`), и проверка повторяется для родителя родителя.
3. Если условие не выполнено, цикл останавливается.
4. Дойдя до record, проверяем его готовность по 2.5: он становится `done` (или `error`, если все его дети в `error`), заполняем `processed_at`.

Проверка родителя (пример для element):

```sql
UPDATE element e
SET status = 'done', finished_at = now()
WHERE e.id = :parent_id
  AND e.status = 'processing'
  AND NOT EXISTS (SELECT 1 FROM chunk c WHERE c.element_id = e.id AND c.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM task  t WHERE t.element_id = e.id AND t.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM text  x WHERE x.element_id = e.id AND x.status <> 'done');
```

Если обновилась одна строка, идём выше. Условие идемпотентно (`status = 'processing'`), поэтому повторный результат ничего не портит. Таймера у цикла готовности нет: лист и цикл — один коммит, поэтому зависших контейнеров не бывает.

**Цикл очистки.** В транзакции `fail` (см. 4.2), одинаково для обеих границ:

1. Блокируется единица: file или собственный text записи. Если она уже в `error`, `fail` игнорируется (у цикла по таймеру своё правило, см. 2.8).
2. Собирается снимок ошибки (см. 2.7): путь от границы до упавшего листа и счётчики листьев по статусам (всех листьев file или всех chunk'ов собственного text). Это делается до любых изменений.
3. **Вверх.** Упавший лист и все его предки до границы переводятся в `error` (`finished_at = now()`). Сообщение об ошибке передаётся вверх и записывается только в границу:
   - лист внутри file: file → `error`, заполняются `error`, `error_detail` и `finished_at`;
   - лист собственного text: text → `error`, затем блокируется record, и в него пишутся `error` и `error_detail`; статус record не меняется.

   В промежуточные fragment, element и text текст ошибки не пишется: путь до листа есть в снимке.
4. **Вниз по слоям.** Всё под границей переводится в `error`, слой за слоем. Под file — fragment верхнего уровня, затем вложенные fragment, у которых родительский fragment в `error`, затем element, у которых fragment в `error`, затем text, у которых родитель в `error`, затем chunk и task, у которых родитель в `error`. Под собственным text — его chunk'и. Так в `error` попадают и задачи в `wait` и `processing`, и уже готовые листья.
5. **Удаление снизу вверх.** Удаляется всё, что в `error` ниже границы: сначала chunk и task, затем text (кроме собственного text записи), затем element, затем fragment — от вложенных к верхнему уровню. Строка file остаётся: это граница, в ней ошибка и снимок. Собственный text записи остаётся в `error` без chunk'ов: это отметка для правила готовности record (2.5).
6. Блокируется record (если ещё не заблокирован на шаге 3) и проверяется его готовность (см. 2.5): если граница была последним незавершённым ребёнком, record становится `done` или `error`.

Так ошибка хранится в единственном экземпляре — у file или у record. Результат или ошибка, пришедшие позже для удалённого или уже не находящегося в `processing` листа, игнорируются: задачи, которые в момент цикла очистки выполнялись на воркере, не прерываются, но их результат при получении отбрасывается.

Если core упал до коммита, транзакция откатывается целиком: лист остаётся в `processing` и при старте core возвращается в очередь (4.5), задача выполняется заново. Проверка и ремонт дерева не нужны; цикл очистки по таймеру (2.8) — страховка от ошибок в коде, а не часть штатной работы.

#### 2.7. Снимок ошибки

Цикл очистки удаляет всё под ошибочным file и chunk'и упавшего собственного text, поэтому всё, что нужно для отладки, сохраняется на самой границе в поле `error_detail` (JSONB): у file или, для собственного text, у record. Снимок собирается в той же транзакции, до любых изменений. Он же пишется у пустышек разбора: у file и, если упал разбор всей записи, у record (см. 3.5). У record в `error` (все дети в `error`) `error_detail` — сводка `stage = children` (см. 2.5): снимок собственного text, если он был, и список упавших file; полные снимки file остаются у самих file.

```json
{
  "stage": "ocr",
  "message": "…",
  "attempts": 2,
  "at": "2026-10-12T10:15:03Z",
  "leaf": {"type": "task_ocr", "id": "…", "taken_at": "…"},
  "path": [
    {"level": "fragment", "id": "…", "meta": {"t": 1235.0}},
    {"level": "photo",    "id": "…", "meta": {}}
  ],
  "progress": {"done": 1840, "wait": 310, "processing": 4}
}
```

| Поле | Значение |
|---|---|
| `stage` | Где упало: `parse` (разбор), `transcribe`, `ocr`, `embed`, `task_storage` (нет данных для задачи, см. 4.2), `sweep` (ошибку нашёл цикл очистки по таймеру, а граница ещё не была в `error`, см. 2.8), `children` (у record все дети в `error`, см. 2.5) |
| `message` | Текст ошибки: от балансировщика (задача упала и в пачке, и в одиночку) или исключение core |
| `attempts` | Сколько раз балансировщик запускал задачу: 2 — в пачке и в одиночку, 1 — если пачка с самого начала состояла из одной этой задачи (приходит в `fail`) |
| `at` | Момент ошибки |
| `leaf` | Упавший лист: тип, id, `taken_at`; у ошибок разбора отсутствует |
| `path` | Путь от границы до упавшего листа: уровень, id и `meta` каждого объекта |
| `progress` | Сколько листьев границы было в каждом статусе в момент ошибки |

Исходный файл после ошибки хранится (см. 3.3). По `path[].meta` той же функцией извлечения из него можно получить ровно те данные (кадр, страницу, аудио), на которых упала задача, и воспроизвести ошибку. По id из снимка находятся строки в логах core и балансировщика: в каждой строке лога, относящейся к объекту дерева, должны быть `record_id`, `file_id` и id самого объекта.

#### 2.8. Цикл очистки по таймеру

Таймерное задание (период — параметр конфигурации, около часа; также запускается при старте core) ищет строки в `error`, оставшиеся ниже границы, и запускает от них цикл очистки. В штатной работе оно ничего не находит: цикл очистки удаляет всё в своём же коммите (2.6). Это страховка от ошибок в коде и ручных правок БД.

Порядок:

1. Найти любой fragment в `error`. Спуститься от него через вложенные fragment до element (если element нет — взять сам fragment) и запустить от него цикл очистки по 2.6 своей транзакцией. После коммита снова искать fragment в `error`.
2. Когда fragment в `error` не осталось, так же обойти element в `error`, затем text в `error` (кроме собственного text записи: он законно остаётся в `error` как отметка, см. 2.5), затем chunk и task в `error`.

Отличие от цикла по `fail`: если граница уже в `error`, цикл не игнорируется и не переписывает её ошибку и снимок, а только проходит вниз, удаляет и проверяет готовность record (шаги 4–6). Если граница ещё не в `error` (такого быть не должно), цикл проходит целиком и пишет в неё сообщение «найдено циклом очистки по таймеру» со `stage = sweep`.

С очисткой хранилищ (3.3) это задание не связано: оно работает только со строками БД.
