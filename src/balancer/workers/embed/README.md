# Воркер embed

Отдельный Python-процесс для эмбеддингов текста и изображений через
`Qwen/Qwen3-VL-Embedding-2B`. Модель загружается один раз на пачку.
Выход — нормализованные векторы полной размерности 2048.

Входы передаются в памяти через stdin. Воркер не скачивает входные данные,
не создаёт временные файлы с текстами или изображениями и не обращается к core.
HTTP API нет. Модель и процессор читаются из локального кеша Hugging Face.

## Подготовка и запуск

Python 3.11. Окружение создаётся отдельно от системного Python:

```bash
python3.11 -m venv /tmp/codex-venv-embed
/tmp/codex-venv-embed/bin/pip install -r requirements.txt
```

До запуска подготовьте веса и процессор в кеше. Эта команда требует сети
и выполняется отдельно от воркера:

```bash
/tmp/codex-venv-embed/bin/hf download Qwen/Qwen3-VL-Embedding-2B
```

Из каталога `src/balancer/workers/embed`:

```bash
/tmp/codex-venv-embed/bin/python src/main.py --config config.example.yaml < batch.json
```

Файл `batch.json` здесь — только пример передачи stdin из оболочки.
Вызывающая программа может передать JSON непосредственно в pipe процесса.
Единственный рабочий аргумент CLI — обязательный `--config`.

## Конфигурация

Все поля обязательны, неизвестные поля запрещены, скрытых дефолтов нет:

```yaml
model: Qwen/Qwen3-VL-Embedding-2B
device: cuda
compute_type: bfloat16
text_batch_size: 4
image_batch_size: 1
max_tokens: 8192
max_image_pixels: 6553600
instruction: "Represent the user's input."
```

- `model`: поддерживается только указанная модель; `embed_model` результата —
  `Qwen3-VL-Embedding-2B`.
- `device`: `cuda` или `cpu`, автоматического перехода на CPU нет.
- `compute_type`: `bfloat16`, `float16` или `float32`. На CPU требуется `float32`.
  Для CUDA с BF16 проверяется поддержка GPU; для старых карт можно явно выбрать FP16.
- `text_batch_size`, `image_batch_size`: положительные целые числа задач
  в отдельных внутренних GPU-батчах. Они независимы от порога балансировщика.
- `max_tokens`: положительный лимит подготовленной последовательности, включая
  инструкцию и служебные токены, не более 32768. Превышение — ошибка, без обрезания.
- `max_image_pixels`: бюджет пикселей после изменения размера процессором;
  кратен 1024, минимум 4096. Пропорции сохраняются с округлением размеров под
  сетку модели. В примере задан бюджет 2560×2560 пикселей.
- `instruction`: непустая инструкция модели, одна для всей пачки.
  Её изменение меняет обработку входов; одинаковую конфигурацию следует применять
  к индексируемым материалам и запросам поиска.

Пример размера батчей — стартовая настройка, а не гарантия расхода VRAM или
20-процентного запаса. Используется SDPA, без градиентов и KV-кеша.
Рабочие версии PyTorch/torchvision/Transformers закреплены в `requirements.txt`.

## Вход

Один JSON-массив UTF-8 на stdin, после записи stdin закрывается:

```json
[
  {"task_id": "1", "text": "Текст для поиска."},
  {"task_id": "2", "image": "<base64 байтов изображения>"}
]
```

Пачка непустая. `task_id` — непустая уникальная строка. У каждой задачи ровно
два поля: `task_id` и одно из `text` или `image`. Пустые и состоящие только из
пробельных символов строки не принимаются. Неизвестные и повторные JSON-ключи
запрещены. Пути, MIME, `type`, `input`, адрес и полномочия core не передаются.

`text` содержит максимум **2000 символов, включая пробелы**. Считаются Unicode
code points, как `len(str)` в Python. Текст передаётся без изменения пробелов.
Более длинные материалы предварительно делит core; воркер их не режет.

`image` — стандартная base64 с корректным padding, без пробельных символов,
URL-safe алфавита и префикса `data:image/...;base64,`. Передаются байты
закодированного изображения (например PNG или JPEG), а не сырые пиксели.
Формат определяется Pillow по содержимому. Требуется одно неподвижное изображение;
многокадровые файлы отклоняются. Применяется EXIF-ориентация и преобразование RGB.

Вся пачка, включая декодируемость изображений, проверяется до импорта PyTorch
и загрузки модели. Изображения повторно декодируются для обработки, но одновременно
удерживаются только изображения одного внутреннего батча. Исходный JSON,
закодированные байты и результаты всей пачки требуют RAM.

Смешанная пачка обрабатывается сначала текстовыми, затем графическими батчами.
Внутри каждой группы сохраняется порядок входов. Перезагрузки модели между группами нет.

В коде `Task` содержит общий идентификатор, а `TextTask` и `ImageTask` — текст
и объект `EncodedImage` соответственно. `EncodedImage` хранит закодированные байты
и открывает RGB-изображение с учётом EXIF только на время проверки или обработки.
Входная `Batch` создаёт однородные `InferenceTextBatch` и `InferenceImageBatch`,
наследующие `InferenceBatch`. Каждый внутренний батч готовит свои входные тензоры;
общая модель `QwenEmbedder` выполняет вычисления, pooling и нормализацию.

## Выход и ошибки

Код `0`, один JSON-объект в stdout:

```json
{
  "embed_model": "Qwen3-VL-Embedding-2B",
  "embeddings": {
    "1": [0.12, -0.34, 0.56],
    "2": [0.78, 0.23, -0.45]
  }
}
```

Векторы в примере сокращены. Реально каждый содержит 2048 конечных чисел,
L2-норма проверяется с допуском 0.0001. Pooling берёт последнюю значимую позицию
каждого входа, затем выполняется нормализация в FP32. Результаты сопоставляются
по `task_id`, порядок ключей не является контрактом. Имя модели передаётся
**один раз на всю пачку**. Обёрток `results` и `payload` нет.

Код `1` — ошибка конфига, входа, загрузки весов или вычислений. Диагностика
`embed: <описание>` идёт в stderr. Ошибки аргументов CLI дают код `2`.
Все вычислительные логи, включая нативную запись в stdout, перенаправляются
в stderr. Ошибка любой задачи завершает всю пачку без частичного JSON.
Неполные или несовместимые веса отклоняются; случайные веса и векторы-заглушки
не допускаются. Повторы и разделение пачки воркер не выполняет.

Чтобы отправить результат в HTTP `/result`, балансировщику предстоит
преобразовать каждую пару из `embeddings` в
`{"task_id": id, "payload": {"embed_model": response.embed_model, "embedding": vector}}`
и добавить свой `balancer_id`. Core сохранит модель в `chunk.embed_model`,
а вектор в `chunk.embed`. Этот HTTP-адаптер и демон балансировщика пока не реализованы.

## Проверки

Из каталога воркера, после установки `requirements-dev.txt` в отдельное окружение:

```bash
PYTHONPATH=src /tmp/codex-venv-embed/bin/python -m unittest discover -s tests -v
/tmp/codex-venv-embed/bin/python -m mypy --config-file mypy.ini
```

Контрактные тесты не загружают веса и не требуют GPU. Реальная загрузка модели,
качество эмбеддингов и расход VRAM проверяются отдельным запуском с весами.
