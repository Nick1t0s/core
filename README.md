# Система сбора, индексации и поиска информации

Система состоит из четырёх частей:

- **скрапперы** собирают данные из внешних источников;
- **core** хранит, индексирует и выполняет поисковые запросы от клиентов;
- **балансировщик** забирает тяжёлые задачи (транскрибация, OCR, эмбеддинги) у источников задач (core и клиентов) и выполняет их на воркерах на GPU;
- **клиенты** держат свою очередь тяжёлых задач (её забирает балансировщик) и обращаются к core за поиском.

Пример использования: спросить LLM «скинь ссылку, я вчера видел видео про asyncio» — модель находит его через SQL-запросы и семантический поиск.

## Модели (на сентябрь 2026)

| Задача | Модель |
|---|---|
| Эмбеддинги | Qwen3-VL-Embedding-2B (BF16) |
| Транскрибирование | whisper large-v3-turbo |
| OCR | PaddleOCR-VL + раскладка |

## Core

core — ядро системы сбора, индексации и поиска информации. Можно сказать, что core — цифровой мозг, который помнит всё, что вам писали.

Пример: LLM можно задать вопрос «скинь ссылку, я вчера видел видео, которое рассказывает про asyncio», и модель благодаря SQL-запросам и семантическому поиску быстро найдёт это видео.

Суть системы — перевод любого входного сообщения в мелкие неделимые части, которые можно обработать на GPU, проиндексировать и найти.

### Что делает core и чего не делает

Core делает:

- принимает записи от скрапперов: сразу регистрирует запись в статусе `parsing` и отвечает, не дожидаясь разбора (см. 3.1);
- сохраняет исходные файлы записи в своём хранилище;
- в фоне разбирает запись на дерево и сохраняет его одной транзакцией;
- при разборе записи извлекает из исходных файлов данные для photo и audio и кладёт их во временное хранилище `task_storage` (см. 1.5 и 3.3);
- хранит очереди задач (транскрибация, OCR, эмбеддинги) и отдаёт их балансировщику через API источника задач: для балансировщика core — один источник (см. 4.2);
- принимает результаты задач и достраивает дерево;
- вычисляет статусы record, file, fragment, element и text: результат задачи фиксируется одной транзакцией вместе с циклом готовности, ошибка задачи — одной транзакцией вместе с циклом очистки (см. 2.6);
- по таймеру запускает цикл очистки — страховку от строк в `error`, оставшихся ниже границы ошибки (см. 2.8);
- при старте удаляет записи, разбор которых прервало падение core (см. 3.2), и возвращает в очередь все задачи, которые были в работе (см. 4.5);
- возвращает в очередь задачи, взятые балансировщиком, по его запросу (`reset(balancer_id)`, см. 4.2);
- отдаёт скрапперам настройку `max_file_size` (см. 3.6);
- выполняет поисковые запросы клиентов: в поиске участвуют только записи в статусе `done` (раздел 5, пока в разработке);
- даёт веб-интерфейс для просмотра ошибок и ручного удаления записей в `error` (см. 6).

Core не делает:

- не знает, что такое YouTube, Telegram или любой другой источник: он видит только record (универсальные поля и `metadata`);
- не исполняет тяжёлые задачи сам: это делают воркеры под управлением балансировщика;
- не хранит долговременно производные данные (аудиодорожки, кадры, отрендеренные страницы): долговременно хранятся только исходные файлы, а данные для задач лежат во временном `task_storage` и удаляются очисткой хранилищ целым каталогом записи после её завершения.

### Термины

| Термин | Значение |
|---|---|
| **record** | Наиболее крупная логическая часть информации: письмо, видео на YouTube, пост в канале. Корень дерева |
| **file** | Файл, прикреплённый к record (например для видео с YouTube — сам ролик) |
| **fragment** | Промежуточное состояние файла: страница PDF, лист в Word, кадр. Бывает вложенным |
| **element** | Наименьшая часть содержимого. Три типа: text, photo, audio |
| **chunk** | Часть text или photo, для которой считается эмбеддинг: кусок текста или картинка |
| **task** | Задача воркера, результат которой порождает новые записи в дереве: транскрибация (`transcribe`) и OCR (`ocr`) |
| **task_storage** | Временное хранилище core на файловой системе: кадры, страницы и аудиодорожки для задач `ocr`, `transcribe` и для chunk-картинок. Один файл на element (photo или audio). Долговременным хранилищем не является: удаляется целым каталогом записи после её завершения |
| **граница ошибки** | Объект, в который пишется ошибка упавшего листа: file для листьев внутри файла, record для листьев собственного text записи (см. 2.4). У file при этом удаляется всё, что под ним; у record удаляются только chunk'и собственного text, а статус record не меняется |
| **снимок ошибки (`error_detail`)** | Описание ошибки на границе ошибки: где и почему упало, путь до упавшего листа, прогресс обработки. Нужен для отладки, так как упавшие объекты удаляются (см. 2.7) |
| **цикл готовности** | Распространение `done` от завершившегося листа вверх по дереву до record. Выполняется в той же транзакции, что и результат задачи (см. 2.6) |
| **цикл очистки** | Обработка ошибки листа одной транзакцией: вверх до границы с передачей сообщения об ошибке, затем вниз по слоям (всё под границей → `error`), затем удаление снизу вверх всего, что в `error` ниже границы (см. 2.6). Запускается ошибкой задачи и по таймеру (см. 2.8) |
| **`balancer_id`** | Постоянный идентификатор балансировщика из его конфига. При `claim` записывается в лист (`taken_by`); по нему балансировщик возвращает в очередь свои задачи (`reset`, см. 4.2) |
| **источник задач** | Адрес IP:PORT, который отдаёт балансировщику задачи по API источника (см. 4.2): core или клиент. Не путать с `record.source` (`youtube`, `telegram`): для балансировщика весь core — один источник, YouTube и Telegram внутри него не различаются |
| **пачка** | Набор задач одного типа от одного источника, который выполняет один запуск воркера |
| **метаданные (`metadata`, `meta`)** | Данные в формате JSONB, специфичные для источника или типа файла, которым не нашлось места среди полей таблицы. Состав уточняется отдельно для каждого источника и типа данных (файла). Универсальные поля (`source`, даты, `title`, `author` и т. д.) метаданными не считаются |

### 1. Структура данных

#### 1.1. Дерево записи

Каждая запись представляется деревом. Корень — record. Путь от record до листа выглядит, например, так: `record → file → fragment → fragment → fragment → photo → chunk`.

Правила:

- **record** имеет до n + 1 детей: n файлов (file) и не более одного собственного text — текста самой записи (для YouTube-видео это склейка названия и описания, для сообщения Telegram — его текст или подпись). Если текста нет, text не создаётся. У записи должен быть хотя бы один ребёнок.
- **file** имеет сколько угодно детей fragment (минимум один).
- **fragment** имеет либо сколько угодно детей fragment, либо ровно один element (text, photo или audio). Смешивать fragment и element в одном родителе нельзя.
- **text** имеет сколько угодно детей chunk (минимум один). Сообщение нарезается на chunk'и в момент создания text.
- **photo** всегда имеет ровно один chunk с картинкой и ровно один `task_ocr`: картинка всегда и эмбедится, и отправляется на OCR. После получения результата OCR появляется ребёнок text, но только если распознан непустой текст. Отсутствие text у photo допустимо.
- **audio** содержит аудиоданные и имеет ребёнка `task_transcribe`. После получения транскрипции появляется ребёнок text (если транскрипция непуста).
- **chunk**, **task_transcribe**, **task_ocr** — листья, детей не имеют.

Видео — это набор фотографий (например, кадр каждые i секунд) и аудио.

Допустимые связи:

| Родитель | Дети | Количество |
|---|---|---|
| record | file, text | file: любое число; text: 0 или 1; в сумме не менее 1 |
| file | fragment | не менее 1 |
| fragment | fragment ИЛИ один element (text, photo, audio) | не менее 1 fragment, либо ровно 1 element |
| text | chunk | не менее 1 |
| photo | chunk (картинка); task_ocr; text | chunk: ровно 1; task_ocr: ровно 1; text: 0 или 1, появляется после OCR, если текст распознан |
| audio | task_transcribe; text | task_transcribe: ровно 1; text: 0 или 1, появляется после транскрибации |
| chunk, task_transcribe, task_ocr | — | листья |

Пример: видео с YouTube.

```
record
├─ text (название + описание)
│   └─ chunk, chunk, …
└─ file (видео)
    ├─ fragment (аудиодорожка)
    │   └─ audio
    │       ├─ task_transcribe
    │       └─ text                  ← появляется по результату транскрибации
    │            └─ chunk, chunk, …
    ├─ fragment (кадр, t = 0 с)
    │   └─ photo
    │       ├─ chunk                 ← картинка
    │       ├─ task_ocr              ← всегда
    │       └─ text                  ← появляется, только если OCR вернул текст
    │            └─ chunk, chunk, …
    └─ fragment (кадр, t = 5 с) …
```

#### 1.2. Chunk

Chunk — объект ровно с тремя полями:

- `text` — текст, максимум x символов (параметр конфигурации);
- `picture` — картинка;
- `embed` — эмбеддинг (список чисел).

`text` и `picture` взаимоисключающие: должно быть заполнено ровно одно. Если заполнены оба или ни одного, при создании должна возникать ошибка. Chunk в момент создания не имеет эмбеддинга (`embed` пуст): его считает воркер.

Картинка chunk'а в БД не хранится: на уровне таблицы поле `picture` — это признак `is_picture`. Пока запись обрабатывается, картинку для воркера core берёт из `task_storage` (файл родительского photo), а после завершения записи строит из исходного файла по `meta` родительского photo (см. 3.3, 7).

Внутри chunk'а текст больше не делится: это наименьшая часть, которая индексируется.

#### 1.3. Атрибуты record

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `id` | UUID (v7) | да | Суррогатный первичный ключ, выдаётся core |
| `source` | text | да | Имя источника: `youtube`, `telegram` |
| `source_url` | text | да | Каноническая ссылка на конкретную запись внутри источника |
| `source_created_at` | timestamptz | нет | Когда запись создана на оригинальном источнике; если источник не отдаёт дату — пусто |
| `scraped_at` | timestamptz | да | Когда скраппер получил запись |
| `registered_at` | timestamptz | да | Когда core зарегистрировал запись: момент приёма (вставки record в статусе `parsing`), до разбора |
| `processed_at` | timestamptz | нет | Когда обработка завершилась (record перешёл в `done` или `error`); пока идёт — `NULL` |
| `status` | enum | да | `parsing`, `processing`, `done`, `error` (см. 2.1) |
| `title` | text | нет | Заголовок, если есть |
| `author` | text | нет | Автор или канал |
| `parent_source_url` | text | нет | Запись, к которой относится эта (ответ, комментарий) |
| `metadata` | JSONB | нет | Данные, специфичные для источника, которым не нашлось места среди полей таблицы. Состав уточняется отдельно для каждого источника |
| `error` | text | нет | Текст ошибки: если запись в статусе `error` (все дети в `error`, см. 2.5) или если упал собственный text записи (тогда запись может быть и в `done`, см. 2.4) |
| `error_detail` | JSONB | нет | Снимок ошибки (см. 2.7) в тех же случаях |

Собственного текста записи в таблице нет: он хранится как дочерний text. Все даты хранятся в UTC. Изменения записей на источнике не отслеживаются.

#### 1.4. Первичный ключ и идентификация

- Первичный ключ — `id` (UUID, лучше v7, он сортируется по времени). Он нужен потому, что на record ссылаются другие таблицы, а тащить в каждую два длинных текстовых поля неудобно. `id` не зависит от правил нормализации ссылок.
- Пара `(source, source_url)` имеет ограничение `UNIQUE`, оба поля `NOT NULL`. Скраппер идентифицирует запись именно этой парой и `id` не генерирует.
- `source_url` каждый скраппер обязан приводить к каноническому виду (правила — в разделах скрапперов), иначе одна запись зарегистрируется дважды.
- Повторная отправка записи с уже существующим `(source, source_url)` ничего не меняет (в том числе пока запись ещё разбирается): core отвечает, что запись существует. Обновления записей не отслеживаются.

#### 1.5. Таблицы и их поля

Каждый тип объектов дерева лежит в своей таблице: `record`, `file`, `fragment`, `text`, `element`, `chunk`, `task`. Общих наборов полей нет: ниже для каждой таблицы перечислены все её поля. Поля record описаны в 1.3.

**Статусы в таблицах.** У `file`, `fragment`, `element` и `text` три статуса: `processing`, `done`, `error`. У `record` их четыре: ещё `parsing` — запись принята и разбирается. У листьев `chunk` и `task` четыре статуса: `wait`, `processing`, `done`, `error` (см. раздел 2). Статус `error` ниже границы ошибки (у fragment, element, text, chunk и task) существует только внутри транзакции цикла очистки: в том же коммите такие строки удаляются (см. 2.6). Исключение — собственный text записи: он остаётся в `error` без chunk'ов как отметка для правила готовности record (см. 2.5).

**Даты.** Дата создания у `file`, `fragment`, `element` и `text` не хранится: её можно узнать по record (`registered_at`). У них есть только `finished_at`. `created_at` остаётся у `chunk` и `task`, потому что по нему строится очередь.

**Поле `meta`.** У `file`, `fragment`, `element` и `text` поле `meta` имеет тип JSONB. Его состав определяется источником и типом файла и уточняется отдельно для каждого из них; из него core получает данные, нужные для работы с этим объектом (в том числе для извлечения данных из исходного файла).

**Таблица `file`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id` | Внешний ключ на record |
| `ord` | Порядок среди файлов записи |
| `status` | `processing`, `done`, `error` |
| `name`, `mime`, `size` | Имя исходного файла (расширение из него идёт в путь), тип и размер |
| `error`, `error_detail` | Текст ошибки и снимок ошибки (см. 2.7), если file в статусе `error` |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSONB |

**Таблица `fragment`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id` | Внешний ключ на record (заполнен всегда) |
| `file_id` | Внешний ключ на file (заполнен всегда) |
| `parent_fragment_id` | Внешний ключ на родительский fragment; пусто у фрагментов верхнего уровня |
| `ord` | Порядок среди соседей |
| `status` | `processing`, `done`, `error` |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSONB |

**Таблица `element`** (только photo и audio):

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id` | Внешний ключ на record (заполнен всегда) |
| `file_id` | Внешний ключ на file (заполнен всегда) |
| `fragment_id` | Внешний ключ на fragment, в котором лежит element |
| `kind` | `photo` или `audio` |
| `ord` | Порядок среди соседей |
| `status` | `processing`, `done`, `error` |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSONB |

**Таблица `text`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `kind` | Тип text (см. ниже) |
| `record_id` | Внешний ключ на record; заполнен всегда |
| `fragment_id` | Внешний ключ на fragment; заполнен, если непосредственный предок text не record: у text как element фрагмента это его fragment, у результата задачи это fragment, в котором лежит element-владелец |
| `element_id` | Внешний ключ на element (photo или audio); заполнен, только если text — результат OCR или транскрибации |

| `kind` | Что это | `record_id` | `fragment_id` | `element_id` |

| Поле | Описание |

**Таблица `task`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `element_id` | Внешний ключ на audio или photo |
| `type` | `transcribe` или `ocr` |
| `status` | `wait`, `processing`, `done`, `error` |
| `taken_at` | Когда задачу взяли в работу; `NULL` в статусе `wait` |
| `taken_by` | `balancer_id` балансировщика, который взял задачу; `NULL` в статусе `wait` |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |

Поля `error` и `error_detail` есть только у file и record, то есть у границ ошибки. У file они заполняются, когда file в `error`. У record — когда упал его собственный text (статус record при этом не меняется, и запись может завершиться в `done`) или когда record в `error`. Всё, что под ошибочным file, и chunk'и упавшего собственного text удаляются циклом очистки (см. 2.6), а то, что о них нужно для отладки, сохраняется в снимке ошибки на границе (см. 2.7). У text полей ошибки нет: ошибка собственного text записи пишется в record.

**Пути файлов.** Пути в БД не хранятся: они выводятся из идентификаторов.

- Исходный файл: `/storage/<source>/<record_id>/<file_id>.<исходное расширение>`; расширение берётся из `file.name`. Хэш файла не хранится: изменения записей не отслеживаются.
- Файл `task_storage`: `/task_storage/<source>/<record_id>/<element_id>.<расширение>`; расширение определяется настроенным форматом (один для изображений, один для аудио).

**`task_storage`** — не таблица БД, а временный каталог файловой системы. Для каждого element (photo или audio) лежит не более одного файла с данными для задач: кадр или страница как изображение, аудиодорожка как аудио. Хранилище принадлежит core, правила хранения — в разделе 3.

### 2. Статусы

#### 2.1. Значения статусов

**Листья chunk, task_transcribe, task_ocr** имеют четыре статуса:

| Статус | Значение |
|---|---|
| `wait` | Задача ждёт взятия: лежит в очереди, `taken_at` и `taken_by` пусты |
| `processing` | Задача в работе: её взял балансировщик, `taken_at` и `taken_by` заполнены |
| `done` | Задача успешно завершена |
| `error` | Задача завершена с ошибкой; существует только внутри транзакции цикла очистки (см. 2.6) |

**Остальные объекты дерева** (record, file, fragment, element, text) имеют три статуса (у record есть ещё четвёртый, см. ниже); `wait` у них не бывает:

| Статус | Значение |
|---|---|
| `processing` | Объект не завершён: не завершены его дети |
| `done` | Объект успешно завершён |
| `error` | Объект завершён с ошибкой. Надолго в `error` остаются только file, record и собственный text записи; остальные строки в `error` удаляются в той же транзакции цикла очистки (см. 2.6) |

У **record** есть ещё четвёртый статус — `parsing`: запись принята, core сохраняет её исходные файлы или разбирает её; детей у record в этом статусе нет. Переходы record:

- `parsing → processing` — коммит дерева (см. 3.1);
- `parsing → error` — разбор записи упал: коммитится дерево из пустышек в `error`, и проверка готовности в той же транзакции переводит record в `error` (см. 3.5, 2.5);
- `processing → done` — нет детей в `processing`, и хотя бы один ребёнок в `done` (см. 2.5);
- `processing → error` — нет детей в `processing`, и все дети (собственный text, если есть, и все file) в `error` (см. 2.5).

Других путей в `error` у record нет: ошибка собственного text пишется в record, но его статус не меняет (см. 2.4), а пустая запись не принимается (см. 3.1).

Если core упал во время приёма или разбора, record в `parsing` удаляется при старте (см. 3.2).

`done` и `error` — терминальные: после перехода статус не меняется. Запись в `error` можно только удалить вручную (см. 6).

Переходы листьев: `wait → processing` (claim), `processing → done` (result), `processing → error` (fail, цикл очистки), `processing → wait` (`reset(balancer_id)`, возврат при старте core, см. 4.2, 4.5). Кроме того, цикл очистки на пути вниз переводит в `error` все листья под границей в любом статусе (см. 2.6).

#### 2.2. Вся работа сидит в листьях

Задачи воркеров привязаны только к листьям:

- эмбеддинг — chunk в статусе `wait` или `processing`;
- транскрибация — лист `task_transcribe`;
- OCR — лист `task_ocr`.

Все остальные объекты (record, file, fragment, audio, photo, text) не имеют собственной работы и являются контейнерами. Это закрывает проблему «пустого успеха»: у audio до завершения транскрибации всегда есть ребёнок `task_transcribe` не в статусе `done`, у photo — `task_ocr`, поэтому проверка «все дети готовы» не может ошибочно пометить контейнер готовым. Никаких дополнительных флагов «готов к обработке» не нужно.

#### 2.3. Правило готовности

Контейнер внутри file (или собственный text записи) готов, когда число его готовых детей равно числу всех его детей, то есть когда у него нет ни одного ребёнка не в статусе `done`. Правило одинаково для всех контейнеров, включая «листовые» fragment (у которых единственный ребёнок — element): особых случаев нет.

#### 2.4. Граница ошибки и ошибки

- **Ошибка листа внутри file** (в любом fragment, element или text этого файла) делает ошибочным этот file. Граница — file: в него пишутся текст ошибки и снимок (см. 2.7), а всё, что под ним, в той же транзакции уходит в `error` и удаляется циклом очистки (см. 2.6).
- Граница — file, а не element: лучше открыто потерять файл целиком, чем незаметно терять его части.
- **Ошибка листа собственного text записи** (chunk этого text) делает ошибочным этот text: он переходит в `error`, его chunk'и удаляются, а текст ошибки и снимок пишутся в record — для собственного text границей служит record. Статус record при этом не меняется: файлы записи обрабатываются дальше.
- На статус record ошибки file и собственного text сами по себе не влияют. Record становится `error`, только если все его дети в `error` (см. 2.5).
- Ошибка воркера всегда серьёзная: сбои воркера (OOM, неправильный файл и т. п.) обрабатывает балансировщик, разбивая упавшую пачку на пачки по одной задаче; `fail` приходит в core только по задаче, которая упала и в одиночку (см. «Балансировщик»).

#### 2.5. Готовность record

Record переходит в терминальный статус, когда у него нет ни одного ребёнка (file или собственного text) в `processing`. Тогда:

- если все дети в `error` (собственный text, если он есть, и все file), `status` = `error`: в `error` пишется «все дети завершились ошибкой», в `error_detail` — сводка `{"stage": "children", "text": …, "files": [{"id": …, "error": …}]}`, где `text` — снимок ошибки собственного text, который уже лежал в record (если text был), а `files` — список упавших file; полные снимки ошибок file остаются у самих file;
- иначе (хотя бы один ребёнок в `done`) `status` = `done`;
- в обоих случаях `processed_at` = текущий момент.

Это единственный случай `error` у record. Записи без детей не бывает: пустая запись не принимается (см. 3.1), а если разбор записи упал, все её дети записываются пустышками в `error` (см. 3.5).

Проверка выполняется только для record в `processing`: record в `parsing` детей ещё не имеет и ею не затрагивается. Она запускается из цикла готовности и цикла очистки (см. 2.6), а также сразу в транзакции коммита дерева (см. 3.1), в том числе дерева из пустышек (см. 3.5): если при разборе ни одного листа не появилось, циклов не будет, и без этой проверки record навсегда остался бы в `processing`.

У записи в `done` есть хотя бы один ребёнок в `done`; отдельные file в `error` и упавший собственный text (его ошибка лежит в `error` самой записи) у неё бывают. Искать в ней при этом может быть нечего: например, у file с беззвучным аудио нет ни одного chunk'а.

У record в `error` все дети — границы в `error` без детей: file в `error` и собственный text в `error` (если он был).

#### 2.6. Обновление статусов: цикл готовности и цикл очистки

Статусы chunk и task (листья) меняются только по операциям API источника (см. 4.2), при восстановлении (см. 4.5) и циклом очистки: `claim` переводит лист из `wait` в `processing`, `result` — в `done`, `fail` — в `error`, `reset(balancer_id)` возвращает в `wait`. Статусы всех остальных объектов (element, fragment, text, file, record) вычисляют два цикла:

- **цикл готовности** распространяет `done` вверх по дереву; его запускает результат задачи (`result`);
- **цикл очистки** распространяет ошибку вверх до границы, затем `error` вниз по слоям и удаляет всё, что в `error` ниже границы; его запускает ошибка задачи (`fail` от балансировщика или `fail`, который core выполняет сам, если для задачи нет файла в `task_storage`, см. 4.2), а также таймер (см. 2.8).

**Правило циклов:** операция над листом (`result` или `fail`) и весь вызванный ею цикл — одна транзакция с одним коммитом. Состояний, когда лист уже завершён, а его предки ещё не пересчитаны, или когда под ошибочной границей остались строки, в БД не бывает.

**Блокировки.** Транзакция первым делом блокирует строку своей единицы блокировки — file или собственного text записи (`SELECT … FOR UPDATE`). Её находят по внешним ключам: у element и fragment есть `file_id`, у text — `fragment_id` (или `kind = 'record'`, тогда единица блокировки — сам text). Строка record блокируется в конце: перед проверкой готовности record, а в цикле очистки собственного text — перед записью ошибки в record.

Зачем это нужно. Без блокировки два последних соседа (например, два последних chunk одного text), завершившиеся одновременно в двух транзакциях, видят друг друга ещё в `processing`: чужая транзакция не закоммичена. Ни одна из них не переводит родителя в `done`, и он зависает навсегда. С блокировкой транзакции внутри одного file идут по очереди, и вторая видит коммит первой (в PostgreSQL на уровне READ COMMITTED каждый запрос видит всё, что закоммичено до его начала). Блокировка record нужна по той же причине: одновременно могут завершиться разные дети одной записи.

Порядок блокировок всегда один — строка единицы (file или собственного text записи), затем record, — и каждой транзакции нужна ровно одна единица, поэтому взаимных блокировок нет. Операции, которые трогают только лист (`claim`, `reset`, возврат при старте core), file и text не блокируют; `claim` выбирает строки с `FOR UPDATE SKIP LOCKED` и не ждёт транзакцию цикла. Цена: результаты внутри одного file фиксируются последовательно, но каждая транзакция занимает миллисекунды, и это не узкое место.

**Цикл готовности.** В транзакции результата листа (см. 4.3):

1. Лист → `done`.
2. Проверяется родитель: если у него нет ни одного ребёнка не в `done` (для record — ни одного в `processing`), он переводится в `done` (`finished_at = now()`), и проверка повторяется для родителя родителя.
3. Если условие не выполнено, цикл останавливается.
4. Дойдя до record, проверяем его готовность по 2.5: он становится `done` (или `error`, если все его дети в `error`), заполняем `processed_at`.

Проверка родителя (пример для element):

```sql
UPDATE element e
SET status = 'done', finished_at = now()
WHERE e.id = :parent_id
  AND e.status = 'processing'
  AND NOT EXISTS (SELECT 1 FROM chunk c WHERE c.element_id = e.id AND c.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM task  t WHERE t.element_id = e.id AND t.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM text  x WHERE x.element_id = e.id AND x.status <> 'done');
```

Если обновилась одна строка, идём выше. Условие идемпотентно (`status = 'processing'`), поэтому повторный результат ничего не портит. Таймера у цикла готовности нет: лист и цикл — один коммит, поэтому зависших контейнеров не бывает.

**Цикл очистки.** В транзакции `fail` (см. 4.2), одинаково для обеих границ:

1. Блокируется единица: file или собственный text записи. Если она уже в `error`, `fail` игнорируется (у цикла по таймеру своё правило, см. 2.8).
2. Собирается снимок ошибки (см. 2.7): путь от границы до упавшего листа и счётчики листьев по статусам (всех листьев file или всех chunk'ов собственного text). Это делается до любых изменений.
3. **Вверх.** Упавший лист и все его предки до границы переводятся в `error` (`finished_at = now()`). Сообщение об ошибке передаётся вверх и записывается только в границу:
   - лист внутри file: file → `error`, заполняются `error`, `error_detail` и `finished_at`;
   - лист собственного text: text → `error`, затем блокируется record, и в него пишутся `error` и `error_detail`; статус record не меняется.

   В промежуточные fragment, element и text текст ошибки не пишется: путь до листа есть в снимке.
4. **Вниз по слоям.** Всё под границей переводится в `error`, слой за слоем. Под file — fragment верхнего уровня, затем вложенные fragment, у которых родительский fragment в `error`, затем element, у которых fragment в `error`, затем text, у которых родитель в `error`, затем chunk и task, у которых родитель в `error`. Под собственным text — его chunk'и. Так в `error` попадают и задачи в `wait` и `processing`, и уже готовые листья.
5. **Удаление снизу вверх.** Удаляется всё, что в `error` ниже границы: сначала chunk и task, затем text (кроме собственного text записи), затем element, затем fragment — от вложенных к верхнему уровню. Строка file остаётся: это граница, в ней ошибка и снимок. Собственный text записи остаётся в `error` без chunk'ов: это отметка для правила готовности record (2.5).
6. Блокируется record (если ещё не заблокирован на шаге 3) и проверяется его готовность (см. 2.5): если граница была последним незавершённым ребёнком, record становится `done` или `error`.

Так ошибка хранится в единственном экземпляре — у file или у record. Результат или ошибка, пришедшие позже для удалённого или уже не находящегося в `processing` листа, игнорируются: задачи, которые в момент цикла очистки выполнялись на воркере, не прерываются, но их результат при получении отбрасывается.

Если core упал до коммита, транзакция откатывается целиком: лист остаётся в `processing` и при старте core возвращается в очередь (4.5), задача выполняется заново. Проверка и ремонт дерева не нужны; цикл очистки по таймеру (2.8) — страховка от ошибок в коде, а не часть штатной работы.

#### 2.7. Снимок ошибки

Цикл очистки удаляет всё под ошибочным file и chunk'и упавшего собственного text, поэтому всё, что нужно для отладки, сохраняется на самой границе в поле `error_detail` (JSONB): у file или, для собственного text, у record. Снимок собирается в той же транзакции, до любых изменений. Он же пишется у пустышек разбора: у file и, если упал разбор всей записи, у record (см. 3.5). У record в `error` (все дети в `error`) `error_detail` — сводка `stage = children` (см. 2.5): снимок собственного text, если он был, и список упавших file; полные снимки file остаются у самих file.

```json
{
  "stage": "ocr",
  "message": "…",
  "attempts": 2,
  "at": "2026-10-12T10:15:03Z",
  "leaf": {"type": "task_ocr", "id": "…", "taken_at": "…"},
  "path": [
    {"level": "fragment", "id": "…", "meta": {"t": 1235.0}},
    {"level": "photo",    "id": "…", "meta": {}}
  ],
  "progress": {"done": 1840, "wait": 310, "processing": 4}
}
```

| Поле | Значение |
|---|---|
| `stage` | Где упало: `parse` (разбор), `transcribe`, `ocr`, `embed`, `task_storage` (нет данных для задачи, см. 4.2), `sweep` (ошибку нашёл цикл очистки по таймеру, а граница ещё не была в `error`, см. 2.8), `children` (у record все дети в `error`, см. 2.5) |
| `message` | Текст ошибки: от балансировщика (задача упала и в пачке, и в одиночку) или исключение core |
| `attempts` | Сколько раз балансировщик запускал задачу: 2 — в пачке и в одиночку, 1 — если пачка с самого начала состояла из одной этой задачи (приходит в `fail`) |
| `at` | Момент ошибки |
| `leaf` | Упавший лист: тип, id, `taken_at`; у ошибок разбора отсутствует |
| `path` | Путь от границы до упавшего листа: уровень, id и `meta` каждого объекта |
| `progress` | Сколько листьев границы было в каждом статусе в момент ошибки |

Исходный файл после ошибки хранится (см. 3.3). По `path[].meta` той же функцией извлечения из него можно получить ровно те данные (кадр, страницу, аудио), на которых упала задача, и воспроизвести ошибку. По id из снимка находятся строки в логах core и балансировщика: в каждой строке лога, относящейся к объекту дерева, должны быть `record_id`, `file_id` и id самого объекта.

#### 2.8. Цикл очистки по таймеру

Таймерное задание (период — параметр конфигурации, около часа; также запускается при старте core) ищет строки в `error`, оставшиеся ниже границы, и запускает от них цикл очистки. В штатной работе оно ничего не находит: цикл очистки удаляет всё в своём же коммите (2.6). Это страховка от ошибок в коде и ручных правок БД.

Порядок:

1. Найти любой fragment в `error`. Спуститься от него через вложенные fragment до element (если element нет — взять сам fragment) и запустить от него цикл очистки по 2.6 своей транзакцией. После коммита снова искать fragment в `error`.
2. Когда fragment в `error` не осталось, так же обойти element в `error`, затем text в `error` (кроме собственного text записи: он законно остаётся в `error` как отметка, см. 2.5), затем chunk и task в `error`.

Отличие от цикла по `fail`: если граница уже в `error`, цикл не игнорируется и не переписывает её ошибку и снимок, а только проходит вниз, удаляет и проверяет готовность record (шаги 4–6). Если граница ещё не в `error` (такого быть не должно), цикл проходит целиком и пишет в неё сообщение «найдено циклом очистки по таймеру» со `stage = sweep`.

С очисткой хранилищ (3.3) это задание не связано: оно работает только со строками БД.

### 3. Приём записи

#### 3.1. Общая схема

Разбор записи может идти минуты (видео длиной 3 часа в 1080p — порядка 4 минут только на извлечение кадров), поэтому core отвечает скрапперу сразу после приёма файлов, а разбирает запись в фоне.

1. Скраппер отправляет в core запись: метаданные (`source`, `source_url`, даты, `title`, `author`, `metadata`), текст и файлы.
2. Core проверяет, что запись не пуста (есть текст или хотя бы один файл), и размер каждого файла по `max_file_size` (см. 3.6) по заявленным размерам, до приёма самих файлов. Пустая запись отклоняется статус-кодом ошибки (HTTP 422), запись с файлом больше лимита — HTTP 413; ничего не сохраняется.
3. Core вставляет record в статусе `parsing` (`INSERT … ON CONFLICT (source, source_url) DO NOTHING`) и коммитит. Если запись с таким `(source, source_url)` уже есть (в любом статусе, включая `parsing`), core отвечает, что запись существует, и файлы не принимает. На этом шаге core выдаёт идентификаторы (UUID v7) записи и её файлов: по ним строятся пути.
4. Только после коммита core записывает исходные файлы в хранилище (см. 3.3). Если загрузка оборвалась, core удаляет record и его каталоги; скраппер получит `unknown` и отправит запись заново.
5. Когда исходные файлы записаны, core отвечает скрапперу `202 Accepted`. Дальше скраппер следит за статусом записи (см. 3.2).
6. Core в фоне **разбирает** запись целиком: нарезает текст на chunk'и, раскладывает файлы на fragment и element (страницы PDF, листы Word, кадры и аудио видео и т. д.), определяя для каждого fragment и element в `meta`, как получить его данные из исходного файла (состав `meta` зависит от источника и типа файла и уточняется отдельно). Идентификаторы (UUID v7) всех объектов дерева, включая `element_id`, core выдаёт на этом шаге. Для каждого photo и audio core по `meta` один раз извлекает данные из исходного файла и кладёт их в `task_storage` (см. 1.5 и 3.3). Дерево строится в памяти, в БД на этом шаге ничего не пишется.
7. Когда разбор завершён полностью, всё дерево записывается **одной транзакцией**: все дети record и их данные, задачи в очередях (chunk и task в статусе `wait`), а record переходит из `parsing` в `processing`. В той же транзакции сразу проверяется готовность record (см. 2.5): если листьев не появилось (все дети — пустышки разбора), record сразу становится `error`.
8. После коммита задачи доступны балансировщику, а файлы для них уже лежат в `task_storage`.

Требования:

- В БД нет частично записанных деревьев: у record в `parsing` детей нет, а дерево появляется целиком одним коммитом.
- Очереди задач — таблицы той же БД (`task` и `chunk` в статусе `wait`), поэтому дерево и его задачи фиксируются атомарно.
- Каталоги записи создаются только после коммита record, а файлы в `task_storage` — до коммита дерева. Поэтому к моменту, когда задача стала доступна балансировщику, её данные уже лежат на диске, и очистка их не тронет, пока запись не завершится (см. 3.3).
- `registered_at` = момент вставки record (шаг 3).
- Повторную отправку той же записи отсекает уникальность `(source, source_url)` на шаге 3: второй запрос получает «запись существует», даже если первая ещё разбирается. Отдельная блокировка на время приёма не нужна.

#### 3.2. Статус для скраппера и прерванный разбор

Пока идёт разбор, record уже существует в статусе `parsing`, поэтому скраппер, проверяя статус, не отправит запись повторно. Ответ на запрос статуса строится только по `record`: `unknown` (записи нет), `processing` (`parsing` или `processing`), `done` или `error`.

Если core упал во время приёма или разбора, record остаётся в `parsing`. При старте core все такие записи заведомо прерваны (core работает в одном экземпляре), поэтому они удаляются вместе с каталогами в хранилище исходных файлов и в `task_storage`. Это делается до того, как core начнёт принимать новые записи, иначе под удаление попала бы запись, принятая уже после старта. Скраппер после этого увидит `unknown` и отправит запись заново; новая попытка получит новый `record_id` и будет писать в свои каталоги.

Прерванная запись удаляется, а не переводится в `error`: на `error` скраппер запись не пересылает (пока её не удалят вручную, см. 6), и из-за падения core она выпала бы из индекса. Пустышки в `error` пишутся, только если упал сам разбор (см. 3.5): повторная отправка того же файла ничего не изменит.

#### 3.3. Хранение файлов

На файловой системе core два хранилища:

- **хранилище исходных файлов** — долговременное;
- **`task_storage`** — временное, для данных задач.

Долговременно core хранит **либо исходный файл, либо ничего**. При приёме видео сохраняется само это видео. Аудиодорожки, кадры и отрендеренные страницы долговременно не хранятся.

Исходные файлы:

- Лежат по пути `/storage/<source>/<record_id>/<file_id>.<исходное расширение>`. В БД путь и хэш не хранятся, путь выводится из `source`, `record_id`, `file_id` и расширения из `file.name`. Временной области приёма нет: файлы сразу кладутся по этому пути. Каталог записи создаётся только после коммита record (см. 3.1).
- Хранятся, пока существует record, в том числе после ошибки file или всей записи: исходник нужен для воспроизведения ошибки по снимку (2.7). Перезапуска обработки нет. Когда запись в `error` удаляют вручную (см. 6), её каталог удаляет очистка: записи больше нет в БД.

`task_storage`:

- Для каждого photo и audio core при разборе один раз извлекает данные из исходного файла по `meta` и кладёт их в `task_storage` по пути `/task_storage/<source>/<record_id>/<element_id>.<расширение>` (см. 1.5). Файлы создаются до коммита дерева; при `claim` ничего не извлекается, core только читает готовый файл.
- Файл один на element. Его читают все листья этого element: chunk-картинка и `task_ocr` у photo, `task_transcribe` у audio.
- Файлы живут, пока record не завершится (`done` или `error`), и удаляются очисткой целым каталогом записи. Задачи, вернувшиеся в `wait`, и повторные запуски по одной задаче после падения пачки берут уже готовые данные. Поштучно, по готовности element, файлы не удаляются: каждый скраппер держит в core не больше K незавершённых записей (см. «Скрапперы»), поэтому объём `task_storage` ограничен.
- Если при `claim` файла нет, это не штатная ситуация (каталог удаляется только вместе с завершённой записью): задача завершается ошибкой со `stage = task_storage` (см. 4.2), заново данные из исходника не извлекаются.
- Клиентские запросы («получить fragment в отрендеренном виде», «получить element») `task_storage` не используют: после завершения записи файлов там уже нет. Данные строятся из исходного файла по `meta` той же функцией извлечения, которую вызывает разбор. Функция одна.

Очистка хранилищ. Общее таймерное задание (период — параметр конфигурации), также запускается при старте core. Оно только читает БД и в циклах готовности и очистки не участвует. Удаляются только каталоги записей целиком, отдельные файлы очистка не трогает:

- в хранилище исходных файлов: каталоги записей (по `record_id`), которых нет в БД;
- в `task_storage`: каталоги записей, которых нет в БД или которые в статусе `done` или `error`.

Гонок с приёмом нет за счёт порядка действий: core коммитит record до того, как создаёт его каталоги (3.1), а очистка сначала получает список каталогов и только потом читает БД. Значит, любой каталог, который увидела очистка, создан после коммита своей записи, и запрос в БД эту запись найдёт. Возрастной порог не нужен.

Если core упал во время приёма или разбора, в хранилищах остаётся мусор. Каждая попытка приёма получает новый `record_id` и пишет в свои каталоги, поэтому каталог прерванной попытки не пересекается с новой: его удаляет либо удаление прерванной записи при старте (3.2), либо очистка.

#### 3.4. Ошибка file

При переходе file в `error` цикл очистки в той же транзакции переводит всё под ним в `error` и удаляет (см. 2.6), в том числе задачи из очередей; что и где упало, сохраняется в снимке ошибки (2.7). При ошибке собственного text записи так же удаляются его chunk'и, а остальная запись обрабатывается дальше. Задачи, которые уже выполняются на воркере, не прерываются, но их результат при получении игнорируется: листа больше нет. Файлы таких element в `task_storage` удаляются вместе с каталогом записи, когда она завершится (3.3): цикл очистки файлы на диске не трогает. Исходный файл остаётся.

#### 3.5. Ошибки при приёме: пустышки

Скрапперы сами отвечают за целостность данных: если получить запись не удалось (например, нет интернета), запись в core не отправляется, и core пустышками не заполняется. Пустышки создаются только в таких случаях:

| Ситуация | Что записывается |
|---|---|
| Непредвиденная ошибка при разборе отдельного файла | Пустышка file: без детей, `status` = `error`, `error` с описанием, `error_detail` со `stage = parse`. Файл пропускается, остальные файлы разбираются; на record это влияет только по общему правилу 2.5 |
| Непредвиденная ошибка при разборе всей записи (в том числе откат транзакции с деревом) | Отдельной транзакцией коммитится дерево из пустышек: каждый file записи — пустышка file (`stage = parse`), собственный text (если был) — в `error` без chunk'ов, а ошибка разбора (`stage = parse`) пишется в record. Проверка готовности (2.5) в той же транзакции переводит record в `error`. Исходные файлы остаются |

Кроме пустышек, без детей бывают только record в `parsing`, file в `error`, чьи дети удалены циклом очистки, и собственный text в `error`, чьи chunk'и удалены.

Пустая запись и превышение `max_file_size` пустышек не создают: запись отклоняется целиком (см. 3.1, 3.6).

#### 3.6. Ограничение размера файла

- В конфигурации core задаётся `max_file_size` — максимальный размер сохраняемого файла, по умолчанию около 15 ГБ.
- Значение отдаётся по API по соответствующему запросу, скраппер может проверить его заранее.
- Если размер какого-либо файла записи больше, core отказывается записывать запись и возвращает ошибку в виде статус-кода (например, HTTP 413). Записи, пустышки и файлы при этом не создаются.
- Скраппер такую запись в core не отправляет, а заносит в свою таблицу пропущенных по размеру (см. «Скрапперы»).

### 4. Задачи и очереди

#### 4.1. Очереди

Три очереди core соответствуют типам задач:

| Очередь (`type`) | Листья |
|---|---|
| `transcribe` | `task` с типом `transcribe` в статусе `wait` |
| `ocr` | `task` с типом `ocr` в статусе `wait` |
| `embed` | `chunk` в статусе `wait` |

Задача находится «в очереди», если `status = 'wait'`, и «на воркере», если `status = 'processing'` (тогда заполнены `taken_at` и `taken_by`). Отдельных структур очередей нет: очередь — это SQL-запрос к `task` или `chunk` в статусе `wait`. Порядок внутри очереди — FIFO по `created_at`.

Для балансировщика core — один источник задач (см. «Термины»): очередей для конкретных `record.source` (`youtube`, `telegram`) не существует, и балансировщик их не различает. Приоритеты очередей и источников задач хранит и применяет балансировщик, core их не знает.

#### 4.2. API источника задач

Балансировщик работает с каждым источником задач (core и клиентами) по одному и тому же API. Источник задач определяется адресом IP:PORT: балансировщик знает, чья задача, потому что сам отправил запрос на этот адрес. Источник, в свою очередь, знает, какой балансировщик взял задачу: `claim` передаёт `balancer_id` (постоянный идентификатор из конфига балансировщика), и источник записывает его в лист (`taken_by`). Core реализует API так:

| Операция | Действие |
|---|---|
| `claim(type, limit, balancer_id)` | `type` — `transcribe`, `ocr` или `embed`. Атомарно берёт до `limit` следующих задач очереди, переводит их из `wait` в `processing`, ставит `taken_at` и `taken_by = balancer_id`. Реализуется как `UPDATE … SET status = 'processing', taken_at = now(), taken_by = :balancer_id WHERE id IN (SELECT … WHERE status = 'wait' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT :limit) RETURNING …`. Возвращает пачку: для каждой задачи `task_id` и данные для воркера (аудио, картинку или текст chunk'а); аудио и картинку core читает из `task_storage` по `element_id`, текст chunk'а берёт из БД. Если для какой-то задачи файла в `task_storage` нет, core после коммита `claim` отдельной транзакцией выполняет `fail` этого листа со `stage = task_storage` (цикл очистки по 2.6) и добирает пачку следующими задачами той же очереди; балансировщик этого не видит. Пустой ответ — очередь пуста |
| `result([(task_id, payload)])` | Принимает результаты пачки (см. 4.3). Каждая задача вместе со своим циклом готовности фиксируется своей транзакцией; ответ приходит после коммита всех |
| `fail(task_ids, error)` | Задача упала и в пачке, и в одиночку (см. «Балансировщик»), поэтому обычно приходит ровно один `task_id`. Для каждого листа — цикл очистки по 2.6, своей транзакцией. `error` — структура: текст ошибки (`message`), число запусков (`attempts`), по желанию воркер и модель; из неё и из дерева core собирает снимок ошибки (2.7) |
| `check_tasks()` | Для каждого типа очереди — есть ли в ней задачи в `wait` (`EXISTS` по частичным индексам очередей). Задачи не выдаёт и ничего не меняет. Балансировщик опрашивает его, чтобы решить, нужно ли вытеснение |
| `reset(balancer_id)` | Все листья в `processing` с `taken_by = balancer_id` → `wait`, `taken_at` и `taken_by` = `NULL`. Балансировщик вызывает его при своём старте (задачи, взятые до перезапуска, он уже не выполнит) и при вытеснении (вернуть задачи из очищенной очереди пачек). Ошибкой это не считается |

`task_id` — идентификатор `task` либо chunk (для очереди `embed`).

Возвращённая и завершившаяся ошибкой задачи — разные события: возвращённую (`reset`) кладём обратно в очередь (`wait`), а ошибка запускает цикл очистки — file переходит в `error` и всё под ним удаляется, либо, если упал собственный text, удаляются его chunk'и, а ошибка пишется в record (2.4, 2.6). Любая операция над объектом, которого уже нет или который не в `processing`, игнорируется и не считается ошибкой.

#### 4.3. Обработка результата

Результат каждой задачи фиксируется **одной транзакцией вместе со всеми порождёнными записями и циклом готовности** (см. 2.6). Коммит происходит до ответа балансировщику, поэтому не бывает момента, когда задача завершена, а её дети ещё не созданы или её предки не пересчитаны.

**Эмбеддинг** (лист chunk): записываются `embed` и `embed_model`, chunk → `done`.

**Транскрибация** (лист `task_transcribe` под audio):

1. `task_transcribe` → `done`.
2. Если транскрипция непуста, создаётся text (`kind` = `task_result`) — ребёнок audio — со статусом `processing`. Текст сразу режется на chunk'и (дети text, статус `wait`, `embed` пуст).
3. Если транскрипция пуста, text не создаётся.

**OCR** (лист `task_ocr` под photo): то же самое, text становится ребёнком photo. Если OCR не вернул текст, text не создаётся; это не ошибка.

Пока созданные chunk'и не получат эмбеддинги, audio (или photo) остаётся в `processing`.

#### 4.4. OCR

OCR обязателен для каждой photo, в том числе для каждого кадра видео: `task_ocr` создаётся всегда, без настроек и политик. Photo с пустым результатом OCR завершается, не имея text.

#### 4.5. Восстановление после сбоев

Возврат задач, взятых в работу:

- **При старте core** все листья в статусе `processing` возвращаются в очередь: `status = 'wait'`, `taken_at` и `taken_by` = `NULL`. Так обрабатывается падение core, в том числе при фиксации результата. Если балансировщик потом пришлёт результат по такой задаче, он будет проигнорирован (задача уже не в `processing`), а сама задача выполнится заново.
- **При старте балансировщика** он вызывает `reset(balancer_id)` (см. 4.2): возвращаются задачи, которые взял именно он; балансировщик состояния не хранит и набирает задачи заново.

Возврата по таймауту нет: длинная транскрибация законно идёт часами, и таймаут срабатывал бы посреди нормальной работы. Если балансировщик завис, его перезапускают, и при старте он сам возвращает свои задачи через `reset(balancer_id)`.

При старте core:

1. удаляет записи в `parsing` вместе с их каталогами (см. 3.2) — до того, как начать принимать новые записи;
2. возвращает все листья из `processing` в `wait` — до того, как начать отвечать балансировщику;
3. запускает цикл очистки по таймеру (см. 2.8) и очистку хранилищ (см. 3.3); дальше они работают по своим таймерам.

Проверки и ремонта дерева нет: операция над листом и весь вызванный ею цикл фиксируются одной транзакцией (2.6), поэтому падение core не оставляет дерево наполовину пересчитанным.

### 5. Поиск

Запись появляется в поиске ровно тогда, когда `record.status = 'done'`. Записи в `parsing`, `processing` и `error` не ищутся. Внутри записи в `done` ищутся только существующие chunk'и: у file в `error` детей нет, у упавшего собственного text нет chunk'ов.

Остальное в разработке.

### 6. Веб-интерфейс core

Веб-интерфейс доступен только из локальной сети. В нём можно:

- смотреть записи в статусе `error`: `error` и `error_detail` записи, а также ошибки и снимки её file;
- смотреть ошибки внутри записей в `done`: file в `error` и упавший собственный text (его ошибка лежит в `error` записи). Только просмотр;
- вручную удалить запись в статусе `error`. Удаляется строка record (всё остальное — каскадом внешних ключей), каталоги в хранилище исходных файлов и в `task_storage` удаляет очистка хранилищ, так как записи больше нет в БД (см. 3.3).

Удалить можно только запись целиком и только в `error`. Удалять отдельные file, а также записи в других статусах нельзя. Перезапуска обработки нет: после удаления скраппер на запрос статуса получает `unknown` и, если снова встретит запись, отправляет её заново как новую (с новым `record_id`). Какие режимы скрапперов встречают запись повторно, описано в разделе «Скрапперы».

### 7. Хранение и технологии

Рекомендуется PostgreSQL с расширением pgvector версии не ниже 0.7 (нужен тип `halfvec`, см. ниже); СУБД пока не зафиксирована. Фрагменты SQL в этом разделе — эскизы для PostgreSQL.

- Типы `record_status`, `container_status`, `task_status`, `element_kind`, `task_type`, `text_kind` — enum. Enum — тип поля, которое может принимать только одно значение из заданного списка. В SQLite enum нет, там используется `TEXT` с проверкой `CHECK`.
- Каждый тип объектов дерева лежит в своей таблице: `record`, `file`, `fragment`, `text`, `element`, `chunk`, `task`. Внешние ключи с `ON DELETE CASCADE`: ручное удаление записи в `error` (см. 6) — это удаление строки record, остальное удаляется каскадом. Цикл очистки удаляет строки явно, снизу вверх (2.6); каскад для него — подстраховка.
- Исходные файлы лежат в долговременном хранилище core по пути `/storage/<source>/<record_id>/<file_id>.<исходное расширение>`; ни пути, ни хэша в БД нет. Данные для задач лежат во временном `task_storage` на файловой системе (не в БД; путь выводится из `record_id` и `element_id`) и удаляются очисткой хранилищ целым каталогом записи (3.3).
- Все поля с данными, специфичными для источника или типа файла (`metadata`, `meta`), имеют тип JSONB.
- Индексы: внешние ключи дочерних таблиц (`file.record_id`, `fragment.record_id`, `fragment.file_id`, `fragment.parent_fragment_id`, `element.record_id`, `element.file_id`, `element.fragment_id`, `text.*_id`, `chunk.*_id`, `task.element_id`) для проверки готовности; частичные индексы очередей `task (type, created_at) WHERE status = 'wait'` и `chunk (created_at) WHERE status = 'wait'`; частичные индексы `task (taken_by) WHERE status = 'processing'` и `chunk (taken_by) WHERE status = 'processing'` для возврата задач по `reset(balancer_id)` и при старте core; частичные индексы `WHERE status = 'error'` на `fragment`, `element`, `text`, `chunk` и `task` для цикла очистки по таймеру; частичный индекс `file (finished_at) WHERE status = 'error'` для списка ошибок внутри записей в `done`; индекс HNSW `chunk USING hnsw (embed halfvec_cosine_ops)` для семантического поиска; частичный индекс `record (id) WHERE status = 'parsing'` для удаления прерванных записей при старте; частичный индекс `record (processed_at) WHERE status = 'error'` для списка ошибочных записей в веб-интерфейсе; уникальный индекс `record(source, source_url)`.
- Ограничения: у `chunk` заполнены ровно один родитель и ровно одно из `text` и `is_picture`, длина текста ограничена; у `text` набор заполненных ссылок согласован с `kind` (см. 1.5); в `wait` поля `taken_at` и `taken_by` пусты, в `processing` заполнены; иерархические правила из 1.1 проверяются при построении дерева в коде (на уровне БД — при необходимости constraint-триггерами).
- Эмбеддинги лежат в столбце типа `halfvec(2048)`: 2048 — размерность Qwen3-VL-Embedding-2B (см. таблицу моделей). Индексы pgvector (HNSW, IVFFlat) по типу `vector` ограничены 2000 измерениями, а по `halfvec` — 4000. В `halfvec` каждое число занимает 16 бит вместо 32: вектор весит 4 КБ вместо 8, а точности хватает, так как модель и так считает в BF16. Если сменить модель на размерность больше 4000, векторы придётся урезать (MRL). В chunk хранится название модели (`embed_model`), чтобы при смене модели можно было пересчитать эмбеддинги.
- Эскиз таблиц:

```sql
CREATE TYPE record_status    AS ENUM ('parsing','processing','done','error');  -- record
CREATE TYPE container_status AS ENUM ('processing','done','error');          -- file, fragment, element, text
CREATE TYPE task_status      AS ENUM ('wait','processing','done','error');   -- chunk, task
CREATE TYPE element_kind     AS ENUM ('photo','audio');
CREATE TYPE task_type        AS ENUM ('transcribe','ocr');
CREATE TYPE text_kind        AS ENUM ('record','element','task_result');

CREATE TABLE record (
  id                 uuid PRIMARY KEY,
  source             text NOT NULL,
  source_url         text NOT NULL,
  source_created_at  timestamptz,
  scraped_at         timestamptz NOT NULL,
  registered_at      timestamptz NOT NULL,
  processed_at       timestamptz,
  status             record_status NOT NULL DEFAULT 'parsing',
  title              text,
  author             text,
  parent_source_url  text,
  metadata           jsonb,
  error              text,
  error_detail       jsonb,
  UNIQUE (source, source_url)
);

CREATE TABLE file (
  id           uuid PRIMARY KEY,
  record_id    uuid NOT NULL REFERENCES record(id) ON DELETE CASCADE,
  ord          int  NOT NULL DEFAULT 0,
  status       container_status NOT NULL DEFAULT 'processing',
  error        text,
  error_detail jsonb,
  name         text,
  mime         text,
  size         bigint,
  finished_at  timestamptz,
  meta         jsonb
);

CREATE TABLE fragment (
  id                 uuid PRIMARY KEY,
  record_id          uuid NOT NULL REFERENCES record(id) ON DELETE CASCADE,
  file_id            uuid NOT NULL REFERENCES file(id) ON DELETE CASCADE,
  parent_fragment_id uuid REFERENCES fragment(id) ON DELETE CASCADE,  -- NULL на верхнем уровне
  ord                int  NOT NULL DEFAULT 0,
  status             container_status NOT NULL DEFAULT 'processing',
  finished_at        timestamptz,
  meta               jsonb
);

CREATE TABLE element (              -- photo и audio
  id           uuid PRIMARY KEY,
  record_id    uuid NOT NULL REFERENCES record(id)   ON DELETE CASCADE,
  file_id      uuid NOT NULL REFERENCES file(id)     ON DELETE CASCADE,
  fragment_id  uuid NOT NULL REFERENCES fragment(id) ON DELETE CASCADE,
  kind         element_kind NOT NULL,
  ord          int  NOT NULL DEFAULT 0,
  status       container_status NOT NULL DEFAULT 'processing',
  finished_at  timestamptz,
  meta         jsonb
);

CREATE TABLE text (
  id           uuid PRIMARY KEY,
  kind         text_kind NOT NULL,
  record_id    uuid NOT NULL REFERENCES record(id) ON DELETE CASCADE,
  fragment_id  uuid REFERENCES fragment(id) ON DELETE CASCADE,  -- пусто только у собственного text записи
  element_id   uuid REFERENCES element(id)  ON DELETE CASCADE,  -- только у результата задачи
  status       container_status NOT NULL DEFAULT 'processing',
  finished_at  timestamptz,
  meta         jsonb,
  CHECK ((kind = 'record'      AND fragment_id IS NULL     AND element_id IS NULL)
      OR (kind = 'element'     AND fragment_id IS NOT NULL AND element_id IS NULL)
      OR (kind = 'task_result' AND fragment_id IS NOT NULL AND element_id IS NOT NULL))
);

CREATE TABLE chunk (
  id           uuid PRIMARY KEY,
  text_id      uuid REFERENCES text(id)    ON DELETE CASCADE,
  element_id   uuid REFERENCES element(id) ON DELETE CASCADE,   -- chunk-картинка photo
  ord          int  NOT NULL DEFAULT 0,
  status       task_status NOT NULL DEFAULT 'wait',
  text         text,
  is_picture   boolean NOT NULL DEFAULT false,
  embed        halfvec(2048),
  embed_model  text,
  taken_at     timestamptz,
  taken_by     text,                                            -- balancer_id
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  CHECK ((text_id    IS NOT NULL AND element_id IS NULL AND text IS NOT NULL AND NOT is_picture)
      OR (element_id IS NOT NULL AND text_id    IS NULL AND text IS NULL     AND is_picture)),
  CHECK (status <> 'wait' OR (taken_at IS NULL AND taken_by IS NULL)),
  CHECK (status <> 'processing' OR (taken_at IS NOT NULL AND taken_by IS NOT NULL))
);

CREATE INDEX ON chunk USING hnsw (embed halfvec_cosine_ops);

CREATE TABLE task (
  id           uuid PRIMARY KEY,
  element_id   uuid NOT NULL REFERENCES element(id) ON DELETE CASCADE,
  type         task_type NOT NULL,
  status       task_status NOT NULL DEFAULT 'wait',
  taken_at     timestamptz,
  taken_by     text,                                            -- balancer_id
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  CHECK (status <> 'wait' OR (taken_at IS NULL AND taken_by IS NULL)),
  CHECK (status <> 'processing' OR (taken_at IS NOT NULL AND taken_by IS NOT NULL))
);
```

### 8. Обработка отказов

| Ситуация | Поведение |
|---|---|
| Запись с таким `(source, source_url)` уже есть | Ответ «существует» (в том числе пока она в `parsing`), ничего не меняется |
| Отправлена запись без содержимого (нет ни текста, ни файлов) | Запись отклоняется статус-кодом ошибки (HTTP 422), ничего не сохраняется (3.1) |
| Файл больше `max_file_size` | Запись отклоняется статус-кодом ошибки (HTTP 413), ничего не сохраняется |
| Загрузка файлов оборвалась | core удаляет record и его каталоги; скраппер получает `unknown` и отправляет запись повторно |
| core упал во время приёма или разбора | Record остаётся в `parsing`; при старте core удаляет его вместе с каталогами (3.2); скраппер получает `unknown` и отправляет запись повторно |
| Разбор отдельного файла упал | Пустышка file в `error` (`stage = parse`); остальные файлы разбираются (3.5) |
| Разбор всей записи упал (исключение, откат транзакции с деревом) | Дерево из пустышек: все file и собственный text в `error`, ошибка разбора в record; record сразу → `error` (3.5, 2.5). Исходники остаются, каталог в `task_storage` удаляется очисткой хранилищ |
| После разбора у записи нет ни одного листа (все дети — пустышки разбора) | Record → `error` сразу в транзакции коммита дерева (3.1, 2.5) |
| Каталог в `task_storage` остался после завершения записи или падения core | Удаляется очисткой хранилищ целиком (3.3) |
| При `claim` нет файла в `task_storage` | `fail` листа со `stage = task_storage` и цикл очистки: file → `error`, всё под ним удаляется (4.2, 2.6). Листья собственного text в `task_storage` не обращаются: текст chunk'а берётся из БД |
| core упал при фиксации результата или ошибки | Транзакция (лист вместе с циклом) откатывается целиком, дерево не меняется; лист остаётся в `processing` и при старте core возвращается в `wait` (4.5) |
| Балансировщик перезапустился | Воркеры завершает ОС вместе с ним; при старте он вызывает `reset(balancer_id)` у каждого источника, и его листья из `processing` возвращаются в `wait` (4.2, 4.5, «Балансировщик») |
| Вытеснение более приоритетным источником | Воркер убивается, очередь пачек очищается, `reset(balancer_id)`: задачи из `processing` возвращаются в `wait`, статус родителей не меняется |
| Воркер упал на пачке из нескольких задач | Балансировщик разбивает пачку на пачки по одной задаче и запускает их по очереди; в core это ошибкой не считается («Балансировщик») |
| Задача упала и в одиночку | `fail` этой задачи → цикл очистки: file → `error` со снимком ошибки, всё под ним удаляется одной транзакцией; record продолжает обработку остальных детей (2.6) |
| Упал лист собственного text записи | Цикл очистки: text → `error`, его chunk'и удаляются, ошибка и снимок пишутся в record; статус record не меняется (2.4, 2.6) |
| Все дети записи (собственный text, если есть, и все file) в `error` | Record → `error` со сводкой `stage = children` (2.5) |
| Ниже границы остались строки в `error` (ошибка в коде, ручная правка БД) | Их находит и удаляет цикл очистки по таймеру (2.8) |
| Запись в `error` удалена вручную в веб-интерфейсе | Строка record и всё под ней удаляются, каталоги удаляет очистка хранилищ; скраппер получает `unknown` (6) |
| Результат или ошибка пришли для объекта, которого нет или который не в `processing` | Игнорируется |
| Результат пришёл повторно | Игнорируется (идемпотентность по статусу) |
| Балансировщик завис | Его перезапускают; воркеры завершает ОС, при старте он вызывает `reset(balancer_id)` (4.5). Возврата по таймауту нет |
| Файл записи больше `max_file_size` на стороне скраппера | Запись в core не отправляется, скраппер заносит её в таблицу пропущенных по размеру («Скрапперы») |

### 9. Инварианты

1. Дерево записи появляется в БД целиком одной транзакцией; до этого record находится в `parsing` и детей не имеет; частичных деревьев не бывает.
2. Каждый контейнер имеет хотя бы одного ребёнка; исключение — record в `parsing`, file в `error` и собственный text в `error` (их дети удалены циклом очистки, или это пустышки разбора).
3. Задачи привязаны только к листьям (chunk, `task_transcribe`, `task_ocr`).
4. Результат задачи фиксируется вместе со всеми порождёнными записями одной транзакцией и коммитится до ответа балансировщику.
5. Каждый photo имеет ровно один chunk-картинку и ровно один `task_ocr` (пока его file не в `error`).
6. Контейнер внутри file (или собственный text записи) `done` только если все его дети `done`; ошибка любого листа внутри file делает ошибочным file, а всё под ним в той же транзакции уходит в `error` и удаляется.
7. Статус `wait` бывает только у chunk, `task_transcribe` и `task_ocr`; у остальных объектов его нет.
8. Операция над листом и весь вызванный ею цикл (готовности или очистки) — один коммит.
9. Record в `error` тогда и только тогда, когда все его дети (собственный text, если есть, и все file) в `error`. Ошибка file или собственного text статус record не меняет; ошибка собственного text пишется в `error` записи.
10. Терминальный статус (`done`, `error`) не меняется. Запись в `error` можно только удалить вручную (см. 6).
11. Пара `(source, source_url)` уникальна и обязательна.
12. Долговременно core хранит только исходные файлы: либо исходный файл, либо ничего. Исходный файл хранится, пока существует record. Данные для задач лежат во временном `task_storage` и удаляются очисткой хранилищ целым каталогом записи, когда record завершён (`done`, `error`) или его нет в БД.
13. К моменту, когда задачи появились в очередях, их данные уже лежат в `task_storage` (файлы создаются до коммита дерева).
14. Статус `parsing` бывает только у record. Запись в `parsing` существует, только пока core её принимает и разбирает; при старте core все такие записи удаляются.
15. В поиске участвуют только record в `done`.
16. Record в `error` имеет хотя бы одного ребёнка, и все его дети — file в `error` и собственный text в `error`, без детей.
17. После старта core и до первого `claim` ни одного листа в `processing` нет.
18. Строки в `error` ниже границы (fragment, element, text, кроме собственного text записи, chunk, task) не переживают коммит цикла очистки.
19. Лист в `processing` всегда помечен балансировщиком, который его взял (`taken_by`); лист в `wait` не помечен.

### 10. Принятые решения и открытые вопросы

Решения, принятые при составлении ТЗ:

1. Разбор записи до коммита дерева выполняет сам core, в фоне, после ответа скрапперу (разбиение PDF и Word на страницы и листы, определение кадров и аудио видео, нарезка текста); это не GPU-работа и в очереди балансировщика не входит. Кадры, аудио и рендер страниц для задач извлекаются при разборе и кладутся во временный `task_storage` (см. 3.3); клиентские запросы строят их из исходного файла по `meta` той же функцией извлечения.
2. Граница ошибки — file (для листьев внутри файла), а не element: лучше открыто потерять файл целиком, чем незаметно терять его части. Для листьев собственного text записи граница — record: в него пишется ошибка, но статус record не меняется. Ошибку обрабатывает цикл очистки: вверх до границы с сообщением, вниз по слоям, удаление снизу вверх — одной транзакцией; упавшее не дорабатывается (иначе работа GPU тратится на то, что нельзя найти). Для отладки остаются исходный файл и снимок ошибки (2.7). Цикл очистки по таймеру — только страховка (2.8).
3. Record становится `error`, только если все его дети (собственный text, если есть, и все file) в `error` (2.5); иначе `done`. Пустая запись не принимается (3.1), а упавший разбор записи даёт дерево из пустышек (3.5), так что других случаев `error` у record нет. Запись видна в поиске ровно тогда, когда она в `done` (5).
4. OCR обязателен для каждой photo, в том числе для каждого кадра видео. Кадры берутся каждые i секунд и не дедуплицируются: каждый кадр и эмбеддится, и отправляется на OCR.
5. Одна аудиодорожка файла — один element audio и одна задача транскрибации; длинное аудио на части не режется. Принятое следствие: при вытеснении (см. «Балансировщик») прогресс длинной транскрибации теряется целиком, и при активном клиенте она может откладываться.
6. `registered_at` — момент приёма записи (вставки record в `parsing`).
7. Параметры нарезки текста: максимум x символов на chunk, границы по абзацам и предложениям, перекрытие настраивается (по умолчанию 0).
8. Шаг кадров i, период очистки хранилищ, период цикла очистки по таймеру и формат материалов в `task_storage` — параметры конфигурации.
9. Element хранится в двух таблицах: photo и audio — в `element`, text-элементы — в `text`. Так text как результат OCR, транскрибации, собственный текст записи и text-элемент фрагмента лежат в одной таблице; колонка `kind` различает их, ссылки `record_id`, `fragment_id`, `element_id` согласованы с ней.
10. Операция над листом и вызванный ею цикл (готовности или очистки) фиксируются одной транзакцией с блокировкой file (или собственного text записи) и record (2.6), поэтому проверка и ремонт дерева не нужны.
11. Статус `wait` есть только у листьев-задач (chunk, `task_transcribe`, `task_ocr`); у контейнеров «ожидания» нет, они с момента создания `processing` (record — `parsing`, пока идёт разбор).
12. `task_storage`: один файл на element, создаётся при разборе до коммита дерева, живёт до завершения record и удаляется очисткой хранилищ целым каталогом записи; очистка хранилищ только читает БД. Пропажа файла — ошибка задачи, заново данные не извлекаются. Лимита размера нет: объём ограничен K незавершёнными записями на скраппер. Для фото, которое само является файлом, копия всё равно делается: выигрыш от ссылки на исходник минимален.
13. Пути файлов выводятся из идентификаторов, поэтому `record_id` и `file_id` выдаются core при приёме (record сразу вставляется в `parsing`) и в БД нет ни путей, ни хэшей файлов: изменения записей не отслеживаются.
14. Приём асинхронный: core отвечает `202` после сохранения исходных файлов и разбирает запись в фоне; отдельной таблицы состояния приёма нет, её роль играет record в статусе `parsing`. Core работает в одном экземпляре, поэтому при старте все записи в `parsing` считаются прерванными. Для нескольких экземпляров core понадобится heartbeat разбора.
15. Источник задач для балансировщика — адрес IP:PORT (core или клиент), все источники реализуют одно API (4.2). Core — один источник: `record.source` балансировщик не различает. Задачи клиентов (транскрибация, OCR, эмбеддинги) живут в очереди самого клиента; core их не хранит.
16. Балансировщик работает пачками на одном GPU: в каждый момент выполняется ровно один воркер, процесс воркера запускается на каждую пачку. Упавшая пачка разбивается на пачки по одной задаче, `fail` получает только задача, упавшая в одиночку; ретраев нет. Состояние балансировщик не хранит, воркеры завершаются вместе с ним средствами ОС; при старте и при вытеснении он вызывает `reset(balancer_id)` и так возвращает только свои задачи. Возврата задач по таймауту нет (4.5).
17. Ручного перезапуска нет. Запись в `error` можно только удалить в веб-интерфейсе core (6), после чего скраппер отправит её заново, если встретит.
18. Эмбеддинги хранятся в `halfvec(2048)` с индексом HNSW (7).
19. Скраппер держит в core до K незавершённых записей. Запись с файлом больше `max_file_size` (по умолчанию около 15 ГБ) в core не отправляется и заносится в таблицу пропущенных по размеру у скраппера.
20. Все компоненты работают в доверенной локальной сети: аутентификации между ними нет, веб-интерфейсы и админки доступны только из локальной сети.

Открытые вопросы:

1. **Повторная отправка из Telegram.** Сканер каналов и чатов читает только сообщения после `last_message_id`, поэтому удалённую вручную запись сам не пришлёт. Есть идея на каждом проходе брать все id сообщений группы или чата и сверять их с core; пока не решено.
2. **Поиск** (раздел 5) в разработке.

## Балансировщик

### Компоненты

- **Балансировщик** — один отдельный демон. Состояния не хранит: после перезапуска начинает набирать задачи заново (см. «Перезапуск»). У него есть постоянный `balancer_id` из конфига: источники записывают его во взятые задачи (см. Core, 4.2).
- **Три воркера-утилиты**: транскрибация, OCR, эмбеддинги. Балансировщик запускает воркер с пачкой задач, воркер завершается после её выполнения.
- **Один GPU**: в каждый момент работает ровно один воркер.
- **Источники задач** — адреса IP:PORT, которые отдают задачи по API источника (см. Core, 4.2): core и клиенты. Список источников и их приоритеты задаются в конфиге балансировщика. Балансировщик знает, чья задача, потому что сам отправил запрос на адрес источника. Очередей задач у самого балансировщика нет: очереди живут в источниках (в core это просто SQL-запрос к таблицам задач). У балансировщика есть только очередь пачек в памяти — набранная, но ещё не выполненная работа (см. «Очередь пачек и сбой воркера»).

### Воркеры

- Воркер не принимает входящих соединений и HTTP-сервера не имеет. Балансировщик запускает его как процесс и передаёт пачку; воркер возвращает балансировщику результаты всей пачки целиком, а балансировщик отправляет их источнику (`result`).
- Процесс запускается на каждую пачку, поэтому модель каждый раз заново загружается в видеопамять. Это принято: когда задач много, пачка набирается полной и загрузка окупается, а когда задач мало, лишние секунды не важны.
- Так как входящих соединений нет, вытеснение (см. ниже) реализуется через завершение процесса воркера.
- Воркер — дочерний процесс балансировщика и не переживает его, как daemon-поток не переживает главный: при запуске воркеру ставится `prctl(PR_SET_PDEATHSIG, SIGKILL)`, и ОС убивает воркер, как только умирает балансировщик. Запускать воркер нужно из главного потока балансировщика: сигнал привязан к потоку, который породил процесс. Второй уровень — systemd-сервис с `KillMode=control-group`: при остановке или перезапуске сервиса убиваются все его процессы.
- В **админке балансировщика** можно управлять тем, выполняются ли сейчас задачи: пока выполнение выключено, балансировщик новые пачки не набирает.

### Приоритеты

- У каждой очереди есть внутренний приоритет (по умолчанию транскрибация — 3, OCR — 2, эмбеддинги — 1).
- Каждый источник задач (комплект из очередей транскрибации, OCR и эмбеддингов) тоже имеет приоритет.
- По умолчанию клиенты — самые приоритетные.
- Все приоритеты различны (среди источников и внутри каждого источника), одинаковых нет.

### Проход балансировщика

Проход — это обход всех источников по убыванию приоритета, а внутри каждого источника — обход его очередей по убыванию приоритета. Очередная очередь источника обрабатывается через очередь пачек (см. ниже), пока она не опустеет; затем балансировщик переходит к следующей очереди и следующему источнику.

После обхода всех источников начинается новый проход. Если все очереди пусты, балансировщик ждёт и повторяет проход (интервал задаётся в конфиге). Так как более приоритетные источники обходятся первыми, они вычищаются раньше остальных.

### Очередь пачек и сбой воркера

Внутри балансировщика — очередь пачек (обычная Queue в памяти). Очередь источника обрабатывается так:

1. Если очередь пачек пуста, создаётся одна пачка: балансировщик вызывает `claim(type, …, balancer_id)` и добавляет задачи в эту пачку, пока в ней меньше N задач (размер пачки задаётся в конфиге для каждого типа) и пока источник их отдаёт. В источнике задачи переходят из `wait` в `processing`; отдельно уведомлять источник не нужно. Если источник ничего не отдал, очередь источника пуста.
2. Пачка из головы очереди пачек отправляется на воркер.
3. Воркер завершился успешно → результаты всей пачки отправляются источнику (`result`), и балансировщик возвращается к шагу 1.
4. Воркер упал на пачке из k > 1 задач (OOM, неправильный файл, непредвиденная ошибка) → в лог пишется WARNING, и вместо этой пачки в очередь кладутся k пачек по одной задаче. Воркер запускается на каждую по очереди, пока очередь пачек не опустеет; результат каждой успешной отправляется источнику сразу после её запуска.
5. Упала пачка из одной задачи → источнику отправляется `fail` этой задачи: текст ошибки и число запусков (см. Core, 4.2). Повторов нет. Ошибка — не то же самое, что вытеснение: упавшая задача в очередь не возвращается.

Так ошибку получает только задача, которая валит воркер и в одиночку, а остальные задачи упавшей пачки выполняются до конца. Цена — модель загружается заново на каждую задачу, но только для упавшей пачки.

### Сканирование и вытеснение

Параллельно с выполнением пачки балансировщик постоянно (период задаётся в конфиге) опрашивает `check_tasks()` всех источников, более приоритетных, чем текущий. `check_tasks()` — отдельный эндпоинт: он только проверяет, есть ли задачи, и ничего не выдаёт. Если у более приоритетного **источника** появилась задача:

1. воркер убивается (KILL), независимо от того, сколько он успел сделать; частичные результаты выбрасываются;
2. очередь пачек очищается;
3. у текущего источника вызывается `reset(balancer_id)` — тот же вызов, что и при старте: все задачи, взятые этим балансировщиком, переходят из `processing` в `wait`. Результаты и ошибки, уже отправленные источнику, остаются;
4. текущий проход завершается и запускается новый, который начнётся с самого приоритетного источника.

Очередь отпускается только в двух случаях:

- она опустела;
- появилась задача более приоритетного источника.

Если более приоритетная очередь появилась внутри того же источника, ничего не происходит: проход продолжается, а эта задача будет обработана в следующем проходе.

Принятое ограничение: длинное аудио — одна задача (см. Core, 10), поэтому при вытеснении её прогресс теряется целиком, и при активном клиенте длинная транскрибация может откладываться.

### Перезапуск

Перезапуск — это когда процесс балансировщика завершился и запущен снова: упал сам, его убила ОС (например, по OOM), перезагрузился сервер, его перезапустили вручную (например, при зависании) или обновили версию. Падение самого балансировщика — редкое событие: тяжёлая работа и почти все сбои происходят в воркерах.

Что происходит:

1. **Воркеры завершаются вместе с балансировщиком** средствами ОС (`PR_SET_PDEATHSIG`, cgroup сервиса, см. «Воркеры»). Двух воркеров на одном GPU и результатов, которые некому отправить, не бывает.
2. **Теряется всё, что в памяти:** очередь пачек и работа текущего воркера. Результаты и ошибки, уже отправленные источникам (`result`, `fail`), там закоммичены и не теряются.
3. **При старте** балансировщик вызывает `reset(balancer_id)` у каждого источника из конфига: задачи, которые он взял до перезапуска, возвращаются в `wait`. Пока `reset` у источника не прошёл (источник недоступен), задачи из него не берутся; вызов повторяется на каждом проходе.
4. После этого начинается проход с самого приоритетного источника. Задачи, которые были на воркере, выполняются заново с нуля.

`balancer_id` задаётся в конфиге и постоянен: если бы он менялся при каждом старте, балансировщик не смог бы вернуть задачи, взятые до перезапуска.

Возврата задач по таймауту нет: если балансировщик завис, его перезапускают, и дальше всё идёт по тем же шагам.

## Скрапперы

Скрапперы отвечают за сбор данных. Core не знает, что такое ютуб или любой другой источник: он получает только record: универсальные поля (ссылка на источник, дата публикации, дата скраппинга и т. п.) и `metadata` со специфичными для источника данными.

Каждый скраппер обязан заполнить `source` и `source_url` (вместе они образуют уникальный ключ записи) и привести `source_url` к каноническому виду.

Скрапперы сами отвечают за целостность данных: если получить запись целиком не удалось (например, нет интернета), она в core не отправляется. Пустую запись (без текста и без файлов) скраппер тоже не отправляет; если core всё же отклонил запись как пустую (HTTP 422), скраппер пишет это в лог и удаляет запись из очереди.

#### Отправка в core

Каждый скраппер держит очередь отправки в core (SQLite, FIFO, персистентна) и папку с файлами записей, ожидающих отправки. В core одновременно находится не больше K незавершённых записей скраппера (K задаётся в конфиге скраппера): пока core разбирает следующую запись, GPU обрабатывает задачи предыдущих.

1. Пока незавершённых записей меньше K, скраппер отправляет следующую запись из начала очереди. Core регистрирует её, сохраняет файлы и сразу отвечает `202`, не дожидаясь разбора (см. Core, 3.1).
2. Скраппер периодически запрашивает статус отправленных записей. Пока запись в обработке (`processing`), она и её файлы остаются в очереди и в папке.
3. Когда core отвечает `done` или `error`, скраппер удаляет запись из очереди и её файлы из папки, освобождая место для следующей.
4. Если core отвечает `unknown` (записи нет: например, core упал при приёме), запись отправляется заново.

#### Файлы больше `max_file_size`

Размер каждого файла не должен превышать `max_file_size` core (значение отдаётся по API core, по умолчанию около 15 ГБ). Запись, в которой хотя бы один файл больше, в core не отправляется целиком: скраппер удаляет скачанное и заносит её в свою SQLite-таблицу «пропущено по размеру». Размер проверяется до скачивания, если источник его сообщает, и после скачивания. Перед добавлением записи в очередь скраппер сверяется и с этой таблицей, поэтому сканеры не скачивают такую запись повторно на каждом проходе. Для Telegram это почти недостижимо: лимит файлов там 2–4 ГБ.

#### Записи с ошибкой и повторная отправка

Когда core отвечает `error`, скраппер удаляет запись из своей очереди и папки с файлами и повторно её не отправляет: запись остаётся в core в статусе `error`. Перезапуска нет; запись можно только удалить вручную в веб-интерфейсе core (см. Core, 6). После удаления core отвечает на неё `unknown`, и скраппер отправит её заново, только если снова встретит.

Ограничение: снова встречают запись только режимы, которые на каждом проходе пересканируют источник целиком, — сканеры каналов, плейлистов и истории YouTube. Сканеры Telegram читают только сообщения после `last_message_id`, а Telegram-бот скраппера YouTube принимает ссылку один раз, поэтому сами удалённую запись не пришлют: ссылку нужно заново отправить боту вручную. Для сканеров Telegram это открытый вопрос (Core, 10).

### YouTube

Скраппер YouTube — демон. У него несколько режимов работы, каждый включается отдельно в конфиге. Режимы выполняются последовательно, а не параллельно, чтобы не получить бан от YouTube.

#### Архитектура

Скраппер состоит из следующих частей:

- **Демон** — по очереди обходит включённые режимы, скачивает видео и кладёт их в очередь отправки в core.
- **Очередь загрузки** — хранится в памяти, не персистентна: после перезагрузки восстанавливается повторным сканированием.
- **Очередь отправки в core** — хранится в SQLite, персистентна (переживает перезагрузку).
- **Папка с файлами** — специальная папка внутри скраппера, где лежат файлы видео, ожидающих отправки в core.
- **Таблица пропущенных по размеру** — SQLite, см. «Файлы больше `max_file_size`».
- **Отправка в core** — скраппер сам отправляет записи в core (см. «Отправка в core»).
- **Telegram-бот** — принимает ссылки от пользователя (см. ниже).
- **Админка** — веб-интерфейс на FastAPI, доступный только из локальной сети.

#### Идентификация записи

- `source` = `youtube`.
- `source_url` = ссылка на видео в каноническом виде: `https://www.youtube.com/watch?v=<video_id>`. Ссылки вида `youtu.be/…` и `/shorts/…` приводятся к этому виду, иначе одно и то же видео из разных режимов получило бы разные ключи.
- `text` = склейка названия и описания видео, `title` = название, `author` = канал.
- `source_created_at` = дата публикации видео, `scraped_at` = момент получения записи скраппером.
- В `metadata` кладутся длительность и признак shorts.

#### Режимы работы

- **Сканер каналов** — обходит список YouTube-каналов и выкачивает все их видео.
- **Сканер плейлистов** — обходит список плейлистов и выкачивает все видео из каждого.
- **Сканер истории** — получает доступ к аккаунту YouTube и на каждом проходе читает всю доступную историю просмотров, сверяет её с core и выкачивает просмотренные видео, которых там нет.
- **Telegram-бот** — принимает ссылки на видео, которые пользователь отправляет ему в чат, и ставит их на загрузку (см. «Telegram-бот»).

#### Устройство загрузчика

Скраппер работает с двумя очередями:

- **очередь загрузки** — содержит объекты `youtube_video`; изначально в них есть только ссылка;
- **очередь отправки в core** — содержит те же объекты после скачивания: с аудио-/видеофайлом (см. ниже) и метаданными.

Порядок работы:

1. Демон по очереди обходит режимы, включённые в конфиге: каждый режим сканирует свой источник и находит видео.
2. Перед добавлением видео в очередь загрузки проверяется, что его нет ни в одной из двух очередей, ни в таблице пропущенных по размеру и ни в core. Проверка в core выполняется по `source` и `source_url`.
3. Пока суммарный размер скачанных файлов меньше X ГБ, загрузчик берёт видео из очереди загрузки и скачивает его. Перед скачиванием ещё раз проверяется по `source` и `source_url`, что видео нет в core и в очереди отправки в core. Если YouTube сообщает размер файла и он больше `max_file_size`, видео не скачивается, а заносится в таблицу пропущенных по размеру.
4. Пока видео не загружено полностью, оно остаётся в очереди загрузки. Как только загрузка завершена, размер проверяется ещё раз: если файл больше `max_file_size`, он удаляется, а видео заносится в таблицу пропущенных по размеру. Иначе объект сразу переносится в очередь отправки в core.

#### Аудио или видео

Для каждого режима настраивается, что именно скачивать: только аудио или видео целиком.

- **Сканер каналов** хранит режим загрузки для каждого канала в списке каналов. В конфиге задаётся значение по умолчанию. Это значение по умолчанию именно для пользователя, а не для системы: оно соответствует положению переключателя при добавлении канала в админке, поэтому поле режима в списке каналов не может быть пустым.
- **Сканер плейлистов** работает так же, как сканер каналов.
- **Сканер истории** настраивается отдельно для shorts и для обычных видео.
- **Telegram-бот** запрашивает режим отдельно для каждого видео.

#### Передача видео в core

Очередь отправки в core — SQLite, FIFO. Записи отправляются по общим правилам (см. «Отправка в core»): в core одновременно не больше K незавершённых записей скраппера, запись и её файлы остаются у скраппера, пока core не ответит `done` или `error`, а на `unknown` запись отправляется заново. При `error` исходник остаётся в core, повторно запись не отправляется, пока её не удалят вручную в веб-интерфейсе core (см. «Записи с ошибкой и повторная отправка»).

#### Telegram-бот

- Пользователь присылает боту ссылку на видео, бот спрашивает режим загрузки (аудио или видео) и ставит видео на загрузку.
- Бот хранит в SQLite список присланного, что ещё не завершено в core. Список переживает перезагрузку: ссылки от бота нельзя восстановить повторным сканированием, а очередь загрузки хранится в памяти.
- Когда core отвечает `done`, элемент удаляется из списка.
- Когда core отвечает `error`, бот явно сообщает об этом пользователю в чате (с текстом ошибки) и удаляет элемент из списка. Чтобы отправить видео заново, запись нужно удалить в веб-интерфейсе core и снова прислать ссылку боту.
- Если видео пропущено по размеру, бот тоже сообщает об этом пользователю.

#### Админка

Админка написана на FastAPI и открывается только из локальной сети. В ней можно:

- смотреть статистику по очередям (загрузки и отправки в core) и список видео, пропущенных по размеру;
- смотреть и редактировать списки каналов и плейлистов, в том числе выбирать режим загрузки (аудио или видео) при добавлении;
- включать и выключать режимы работы.

### Telegram

Скраппер Telegram — демон, устроенный так же, как скраппер YouTube: режимы выполняются последовательно, записи отправляются в core по общим правилам (см. «Отправка в core»), записи с файлами больше `max_file_size` заносятся в таблицу пропущенных по размеру. Админка — на FastAPI, только из локальной сети. Своего Telegram-бота у скраппера нет.

#### Доступ к Telegram

История каналов и чатов читается через MTProto (например, Telethon или Pyrogram) от имени пользовательского аккаунта: Bot API не умеет читать историю каналов, в которых нет бота. Файл сессии — секрет, в репозиторий не попадает. При `FloodWait` скраппер ждёт указанное время и продолжает.

#### Идентификация записи

- Record — одно сообщение канала или чата. Альбом (сообщения с общим `grouped_id`) — один record с несколькими файлами.
- `source` = `telegram`.
- `source_url` в каноническом виде:
  - публичные каналы и супергруппы — `https://t.me/<username>/<message_id>`;
  - приватные каналы и супергруппы — `https://t.me/c/<internal_id>/<message_id>`;
  - личные диалоги и обычные (не супер-) группы — у них нет ссылок t.me, а id сообщений свои у каждого аккаунта, поэтому используется псевдоссылка `tg://chat/<peer_id>/<message_id>`. Она уникальна и не меняется для нашего аккаунта, но по ней нельзя перейти.

  Для альбома берётся ссылка на первое сообщение.
- `text` = текст или подпись, `author` = канал или отправитель, `source_created_at` = дата отправки сообщения.
- `parent_source_url` = сообщение, на которое это ответ. У пересланных сообщений оригинал записывается в `metadata`, а ключ строится по текущему сообщению.

#### Режимы работы

- **Сканер каналов** — обходит список каналов. Для каждого хранится `last_message_id`: скраппер читает только новые сообщения, а при первом запуске — всю историю.
- **Сканер чатов** — то же самое для групп и личных диалогов из явного списка.

Перед добавлением сообщения в очередь отправки проверяется, что его нет в очереди, в таблице пропущенных по размеру и в core (по `source` и `source_url`). Проверка в core нужна и при наличии `last_message_id`, на случай сброса состояния.

Из-за `last_message_id` сканеры не увидят заново запись, удалённую вручную в core (см. «Записи с ошибкой и повторная отправка»). Есть идея на каждом проходе брать все id сообщений группы или чата и сверять их с core; пока это открытый вопрос.

#### Что скачивать

Для каждого канала или чата настраивается глубина: только текст, текст и фото, или всё (включая видео и документы). Отдельного ограничения по размеру у глубины нет: действует общее правило `max_file_size` — сообщение с файлом больше него пропускается целиком и заносится в таблицу пропущенных по размеру (на практике недостижимо: лимит файлов Telegram 2–4 ГБ). Значение по умолчанию в конфиге задаётся для пользователя, а не для системы: оно соответствует положению переключателя при добавлении канала в админке, поэтому поле в списке каналов не бывает пустым. Голосовые сообщения и кружки идут как аудио на транскрибацию.

#### Ограничения

- Отредактированные сообщения не перечитываются.
- Удалённые на источнике сообщения не отслеживаются.

#### Админка

- статистика по очереди отправки в core и список сообщений, пропущенных по размеру;
- список каналов и чатов, в том числе выбор глубины скачивания при добавлении;
- включение и выключение режимов работы.

## Клиенты

Клиент — это ИИ-агент со своим интерфейсом (сейчас Telegram-бот). Клиент отделён от core и является для балансировщика отдельным источником задач со своим адресом IP:PORT и наивысшим приоритетом. Он держит собственную очередь тяжёлых задач — транскрибация, OCR, эмбеддинги — и отдаёт их балансировщику по API источника (см. Core, 4.2). Core клиентские задачи не хранит. К core клиент обращается за поиском.

### Цикл обработки запроса

1. Пользователь отправляет боту голосовое сообщение.
2. Клиент кладёт задачу транскрибации в свою очередь. Клиенты самые приоритетные: балансировщик при следующем опросе `check_tasks()` вытеснит текущую работу и заберёт эту задачу.
3. Когда транскрипция готова, клиент запускает ИИ-агента с текстом запроса. Тяжёлые задачи, которые понадобятся агенту дальше (эмбеддинг запроса для семантического поиска, OCR присланной картинки), клиент так же ставит в свою очередь.
4. Агент ищет ответ с помощью инструментов (см. ниже).
5. Клиент отправляет пользователю одно сообщение с ответом и ссылками.

### Инструменты агента

- **Семантический поиск** по эмбеддингам в core. Ищутся только записи в `done` (см. Core, 5).
- **SQL-запросы** по полям record и `metadata` (дата публикации, источник и т. д.).
- **Получение fragment** в отрендеренном виде (например, страница PDF как изображение).
- **Получение element** (текст, картинка, транскрипция аудио).

### Формат ответа

Ответ приходит одним сообщением: сам ответ на вопрос и список ссылок на источники. Ссылки берутся из `source_url` записей (record), на которых основан ответ. Для записей с псевдоссылкой `tg://chat/…` (личные диалоги и обычные группы Telegram) вместо ссылки показываются название чата и дата сообщения.
