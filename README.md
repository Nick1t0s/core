# Система сбора, индексации и поиска информации

Система состоит из четырёх частей:

- **скрапперы** собирают данные из внешних источников;
- **core** хранит, индексирует и выполняет поисковые запросы от агента;
- **балансировщик** забирает тяжёлые задачи (транскрибация, OCR, эмбеддинги) только из core, где находятся собственные очереди core и отдельные очереди агентов и выполняет их на воркерах на GPU;
- **[агенты](docs/agent/README.md)** — пользовательские приложения с ИИ-поиском, ручным поиском и Telegram-ботом. Каждый режим зарегистрирован в core под отдельным agent_id со своим владельцем, уровнем доверия и очередью тяжёлых задач. Режимы могут работать в одном контейнере.

Пример использования: спросить LLM «скинь ссылку, я вчера видел видео про asyncio» — ИИ-агент находит его через поисковый API core, используя фильтры и семантический поиск.

Пользователи входят по логину и паролю и работают только со своими записями. Администратор имеет доступ ко всему, управляет пользователями и режимом регистрации (закрытая, открытая или по одноразовым приглашениям). Пользователи создают агентов и скрапперы через свой сайт. Core хранит регистрации и проверяет права; единственный балансировщик получает актуальный список источников задач из core. Подробнее — [пользователи и доступ](docs/core/11_users_and_access.md).

Методы, пути, параметры, заголовки и ответы всех внутренних запросов описаны в [HTTP API](docs/api.md).

## Core

core — ядро системы сбора, индексации и поиска информации. Можно сказать, что core — цифровой мозг, который помнит всё, что вам писали.

Пример: LLM можно задать вопрос «скинь ссылку, я вчера видел видео, которое рассказывает про asyncio», и ИИ-агент через поисковый API core с фильтрами и семантическим поиском быстро найдёт это видео.

Суть системы — перевод любого входного сообщения в мелкие неделимые части, которые можно обработать на GPU, проиндексировать и найти.

### Что делает core и чего не делает

Core делает:

- принимает записи от скрапперов: сразу регистрирует запись в статусе `parsing` и отвечает, не дожидаясь разбора (см. 3.1);
- сохраняет исходные файлы записи в своём хранилище;
- в фоне разбирает запись на дерево и сохраняет его одной транзакцией;
- при разборе записи извлекает из исходных файлов данные для photo и audio и кладёт их во временное хранилище `task_storage` (см. 1.5 и 3.3);
- хранит собственные очереди обработки записей и отдельные очереди каждого агента (транскрибация, OCR, эмбеддинги), вычисляет сложность и выдаёт задачи единственному балансировщику (см. 4.2);
- принимает результаты задач и достраивает дерево;
- вычисляет статусы record, file, fragment, element и text: результат задачи фиксируется одной транзакцией вместе с циклом готовности, ошибка задачи — одной транзакцией вместе с циклом очистки (см. 2.6);
- по таймеру запускает цикл очистки — страховку от строк в `error`, оставшихся ниже границы ошибки (см. 2.8);
- при старте удаляет записи, разбор которых прервало падение core (см. 3.2), и возвращает в очередь все задачи, которые были в работе (см. 4.5);
- возвращает в очередь задачи, взятые балансировщиком, по его запросу (`POST /api/task-sources/{task_source_id}/reset`, см. 4.2);
- отдаёт скрапперам настройку `max_file_size` (см. 3.6);
- выполняет поисковые запросы агента: в поиске участвуют только записи в статусе `done` (раздел 5, пока в разработке);
- хранит пользователей, приглашения и режим внешней регистрации; администратор управляет пользователями и имеет доступ ко всем данным (см. 11);
- регистрирует пользовательские агенты и скрапперы; owner и trust_level агентов хранит на сервере и сам применяет к запросам;
- разделяет записи по owner, а доступ агентов дополнительно ограничивает строгим условием record.trust_level < agent.trust_level;
- отдаёт единственному балансировщику единый список логических источников (core и агенты), наличие задач и приоритеты всех очередей;
- даёт кабинет пользователя для создания агентов и скрапперов, просмотра своих записей и ошибок, изменения trust_level и удаления записей (см. 6).

Core не делает:

- не знает, что такое YouTube, Telegram или любой другой источник: он видит только record (универсальные поля и `metadata`);
- не исполняет тяжёлые задачи сам: это делают воркеры под управлением балансировщика;
- не хранит долговременно производные данные (аудиодорожки, кадры, отрендеренные страницы): долговременно хранятся только исходные файлы, а данные для задач лежат во временном `task_storage` и удаляются очисткой хранилищ целым каталогом записи после её завершения.

### Термины

| Термин | Значение |
|---|---|
| **клиент (пользователь)** | Учётная запись человека в core, хранится в app_user. Клиент управляет своими агентами и скрапперами; у одного клиента может быть несколько агентов |
| **record** | Наиболее крупная логическая часть информации: письмо, видео на YouTube, пост в канале. Корень дерева |
| **file** | Файл, прикреплённый к record (например для видео с YouTube — сам ролик) |
| **fragment** | Промежуточное состояние файла: страница PDF, лист в Word, кадр. Бывает вложенным |
| **element** | Наименьшая часть содержимого. Три типа: text, photo, audio |
| **chunk** | Часть text или photo, для которой считается эмбеддинг: кусок текста или картинка |
| **task** | Задача воркера, результат которой порождает новые записи в дереве: транскрибация (`transcribe`) и OCR (`ocr`) |
| **task_storage** | Временное хранилище core на файловой системе: кадры, страницы и аудиодорожки для задач `ocr`, `transcribe` и для chunk-картинок. Один файл на element (photo или audio). Долговременным хранилищем не является: удаляется целым каталогом записи после её завершения |
| **граница ошибки** | Объект, в который пишется ошибка упавшего листа: file для листьев внутри файла, record для листьев собственного text записи (см. 2.4). У file при этом удаляется всё, что под ним; у record удаляются только chunk'и собственного text, а статус record не меняется |
| **снимок ошибки (`error_detail`)** | Описание ошибки на границе ошибки: где и почему упало, путь до упавшего листа, прогресс обработки. Нужен для отладки, так как упавшие объекты удаляются (см. 2.7) |
| **цикл готовности** | Распространение `done` от завершившегося листа вверх по дереву до record. Выполняется в той же транзакции, что и результат задачи (см. 2.6) |
| **цикл очистки** | Обработка ошибки листа одной транзакцией: вверх до границы с передачей сообщения об ошибке, затем вниз по слоям (всё под границей → `error`), затем удаление снизу вверх всего, что в `error` ниже границы (см. 2.6). Запускается ошибкой задачи и по таймеру (см. 2.8) |
| **`balancer_id`** | Постоянный идентификатор балансировщика из его конфига. При `claim` записывается в лист (`taken_by`); по нему балансировщик возвращает в очередь свои задачи (`reset`, см. 4.2) |
| **агент** | Зарегистрированный режим пользовательского приложения: свой agent_id, owner, trust_level и область очередей. Несколько режимов могут работать в одном контейнере, но для core и балансировщика это отдельные агенты |
| **owner** | ID владельца — клиента (пользователя core), ссылка на app_user.id. У record, agent и scraper ровно один owner; одинаковые материалы разных владельцев хранятся отдельно |
| **trust_level** | Неотрицательное целое число внутри одного owner: агенту доступны только его записи с record.trust_level строго меньше agent.trust_level |
| **источник задач** | Логическая область очередей внутри core: сам core или зарегистрированный agent_id с отдельным task_source_id (4.2). Все запросы балансировщика идут только в core. Не путать с record.source_id (`youtube`, `telegram`): весь core — один источник задач |
| **пачка** | Набор задач одного типа от одного источника, который выполняет один запуск воркера |
| **метаданные (`metadata`, `meta`)** | Данные в формате JSONB, специфичные для источника или типа файла, которым не нашлось места среди полей таблицы. Состав уточняется отдельно для каждого источника и типа данных (файла). Универсальные поля (`source_id`, даты, `title`, `author` и т. д.) метаданными не считаются |

### 1. Структура данных

#### 1.1. Дерево записи

Каждая запись представляется деревом. Корень — record. Путь от record до листа выглядит, например, так: `record → file → fragment → fragment → fragment → photo → chunk`.

Правила:

- **record** имеет до n + 1 детей: n файлов (file) и не более одного собственного text — текста самой записи (для YouTube-видео это склейка названия и описания, для сообщения Telegram — его текст или подпись). Если текста нет, text не создаётся. У записи должен быть хотя бы один ребёнок.
- **file** имеет сколько угодно детей fragment (минимум один).
- **fragment** имеет либо сколько угодно детей fragment, либо ровно один element (text, photo или audio). Смешивать fragment и element в одном родителе нельзя.
- **text** имеет сколько угодно детей chunk (минимум один). Сообщение нарезается на chunk'и в момент создания text.
- **photo** всегда имеет ровно один chunk с картинкой и ровно один `task_ocr`: картинка всегда и эмбедится, и отправляется на OCR. После получения результата OCR появляется ребёнок text, но только если распознан непустой текст. Отсутствие text у photo допустимо.
- **audio** содержит аудиоданные и имеет ребёнка `task_transcribe`. После получения транскрипции появляется ребёнок text (если транскрипция непуста).
- **chunk**, **task_transcribe**, **task_ocr** — листья, детей не имеют.

Видео — это набор фотографий (например, кадр каждые i секунд) и аудио.

Допустимые связи:

| Родитель | Дети | Количество |
|---|---|---|
| record | file, text | file: любое число; text: 0 или 1; в сумме не менее 1 |
| file | fragment | не менее 1 |
| fragment | fragment ИЛИ один element (text, photo, audio) | не менее 1 fragment, либо ровно 1 element |
| text | chunk | не менее 1 |
| photo | chunk (картинка); task_ocr; text | chunk: ровно 1; task_ocr: ровно 1; text: 0 или 1, появляется после OCR, если текст распознан |
| audio | task_transcribe; text | task_transcribe: ровно 1; text: 0 или 1, появляется после транскрибации |
| chunk, task_transcribe, task_ocr | — | листья |

Пример: видео с YouTube.

```
record
├─ text (название + описание)
│   └─ chunk, chunk, …
└─ file (видео)
    ├─ fragment (аудиодорожка)
    │   └─ audio
    │       ├─ task_transcribe
    │       └─ text                  ← появляется по результату транскрибации
    │            └─ chunk, chunk, …
    ├─ fragment (кадр, t = 0 с)
    │   └─ photo
    │       ├─ chunk                 ← картинка
    │       ├─ task_ocr              ← всегда
    │       └─ text                  ← появляется, только если OCR вернул текст
    │            └─ chunk, chunk, …
    └─ fragment (кадр, t = 5 с) …
```

#### 1.2. Chunk

Chunk — объект ровно с тремя полями:

- `text` — текст, максимум x символов (параметр конфигурации);
- `picture` — картинка;
- `embed` — эмбеддинг (список чисел).

`text` и `picture` взаимоисключающие: должно быть заполнено ровно одно. Если заполнены оба или ни одного, при создании должна возникать ошибка. Chunk в момент создания не имеет эмбеддинга (`embed` пуст): его считает воркер.

Картинка chunk'а в БД не хранится: на уровне таблицы поле `picture` — это признак `is_picture`. Пока запись обрабатывается, картинку для воркера core берёт из `task_storage` (файл родительского photo), а после завершения записи строит из исходного файла по `meta` родительского photo (см. 3.3, 7).

Внутри chunk'а текст больше не делится: это наименьшая часть, которая индексируется.

#### 1.3. Атрибуты record

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `id` | UUID (v7) | да | Суррогатный первичный ключ, выдаётся core |
| `owner` | UUID | да | Владелец записи, внешний ключ на пользователя; core подставляет из регистрации скраппера |
| `scrapper` | UUID | да | scrapper_id скраппера, впервые добавившего запись; core подставляет из проверенной регистрации, внешний ключ на scraper.scrapper_id |
| `trust_level` | integer ≥ 0 | да | Уровень доверия записи внутри владельца; назначается скраппером |
| `source_id` | text | да | Имя источника: `youtube`, `telegram` |
| `source_url` | text | да | Каноническая ссылка на конкретную запись внутри источника |
| `source_created_at` | timestamptz | нет | Когда запись создана на оригинальном источнике; если источник не отдаёт дату — пусто |
| `scraped_at` | timestamptz | да | Когда скраппер получил запись |
| `registered_at` | timestamptz | да | Когда core зарегистрировал запись: момент приёма (вставки record в статусе `parsing`), до разбора |
| `processed_at` | timestamptz | нет | Когда обработка завершилась (record перешёл в `done` или `error`); пока идёт — `NULL` |
| `status` | enum | да | `parsing`, `processing`, `done`, `error` (см. 2.1) |
| `title` | text | нет | Заголовок, если есть |
| `author` | text | нет | Автор или канал |
| `parent_source_url` | text | нет | Запись, к которой относится эта (ответ, комментарий) |
| `metadata` | JSONB | нет | Данные, специфичные для источника, которым не нашлось места среди полей таблицы. Состав уточняется отдельно для каждого источника |
| `error` | text | нет | Текст ошибки: если запись в статусе `error` (все дети в `error`, см. 2.5) или если упал собственный text записи (тогда запись может быть и в `done`, см. 2.4) |
| `error_detail` | JSONB | нет | Снимок ошибки (см. 2.7) в тех же случаях |

Собственного текста записи в таблице нет: он хранится как дочерний text. Все даты хранятся в UTC. Изменения записей на источнике не отслеживаются.

#### 1.4. Первичный ключ и идентификация

- Первичный ключ — `id` (UUID, лучше v7, он сортируется по времени). Он нужен потому, что на record ссылаются другие таблицы, а тащить в каждую два длинных текстовых поля неудобно. `id` не зависит от правил нормализации ссылок.
- Тройка `(owner, source_id, source_url)` имеет ограничение `UNIQUE`, все поля `NOT NULL`. Скраппер передаёт source_id и source_url, а owner core берёт из его аутентифицированной регистрации. Скраппер id записи не генерирует. Одинаковые материалы разных владельцев хранятся независимо, со своими деревьями и файлами.
- `source_url` каждый скраппер обязан приводить к каноническому виду (правила — в разделах скрапперов), иначе одна запись зарегистрируется дважды.
- Повторная отправка записи с уже существующим `(owner, source_id, source_url)` ничего не меняет, включая trust_level и scrapper (в том числе пока запись ещё разбирается): core отвечает, что запись существует у этого владельца. Наличие такой ссылки у другого владельца не влияет на приём. Обновления записей на источнике не отслеживаются.
- Поле source_id ранее называлось source. Оно обозначает тип источника (`youtube`, `telegram`), а не scrapper_id или task_source_id балансировщика. Правила доступа — в разделе 11; таблица связи владельцев с записями не используется.

#### 1.5. Таблицы и их поля

Каждый тип объектов дерева лежит в своей таблице: `record`, `file`, `fragment`, `text`, `element`, `chunk`, `task`. Общих наборов полей нет: ниже для каждой таблицы перечислены все её поля. Поля record описаны в 1.3.

**Статусы в таблицах.** У `file`, `fragment`, `element` и `text` три статуса: `processing`, `done`, `error`. У `record` их четыре: ещё `parsing` — запись принята и разбирается. У листьев `chunk` и `task` четыре статуса: `wait`, `processing`, `done`, `error` (см. раздел 2). Статус `error` ниже границы ошибки (у fragment, element, text, chunk и task) существует только внутри транзакции цикла очистки: в том же коммите такие строки удаляются (см. 2.6). Исключение — собственный text записи: он остаётся в `error` без chunk'ов как отметка для правила готовности record (см. 2.5).

**Даты.** Дата создания у `file`, `fragment`, `element` и `text` не хранится: её можно узнать по record (`registered_at`). У них есть только `finished_at`. `created_at` остаётся у `chunk` и `task`, потому что по нему строится очередь.

**Поле `meta`.** У `file`, `fragment`, `element` и `text` поле `meta` имеет тип JSONB. Его состав определяется источником и типом файла и уточняется отдельно для каждого из них; из него core получает данные, нужные для работы с этим объектом (в том числе для извлечения данных из исходного файла).

**Таблица `file`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id` | Внешний ключ на record |
| `ord` | Порядок среди файлов записи |
| `status` | `processing`, `done`, `error` |
| `name`, `mime`, `size` | Имя исходного файла (расширение из него идёт в путь), тип и размер |
| `error`, `error_detail` | Текст ошибки и снимок ошибки (см. 2.7), если file в статусе `error` |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSONB |

**Таблица `fragment`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id` | Внешний ключ на record (заполнен всегда) |
| `file_id` | Внешний ключ на file (заполнен всегда) |
| `parent_fragment_id` | Внешний ключ на родительский fragment; пусто у фрагментов верхнего уровня |
| `ord` | Порядок среди соседей |
| `status` | `processing`, `done`, `error` |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSONB |

**Таблица `element`** (только photo и audio):

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id` | Внешний ключ на record (заполнен всегда) |

| `fragment_id` | Внешний ключ на fragment, в котором лежит element |
| `kind` | `photo` или `audio` |
| `ord` | Порядок среди соседей |
| `status` | `processing`, `done`, `error` |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSONB |

**Таблица `text`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `kind` | Тип text (см. ниже) |
| `record_id` | Внешний ключ на record; заполнен всегда |
| `fragment_id` | Внешний ключ на fragment; заполнен, если непосредственный предок text не record: у text как element фрагмента это его fragment, у результата задачи это fragment, в котором лежит element-владелец |
| `element_id` | Внешний ключ на element (photo или audio); заполнен, только если text — результат OCR или транскрибации |
| `status` | `processing`, `done`, `error` |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSONB |

Значения `kind` и заполненные ссылки согласованы:

| `kind` | Что это | `record_id` | `fragment_id` | `element_id` |
|---|---|---|---|---|
| `record` | Собственный text записи (название и описание, текст сообщения) | да | пусто | пусто |
| `element` | text как element фрагмента (например, текстовый слой страницы) | да | да | пусто |
| `task_result` | text, созданный задачей: результат OCR или транскрибации, ребёнок photo или audio | да | да | да |

**Таблица `chunk`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |

| `ord` | Порядок среди соседей |
| `status` | `wait`, `processing`, `done`, `error` |
| `text` или `is_picture` | Текст chunk'а либо признак картинки (ровно одно из двух) |
| `embed`, `embed_model` | Эмбеддинг и название модели, которая его посчитала |
| `taken_at` | Когда chunk взяли в работу; `NULL` в статусе `wait` |
| `taken_by` | `balancer_id` балансировщика, который взял chunk; `NULL` в статусе `wait` |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |

**Таблица `task`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `element_id` | Внешний ключ на audio или photo |
| `type` | `transcribe` или `ocr` |
| `status` | `wait`, `processing`, `done`, `error` |
| `taken_at` | Когда задачу взяли в работу; `NULL` в статусе `wait` |
| `taken_by` | `balancer_id` балансировщика, который взял задачу; `NULL` в статусе `wait` |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |

Поля `error` и `error_detail` есть только у file и record, то есть у границ ошибки. У file они заполняются, когда file в `error`. У record — когда упал его собственный text (статус record при этом не меняется, и запись может завершиться в `done`) или когда record в `error`. Всё, что под ошибочным file, и chunk'и упавшего собственного text удаляются циклом очистки (см. 2.6), а то, что о них нужно для отладки, сохраняется в снимке ошибки на границе (см. 2.7). У text полей ошибки нет: ошибка собственного text записи пишется в record.

**Пути файлов.** Пути в БД не хранятся: они выводятся из идентификаторов.

- Исходный файл: `/storage/<source_id>/<record_id>/<file_id>.<исходное расширение>`; расширение берётся из `file.name`. Хэш файла не хранится: изменения записей не отслеживаются.
- Файл `task_storage`: `/task_storage/<source_id>/<record_id>/<element_id>.<расширение>`; расширение определяется настроенным форматом (один для изображений, один для аудио).

**`task_storage`** — не таблица БД, а временный каталог файловой системы. Для каждого element (photo или audio) лежит не более одного файла с данными для задач: кадр или страница как изображение, аудиодорожка как аудио. Хранилище принадлежит core, правила хранения — в разделе 3.

### 2. Статусы

#### 2.1. Значения статусов

**Листья chunk, task_transcribe, task_ocr** имеют четыре статуса:

| Статус | Значение |
|---|---|
| `wait` | Задача ждёт взятия: лежит в очереди, `taken_at` и `taken_by` пусты |
| `processing` | Задача в работе: её взял балансировщик, `taken_at` и `taken_by` заполнены |
| `done` | Задача успешно завершена |
| `error` | Задача завершена с ошибкой; существует только внутри транзакции цикла очистки (см. 2.6) |

**Остальные объекты дерева** (record, file, fragment, element, text) имеют три статуса (у record есть ещё четвёртый, см. ниже); `wait` у них не бывает:

| Статус | Значение |
|---|---|
| `processing` | Объект не завершён: не завершены его дети |
| `done` | Объект успешно завершён |
| `error` | Объект завершён с ошибкой. Надолго в `error` остаются только file, record и собственный text записи; остальные строки в `error` удаляются в той же транзакции цикла очистки (см. 2.6) |

У **record** есть ещё четвёртый статус — `parsing`: запись принята, core сохраняет её исходные файлы или разбирает её; детей у record в этом статусе нет. Переходы record:

- `parsing → processing` — коммит дерева (см. 3.1);
- `parsing → error` — разбор записи упал: коммитится дерево из пустышек в `error`, и проверка готовности в той же транзакции переводит record в `error` (см. 3.5, 2.5);
- `processing → done` — нет детей в `processing`, и хотя бы один ребёнок в `done` (см. 2.5);
- `processing → error` — нет детей в `processing`, и все дети (собственный text, если есть, и все file) в `error` (см. 2.5).

Других путей в `error` у record нет: ошибка собственного text пишется в record, но его статус не меняет (см. 2.4), а пустая запись не принимается (см. 3.1).

Если core упал во время приёма или разбора, record в `parsing` удаляется при старте (см. 3.2).

`done` и `error` — терминальные: после перехода статус не меняется. Запись в `error` можно только удалить вручную (см. 6).

Переходы листьев: `wait → processing` (claim), `processing → done` (result), `processing → error` (fail, цикл очистки), `processing → wait` (`POST /api/task-sources/{task_source_id}/reset`, возврат при старте core, см. 4.2, 4.5). Кроме того, цикл очистки на пути вниз переводит в `error` все листья под границей в любом статусе (см. 2.6).

#### 2.2. Вся работа сидит в листьях

Задачи воркеров привязаны только к листьям:

- эмбеддинг — chunk в статусе `wait` или `processing`;
- транскрибация — лист `task_transcribe`;
- OCR — лист `task_ocr`.

Все остальные объекты (record, file, fragment, audio, photo, text) не имеют собственной работы и являются контейнерами. Это закрывает проблему «пустого успеха»: у audio до завершения транскрибации всегда есть ребёнок `task_transcribe` не в статусе `done`, у photo — `task_ocr`, поэтому проверка «все дети готовы» не может ошибочно пометить контейнер готовым. Никаких дополнительных флагов «готов к обработке» не нужно.

#### 2.3. Правило готовности

Контейнер внутри file (или собственный text записи) готов, когда число его готовых детей равно числу всех его детей, то есть когда у него нет ни одного ребёнка не в статусе `done`. Правило одинаково для всех контейнеров, включая «листовые» fragment (у которых единственный ребёнок — element): особых случаев нет.

#### 2.4. Граница ошибки и ошибки

- **Ошибка листа внутри file** (в любом fragment, element или text этого файла) делает ошибочным этот file. Граница — file: в него пишутся текст ошибки и снимок (см. 2.7), а всё, что под ним, в той же транзакции уходит в `error` и удаляется циклом очистки (см. 2.6).
- Граница — file, а не element: лучше открыто потерять файл целиком, чем незаметно терять его части.
- **Ошибка листа собственного text записи** (chunk этого text) делает ошибочным этот text: он переходит в `error`, его chunk'и удаляются, а текст ошибки и снимок пишутся в record — для собственного text границей служит record. Статус record при этом не меняется: файлы записи обрабатываются дальше.
- На статус record ошибки file и собственного text сами по себе не влияют. Record становится `error`, только если все его дети в `error` (см. 2.5).
- Ошибка воркера всегда серьёзная: сбои воркера (OOM, неправильный файл и т. п.) обрабатывает балансировщик, разбивая упавшую пачку на пачки по одной задаче; `fail` приходит в core только по задаче, которая упала и в одиночку (см. «Балансировщик»).

#### 2.5. Готовность record

Record переходит в терминальный статус, когда у него нет ни одного ребёнка (file или собственного text) в `processing`. Тогда:

- если все дети в `error` (собственный text, если он есть, и все file), `status` = `error`: в `error` пишется «все дети завершились ошибкой», в `error_detail` — сводка `{"stage": "children", "text": …, "files": [{"id": …, "error": …}]}`, где `text` — снимок ошибки собственного text, который уже лежал в record (если text был), а `files` — список упавших file; полные снимки ошибок file остаются у самих file;
- иначе (хотя бы один ребёнок в `done`) `status` = `done`;
- в обоих случаях `processed_at` = текущий момент.

Это единственный случай `error` у record. Записи без детей не бывает: пустая запись не принимается (см. 3.1), а если разбор записи упал, все её дети записываются пустышками в `error` (см. 3.5).

Проверка выполняется только для record в `processing`: record в `parsing` детей ещё не имеет и ею не затрагивается. Она запускается из цикла готовности и цикла очистки (см. 2.6), а также сразу в транзакции коммита дерева (см. 3.1), в том числе дерева из пустышек (см. 3.5): если при разборе ни одного листа не появилось, циклов не будет, и без этой проверки record навсегда остался бы в `processing`.

У записи в `done` есть хотя бы один ребёнок в `done`; отдельные file в `error` и упавший собственный text (его ошибка лежит в `error` самой записи) у неё бывают. Искать в ней при этом может быть нечего: например, у file с беззвучным аудио нет ни одного chunk'а.

У record в `error` все дети — границы в `error` без детей: file в `error` и собственный text в `error` (если он был).

#### 2.6. Обновление статусов: цикл готовности и цикл очистки

Статусы chunk и task (листья) меняются только по операциям API источника (см. 4.2), при восстановлении (см. 4.5) и циклом очистки: `claim` переводит лист из `wait` в `processing`, `result` — в `done`, `fail` — в `error`, `POST /api/task-sources/{task_source_id}/reset` возвращает в `wait`. Статусы всех остальных объектов (element, fragment, text, file, record) вычисляют два цикла:

- **цикл готовности** распространяет `done` вверх по дереву; его запускает результат задачи (`result`);
- **цикл очистки** распространяет ошибку вверх до границы, затем `error` вниз по слоям и удаляет всё, что в `error` ниже границы; его запускает ошибка задачи (`fail` от балансировщика или `fail`, который core выполняет сам, если для задачи нет файла в `task_storage`, см. 4.2), а также таймер (см. 2.8).

**Правило циклов:** операция над листом (`result` или `fail`) и весь вызванный ею цикл — одна транзакция с одним коммитом. Состояний, когда лист уже завершён, а его предки ещё не пересчитаны, или когда под ошибочной границей остались строки, в БД не бывает.

**Блокировки.** Транзакция первым делом блокирует строку своей единицы блокировки — file или собственного text записи (`SELECT … FOR UPDATE`). Её находят по внешним ключам: у element и fragment есть `file_id`, у text — `fragment_id` (или `kind = 'record'`, тогда единица блокировки — сам text). Строка record блокируется в конце: перед проверкой готовности record, а в цикле очистки собственного text — перед записью ошибки в record.

Зачем это нужно. Без блокировки два последних соседа (например, два последних chunk одного text), завершившиеся одновременно в двух транзакциях, видят друг друга ещё в `processing`: чужая транзакция не закоммичена. Ни одна из них не переводит родителя в `done`, и он зависает навсегда. С блокировкой транзакции внутри одного file идут по очереди, и вторая видит коммит первой (в PostgreSQL на уровне READ COMMITTED каждый запрос видит всё, что закоммичено до его начала). Блокировка record нужна по той же причине: одновременно могут завершиться разные дети одной записи.

Порядок блокировок всегда один — строка единицы (file или собственного text записи), затем record, — и каждой транзакции нужна ровно одна единица, поэтому взаимных блокировок нет. Операции, которые трогают только лист (`claim`, `reset`, возврат при старте core), file и text не блокируют; `claim` выбирает строки с `FOR UPDATE SKIP LOCKED` и не ждёт транзакцию цикла. Цена: результаты внутри одного file фиксируются последовательно, но каждая транзакция занимает миллисекунды, и это не узкое место.

**Цикл готовности.** В транзакции результата листа (см. 4.3):

1. Лист → `done`.
2. Проверяется родитель: если у него нет ни одного ребёнка не в `done` (для record — ни одного в `processing`), он переводится в `done` (`finished_at = now()`), и проверка повторяется для родителя родителя.
3. Если условие не выполнено, цикл останавливается.
4. Дойдя до record, проверяем его готовность по 2.5: он становится `done` (или `error`, если все его дети в `error`), заполняем `processed_at`.

Проверка родителя (пример для element):

```sql
UPDATE element e
SET status = 'done', finished_at = now()
WHERE e.id = :parent_id
  AND e.status = 'processing'
  AND NOT EXISTS (SELECT 1 FROM chunk c WHERE c.element_id = e.id AND c.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM task  t WHERE t.element_id = e.id AND t.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM text  x WHERE x.element_id = e.id AND x.status <> 'done');
```

Если обновилась одна строка, идём выше. Условие идемпотентно (`status = 'processing'`), поэтому повторный результат ничего не портит. Таймера у цикла готовности нет: лист и цикл — один коммит, поэтому зависших контейнеров не бывает.

**Цикл очистки.** В транзакции `fail` (см. 4.2), одинаково для обеих границ:

1. Блокируется единица: file или собственный text записи. Если она уже в `error`, `fail` игнорируется (у цикла по таймеру своё правило, см. 2.8).
2. Собирается снимок ошибки (см. 2.7): путь от границы до упавшего листа и счётчики листьев по статусам (всех листьев file или всех chunk'ов собственного text). Это делается до любых изменений.
3. **Вверх.** Упавший лист и все его предки до границы переводятся в `error` (`finished_at = now()`). Сообщение об ошибке передаётся вверх и записывается только в границу:
   - лист внутри file: file → `error`, заполняются `error`, `error_detail` и `finished_at`;
   - лист собственного text: text → `error`, затем блокируется record, и в него пишутся `error` и `error_detail`; статус record не меняется.

   В промежуточные fragment, element и text текст ошибки не пишется: путь до листа есть в снимке.
4. **Вниз по слоям.** Всё под границей переводится в `error`, слой за слоем. Под file — fragment верхнего уровня, затем вложенные fragment, у которых родительский fragment в `error`, затем element, у которых fragment в `error`, затем text, у которых родитель в `error`, затем chunk и task, у которых родитель в `error`. Под собственным text — его chunk'и. Так в `error` попадают и задачи в `wait` и `processing`, и уже готовые листья.
5. **Удаление снизу вверх.** Удаляется всё, что в `error` ниже границы: сначала chunk и task, затем text (кроме собственного text записи), затем element, затем fragment — от вложенных к верхнему уровню. Строка file остаётся: это граница, в ней ошибка и снимок. Собственный text записи остаётся в `error` без chunk'ов: это отметка для правила готовности record (2.5).
6. Блокируется record (если ещё не заблокирован на шаге 3) и проверяется его готовность (см. 2.5): если граница была последним незавершённым ребёнком, record становится `done` или `error`.

Так ошибка хранится в единственном экземпляре — у file или у record. Результат или ошибка, пришедшие позже для удалённого или уже не находящегося в `processing` листа, игнорируются: задачи, которые в момент цикла очистки выполнялись на воркере, не прерываются, но их результат при получении отбрасывается.

Если core упал до коммита, транзакция откатывается целиком: лист остаётся в `processing` и при старте core возвращается в очередь (4.5), задача выполняется заново. Проверка и ремонт дерева не нужны; цикл очистки по таймеру (2.8) — страховка от ошибок в коде, а не часть штатной работы.

#### 2.7. Снимок ошибки

Цикл очистки удаляет всё под ошибочным file и chunk'и упавшего собственного text, поэтому всё, что нужно для отладки, сохраняется на самой границе в поле `error_detail` (JSONB): у file или, для собственного text, у record. Снимок собирается в той же транзакции, до любых изменений. Он же пишется у пустышек разбора: у file и, если упал разбор всей записи, у record (см. 3.5). У record в `error` (все дети в `error`) `error_detail` — сводка `stage = children` (см. 2.5): снимок собственного text, если он был, и список упавших file; полные снимки file остаются у самих file.

```json
{
  "stage": "ocr",
  "message": "…",
  "attempts": 2,
  "at": "2026-10-12T10:15:03Z",
  "leaf": {"type": "task_ocr", "id": "…", "taken_at": "…"},
  "path": [
    {"level": "fragment", "id": "…", "meta": {"t": 1235.0}},
    {"level": "photo",    "id": "…", "meta": {}}
  ],
  "progress": {"done": 1840, "wait": 310, "processing": 4}
}
```

| Поле | Значение |
|---|---|
| `stage` | Где упало: `parse` (разбор), `transcribe`, `ocr`, `embed`, `task_storage` (нет данных для задачи, см. 4.2), `sweep` (ошибку нашёл цикл очистки по таймеру, а граница ещё не была в `error`, см. 2.8), `children` (у record все дети в `error`, см. 2.5) |
| `message` | Текст ошибки: от балансировщика (задача упала и в пачке, и в одиночку) или исключение core |
| `attempts` | Сколько раз балансировщик запускал задачу: 2 — в пачке и в одиночку, 1 — если пачка с самого начала состояла из одной этой задачи (приходит в `fail`) |
| `at` | Момент ошибки |
| `leaf` | Упавший лист: тип, id, `taken_at`; у ошибок разбора отсутствует |
| `path` | Путь от границы до упавшего листа: уровень, id и `meta` каждого объекта |
| `progress` | Сколько листьев границы было в каждом статусе в момент ошибки |

Исходный файл после ошибки хранится (см. 3.3). По `path[].meta` той же функцией извлечения из него можно получить ровно те данные (кадр, страницу, аудио), на которых упала задача, и воспроизвести ошибку. По id из снимка находятся строки в логах core и балансировщика: в каждой строке лога, относящейся к объекту дерева, должны быть `record_id`, `file_id` и id самого объекта.

#### 2.8. Цикл очистки по таймеру

Таймерное задание (период — параметр конфигурации, около часа; также запускается при старте core) ищет строки в `error`, оставшиеся ниже границы, и запускает от них цикл очистки. В штатной работе оно ничего не находит: цикл очистки удаляет всё в своём же коммите (2.6). Это страховка от ошибок в коде и ручных правок БД.

Порядок:

1. Найти любой fragment в `error`. Спуститься от него через вложенные fragment до element (если element нет — взять сам fragment) и запустить от него цикл очистки по 2.6 своей транзакцией. После коммита снова искать fragment в `error`.
2. Когда fragment в `error` не осталось, так же обойти element в `error`, затем text в `error` (кроме собственного text записи: он законно остаётся в `error` как отметка, см. 2.5), затем chunk и task в `error`.

Отличие от цикла по `fail`: если граница уже в `error`, цикл не игнорируется и не переписывает её ошибку и снимок, а только проходит вниз, удаляет и проверяет готовность record (шаги 4–6). Если граница ещё не в `error` (такого быть не должно), цикл проходит целиком и пишет в неё сообщение «найдено циклом очистки по таймеру» со `stage = sweep`.

С очисткой хранилищ (3.3) это задание не связано: оно работает только со строками БД.

### 3. Приём записи

#### 3.1. Общая схема

Скраппер отправляет `POST /api/records` с заголовками `X-Scrapper-ID: <scrapper_id>` и `Authorization: Bearer <token скраппера>`. Тело — `multipart/form-data`: первая часть `record` содержит JSON метаданных и описание файлов, следующие части `files` — их бинарные данные. Поля, порядок частей, ответы и примеры запросов закреплены в [HTTP API](docs/api.md).

Разбор записи может идти минуты (видео длиной 3 часа в 1080p — порядка 4 минут только на извлечение кадров), поэтому core отвечает скрапперу сразу после приёма файлов, а разбирает запись в фоне.

1. Скраппер аутентифицируется парой scrapper_id/token и отправляет в core запись: метаданные (`source_id`, `source_url`, даты, `title`, `author`, `metadata`), trust_level, текст и файлы. Core проверяет активность скраппера и пользователя, соответствие source_id регистрации скраппера, подставляет owner и scrapper = scrapper_id из проверенной регистрации и проверяет, что trust_level — неотрицательное целое число. Переданные клиентом owner и scrapper не используются; чужого владельца или другого скраппера указать нельзя.
2. Core проверяет, что запись не пуста (есть текст или хотя бы один файл), и размер каждого файла по `max_file_size` (см. 3.6) по заявленным размерам, до приёма самих файлов. Пустая запись отклоняется статус-кодом ошибки (HTTP 422), запись с файлом больше лимита — HTTP 413; ничего не сохраняется.
3. Core вставляет record с owner, scrapper и trust_level в статусе `parsing` (`INSERT … ON CONFLICT (owner, source_id, source_url) DO NOTHING`) и коммитит. Если запись с таким `(owner, source_id, source_url)` уже есть (в любом статусе, включая `parsing`), core отвечает, что запись существует у этого владельца, и файлы не принимает; trust_level и scrapper повторная отправка не меняет, даже если её выполняет другой скраппер владельца. Копия другого владельца не считается конфликтом. На этом шаге core выдаёт идентификаторы (UUID v7) записи и её файлов: по ним строятся пути.
4. Только после коммита core записывает исходные файлы в хранилище (см. 3.3). Если загрузка оборвалась, core удаляет record и его каталоги; скраппер получит `unknown` и отправит запись заново.
5. Когда исходные файлы записаны, core отвечает скрапперу `202 Accepted`. Дальше скраппер следит за статусом записи (см. 3.2).
6. Core в фоне **разбирает** запись целиком: нарезает текст на chunk'и, раскладывает файлы на fragment и element (страницы PDF, листы Word, кадры и аудио видео и т. д.), определяя для каждого fragment и element в `meta`, как получить его данные из исходного файла (состав `meta` зависит от источника и типа файла и уточняется отдельно). Идентификаторы (UUID v7) всех объектов дерева, включая `element_id`, core выдаёт на этом шаге. Для каждого photo и audio core по `meta` один раз извлекает данные из исходного файла и кладёт их в `task_storage` (см. 1.5 и 3.3). Дерево строится в памяти, в БД на этом шаге ничего не пишется.
7. Когда разбор завершён полностью, всё дерево записывается **одной транзакцией**: все дети record и их данные, задачи в очередях (chunk и task в статусе `wait`), а record переходит из `parsing` в `processing`. В той же транзакции сразу проверяется готовность record (см. 2.5): если листьев не появилось (все дети — пустышки разбора), record сразу становится `error`.
8. После коммита задачи доступны балансировщику, а файлы для них уже лежат в `task_storage`.

Удаление записи через API согласовано с фоновым приёмом и разбором по record_id: при удалении обработчик останавливается и больше не пишет её файлы или дерево. Коммит дерева проверяет, что исходный record ещё существует. Удалённую запись не восстанавливают; остатки каталогов забирает очистка хранилищ (см. 11.5).

Требования:

- В БД нет частично записанных деревьев: у record в `parsing` детей нет, а дерево появляется целиком одним коммитом.
- Очереди задач — таблицы той же БД (`task` и `chunk` в статусе `wait`), поэтому дерево и его задачи фиксируются атомарно.
- Каталоги записи создаются только после коммита record, а файлы в `task_storage` — до коммита дерева. Поэтому к моменту, когда задача стала доступна балансировщику, её данные уже лежат на диске, и очистка их не тронет, пока запись не завершится (см. 3.3).
- `registered_at` = момент вставки record (шаг 3).
- Повторную отправку той же записи отсекает уникальность `(owner, source_id, source_url)` на шаге 3: второй запрос получает «запись существует», даже если первая ещё разбирается. Отдельная блокировка на время приёма не нужна.

#### 3.2. Статус для скраппера и прерванный разбор

Статус запрашивается через `GET /api/records/status?source_id=...&source_url=...` (оба query-параметра обязательны, ссылка URL-кодируется) либо `GET /api/records/{record_id}/status`. Заголовки те же, что у загрузки. Ответ `200`: `{"record_id":"<UUID>","status":"processing"}`; для отсутствующей записи — `{"record_id":null,"status":"unknown"}`.

Пока идёт разбор, record уже существует в статусе `parsing`, поэтому скраппер, проверяя статус, не отправит запись повторно. Ответ на запрос статуса строится по record только своего owner, полученного из регистрации скраппера: `unknown` (записи нет у этого владельца), `processing` (`parsing` или `processing`), `done` или `error`. Это относится и к проверкам по source_id/source_url, и к проверкам по record_id. Существование, статус и ошибки чужой копии не раскрываются.

Если core упал во время приёма или разбора, record остаётся в `parsing`. При старте core все такие записи заведомо прерваны (core работает в одном экземпляре), поэтому они удаляются вместе с каталогами в хранилище исходных файлов и в `task_storage`. Это делается до того, как core начнёт принимать новые записи, иначе под удаление попала бы запись, принятая уже после старта. Скраппер после этого увидит `unknown` и отправит запись заново; новая попытка получит новый `record_id` и будет писать в свои каталоги.

Прерванная запись удаляется, а не переводится в `error`: на `error` скраппер запись не пересылает (пока её не удалят вручную, см. 6), и из-за падения core она выпала бы из индекса. Пустышки в `error` пишутся, только если упал сам разбор (см. 3.5): повторная отправка того же файла ничего не изменит.

#### 3.3. Хранение файлов

На файловой системе core два хранилища:

- **хранилище исходных файлов** — долговременное;
- **`task_storage`** — временное, для данных задач.

Долговременно core хранит **либо исходный файл, либо ничего**. При приёме видео сохраняется само это видео. Аудиодорожки, кадры и отрендеренные страницы долговременно не хранятся.

Исходные файлы:

- Лежат по пути `/storage/<source_id>/<record_id>/<file_id>.<исходное расширение>`. В БД путь и хэш не хранятся, путь выводится из `source_id`, `record_id`, `file_id` и расширения из `file.name`. Временной области приёма нет: файлы сразу кладутся по этому пути. Каталог записи создаётся только после коммита record (см. 3.1).
- Хранятся, пока существует record, в том числе после ошибки file или всей записи: исходник нужен для воспроизведения ошибки по снимку (2.7). Перезапуска обработки нет. При авторизованном удалении записи в любом статусе (6, 11.5) её каталог удаляет очистка: записи больше нет в БД.

`task_storage`:

- Для каждого photo и audio core при разборе один раз извлекает данные из исходного файла по `meta` и кладёт их в `task_storage` по пути `/task_storage/<source_id>/<record_id>/<element_id>.<расширение>` (см. 1.5). Файлы создаются до коммита дерева; при `claim` ничего не извлекается, core только читает готовый файл.
- Файл один на element. Его читают все листья этого element: chunk-картинка и `task_ocr` у photo, `task_transcribe` у audio.
- Файлы живут, пока record не завершится (`done` или `error`), и удаляются очисткой целым каталогом записи. Задачи, вернувшиеся в `wait`, и повторные запуски по одной задаче после падения пачки берут уже готовые данные. Поштучно, по готовности element, файлы не удаляются: каждый скраппер держит в core не больше K незавершённых записей (см. «Скрапперы»), поэтому объём `task_storage` ограничен.
- Если при `claim` файла нет, это не штатная ситуация (каталог удаляется только вместе с завершённой записью): задача завершается ошибкой со `stage = task_storage` (см. 4.2), заново данные из исходника не извлекаются.
- Запросы агента («получить fragment в отрендеренном виде», «получить element») `task_storage` не используют: после завершения записи файлов там уже нет. Данные строятся из исходного файла по `meta` той же функцией извлечения, которую вызывает разбор. Функция одна.

Очистка хранилищ. Общее таймерное задание (период — параметр конфигурации), также запускается при старте core. Оно только читает БД и в циклах готовности и очистки не участвует. Удаляются только каталоги записей целиком, отдельные файлы очистка не трогает:

- в хранилище исходных файлов: каталоги записей (по `record_id`), которых нет в БД;
- в `task_storage`: каталоги записей, которых нет в БД или которые в статусе `done` или `error`.

Гонок с приёмом нет за счёт порядка действий: core коммитит record до того, как создаёт его каталоги (3.1), а очистка сначала получает список каталогов и только потом читает БД. Значит, любой каталог, который увидела очистка, создан после коммита своей записи, и запрос в БД эту запись найдёт. Возрастной порог не нужен.

Если core упал во время приёма или разбора, в хранилищах остаётся мусор. Каждая попытка приёма получает новый `record_id` и пишет в свои каталоги, поэтому каталог прерванной попытки не пересекается с новой: его удаляет либо удаление прерванной записи при старте (3.2), либо очистка.

#### 3.4. Ошибка file

При переходе file в `error` цикл очистки в той же транзакции переводит всё под ним в `error` и удаляет (см. 2.6), в том числе задачи из очередей; что и где упало, сохраняется в снимке ошибки (2.7). При ошибке собственного text записи так же удаляются его chunk'и, а остальная запись обрабатывается дальше. Задачи, которые уже выполняются на воркере, не прерываются, но их результат при получении игнорируется: листа больше нет. Файлы таких element в `task_storage` удаляются вместе с каталогом записи, когда она завершится (3.3): цикл очистки файлы на диске не трогает. Исходный файл остаётся.

#### 3.5. Ошибки при приёме: пустышки

Скрапперы сами отвечают за целостность данных: если получить запись не удалось (например, нет интернета), запись в core не отправляется, и core пустышками не заполняется. Пустышки создаются только в таких случаях:

| Ситуация | Что записывается |
|---|---|
| Непредвиденная ошибка при разборе отдельного файла | Пустышка file: без детей, `status` = `error`, `error` с описанием, `error_detail` со `stage = parse`. Файл пропускается, остальные файлы разбираются; на record это влияет только по общему правилу 2.5 |
| Непредвиденная ошибка при разборе всей записи (в том числе откат транзакции с деревом) | Отдельной транзакцией коммитится дерево из пустышек: каждый file записи — пустышка file (`stage = parse`), собственный text (если был) — в `error` без chunk'ов, а ошибка разбора (`stage = parse`) пишется в record. Проверка готовности (2.5) в той же транзакции переводит record в `error`. Исходные файлы остаются |

Кроме пустышек, без детей бывают только record в `parsing`, file в `error`, чьи дети удалены циклом очистки, и собственный text в `error`, чьи chunk'и удалены.

Пустая запись и превышение `max_file_size` пустышек не создают: запись отклоняется целиком (см. 3.1, 3.6).

#### 3.6. Ограничение размера файла

- В конфигурации core задаётся `max_file_size` — максимальный размер сохраняемого файла, по умолчанию около 15 ГБ.
- Значение отдаётся через `GET /api/limits` с заголовками скраппера; ответ `200`: `{"max_file_size":16106127360}` (пример). Скраппер проверяет лимит заранее.
- Если размер какого-либо файла записи больше, core отказывается записывать запись и возвращает ошибку в виде статус-кода (например, HTTP 413). Записи, пустышки и файлы при этом не создаются.
- Скраппер такую запись в core не отправляет, а заносит в свою таблицу пропущенных по размеру (см. «Скрапперы»).

### 4. Задачи и очереди

#### 4.1. Очереди

Три очереди core соответствуют типам задач:

| Очередь (`type`) | Листья |
|---|---|
| `transcribe` | `task` с типом `transcribe` в статусе `wait` |
| `ocr` | `task` с типом `ocr` в статусе `wait` |
| `embed` | `chunk` в статусе `wait` |

Задача находится «в очереди», если `status = 'wait'`, и «на воркере», если `status = 'processing'` (тогда заполнены `taken_at` и `taken_by`). Отдельных структур очередей нет: очередь — это SQL-запрос к `task` или `chunk` в статусе `wait`. Порядок внутри очереди — FIFO по `created_at`.

Для балансировщика core — один источник задач (см. «Термины»): очередей для конкретных `record.source_id` (`youtube`, `telegram`) не существует, и балансировщик их не различает. Кроме собственных очередей, core хранит отдельные очереди каждого агента. Все приоритеты и наличие задач балансировщик получает одним запросом к core. Политика приоритетов — в 11.6.

#### 4.2. Централизованное API задач

Полный HTTP-контракт для реализации сервера и клиента находится в [ТЗ балансировщика](docs/balancer/README.md#http-контракт-с-core). Правила служебной регистрации и приоритетов — в 11.6. Здесь описано, как core обслуживает эти вызовы.

`task_source_id` выбирает собственные задачи обработки записей либо задачи отдельного `agent_id`. У каждого агента три изолированные очереди. Агенты отправляют входные данные в core и получают оттуда результаты под своими ID/token; скрапперы отправляют только записи, задачи по ним создаёт сам core.

| Операция | Обязанность core |
|---|---|
| Снимок источников (`GET /api/task-sources`) | Включить все источники и все три типа очередей, в том числе пустые; `has_tasks` вычислить как `EXISTS` задач в `wait`. Ничего не резервировать |
| Claim | Атомарно взять одну задачу выбранного источника и типа по FIFO (`created_at`, при равенстве ID), перевести из `wait` в `processing`, заполнить `taken_at`, `taken_by`. Для PostgreSQL — `FOR UPDATE SKIP LOCKED LIMIT 1` и UPDATE в одной транзакции |
| Выдача входа | Проверить источник, `processing` и `taken_by`; выдать подготовленные байты. Чужой или недоступный вход не выдавать |
| Result | Каждую задачу зафиксировать своей транзакцией, для задач дерева — вместе с циклом готовности (4.3). Для агентских задач сохранить результат в области инициировавшей регистрации. Ответить после всех коммитов |
| Fail | Для задач дерева выполнить цикл очистки (2.6), для самостоятельной задачи агента сохранить `error`. Ответить после фиксации; не возвращать задачу в `wait` |
| Reset | У выбранного источника вернуть задачи из `processing` с `taken_by` этого балансировщика в `wait`, очистить `taken_at`, `taken_by`. Завершённые задачи не менять |

Core вычисляет сложность по входным данным до выдачи claim; агент и скраппер её не задают. `complexity` — конечное неотрицательное число в единицах типа: минуты для аудио, символы для текстового embed. Метрики OCR и изображений для embed, точные формулы и крайние случаи пока открыты. Нормализация разных входов одного типа относится к расчёту core; порог пачки в конфигурации балансировщика должен использовать те же единицы. Статус `processing` включает набор и загрузку пачки.

Для собственных очередей `task_id` — ID task либо chunk (embed); для агента — ID самостоятельной задачи в core. Агентские задачи не привязаны к record и не создают дерево. Формат отправки и чтения результата агентом — в [HTTP API](docs/api.md). Операции claim, result, fail и reset изолированы по `task_source_id`; переданный ID задачи другого источника отклоняется без изменения задачи. Доступ к существующей задаче другого балансировщика также отклоняется. Коды ошибок заданы HTTP-контрактом.

Данные собственных задач дерева читаются из `task_storage`, текст chunk — из БД и выдаётся как байты. Если до выдачи обнаружено отсутствие необходимого файла, core после фиксации claim отдельной транзакцией завершает этот лист ошибкой `stage = task_storage` (2.6) и пробует следующую задачу той же очереди; ответ по-прежнему содержит не более одной задачи. Для самостоятельной задачи агента отсутствие входа фиксируется как её `error`, без цикла очистки дерева. Если файл пропал между claim и загрузкой, core также фиксирует ошибку и возвращает `404`; задача исключается из пачки.

Операции result и fail над удалённой задачей или задачей вне `processing` игнорируются; поэтому повторная отправка после потери ответа безопасна. Reset затрагивает только указанный источник. Возвращённая задача вновь ожидает выполнения, завершённая ошибкой — нет.

#### 4.3. Обработка результата собственных задач core

Результат каждой задачи фиксируется **одной транзакцией вместе со всеми порождёнными записями и циклом готовности** (см. 2.6). Коммит происходит до ответа балансировщику, поэтому не бывает момента, когда задача завершена, а её дети ещё не созданы или её предки не пересчитаны.

**Эмбеддинг** (лист chunk): записываются `embed` и `embed_model`, chunk → `done`.

**Транскрибация** (лист `task_transcribe` под audio):

1. `task_transcribe` → `done`.
2. Если транскрипция непуста, создаётся text (`kind` = `task_result`) — ребёнок audio — со статусом `processing`. Текст сразу режется на chunk'и (дети text, статус `wait`, `embed` пуст).
3. Если транскрипция пуста, text не создаётся.

**OCR** (лист `task_ocr` под photo): то же самое, text становится ребёнком photo. Если OCR не вернул текст, text не создаётся; это не ошибка.

Пока созданные chunk'и не получат эмбеддинги, audio (или photo) остаётся в `processing`.

#### 4.4. OCR

OCR обязателен для каждой photo, в том числе для каждого кадра видео: `task_ocr` создаётся всегда, без настроек и политик. Photo с пустым результатом OCR завершается, не имея text.

#### 4.5. Восстановление после сбоев

Возврат задач, взятых в работу:

- **При старте core** все самостоятельные задачи агентов и все листья собственных задач в статусе `processing` возвращаются в очередь: `status = 'wait'`, `taken_at` и `taken_by` = `NULL`. Так обрабатывается падение core, в том числе при фиксации результата. Если балансировщик потом пришлёт результат по такой задаче, он будет проигнорирован (задача уже не в `processing`), а сама задача выполнится заново.
- **При старте балансировщика** он вызывает `POST /api/task-sources/{task_source_id}/reset` (см. 4.2): возвращаются задачи, которые взял именно он; балансировщик состояния не хранит и набирает задачи заново.

Возврата по таймауту нет: длинная транскрибация законно идёт часами, и таймаут срабатывал бы посреди нормальной работы. Если балансировщик завис, его перезапускают, и при старте он сам возвращает свои задачи через `POST /api/task-sources/{task_source_id}/reset`.

При старте core:

1. удаляет записи в `parsing` вместе с их каталогами (см. 3.2) — до того, как начать принимать новые записи;
2. возвращает самостоятельные задачи агентов и все листья из `processing` в `wait` — до того, как начать отвечать балансировщику;
3. запускает цикл очистки по таймеру (см. 2.8) и очистку хранилищ (см. 3.3); дальше они работают по своим таймерам.

Проверки и ремонта дерева нет: операция над листом и весь вызванный ею цикл фиксируются одной транзакцией (2.6), поэтому падение core не оставляет дерево наполовину пересчитанным.

### 5. Поиск

Запись доступна конкретному агенту в поиске, только если одновременно `record.status = 'done'`, `record.owner = agent.owner` и `record.trust_level < agent.trust_level`. Owner и уровень агента core получает из его серверной регистрации (раздел 11), а фильтры добавляет самостоятельно до поиска и ранжирования. При равных уровнях доступа нет; уровень чужой записи значения не имеет. Записи в `parsing`, `processing` и `error` не ищутся. Внутри записи в `done` ищутся только существующие chunk'и: у file в `error` детей нет, у упавшего собственного text нет chunk'ов.

Агент обращается к поисковому API core из режима ИИ-агента и из ручного поиска. Оба режима доступны в веб-интерфейсе и Telegram-боте и используют одни эндпоинты `GET /api/search/schema`, `POST /api/search`, `POST /api/read`, описанные в [спецификации агента](docs/agent/README.md). Детали реализации поиска в core остаются в разработке.

HTTP-методы, параметры, заголовки `X-Agent-ID: <agent_id>` и `Authorization: Bearer <token агента>` и примеры ответов закреплены в [HTTP API](docs/api.md).

### 6. Веб-интерфейс core

Для входа нужны логин и пароль. При разрешённой внешней регистрации доступна форма создания пользователя: только логин и пароль либо дополнительно одноразовый код приглашения. Настройки регистрации и правила аутентификации — в разделе 11. Доступ из локальной сети сам по себе прав не даёт.

**Пользовательский кабинет** показывает только данные вошедшего пользователя. В нём можно:

- создавать и настраивать свои агенты: при создании задавать agent_id каждого режима, получать автоматически созданный token, перевыпускать token и менять trust_level;
- создавать свои скрапперы с заданным scrapper_id, получать и перевыпускать token и переходить на их собственные сайты настройки; администратор не создаёт скрапперы за пользователя;
- смотреть собственные записи, ID добавившего скраппера (scrapper), статусы, trust_level и ошибки: error и error_detail записи и её file, включая ошибки внутри записей в done;
- менять trust_level своих записей и удалять свои записи в любом статусе.

**Административный раздел** управляет пользователями, режимом внешней регистрации и одноразовыми приглашениями. Администратор имеет доступ ко всем данным, в том числе для просмотра ошибок и удаления записей; создание агентов и скрапперов находится в пользовательском кабинете.

Удаляется record целиком, его дерево и задачи — каскадом внешних ключей. Каталоги в хранилище исходных файлов и task_storage удаляет очистка хранилищ, так как записи больше нет в БД (3.3). Удаление не затрагивает отдельные копии материала других пользователей. Отдельные file не удаляются. Фоновый приём и разбор останавливаются для удаляемого record; поздние результаты задач игнорируются (11.5).

Тот же API удаления доступен зарегистрированному агенту только при совпадении owner и строгом условии record.trust_level < agent.trust_level. Поисковые права агента и права сессии человека различаются: агент не может воспользоваться ролью администратора своего владельца.

Перезапуска обработки нет: после удаления скраппер этого владельца на запрос статуса получает unknown и, если снова встретит запись, отправляет её заново с новым record_id. Какие режимы скрапперов встречают запись повторно, описано в разделе «Скрапперы».


#### HTTP-запросы кабинета

Вход — `POST /api/auth/login` с JSON `login`, `password`; регистрация — `POST /api/auth/register` с теми же полями и `invite_code` в режиме приглашений. После входа используются cookie `session` и `X-CSRF-Token` для изменяющих запросов.

Агенты создаются через `POST /api/agents`, скрапперы — `POST /api/scrapers`; списки доступны через GET по тем же путям. Собственные записи — `GET /api/records`, просмотр — `GET /api/records/{record_id}`, изменение уровня — `PATCH /api/records/{record_id}` с JSON `trust_level`, удаление — `DELETE /api/records/{record_id}`.

Административные операции находятся под `/api/admin/`: пользователи, настройки регистрации, приглашения и записи всех владельцев. Полный список эндпоинтов с обязательными полями и ответами — в [HTTP API](docs/api.md).

### 7. Хранение и технологии

Рекомендуется PostgreSQL с расширением pgvector версии не ниже 0.7 (нужен тип `halfvec`, см. ниже); СУБД пока не зафиксирована. Фрагменты SQL в этом разделе — эскизы для PostgreSQL.

- Типы `record_status`, `container_status`, `task_status`, `element_kind`, `task_type`, `text_kind` — enum. Enum — тип поля, которое может принимать только одно значение из заданного списка. В SQLite enum нет, там используется `TEXT` с проверкой `CHECK`.
- Каждый тип объектов дерева лежит в своей таблице: `record`, `file`, `fragment`, `text`, `element`, `chunk`, `task`. Внешние ключи с `ON DELETE CASCADE`: авторизованное удаление записи (см. 6 и 11.5) — это удаление строки record, остальное удаляется каскадом. Цикл очистки удаляет строки явно, снизу вверх (2.6); каскад для него — подстраховка.
- Исходные файлы лежат в долговременном хранилище core по пути `/storage/<source_id>/<record_id>/<file_id>.<исходное расширение>`; ни пути, ни хэша в БД нет. Данные для задач лежат во временном `task_storage` на файловой системе (не в БД; путь выводится из `record_id` и `element_id`) и удаляются очисткой хранилищ целым каталогом записи (3.3).
- Все поля с данными, специфичными для источника или типа файла (`metadata`, `meta`), имеют тип JSONB.
- Пользователи, настройки регистрации, приглашения и регистрации агентов/скрапперов хранятся в core, а не в параметрах клиента. Owner у record, agent и scraper — внешний ключ на app_user. Индекс record(owner, trust_level, id) поддерживает обязательный фильтр доступа; индексы agent(owner) и scraper(owner) — списки в кабинете. Между пользователями общих record и таблицы связи владельцев нет. Удаление пользователя не должно каскадно уничтожать его записи: вместо этого учётную запись блокируют; отдельный сценарий окончательного удаления данных не входит в этот контракт.
- ID компонентов постоянны; вместо хеширования agent_id хранится token_hash. Удаление скраппера логическое: token отзывается, строка сохраняется для record.scrapper, ID не переиспользуется. Core проверяет совпадение owner скраппера и записи и заполняет scrapper из авторизованной регистрации при приёме; клиент изменить его не может. Балансировщик использует один служебный token для всех очередей core; достаточно хранить его хеш. Отдельных токенов очередей нет.
- Индексы: внешние ключи дочерних таблиц (`file.record_id`, `fragment.record_id`, `fragment.file_id`, `fragment.parent_fragment_id`, `element.record_id`, `element.file_id`, `element.fragment_id`, `text.*_id`, `chunk.*_id`, `task.element_id`) для проверки готовности; частичные индексы очередей `task (type, created_at) WHERE status = 'wait'` и `chunk (created_at) WHERE status = 'wait'`; частичные индексы `task (taken_by) WHERE status = 'processing'` и `chunk (taken_by) WHERE status = 'processing'` для возврата задач по `POST /api/task-sources/{task_source_id}/reset` и при старте core; частичные индексы `WHERE status = 'error'` на `fragment`, `element`, `text`, `chunk` и `task` для цикла очистки по таймеру; частичный индекс `file (finished_at) WHERE status = 'error'` для списка ошибок внутри записей в `done`; индекс HNSW `chunk USING hnsw (embed halfvec_cosine_ops)` для семантического поиска; частичный индекс `record (id) WHERE status = 'parsing'` для удаления прерванных записей при старте; частичный индекс `record (processed_at) WHERE status = 'error'` для списка ошибочных записей в веб-интерфейсе; уникальный индекс `record(owner, source_id, source_url)`.
- Ограничения: у `chunk` заполнены ровно один родитель и ровно одно из `text` и `is_picture`, длина текста ограничена; у `text` набор заполненных ссылок согласован с `kind` (см. 1.5); в `wait` поля `taken_at` и `taken_by` пусты, в `processing` заполнены; иерархические правила из 1.1 проверяются при построении дерева в коде (на уровне БД — при необходимости constraint-триггерами).
- Эмбеддинги лежат в столбце типа `halfvec(2048)`: 2048 — размерность Qwen3-VL-Embedding-2B (см. таблицу моделей). Индексы pgvector (HNSW, IVFFlat) по типу `vector` ограничены 2000 измерениями, а по `halfvec` — 4000. В `halfvec` каждое число занимает 16 бит вместо 32: вектор весит 4 КБ вместо 8, а точности хватает, так как модель и так считает в BF16. Если сменить модель на размерность больше 4000, векторы придётся урезать (MRL). В chunk хранится название модели (`embed_model`), чтобы при смене модели можно было пересчитать эмбеддинги.
- Входные данные самостоятельных задач агента хранятся в core отдельно от каталогов record, с адресацией по agent_id/task_id; текстовый embed принимается как байты UTF-8. Результаты и ошибки хранятся в `agent_task`. Сроки хранения, квоты, удаление и очистка будут определены отдельно. Сложность собственных задач core вычисляется по данным task/chunk до выдачи; способ её хранения или кеширования пока не закреплён.
- Эскиз таблиц:

```sql
CREATE TYPE container_status AS ENUM ('processing','done','error');          -- file, fragment, element, text
CREATE TYPE task_status      AS ENUM ('wait','processing','done','error');   -- chunk, task
CREATE TYPE element_kind     AS ENUM ('photo','audio');
CREATE TYPE task_type        AS ENUM ('transcribe','ocr');
CREATE TYPE text_kind        AS ENUM ('record','element','task_result');

CREATE TABLE app_user (
  id             uuid PRIMARY KEY,
  login          text NOT NULL UNIQUE,  -- нормализованный логин
  password_hash  text NOT NULL,
  role           text NOT NULL CHECK (role IN ('user', 'admin')),
  enabled        boolean NOT NULL DEFAULT true
);

CREATE TABLE registration_settings (
  singleton          boolean PRIMARY KEY DEFAULT true CHECK (singleton),
  registration_mode  text NOT NULL DEFAULT 'closed'
    CHECK (registration_mode IN ('closed', 'open', 'invite'))
);
INSERT INTO registration_settings (singleton) VALUES (true);

CREATE TABLE invitation (
  id          uuid PRIMARY KEY,
  code_hash   text NOT NULL UNIQUE,
  created_by  uuid NOT NULL REFERENCES app_user(id),
  used_by     uuid UNIQUE REFERENCES app_user(id),
  used_at     timestamptz,
  revoked     boolean NOT NULL DEFAULT false,
  CHECK ((used_by IS NULL) = (used_at IS NULL))
);

CREATE TABLE agent (
  agent_id       uuid PRIMARY KEY,  -- задаётся при создании, совпадает с task_source_id
  token_hash     text NOT NULL UNIQUE,  -- хеш автоматически созданного token
  owner          uuid NOT NULL REFERENCES app_user(id),
  mode           text NOT NULL,  -- отдельная регистрация каждого режима
  trust_level    integer NOT NULL CHECK (trust_level >= 0),
  enabled        boolean NOT NULL DEFAULT true,
  deleted_at     timestamptz  -- регистрация сохраняется после окончательного удаления
);

CREATE TABLE scraper (
  scrapper_id    uuid PRIMARY KEY,
  owner         uuid NOT NULL REFERENCES app_user(id),
  source_id     text NOT NULL,
  web_endpoint  text,
  token_hash    text NOT NULL UNIQUE,
  enabled       boolean NOT NULL DEFAULT true,
  deleted_at    timestamptz  -- удалённый скраппер нельзя включить повторно
);

-- Единственная служебная регистрация создаётся при настройке сервера.
CREATE TABLE balancer (
  balancer_id  text PRIMARY KEY,
  token_hash   text NOT NULL UNIQUE,
  enabled      boolean NOT NULL DEFAULT true
);
-- Этот token применяется ко всем очередям; отдельных секретов источников нет.

-- Самостоятельные задачи агентов не являются листьями дерева record.
CREATE TABLE agent_task (
  id           uuid PRIMARY KEY,
  agent_id     uuid NOT NULL REFERENCES agent(agent_id),
  type         text NOT NULL CHECK (type IN ('transcribe', 'ocr', 'embed')),
  status       task_status NOT NULL DEFAULT 'wait',
  input_mime   text NOT NULL,
  complexity   double precision, -- вычисляет core до claim; формулы пока открыты
  payload      jsonb,
  error        jsonb,
  taken_at     timestamptz,
  taken_by     text,
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  CHECK (complexity IS NULL OR (complexity >= 0 AND complexity < 'Infinity'::float8)),
  CHECK (status <> 'wait' OR (taken_at IS NULL AND taken_by IS NULL)),
  CHECK (status <> 'processing' OR (taken_at IS NOT NULL AND taken_by IS NOT NULL AND complexity IS NOT NULL))
);
CREATE INDEX ON agent_task (agent_id, type, created_at, id) WHERE status = 'wait';
CREATE INDEX ON agent_task (agent_id, taken_by) WHERE status = 'processing';

  owner              uuid NOT NULL REFERENCES app_user(id),
  scrapper           uuid NOT NULL REFERENCES scraper(scrapper_id) ON DELETE RESTRICT,
  trust_level        integer NOT NULL CHECK (trust_level >= 0),
  source_id          text NOT NULL,
  source_url         text NOT NULL,
  source_created_at  timestamptz,
  scraped_at         timestamptz NOT NULL,
  registered_at      timestamptz NOT NULL,
  processed_at       timestamptz,
  status             record_status NOT NULL DEFAULT 'parsing',
  title              text,
  author             text,
  parent_source_url  text,
  metadata           jsonb,
  error              text,
  error_detail       jsonb,
  UNIQUE (owner, source_id, source_url)
);

CREATE INDEX ON record (owner, trust_level, id);
CREATE INDEX ON record (scrapper);
CREATE INDEX ON agent (owner);
CREATE INDEX ON scraper (owner);

CREATE TABLE file (
  id           uuid PRIMARY KEY,
  record_id    uuid NOT NULL REFERENCES record(id) ON DELETE CASCADE,
  ord          int  NOT NULL DEFAULT 0,
  status       container_status NOT NULL DEFAULT 'processing',
  error        text,
  error_detail jsonb,
  name         text,
  mime         text,
  size         bigint,
  finished_at  timestamptz,
  meta         jsonb
);

CREATE TABLE fragment (
  id                 uuid PRIMARY KEY,
  record_id          uuid NOT NULL REFERENCES record(id) ON DELETE CASCADE,
  file_id            uuid NOT NULL REFERENCES file(id) ON DELETE CASCADE,
  parent_fragment_id uuid REFERENCES fragment(id) ON DELETE CASCADE,  -- NULL на верхнем уровне
  ord                int  NOT NULL DEFAULT 0,
  status             container_status NOT NULL DEFAULT 'processing',
  finished_at        timestamptz,
  meta               jsonb
);

CREATE TABLE element (              -- photo и audio
  id           uuid PRIMARY KEY,
  record_id    uuid NOT NULL REFERENCES record(id)   ON DELETE CASCADE,
  file_id      uuid NOT NULL REFERENCES file(id)     ON DELETE CASCADE,
  fragment_id  uuid NOT NULL REFERENCES fragment(id) ON DELETE CASCADE,
  kind         element_kind NOT NULL,
  ord          int  NOT NULL DEFAULT 0,
  status       container_status NOT NULL DEFAULT 'processing',
  finished_at  timestamptz,
  meta         jsonb
);

CREATE TABLE text (
  id           uuid PRIMARY KEY,
  kind         text_kind NOT NULL,
  record_id    uuid NOT NULL REFERENCES record(id) ON DELETE CASCADE,
  fragment_id  uuid REFERENCES fragment(id) ON DELETE CASCADE,  -- пусто только у собственного text записи
  element_id   uuid REFERENCES element(id)  ON DELETE CASCADE,  -- только у результата задачи
  status       container_status NOT NULL DEFAULT 'processing',
  finished_at  timestamptz,
  meta         jsonb,
  CHECK ((kind = 'record'      AND fragment_id IS NULL     AND element_id IS NULL)
      OR (kind = 'element'     AND fragment_id IS NOT NULL AND element_id IS NULL)
      OR (kind = 'task_result' AND fragment_id IS NOT NULL AND element_id IS NOT NULL))
);

CREATE TABLE chunk (
  id           uuid PRIMARY KEY,
  text_id      uuid REFERENCES text(id)    ON DELETE CASCADE,
  element_id   uuid REFERENCES element(id) ON DELETE CASCADE,   -- chunk-картинка photo
  ord          int  NOT NULL DEFAULT 0,
  status       task_status NOT NULL DEFAULT 'wait',
  text         text,
  is_picture   boolean NOT NULL DEFAULT false,
  embed        halfvec(2048),
  embed_model  text,
  taken_at     timestamptz,
  taken_by     text,                                            -- balancer_id
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  CHECK ((text_id    IS NOT NULL AND element_id IS NULL AND text IS NOT NULL AND NOT is_picture)
      OR (element_id IS NOT NULL AND text_id    IS NULL AND text IS NULL     AND is_picture)),
  CHECK (status <> 'wait' OR (taken_at IS NULL AND taken_by IS NULL)),
  CHECK (status <> 'processing' OR (taken_at IS NOT NULL AND taken_by IS NOT NULL))
);

CREATE INDEX ON chunk USING hnsw (embed halfvec_cosine_ops);

CREATE TABLE task (
  id           uuid PRIMARY KEY,
  element_id   uuid NOT NULL REFERENCES element(id) ON DELETE CASCADE,
  type         task_type NOT NULL,
  status       task_status NOT NULL DEFAULT 'wait',
  taken_at     timestamptz,
  taken_by     text,                                            -- balancer_id
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  CHECK (status <> 'wait' OR (taken_at IS NULL AND taken_by IS NULL)),
  CHECK (status <> 'processing' OR (taken_at IS NOT NULL AND taken_by IS NOT NULL))
);
```

### 8. Обработка отказов

| Ситуация | Поведение |
|---|---|
| Запись с таким `(owner, source_id, source_url)` уже есть | Ответ «существует» (в том числе пока она в `parsing`), ничего не меняется |
| Отправлена запись без содержимого (нет ни текста, ни файлов) | Запись отклоняется статус-кодом ошибки (HTTP 422), ничего не сохраняется (3.1) |
| Файл больше `max_file_size` | Запись отклоняется статус-кодом ошибки (HTTP 413), ничего не сохраняется |
| Загрузка файлов оборвалась | core удаляет record и его каталоги; скраппер получает `unknown` и отправляет запись повторно |
| core упал во время приёма или разбора | Record остаётся в `parsing`; при старте core удаляет его вместе с каталогами (3.2); скраппер получает `unknown` и отправляет запись повторно |
| Разбор отдельного файла упал | Пустышка file в `error` (`stage = parse`); остальные файлы разбираются (3.5) |
| Разбор всей записи упал (исключение, откат транзакции с деревом) | Дерево из пустышек: все file и собственный text в `error`, ошибка разбора в record; record сразу → `error` (3.5, 2.5). Исходники остаются, каталог в `task_storage` удаляется очисткой хранилищ |
| После разбора у записи нет ни одного листа (все дети — пустышки разбора) | Record → `error` сразу в транзакции коммита дерева (3.1, 2.5) |
| Каталог в `task_storage` остался после завершения записи или падения core | Удаляется очисткой хранилищ целиком (3.3) |
| При `claim` нет файла в `task_storage` | `fail` листа со `stage = task_storage` и цикл очистки: file → `error`, всё под ним удаляется (4.2, 2.6). Листья собственного text в `task_storage` не обращаются: текст chunk'а берётся из БД |
| core упал при фиксации результата или ошибки | Транзакция (лист вместе с циклом) откатывается целиком, дерево не меняется; лист остаётся в `processing` и при старте core возвращается в `wait` (4.5) |
| Балансировщик перезапустился | Воркеры завершает ОС вместе с ним; при старте он вызывает `POST /api/task-sources/{task_source_id}/reset` на core для каждого логического источника, и его задачи из `processing` возвращаются в `wait` (4.2, 4.5, «Балансировщик») |
| Вытеснение более приоритетным источником | Воркер убивается, очередь пачек очищается, `POST /api/task-sources/{task_source_id}/reset`: задачи из `processing` возвращаются в `wait`, статус родителей не меняется |
| Воркер упал на пачке из нескольких задач | Балансировщик разбивает пачку на пачки по одной задаче и запускает их по очереди; в core это ошибкой не считается («Балансировщик») |
| Задача упала и в одиночку | `fail` этой задачи → цикл очистки: file → `error` со снимком ошибки, всё под ним удаляется одной транзакцией; record продолжает обработку остальных детей (2.6) |
| Упал лист собственного text записи | Цикл очистки: text → `error`, его chunk'и удаляются, ошибка и снимок пишутся в record; статус record не меняется (2.4, 2.6) |
| Все дети записи (собственный text, если есть, и все file) в `error` | Record → `error` со сводкой `stage = children` (2.5) |
| Ниже границы остались строки в `error` (ошибка в коде, ручная правка БД) | Их находит и удаляет цикл очистки по таймеру (2.8) |
| Запись удалена в кабинете или через авторизованный API | Record, его дерево и задачи удаляются; фоновый приём и разбор останавливаются, поздние результаты игнорируются; каталоги удаляет очистка хранилищ. Скраппер этого owner получает unknown; чужие копии не затрагиваются (6, 11.5) |
| Результат или ошибка пришли для объекта, которого нет или который не в `processing` | Игнорируется |
| Результат пришёл повторно | Игнорируется (идемпотентность по статусу) |
| Балансировщик завис | Его перезапускают; воркеры завершает ОС, при старте он вызывает `POST /api/task-sources/{task_source_id}/reset` (4.5). Возврата по таймауту нет |
| Файл записи больше `max_file_size` на стороне скраппера | Запись в core не отправляется, скраппер заносит её в таблицу пропущенных по размеру («Скрапперы») |
| Нет действующей аутентификации агента, скраппера или пользователя | Запрос отклоняется до доступа к данным; локальная сеть не заменяет аутентификацию |
| Агент обращается к чужой записи либо record.trust_level ≥ agent.trust_level | Объект недоступен для поиска, чтения и удаления; ответ по ID не отличается от отсутствующего объекта |
| У пользователя заблокирована учётная запись | Его сессии, агенты и скрапперы не могут выполнять пользовательские запросы; данные остаются, служебный reset очередей доступен |
| Два запроса регистрации используют одно приглашение | Только один создаёт пользователя и расходует код; проверка и погашение атомарны (11.2) |
| Core недоступен балансировщику | Новые пачки не набираются; уже загруженная может завершиться, результат ждёт восстановления связи с core. При запуске без списка и успешного reset core работа не начинается (11.6) |
| Появились задачи другого агента с тем же приоритетом | Текущий агент не вытесняется; при обходе равенство приоритетов разрешается по ID |

### 9. Инварианты

1. Дерево записи появляется в БД целиком одной транзакцией; до этого record находится в `parsing` и детей не имеет; частичных деревьев не бывает.
2. Каждый контейнер имеет хотя бы одного ребёнка; исключение — record в `parsing`, file в `error` и собственный text в `error` (их дети удалены циклом очистки, или это пустышки разбора).
3. Задачи привязаны только к листьям (chunk, `task_transcribe`, `task_ocr`).
4. Результат задачи фиксируется вместе со всеми порождёнными записями одной транзакцией и коммитится до ответа балансировщику.
5. Каждый photo имеет ровно один chunk-картинку и ровно один `task_ocr` (пока его file не в `error`).
6. Контейнер внутри file (или собственный text записи) `done` только если все его дети `done`; ошибка любого листа внутри file делает ошибочным file, а всё под ним в той же транзакции уходит в `error` и удаляется.
7. Статус `wait` бывает только у chunk, `task_transcribe` и `task_ocr`; у остальных объектов его нет.
8. Операция над листом и весь вызванный ею цикл (готовности или очистки) — один коммит.
9. Record в `error` тогда и только тогда, когда все его дети (собственный text, если есть, и все file) в `error`. Ошибка file или собственного text статус record не меняет; ошибка собственного text пишется в `error` записи.
10. Терминальный статус (`done`, `error`) не меняется; перезапуска обработки нет. Авторизованное удаление записи доступно в любом статусе (6, 11.5).
11. Тройка `(owner, source_id, source_url)` уникальна и обязательна. У record ровно один owner и собственный trust_level; одинаковые материалы разных владельцев — независимые записи.
12. Долговременно core хранит только исходные файлы: либо исходный файл, либо ничего. Исходный файл хранится, пока существует record. Данные для задач лежат во временном `task_storage` и удаляются очисткой хранилищ целым каталогом записи, когда record завершён (`done`, `error`) или его нет в БД.
13. К моменту появления задач в очередях их входы сохранены в core: файлы задач дерева лежат в `task_storage` до коммита дерева, текстовые chunk — в БД, входы самостоятельных задач агента — в отдельном хранилище core.
14. Статус `parsing` бывает только у record. Запись в `parsing` существует, только пока core её принимает и разбирает; при старте core все такие записи удаляются.
15. Агенту в поиске и чтении доступны только record в done с owner этого агента и record.trust_level строго меньше agent.trust_level. Полномочия core определяет по аутентифицированной регистрации, а не по параметрам запроса.
16. Record в `error` имеет хотя бы одного ребёнка, и все его дети — file в `error` и собственный text в `error`, без детей.
17. После старта core и до первого `claim` ни одного листа в `processing` нет.
18. Строки в `error` ниже границы (fragment, element, text, кроме собственного text записи, chunk, task) не переживают коммит цикла очистки.
19. Лист в `processing` всегда помечен балансировщиком, который его взял (`taken_by`); лист в `wait` не помечен.
20. Каждый режим агента имеет собственный зарегистрированный agent_id, owner, trust_level и область очередей; общая реализация не объединяет права.
21. Балансировщик один, его нельзя создать через пользовательские API. Список источников, наличие задач и приоритеты он получает одним запросом к core; все агенты имеют равный приоритет выше core, равенства разрешаются по ID.
22. Удаление агентом возможно только для собственного owner при record.trust_level < agent.trust_level; дерево и задачи удаляются вместе с записью, копии других владельцев не затрагиваются.
23. Одно приглашение создаёт не более одного пользователя; регистрация и погашение кода атомарны. Внешняя регистрация никогда не выдаёт роль администратора.
24. Агенты, скрапперы и балансировщик авторизуются только парой постоянного ID и отдельного действующего token; перевыпуск token не меняет ID и привязки.
25. Record.scrapper обязателен, неизменен и равен scrapper_id проверенного скраппера при первом добавлении; его owner совпадает с owner записи. Повторная отправка и удаление регистрации не меняют происхождение записи.

### 10. Принятые решения и открытые вопросы

Решения, принятые при составлении ТЗ:

1. Разбор записи до коммита дерева выполняет сам core, в фоне, после ответа скрапперу (разбиение PDF и Word на страницы и листы, определение кадров и аудио видео, нарезка текста); это не GPU-работа и в очереди балансировщика не входит. Кадры, аудио и рендер страниц для задач извлекаются при разборе и кладутся во временный `task_storage` (см. 3.3); запросы агента строят их из исходного файла по `meta` той же функцией извлечения.
2. Граница ошибки — file (для листьев внутри файла), а не element: лучше открыто потерять файл целиком, чем незаметно терять его части. Для листьев собственного text записи граница — record: в него пишется ошибка, но статус record не меняется. Ошибку обрабатывает цикл очистки: вверх до границы с сообщением, вниз по слоям, удаление снизу вверх — одной транзакцией; упавшее не дорабатывается (иначе работа GPU тратится на то, что нельзя найти). Для отладки остаются исходный файл и снимок ошибки (2.7). Цикл очистки по таймеру — только страховка (2.8).
3. Record становится `error`, только если все его дети (собственный text, если есть, и все file) в `error` (2.5); иначе `done`. Пустая запись не принимается (3.1), а упавший разбор записи даёт дерево из пустышек (3.5), так что других случаев `error` у record нет. Запись доступна в поиске агенту, только когда она в done, owner совпадает и record.trust_level < agent.trust_level (5, 11).
4. OCR обязателен для каждой photo, в том числе для каждого кадра видео. Кадры берутся каждые i секунд и не дедуплицируются: каждый кадр и эмбеддится, и отправляется на OCR.
5. Одна аудиодорожка файла — один element audio и одна задача транскрибации; длинное аудио на части не режется. Принятое следствие: при вытеснении (см. «Балансировщик») прогресс длинной транскрибации теряется целиком, и при активных агентах обработка записей core может откладываться. Равноприоритетные агенты друг друга не вытесняют.
6. `registered_at` — момент приёма записи (вставки record в `parsing`).
7. Параметры нарезки текста: максимум x символов на chunk, границы по абзацам и предложениям, перекрытие настраивается (по умолчанию 0).
8. Шаг кадров i, период очистки хранилищ, период цикла очистки по таймеру и формат материалов в `task_storage` — параметры конфигурации.
9. Element хранится в двух таблицах: photo и audio — в `element`, text-элементы — в `text`. Так text как результат OCR, транскрибации, собственный текст записи и text-элемент фрагмента лежат в одной таблице; колонка `kind` различает их, ссылки `record_id`, `fragment_id`, `element_id` согласованы с ней.
10. Операция над листом и вызванный ею цикл (готовности или очистки) фиксируются одной транзакцией с блокировкой file (или собственного text записи) и record (2.6), поэтому проверка и ремонт дерева не нужны.
11. Статус `wait` есть только у листьев-задач (chunk, `task_transcribe`, `task_ocr`); у контейнеров «ожидания» нет, они с момента создания `processing` (record — `parsing`, пока идёт разбор).
12. `task_storage`: один файл на element, создаётся при разборе до коммита дерева, живёт до завершения record и удаляется очисткой хранилищ целым каталогом записи; очистка хранилищ только читает БД. Пропажа файла — ошибка задачи, заново данные не извлекаются. Лимита размера нет: объём ограничен K незавершёнными записями на скраппер. Для фото, которое само является файлом, копия всё равно делается: выигрыш от ссылки на исходник минимален.
13. Пути файлов выводятся из идентификаторов, поэтому `record_id` и `file_id` выдаются core при приёме (record сразу вставляется в `parsing`) и в БД нет ни путей, ни хэшей файлов: изменения записей не отслеживаются.
14. Приём асинхронный: core отвечает `202` после сохранения исходных файлов и разбирает запись в фоне; отдельной таблицы состояния приёма нет, её роль играет record в статусе `parsing`. Core работает в одном экземпляре, поэтому при старте все записи в `parsing` считаются прерванными. Для нескольких экземпляров core понадобится heartbeat разбора.
15. Источник задач определяется task_source_id (core или отдельный agent_id), все очереди обслуживает API core (4.2). Core — один источник: record.source_id и владельцев записей балансировщик внутри него не различает. Задачи и результаты агента хранятся в его отдельной области очередей в core. Балансировщик обращается только к core с едиными служебными полномочиями; список источников, наличие задач и приоритеты получает одним запросом (11.6).
16. Для GPU-задач принят запуск отдельного процесса воркера на каждую пачку. Модель при этом загружается заново: при большой очереди накладные расходы окупаются полной пачкой, при малой допустимы дополнительные секунды ожидания. Контракты воркеров, алгоритм пачек и восстановление клиентского состояния — в [ТЗ балансировщика](docs/balancer/README.md); восстановление очередей core — в 4.5.
17. Ручного перезапуска нет. Запись можно удалить в кабинете core или через API (6, 11.5); при вызове агентом обязательны совпадение owner и record.trust_level < agent.trust_level. После удаления скраппер отправит запись заново, если встретит.
18. Эмбеддинги хранятся в `halfvec(2048)` с индексом HNSW (7).
19. Скраппер держит в core до K незавершённых записей. Запись с файлом больше `max_file_size` (по умолчанию около 15 ГБ) в core не отправляется и заносится в таблицу пропущенных по размеру у скраппера.
20. Доступ аутентифицируется и в локальной сети: в core люди входят по логину и паролю, агенты, скрапперы и балансировщик предъявляют постоянный ID и отдельный token, автоматически генерируемый core при создании регистрации. Внешняя регистрация закрыта, открыта или требует одноразового приглашения по выбору администратора. Администратор имеет доступ ко всему и управляет пользователями; пользователь создаёт свои агенты и скрапперы (11).
21. Приложение агента может оставаться одним монолитом в контейнере: веб-интерфейс, ИИ-поиск, ручной поиск и Telegram-бот. Каждый режим регистрируется отдельно со своим agent_id, owner, trust_level и областью очередей, даже при общем сервере приложения. Core и балансировщик разворачиваются отдельно.
22. У record один owner и один trust_level; уникальность — (owner, source_id, source_url). Материалы разных владельцев дублируются полностью. Таблицы связи многие ко многим и поля owners нет.
23. Балансировщик один, пользователи не могут создавать его экземпляры через API. Политика приоритетов источников и типов принадлежит core (11.6); балансировщик получает значения через API и не содержит правил для отдельных источников.
24. Owner и trust_level агента подставляет core из своей регистрации. Равенство уровней не даёт доступа; агенты не могут менять свои полномочия. Административная роль владельца не передаётся агенту.
25. Сайты агентов и скрапперов пользователь размещает и защищает по своему усмотрению, включая публикацию в интернете и собственные логины/пароли. Сессия core для этих сайтов не обязательна; локальный admin не даёт прав в core. Agent_id — постоянный несекретный ID, совпадающий с task_source_id; core проверяет пару agent_id/token при каждом вызове API агента. Record.scrapper хранит scrapper_id первоначального скраппера и заполняется core; повторная отправка его не меняет.
26. Удаление record допустимо в любом статусе при проверке прав, удаляет его дерево и задачи и согласовано с фоновым разбором. Данные других владельцев не затрагиваются (11.5).

27. Сложность вычисляет core и возвращает в claim вместе с метаданными задачи. Балансировщик суммирует её и только после набора пачки скачивает входные данные, включая текстовый embed как байты UTF-8. Агенты и скрапперы сложность не передают.

Открытые вопросы:

1. **Повторная отправка из Telegram.** Сканер каналов и чатов читает только сообщения после `last_message_id`, поэтому удалённую вручную запись сам не пришлёт. Есть идея на каждом проходе брать все id сообщений группы или чата и сверять их с core; пока не решено.
2. **Поиск** (раздел 5) в разработке.
3. **Сложность задач.** Формулы, метрики OCR и изображений для embed, приведение входов одного типа к единицам его порога и крайние случаи будут определены отдельно. Принятые единицы: минуты аудио и число символов для текстового embed.
4. **Самостоятельные задачи агентов.** Сроки хранения входов и результатов, квоты, удаление и очистка будут определены отдельно. Эти задачи хранятся отдельно от дерева record.

### 11. Пользователи, регистрация и доступ

#### 11.1. Учётные записи и роли

Клиент — пользователь core, управляющий своими агентами и скрапперами. Его учётная запись хранится в app_user; каждый из его агентов хранится отдельной строкой agent с owner = app_user.id. Один клиент может владеть несколькими агентами. Далее термины «клиент» и «пользователь core» означают одну сущность.

Core хранит пользователей и аутентифицирует вход по логину и паролю. Телефон и электронная почта для создания пользователя и входа не нужны. Логин уникален с учётом единого правила нормализации регистра; пароль хранится только как стойкий хеш с солью. Первый администратор создаётся при первоначальной настройке сервера, а не через открытую регистрацию.

- **Администратор** имеет доступ ко всем данным и управляет пользователями: создаёт и блокирует учётные записи, сбрасывает пароли, управляет внешней регистрацией и приглашениями. Административный интерфейс не создаёт пользовательские агенты и скрапперы. Если администратору нужны собственные источники, он создаёт их через пользовательский раздел в своей учётной записи.
- **Пользователь** видит только собственные записи и настройки, создаёт своих агентов и скрапперы на своём сайте. Совпадение уровней доверия у разных пользователей не связывает их права.

Административный доступ — отдельное право сессии человека. Агент администратора подчиняется тем же проверкам owner и trust_level, что любой другой агент; роль владельца не даёт агенту обхода ограничений. Блокировка пользователя делает недействительными его сессии и полномочия агентов и скрапперов. Существующие записи при блокировке сохраняются.

#### 11.2. Внешняя регистрация и приглашения

Администратор выбирает один из трёх режимов `registration_mode`:

| Режим | Создание учётной записи |
|---|---|
| `closed` | Только администратором; внешняя регистрация выключена |
| `open` | Любой посетитель задаёт логин и пароль |
| `invite` | Посетитель задаёт логин, пароль и одноразовый код приглашения |

По умолчанию регистрация закрыта. Внешняя регистрация всегда создаёт обычного пользователя; роль из запроса не принимается. Администратор может создавать пользователей при любом режиме, без кода.

Коды создаёт администратор; код непредсказуем, показывается при выдаче, на сервере хранится его хеш. Код можно отозвать. В режиме `invite` проверка кода, создание пользователя и отметка об использовании фиксируются одной транзакцией с блокировкой приглашения: из двух одновременных регистраций с одним кодом успешна только одна. При ошибке создания пользователя код не расходуется. Режим регистрации проверяется сервером в той же операции, а не только в форме сайта. Смена режима не удаляет существующих пользователей.

#### 11.3. Регистрация агентов и скрапперов

Пользователь создаёт агент через свой сайт. Каждый режим работы имеет отдельную регистрацию и собственный `agent_id`; общий контейнер не означает общих полномочий. Для веб-интерфейса и Telegram режимы регистрируются отдельно, если используются оба интерфейса. Например, ИИ-поиск в веб-интерфейсе и ручной поиск в боте могут иметь разные уровни доверия.

Для агентов, скрапперов и единственного балансировщика действует единая схема: постоянный несекретный ID и отдельный секретный `token`. ID задаётся при создании регистрации и далее не меняется: `agent_id` и `scrapper_id` — UUID, задаваемые владельцем в запросе создания, `balancer_id` задаётся администратором при настройке сервера. ID уникален в пределах своего типа во всём core, в том числе среди удалённых регистраций; повторное использование запрещено. Конфликт ID возвращает `409 Conflict` без сведений о владельце.

Core автоматически генерирует token при создании регистрации: 256 случайных бит криптографического генератора в текстовом виде. Пользователь не задаёт token. Token показывается при выдаче, core хранит только его хеш. Перевыпуск создаёт новый token и сразу отзывает прежний, не меняя ID, owner, права и привязки задач или записей. Токены компонентов используются только на серверной стороне и не попадают в публичные HTML, клиентский JavaScript, URL или логи.

В каждом запросе компонент передаёт свой ID в заголовке `X-Agent-ID`, `X-Scrapper-ID` или `X-Balancer-ID`, а token — в `Authorization: Bearer <token>`. Для всех API очередей балансировщик использует свой единый служебный token (11.6). Сервер проверяет пару ID/token, активность регистрации и её допустимые операции. Удалённая регистрация не может быть включена или получить новый token; её ID сохраняется для запрета повторного использования. Отсутствие любого из двух значений, неверный token или token другой регистрации даёт `401`. Одного ID недостаточно.

Core хранит в agent `agent_id`, `token_hash`, owner (ID пользователя), mode, trust_level и состояние enabled. Owner определяется по сессии при создании и далее не меняется. Владелец меняет уровень доверия своих агентов, отключает их и перевыпускает token. Агент не может менять свою регистрацию, owner или trust_level. По проверенной паре agent_id/token core определяет owner, trust_level и допустимые операции при каждом запросе; переданные клиентом owner, trust_level и фильтры эти права не расширяют. Отдельный пароль агента не требуется.

Сайты агентов и скрапперов принадлежат пользователю: он может менять их, публиковать в интернете, открывать без входа или назначать любые собственные логины и пароли, включая admin. Core не требует на этих сайтах своей сессии, своей формы входа или обязательного доступа системного администратора. Локальный логин admin не даёт административных прав в core. Кабинет и административный сайт самого core остаются под его аутентификацией. Посетители открытого сайта агента могут пользоваться предоставленными владельцем возможностями, но каждый запрос приложения к core всё равно ограничен зарегистрированным агентом и его правами; публичность сайта этих прав не меняет.

Скраппер также создаётся пользователем через его сайт и имеет отдельные `scrapper_id` и `token`. Core хранит owner и состояние скраппера. После создания экземпляр скраппера поднимает собственный сайт для настройки источников, режимов, очередей и уровня доверия отправляемых записей. Публикацию сайта и правила входа на него определяет владелец, независимо от входа в core. Скраппер назначает `trust_level` своим записям при отправке; owner и `scrapper = scrapper_id` core подставляет из проверенной регистрации скраппера. Скраппер не получает поисковые права агента и не может записывать данные от имени другого владельца.

#### 11.4. Владение записью и уровни доверия

Каждая запись имеет ровно одного владельца. В таблицу record добавляются три обязательных поля:

| Поле | Значение |
|---|---|
| `owner` | Внешний ключ на пользователя |
| `trust_level` | Уровень доверия записи, назначенный скраппером владельца |
| `scrapper` | UUID скраппера, впервые добавившего запись: ссылка на scraper.scrapper_id; core заполняет из проверенной регистрации |

Уникальный ключ записи — `(owner, source_id, source_url)`. `source_id` — имя источника (`youtube`, `telegram`), в прежней версии ТЗ поле называлось `source`. Owner записи и скраппера не меняется после создания. Одинаковый материал у разных пользователей хранится отдельными record с отдельными деревьями, файлами, статусами, задачами и уровнями доверия. Между пользователями дедупликации нет; таблицы связи многие ко многим и поля `owners` нет. Поле scrapper неизменно и имеет того же owner, что запись. Повторная отправка внутри одного владельца, включая отправку другим скраппером, не обновляет существующую запись, в том числе её trust_level и scrapper. Удаление скраппера отзывает token и скрывает регистрацию из активных списков, но сохраняет строку регистрации и её ID для ссылок record.scrapper; записи не удаляются. Поле scrapper хранит происхождение и не добавляет ограничений к существующим правилам доступа по owner и trust_level.

Уровни — неотрицательные целые числа; большее значение агента даёт доступ к большему диапазону записей своего владельца. Уровни разных пользователей между собой не сравниваются. Владелец может менять trust_level своей записи через кабинет; агент не может менять уровни записей, собственные права или владельца.

Для запроса агента core сам добавляет обязательное условие:

```sql
record.owner = :authenticated_agent_owner
AND record.trust_level < :authenticated_agent_trust_level
```

Оба параметра получены core из аутентифицированной регистрации агента. Сравнение строгое: при равных уровнях доступа нет. Например, при уровне агента 5 доступны записи его владельца с уровнями 0–4, но не 5; агент уровня 0 не получает ни одной записи. Запись другого пользователя недоступна при любом её уровне.

Условие применяется до поиска, ранжирования, подсчётов, лимитов и формирования ответа ко всем объектам через их record: к `search`, `read`, чтению по ID, дереву, файлам и возможному будущему извлечению медиа. Для поиска и чтения содержимого дополнительно обязательно `record.status = 'done'`. Пользовательский кабинет показывает собственные записи всех статусов; сессия владельца позволяет управлять своими записями и их уровнями. Агенту такое право сессии не передаётся.

Хранилища исходников и task_storage не публикуются как открытые каталоги: файл выдаётся только через авторизованную операцию core. Знание record_id, file_id или пути не заменяет проверку доступа.

Курсоры, кеши и сохранённая выдача разделяются по agent_id и владельцу; секретный token в них не раскрывается. На каждой странице core снова проверяет действующие права и принадлежность записей: снижение уровня агента, повышение уровня записи, удаление записи или отзыв доступа не позволяют дочитать старую выдачу. Недоступный ID возвращает тот же ответ, что отсутствующий; поля, ошибки, счётчики и ссылки не раскрывают чужие записи.

#### 11.5. Удаление записи у себя

Core предоставляет операцию `DELETE /api/records/{record_id}`. При вызове агентом удаляется record, только если его owner совпадает с owner агента, а текущий `record.trust_level` строго меньше текущего уровня агента. Проверка полномочий и удаление выполняются одной транзакцией с согласованными блокировками регистрации агента и record: изменение уровней не даёт обойти проверку. Передать другого owner нельзя. Операция доступна для записи в любом статусе; фильтр `done` относится к поиску и чтению, а не к удалению.

Дерево и задачи удаляются каскадом, каталоги исходных файлов и task_storage удаляет очистка хранилищ. Поздние результаты удалённых задач игнорируются. Фоновый приём и разбор синхронизируются с удалением по record_id: после коммита удаления они не могут повторно создать дерево или файлы удалённой записи. Копии материала других пользователей не затрагиваются. Повторное удаление не раскрывает, существовала ли чужая запись. Владелец может выполнить удаление из своего кабинета без посредничества агента; администратор — для любой записи.

Повторная отправка скраппером после удаления считается новым добавлением для владельца с новым record_id; правила повторного сканирования описаны в разделе «Скрапперы».

#### 11.6. Единственный балансировщик и централизованные очереди

Балансировщик в системе один; постоянный `balancer_id` и token задаются при настройке сервера. Core проверяет их во всех служебных запросах. Одна пара даёт доступ к очередям всех логических источников, но не к поиску и кабинету. Пользовательские API не создают балансировщики и не выдают их полномочия.

Все очереди и результаты находятся в core. Логические источники — сам core и каждый зарегистрированный `agent_id`. При регистрации агента core создаёт его область очередей `transcribe`, `ocr`, `embed`; для агента `task_source_id = agent_id`, для собственных задач core используется постоянный служебный ID. Скрапперы отправляют записи, а core создаёт задачи в своих общих очередях; отдельных очередей скрапперов нет. `task_source_id` не равнозначен `record.source_id` (`youtube`, `telegram`).

Агент ставит задачи и читает результаты через core с существующей парой `agent_id/token`. Core определяет источник и owner по авторизации, не по параметрам клиента. Агент не может читать чужие задачи, задавать сложность или приоритет и вызывать служебные операции балансировщика. Задачи и результаты разных регистраций изолированы, в том числе при общем сервере приложения. Агентам не требуется `task_endpoint` или входящее API очередей.

Core публикует список источников, наличие задач и приоритеты через `GET /api/task-sources`; все служебные операции очередей обслуживает сам. Полный контракт — в [ТЗ балансировщика](docs/balancer/README.md#http-контракт-с-core), серверная обработка — в 4.2.

Новый агент появляется в списке без перезапуска балансировщика. При удалении агента core исключает источник из списка и отменяет его ожидающие и взятые задачи. Поздние result/fail игнорируются, reset ничего не меняет; эти операции подтверждаются `204`. Claim и скачивание входа удалённого источника возвращают `404 task_source_not_found`. Данные очищаются по политике хранения агентских задач. Блокировка пользовательского доступа не мешает служебному reset.

Приоритеты источников и типов задаёт core. Все агенты равноприоритетны и строго выше core. По умолчанию транскрибация — 3, OCR — 2, embed — 1. Пользователь не может менять приоритет своего агента; trust_level на него не влияет. Порядок обхода и вытеснение определяет балансировщик по полученным значениям, как описано в его ТЗ.

#### 11.7. Проверяемые сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Два пользователя прислали одинаковые source_id/source_url | Два record с разными owner, ID, деревьями, файлами и независимой обработкой |
| Повторная отправка той же ссылки тем же владельцем с другим trust_level | Существующая запись не меняется; новая не создаётся |
| Агент уровня 5 обращается к собственным записям уровней 4 и 5 | Первая доступна, вторая недоступна для поиска, чтения и удаления |
| Агент с любым уровнем передал чужой ID или подставил owner/trust_level в запрос | Чужие данные не выдаются и не удаляются; полномочия не меняются |
| После первой страницы понизили уровень агента, повысили уровень записи или отозвали доступ | Следующая страница и кеш не выдают ставшие недоступными данные |
| Запись удалили во время приёма, разбора или выполнения задачи | Дерево не восстанавливается, поздний результат игнорируется, файлы удаляет очистка |
| Две регистрации одновременно используют один код | Ровно одна успешна; ошибка создания пользователя не расходует код |
| Создали новый режим агента в работающей системе | Core создаёт отдельные очереди agent_id; он появляется в списке без перезапуска балансировщика и проходит reset до claim |
| При работе агента появились задачи другого агента того же приоритета | Вытеснения нет; при следующем обходе равенство разрешается по ID |
| Владелец опубликовал сайт агента без входа или с локальным логином admin | Посетители используют возможности этого сайта; запросы к core ограничены его зарегистрированными агентами, локальный admin не даёт прав администратора core |
| Запрос к API агента в core не содержит действующего agent_id | Доступ отклонён независимо от публикации сайта и локального входа на нём |
| Пользователь вызвал административное API или API балансировщика | Доступ отклонён; регистрация администратором или балансировщиком через пользовательский запрос невозможна |
| Агент ставит задачу и запрашивает чужой task_id | Источник выбирается по регистрации; чужой результат возвращает `404`, очереди другого агента не затрагиваются |
| Балансировщик проверяет очереди | Один JSON содержит все task_source_id, наличие задач и приоритеты типов; адресов и токенов источников нет |
| Балансировщик набирает пачку | Claim выдаёт сложность core и метаданные; входы, включая текст, скачиваются только после завершения набора |
| Скраппер отправляет запись | Задачи создаёт core в собственных очередях; отдельного источника задач скраппера нет |

## Балансировщик

### Назначение и конфигурация

Балансировщик — демон, который получает задачи из core, собирает пачки и запускает воркеры `transcribe`, `ocr`, `embed`. В каждый момент на GPU работает один процесс воркера. Очередь пачек и состояние выполнения хранятся в памяти; входы скачиваются во временные локальные файлы.

Конфигурация: адрес core, постоянный `balancer_id`, служебный token, команда запуска каждого воркера (массив argv), порог пачки X для каждого типа, интервалы проверки очередей, ожидания при пустых очередях и повторов HTTP-запросов, таймаут HTTP-запроса, каталог временных файлов. Пороги — конечные неотрицательные числа в единицах `complexity`, возвращаемой core для соответствующего типа.

Для балансировщика `task_source_id` — непрозрачный ID источника. Список источников, приоритеты и наличие задач приходят из API. Балансировщик применяет их одинаково ко всем источникам и типам, без зашитых значений приоритетов и исключений по ID. Политика приоритетов, устройство очередей и расчёт сложности принадлежат [core](docs/core/04_tasks_and_queues.md).

### Источники и порядок выполнения

1. При запуске, в начале каждого прохода и каждого цикла проверки во время работы воркера получать `GET /api/task-sources`.
2. Каждый впервые обнаруженный источник инициализировать через `/reset`. До успешного ответа его задачи не брать; неуспешную инициализацию повторять на следующих проходах. Это правило одинаково для всех источников. Источники, исчезнувшие из снимка, исключать из обхода; вновь появившийся источник инициализировать заново.
3. Обходить источники по убыванию `priority`, при равенстве — по `task_source_id` в лексикографическом порядке. Внутри источника обходить типы по убыванию приоритета очереди, при равенстве — по имени типа в лексикографическом порядке.
4. Брать задачи только из очередей с `has_tasks = true`. Выбранную очередь обрабатывать до пустого `/claim` или вытеснения. Затем переходить к следующему типу, источнику и новому проходу. Снимок не гарантирует выдачу задачи: окончательный ответ даёт `/claim`.
5. Если все доступные очереди пусты, ждать интервал из конфигурации. Пока выполнение выключено администратором в интерфейсе балансировщика, новые пачки не набирать; уже запущенная пачка завершается и передаёт результат.

### Набор и выполнение пачки

Когда локальная очередь пачек пуста, набирать одну пачку одного типа от одного источника:

1. Последовательно вызывать `/claim`, добавляя задачу и её `complexity` в сумму. Входы на этом этапе не скачивать.
2. Остановить набор, когда сумма строго больше X либо `/claim` вернул `{"tasks":[]}`. При равенстве продолжать; превысившая порог задача входит в пачку. Пустую пачку не запускать.
3. Скачать каждый вход через GET по `input.url` с теми же служебными заголовками. После полного скачивания всех входов запустить воркер по контракту ниже. Ответ `404` на вход исключает задачу из пачки; `/fail` для неё не отправляется. Если пачка опустела, перейти к новому проходу.
4. Получить и проверить результат всей пачки, отправить его через `/result`. До подтверждения результатов или ошибки следующую пачку не запускать и новые задачи не брать.
5. Удалить локальные входы после подтверждения `/result` или `/fail`, отмены работы либо исключения задачи из пачки. После перезапуска удалить оставшиеся временные файлы предыдущего запуска.

### Сбой воркера

Если воркер завершился с ошибкой на пачке из k > 1 задач, записать WARNING и заменить её в локальной очереди k пачками по одной задаче, сохранив порядок. Уже скачанные входы использовать повторно. Каждую успешную одиночную задачу немедленно отправлять через `/result`.

При падении одиночной задачи отправить `/fail`; дальнейших запусков для неё нет. `error.attempts` — число запусков воркера с этой задачей после последнего claim: 1 для исходной одиночной пачки, 2 после падения общей пачки и одиночного запуска. Сетевые повторы и принудительное завершение при вытеснении в это число не входят.

### Проверка и вытеснение

Параллельно с работой воркера с заданным интервалом получать свежий снимок источников. Если у инициализированного источника со строго большим приоритетом есть непустая очередь:

1. Завершить процесс воркера сигналом `SIGKILL`, дождаться его завершения, отбросить частичный результат.
2. Очистить локальную очередь пачек и входы отменённой работы.
3. Вызвать `/reset` текущего источника и дождаться успешного ответа.
4. Обновить снимок и начать новый проход.

Сравнивать приоритеты источников по свежему снимку, включая приоритет выполняемого источника. При равенстве вытеснения нет. Более высокий приоритет другого типа внутри того же источника текущую работу не прерывает: тип будет выбран в следующем проходе. Если текущий источник исчез из снимка, отменить его локальную работу и начать новый проход. Подтверждённые результаты и ошибки повторно не отправлять.

### Сеть и перезапуск

При недоступности core приостановить набор. Уже загруженная пачка может завершиться; результат хранить до восстановления связи. Вытеснение по устаревшему снимку не выполнять. Ошибка скачивания — повод повторить GET, а не запускать воркер или отправлять `/fail`.

Поведение при ошибках HTTP и потере ответа определено в контракте ниже. Перед возобновлением claim после восстановления связи обновлять список источников.

Воркер запускать из главного потока как дочерний процесс с `prctl(PR_SET_PDEATHSIG, SIGKILL)`: он должен завершаться при гибели балансировщика. После установки сигнала проверять, что родитель ещё тот же, чтобы закрыть гонку с его завершением. После перезапуска локальная работа не восстанавливается: получить список источников и заново пройти их инициализацию через `/reset`.

### HTTP-контракт с core

Это полное описание исходящих HTTP-вызовов балансировщика. Все пути относятся к адресу core из конфигурации. В каждом запросе, включая скачивание входа:

```http
X-Balancer-ID: <balancer_id>
Authorization: Bearer <token балансировщика>
```

Все POST передают JSON с `Content-Type: application/json`. GET не имеют тела и query-параметров. Все поля в примерах обязательны, если явно не указано обратное. `balancer_id` в теле должен совпадать с заголовком. ID источника и задачи — непустые строки; при подстановке в URL каждый ID кодируется как один сегмент пути.

#### `GET /api/task-sources`

Ответ `200`, `Content-Type: application/json`:

```json
{
  "items": [
    {
      "task_source_id": "<ID источника>",
      "priority": 10,
      "queues": {
        "transcribe": {"has_tasks": true, "priority": 0},
        "ocr": {"has_tasks": false, "priority": 5},
        "embed": {"has_tasks": true, "priority": 5}
      }
    }
  ]
}
```

`items` — полный список без пагинации, может быть пустым; ID источников уникальны. `queues` содержит все три типа, в том числе пустые. `has_tasks` — boolean, наличие ожидающих задач на момент ответа. Оба уровня `priority` — конечные числа: большее значение означает больший приоритет; допустимы отрицательные значения и равенства. Значения в примере не задают политику или значения по умолчанию. Порядок элементов ответа не задаёт порядок обработки.

#### `POST /api/task-sources/{task_source_id}/claim`

Тело:

```json
{"type":"transcribe","balancer_id":"<balancer_id>"}
```

`type` — `transcribe`, `ocr` или `embed`. Ответ `200`, JSON с массивом `tasks` длиной 0 или 1:

```json
{
  "tasks": [
    {
      "task_id": "<ID задачи>",
      "type": "transcribe",
      "complexity": 12.5,
      "input": {
        "url": "/api/task-sources/<ID источника>/tasks/<ID задачи>/input",
        "mime": "audio/flac"
      }
    }
  ]
}
```

Пустая очередь: `{"tasks":[]}`. Параметра `limit` нет. `type` выданной задачи совпадает с запрошенным. `complexity` — конечное неотрицательное число; балансировщик использует его как готовую оценку и не пересчитывает по данным. `input.url` — путь на том же core, ведущий к эндпоинту скачивания этой задачи; `input.mime` — строка MIME. Входного содержимого в claim нет.

Успешная выдача резервирует задачу за этим балансировщиком; резервирование может быть отменено на стороне core, что проверяется при последующих вызовах. Если ответ потерян, неизвестно, была ли задача взята: перед продолжением отбросить набранную пачку и выполнить `/reset` этого источника. Простой повтор claim может взять другую задачу и не восстанавливает потерянную выдачу.

#### `GET /api/task-sources/{task_source_id}/tasks/{task_id}/input`

Вызывать по `input.url`, полученному в claim. Ответ `200` — байты входа, `Content-Type` равен `input.mime`. Для текстового embed — UTF-8 с `text/plain; charset=utf-8`; остальные входы сохраняются как бинарные данные. Вход доступен только пока задача зарезервирована за этим балансировщиком. `404 task_not_available` означает, что вход уже недоступен; такую задачу исключить из пачки.

#### `POST /api/task-sources/{task_source_id}/result`

Тело для `transcribe` и `ocr`:

```json
{
  "balancer_id": "<balancer_id>",
  "results": [{"task_id": "<ID задачи>", "payload": {"text": "Полученный текст"}}]
}
```

`results` — непустой массив результатов задач одного источника. `payload.text` — строка; пустая строка допустима и является успешным результатом.

Для `embed` каждый элемент имеет следующий вид:

```json
{
  "task_id": "<ID задачи>",
  "payload": {"embed_model": "<имя модели>", "embedding": [0.12, -0.34, 0.56]}
}
```

`embed_model` — непустая строка с фактическим именем модели воркера; `embedding` — непустой массив конечных чисел полной размерности этой модели. В примере вектор сокращён. Балансировщик передаёт значения воркера без подмены модели или преобразования вектора.

Ответ `204 No Content`, без тела, после фиксации всех результатов. Результаты фиксируются по отдельности: если запрос оборвался, часть могла сохраниться. Повторять всё то же тело безопасно: удалённые, отменённые и уже завершённые задачи игнорируются. Существующая задача другого источника или другого исполнителя отклоняется с `404 task_not_available` без изменения этой задачи.

#### `POST /api/task-sources/{task_source_id}/fail`

Тело:

```json
{
  "balancer_id": "<balancer_id>",
  "task_ids": ["<ID задачи>"],
  "error": {
    "message": "CUDA out of memory",
    "attempts": 2,
    "worker": "transcribe",
    "model": "<имя модели>"
  }
}
```

`task_ids` — непустой массив, `error.message` — непустая строка, `error.attempts` — положительное целое. `error.worker` и `error.model` — необязательные строки. Балансировщик отправляет одну упавшую одиночную задачу за вызов.

Ответ `204 No Content`, без тела, после фиксации ошибки. Правила игнорирования устаревших задач, отклонения чужих задач и повторной отправки те же, что у `/result`. `/fail` завершает задачу ошибкой; для отмены и повторного выполнения используется `/reset`.

#### `POST /api/task-sources/{task_source_id}/reset`

Тело:

```json
{"balancer_id":"<balancer_id>"}
```

Ответ `204 No Content`, без тела. Все незавершённые задачи указанного источника, зарезервированные за этим балансировщиком, вновь доступны для claim. Завершённые задачи не меняются. Повтор безопасен; пока reset не подтверждён, новые задачи этого источника не брать.

Для удалённого источника `/result` и `/fail` игнорируют поздние сообщения, `/reset` ничего не меняет; все три возвращают `204`. Claim и скачивание входа удалённого источника возвращают `404 task_source_not_found`. Для неизвестного ID источника все операции возвращают `404 task_source_not_found`.

#### Ошибки и повторы

Ошибки core имеют `Content-Type: application/json` и тело:

```json
{"error":{"code":"invalid_request","message":"Описание ошибки"}}
```

| Ответ / ситуация | Действие балансировщика |
|---|---|
| `400 invalid_request` — `balancer_id` в теле не совпал с заголовком; `422 invalid_request` — неверные поля, тип задачи или payload | Записать ошибку протокола и приостановить выполнение до исправления. Не повторять неизменённый запрос и не отправлять `/fail` из-за HTTP-ошибки |
| `401 unauthorized` — неверные полномочия; `403 forbidden` — нет права на операцию | Приостановить выполнение до исправления конфигурации/полномочий |
| `404 task_source_not_found` — источник неизвестен либо удалён для claim/input | Отменить локальную работу этого источника, обновить список; не продолжать claim по старому снимку |
| `404 task_not_available` при скачивании входа | Исключить задачу из пачки |
| `404 task_not_available` при result/fail | Записать нарушение контракта владения задачей и приостановить выполнение до исправления |
| `5xx`, обрыв связи, таймаут, неполный ответ | Подождать интервал повторов. GET повторить; result/fail повторить с тем же телом; reset повторить до подтверждения. Для claim сначала выполнить reset источника, как описано выше |

При неизвестном результате result/fail не делать reset и не брать новую работу до подтверждения отправки. Неверный успешный ответ (некорректный JSON, отсутствующие поля, неподходящие значения) — ошибка протокола; для claim перед продолжением также требуется reset, поскольку резервирование могло состояться.

### Контракт запуска воркера

У воркеров нет HTTP API. Балансировщик запускает команду выбранного типа из конфигурации без shell, передаёт один JSON-документ UTF-8 в stdin и закрывает stdin:

```json
{
  "type": "transcribe",
  "tasks": [
    {"task_id": "<ID задачи>", "input": {"path": "/tmp/balancer/batch/input-1", "mime": "audio/flac"}}
  ]
}
```

Все поля обязательны. `tasks` — непустая пачка одного типа и источника, ID уникальны. `input.path` — абсолютный путь к полностью скачанному локальному файлу, доступному воркеру для чтения; `input.mime` берётся из claim. Текстовые входы также передаются файлом. Воркеру не передаются HTTP-полномочия и адрес core.

Успех: код завершения 0 и один JSON-документ UTF-8 в stdout:

```json
{"results":[{"task_id":"<ID задачи>","payload":{"text":"Полученный текст"}}]}
```

`payload` имеет формат `/result` для выбранного типа. На каждую входную задачу должен быть ровно один результат; посторонние ID, пропуски и дубликаты запрещены. Порядок результатов произвольный, сопоставление — по `task_id`. Логи идут только в stderr; stdout читается параллельно с stderr, чтобы процесс не блокировался на заполненной трубе.

Ненулевой код завершения, сигнал, неполный или некорректный ответ означают падение всей пачки. Частичные результаты не принимаются. Сообщение для `/fail` формируется из причины завершения и stderr; имя воркера и известное имя модели передаются необязательными полями. Принудительное завершение при вытеснении обрабатывается как отмена через `/reset`.

## Скрапперы

Скрапперы отвечают за сбор данных. Core не знает, что такое ютуб или любой другой источник: он получает только record: универсальные поля (ссылка на источник, дата публикации, дата скраппинга и т. п.) и `metadata` со специфичными для источника данными.

Каждый скраппер создаётся пользователем в его кабинете, регистрируется в core с собственным scrapper_id и owner и после создания поднимает свой сайт настройки. Это пользовательский компонент; администратор управляет учётными записями, а не создаёт скрапперы за пользователей. Владелец сам определяет публикацию, устройство и доступ к сайту: может открыть его в интернете, оставить без входа или задать свои логин и пароль. Сессия core и доступ системного администратора на этот сайт не обязательны; местный логин admin не даёт административных прав в core. Независимо от сайта core принимает данные только с действующими полномочиями зарегистрированного скраппера и подставляет его owner.

Каждый скраппер обязан заполнить source_id, source_url и trust_level записи и привести source_url к каноническому виду. Core проверяет пару scrapper_id/token, подставляет owner и scrapper = scrapper_id из регистрации и проверяет неотрицательный целочисленный trust_level. Уникальный ключ — (owner, source_id, source_url). Одинаковые материалы разных владельцев принимаются как независимые записи, включая отдельные файлы и обработку; совпадение URL не открывает чужую копию. Source_id обозначает тип источника (youtube, telegram), а не идентификатор экземпляра скраппера.

Уровень доверия назначает скраппер по настройкам своего сайта при формировании записи. Он сохраняется вместе с записью в локальной очереди, чтобы повторная отправка использовала то же значение. Повторная отправка существующей записи этого owner не меняет её trust_level и scrapper. Владелец может отдельно изменить уровень своей записи в кабинете core. Скраппер не выбирает другого owner и не получает доступ к поиску или служебным очередям балансировщика.

Скрапперы сами отвечают за целостность данных: если получить запись целиком не удалось (например, нет интернета), она в core не отправляется. Пустую запись (без текста и без файлов) скраппер тоже не отправляет; если core всё же отклонил запись как пустую (HTTP 422), скраппер пишет это в лог и удаляет запись из очереди.

#### Отправка в core

Все запросы содержат `X-Scrapper-ID: <scrapper_id>` и `Authorization: Bearer <token скраппера>`. Лимит файла — `GET /api/limits`; проверка записи — `GET /api/records/status?source_id=...&source_url=...` или `GET /api/records/{record_id}/status`; отправка — `POST /api/records` (`multipart/form-data`: JSON-часть `record`, затем бинарные части `files`). Точные поля и ответы — в [HTTP API](docs/api.md).

Каждый скраппер держит очередь отправки в core (SQLite, FIFO, персистентна) и папку с файлами записей, ожидающих отправки. В core одновременно находится не больше K незавершённых записей скраппера (K задаётся в конфиге скраппера): пока core разбирает следующую запись, GPU обрабатывает задачи предыдущих.

1. Пока незавершённых записей меньше K, скраппер отправляет следующую запись из начала очереди через `POST /api/records`. Core регистрирует её, сохраняет файлы и сразу отвечает `202`, не дожидаясь разбора (см. Core, 3.1).
2. Скраппер периодически вызывает `GET /api/records/{record_id}/status` для отправленных записей. Любая проверка существования или статуса в core ограничена owner его регистрации, в том числе по ID и по source_id/source_url; чужая копия даёт тот же ответ unknown, что отсутствующая. Пока запись в обработке (processing), она и её файлы остаются в очереди и в папке.
3. Когда core отвечает `done` или `error`, скраппер удаляет запись из очереди и её файлы из папки, освобождая место для следующей.
4. Если core отвечает `unknown` (записи нет: например, core упал при приёме), запись отправляется заново.

#### Файлы больше `max_file_size`

Размер каждого файла не должен превышать `max_file_size` core (значение отдаётся по API core, по умолчанию около 15 ГБ). Запись, в которой хотя бы один файл больше, в core не отправляется целиком: скраппер удаляет скачанное и заносит её в свою SQLite-таблицу «пропущено по размеру». Размер проверяется до скачивания, если источник его сообщает, и после скачивания. Перед добавлением записи в очередь скраппер сверяется и с этой таблицей, поэтому сканеры не скачивают такую запись повторно на каждом проходе. Для Telegram это почти недостижимо: лимит файлов там 2–4 ГБ.

#### Записи с ошибкой и повторная отправка

Когда core отвечает error, скраппер удаляет запись из своей очереди и папки с файлами и повторно её не отправляет: запись остаётся в core в статусе error. Перезапуска нет; запись можно удалить в кабинете core или через API с проверкой прав (Core, 6 и 11.5). После удаления своей копии core отвечает на неё unknown, даже если у другого пользователя есть такой материал. Скраппер отправит её заново, только если снова встретит.

Ограничение: снова встречают запись только режимы, которые на каждом проходе пересканируют источник целиком, — сканеры каналов, плейлистов и истории YouTube. Сканеры Telegram читают только сообщения после `last_message_id`, а Telegram-бот скраппера YouTube принимает ссылку один раз, поэтому сами удалённую запись не пришлют: ссылку нужно заново отправить боту вручную. Для сканеров Telegram это открытый вопрос (Core, 10).

### YouTube

Скраппер YouTube — демон. У него несколько режимов работы, каждый включается отдельно в конфиге. Режимы выполняются последовательно, а не параллельно, чтобы не получить бан от YouTube.

#### Архитектура

Скраппер состоит из следующих частей:

- **Демон** — по очереди обходит включённые режимы, скачивает видео и кладёт их в очередь отправки в core.
- **Очередь загрузки** — хранится в памяти, не персистентна: после перезагрузки восстанавливается повторным сканированием.
- **Очередь отправки в core** — хранится в SQLite, персистентна (переживает перезагрузку).
- **Папка с файлами** — специальная папка внутри скраппера, где лежат файлы видео, ожидающих отправки в core.
- **Таблица пропущенных по размеру** — SQLite, см. «Файлы больше `max_file_size`».
- **Отправка в core** — скраппер сам отправляет записи в core (см. «Отправка в core»).
- **Telegram-бот** — принимает ссылки от пользователя (см. ниже).
- **Сайт скраппера** — веб-интерфейс на FastAPI, поднимаемый экземпляром после создания в кабинете пользователя. Владелец сам определяет размещение и доступ, включая публикацию в интернете и собственные логины/пароли; сессия core не требуется.

#### Идентификация записи

- `source_id` = `youtube`.
- Owner core подставляет из регистрации экземпляра скраппера; trust_level назначается по настройкам его сайта. Ключ записи в core — (owner, source_id, source_url). Проверки существования относятся только к owner скраппера.
- `source_url` = ссылка на видео в каноническом виде: `https://www.youtube.com/watch?v=<video_id>`. Ссылки вида `youtu.be/…` и `/shorts/…` приводятся к этому виду, иначе одно и то же видео из разных режимов получило бы разные ключи.
- `text` = склейка названия и описания видео, `title` = название, `author` = канал.
- `source_created_at` = дата публикации видео, `scraped_at` = момент получения записи скраппером.
- В `metadata` кладутся длительность и признак shorts.

#### Режимы работы

- **Сканер каналов** — обходит список YouTube-каналов и выкачивает все их видео.
- **Сканер плейлистов** — обходит список плейлистов и выкачивает все видео из каждого.
- **Сканер истории** — получает доступ к аккаунту YouTube и на каждом проходе читает всю доступную историю просмотров, сверяет её с core и выкачивает просмотренные видео, которых там нет.
- **Telegram-бот** — принимает ссылки на видео, которые пользователь отправляет ему в чат, и ставит их на загрузку (см. «Telegram-бот»).

#### Устройство загрузчика

Скраппер работает с двумя очередями:

- **очередь загрузки** — содержит объекты `youtube_video`; изначально в них есть только ссылка;
- **очередь отправки в core** — содержит те же объекты после скачивания: с аудио-/видеофайлом (см. ниже) и метаданными.

Порядок работы:

1. Демон по очереди обходит режимы, включённые в конфиге: каждый режим сканирует свой источник и находит видео.
2. Перед добавлением видео в очередь загрузки проверяется, что его нет ни в одной из двух очередей, ни в таблице пропущенных по размеру и ни в core. Проверка в core выполняется по `source_id` и `source_url`.
3. Пока суммарный размер скачанных файлов меньше X ГБ, загрузчик берёт видео из очереди загрузки и скачивает его. Перед скачиванием ещё раз проверяется по `source_id` и `source_url`, что видео нет в core и в очереди отправки в core. Если YouTube сообщает размер файла и он больше `max_file_size`, видео не скачивается, а заносится в таблицу пропущенных по размеру.
4. Пока видео не загружено полностью, оно остаётся в очереди загрузки. Как только загрузка завершена, размер проверяется ещё раз: если файл больше `max_file_size`, он удаляется, а видео заносится в таблицу пропущенных по размеру. Иначе объект сразу переносится в очередь отправки в core.

#### Аудио или видео

Для каждого режима настраивается, что именно скачивать: только аудио или видео целиком.

- **Сканер каналов** хранит режим загрузки для каждого канала в списке каналов. В конфиге задаётся значение по умолчанию. Это значение по умолчанию именно для пользователя, а не для системы: оно соответствует положению переключателя при добавлении канала в админке, поэтому поле режима в списке каналов не может быть пустым.
- **Сканер плейлистов** работает так же, как сканер каналов.
- **Сканер истории** настраивается отдельно для shorts и для обычных видео.
- **Telegram-бот** запрашивает режим отдельно для каждого видео.

#### Передача видео в core

Очередь отправки в core — SQLite, FIFO. Записи отправляются по общим правилам (см. «Отправка в core»): в core одновременно не больше K незавершённых записей скраппера, запись и её файлы остаются у скраппера, пока core не ответит `done` или `error`, а на `unknown` запись отправляется заново. При `error` исходник остаётся в core, повторно запись не отправляется, пока её не удалят вручную в веб-интерфейсе core (см. «Записи с ошибкой и повторная отправка»).

#### Telegram-бот

- Владелец скраппера сам определяет, какие Telegram-аккаунты могут присылать ссылки боту. Это не меняет owner и полномочия скраппера в core.
- Пользователь присылает боту ссылку на видео, бот спрашивает режим загрузки (аудио или видео) и ставит видео на загрузку.
- Бот хранит в SQLite список присланного, что ещё не завершено в core. Список переживает перезагрузку: ссылки от бота нельзя восстановить повторным сканированием, а очередь загрузки хранится в памяти.
- Когда core отвечает `done`, элемент удаляется из списка.
- Когда core отвечает `error`, бот явно сообщает об этом пользователю в чате (с текстом ошибки) и удаляет элемент из списка. Чтобы отправить видео заново, запись нужно удалить в веб-интерфейсе core и снова прислать ссылку боту.
- Если видео пропущено по размеру, бот тоже сообщает об этом пользователю.

#### Сайт скраппера

Сайт написан на FastAPI; владелец сам задаёт, кому и с какими локальными логинами/паролями он доступен. В нём можно:

- смотреть статистику по очередям (загрузки и отправки в core) и список видео, пропущенных по размеру;
- смотреть и редактировать списки каналов и плейлистов, в том числе выбирать режим загрузки (аудио или видео) при добавлении;
- включать и выключать режимы работы;
- задавать trust_level отправляемых записей.

### Telegram

Скраппер Telegram — демон, создаваемый пользователем через его кабинет, как скраппер YouTube. Режимы выполняются последовательно, записи отправляются в core по общим правилам (см. «Отправка в core»), записи с файлами больше max_file_size заносятся в таблицу пропущенных по размеру. После создания экземпляр поднимает свой сайт на FastAPI, с публикацией и правилами входа по выбору владельца; сессия core не обязательна. Своего Telegram-бота у скраппера нет.

#### Доступ к Telegram

История каналов и чатов читается через MTProto (например, Telethon или Pyrogram) от имени пользовательского аккаунта: Bot API не умеет читать историю каналов, в которых нет бота. Файл сессии — секрет, в репозиторий не попадает. При `FloodWait` скраппер ждёт указанное время и продолжает.

#### Идентификация записи

- Record — одно сообщение канала или чата. Альбом (сообщения с общим `grouped_id`) — один record с несколькими файлами.
- `source_id` = `telegram`.
- Owner core подставляет из регистрации экземпляра скраппера; trust_level назначается по настройкам его сайта. Ключ записи в core — (owner, source_id, source_url). Проверки существования относятся только к owner скраппера.
- `source_url` в каноническом виде:
  - публичные каналы и супергруппы — `https://t.me/<username>/<message_id>`;
  - приватные каналы и супергруппы — `https://t.me/c/<internal_id>/<message_id>`;
  - личные диалоги и обычные (не супер-) группы — у них нет ссылок t.me, а id сообщений свои у каждого аккаунта, поэтому используется псевдоссылка `tg://chat/<peer_id>/<message_id>`. Она уникальна и не меняется для нашего аккаунта, но по ней нельзя перейти.

  Для альбома берётся ссылка на первое сообщение.
- `text` = текст или подпись, `author` = канал или отправитель, `source_created_at` = дата отправки сообщения.
- `parent_source_url` = сообщение, на которое это ответ. У пересланных сообщений оригинал записывается в `metadata`, а ключ строится по текущему сообщению.

#### Режимы работы

- **Сканер каналов** — обходит список каналов. Для каждого хранится `last_message_id`: скраппер читает только новые сообщения, а при первом запуске — всю историю.
- **Сканер чатов** — то же самое для групп и личных диалогов из явного списка.

Перед добавлением сообщения в очередь отправки проверяется, что его нет в очереди, в таблице пропущенных по размеру и в core (по `source_id` и `source_url`). Проверка в core нужна и при наличии `last_message_id`, на случай сброса состояния.

Из-за `last_message_id` сканеры не увидят заново запись, удалённую вручную в core (см. «Записи с ошибкой и повторная отправка»). Есть идея на каждом проходе брать все id сообщений группы или чата и сверять их с core; пока это открытый вопрос.

#### Что скачивать

Для каждого канала или чата настраивается глубина: только текст, текст и фото, или всё (включая видео и документы). Отдельного ограничения по размеру у глубины нет: действует общее правило `max_file_size` — сообщение с файлом больше него пропускается целиком и заносится в таблицу пропущенных по размеру (на практике недостижимо: лимит файлов Telegram 2–4 ГБ). Значение по умолчанию в конфиге задаётся для пользователя, а не для системы: оно соответствует положению переключателя при добавлении канала в админке, поэтому поле в списке каналов не бывает пустым. Голосовые сообщения и кружки идут как аудио на транскрибацию.

#### Ограничения

- Отредактированные сообщения не перечитываются.
- Удалённые на источнике сообщения не отслеживаются.

#### Сайт скраппера

- статистика по очереди отправки в core и список сообщений, пропущенных по размеру;
- список каналов и чатов, в том числе выбор глубины скачивания при добавлении;
- включение и выключение режимов работы;
- настройка trust_level отправляемых записей.

## Агент

Приложение агента предоставляет пользователю ИИ-поиск, ручной поиск и Telegram-бот. Они могут входить в один монолит и разворачиваться в одном контейнере. При этом каждый режим — отдельный зарегистрированный агент со своим agent_id, owner и trust_level на сервере core (Core, 11). Для веб-интерфейса и Telegram режимы регистрируются отдельно, если используются оба интерфейса; ИИ-поиск и ручной поиск не делят одну регистрацию.

Каждый зарегистрированный agent_id имеет отдельные очереди транскрибации, OCR и эмбеддингов в core. Приложение отправляет задачи и входные данные в core и получает результаты оттуда с существующей парой agent_id/token. Core сам определяет источник по авторизации и изолирует задачи и результаты регистраций. Балансировщик общается только с core; входящее API очередей на сервере агента не требуется. Все агенты равноприоритетны и выше собственных очередей core. Пользователь не задаёт сложность и приоритет задач. Поиск и чтение также используют проверенную пару agent_id/token. Форматы постановки задач и получения результатов — в [HTTP API](docs/api.md).

### Главный веб-интерфейс

Веб-интерфейс — основная точка входа в пользовательское приложение агента. Владелец может менять его, публиковать в интернете и сам задавать доступ: открытый сайт либо собственные логины и пароли, в том числе admin. Сессия core на сайте агента не обязательна; местные роли не дают прав в core. Создание агентов, назначение их прав и управление пользователями выполняются в отдельном кабинете core под его аутентификацией (Core, 6 и 11).

Приложение хранит agent_id и token на серверной стороне и использует их при обращениях к core. Посетитель сайта получает те возможности, которые открыл ему владелец; публичный интерфейс не расширяет owner и trust_level зарегистрированного агента. Настройки, история и результаты локального приложения управляются владельцем сайта. Core обеспечивает изоляцию своих данных независимо от устройства интерфейса, включая обращения по прямому ID. Из приложения доступны разделы:

- **ИИ-агент** — диалог на естественном языке: ИИ-агент сам составляет поисковые запросы, читает найденное и формирует ответ со ссылками на источники.
- **Ручной поиск** — пользователь сам задаёт запрос и фильтры, просматривает результаты и открывает найденные данные без участия LLM.
- **Telegram-бот** — просмотр состояния, включение и выключение бота. Выбранное состояние сохраняется между перезапусками контейнера. Выключение бота прекращает приём новых запросов из Telegram; веб-интерфейс и оба режима поиска в нём продолжают работать.

### Telegram-бот

Бот — встроенный интерфейс того же приложения. В Telegram пользователь может выбрать **поиск через ИИ-агента** или **ручной поиск**. Оба режима используют ту же реализацию поиска и контракт API core, что и веб-интерфейс, но каждый обращается со своим agent_id и использует свою область очередей. Какие Telegram-аккаунты могут пользоваться ботом, определяет владелец приложения. Выбор режима выбирает настроенную для него регистрацию; приложение обращается к core с её agent_id и token. Вне зависимости от доступа к боту core проверяет полномочия этой регистрации.

В режиме ИИ-агента бот принимает запрос, проводит поиск через ИИ-агента и возвращает ответ со ссылками. В ручном режиме бот позволяет задать поисковый запрос и фильтры, перейти к следующей странице результатов и открыть найденный объект. Переключение режимов доступно в интерфейсе бота.

### Ручной поиск

Веб-интерфейс предоставляет форму поиска, а бот — диалог и кнопки для задания тех же условий. Пользователь выбирает тип искомого объекта, фильтры и сортировку. Доступные поля и операции определяются через `GET /api/search/schema`. Для поиска по смыслу можно указать семантический запрос; его эмбеддинг агент получает через свою очередь и балансировщик. Поиск только по фильтрам эмбеддинга не требует.

Приложение преобразует выбранные условия в JSON-тело `POST /api/search`, показывает результаты со ссылками на источники и поддерживает постраничную выдачу. Через `POST /api/read` пользователь может открыть метаданные, дочерние объекты и сохранённый текст. LLM в ручном режиме не вызывается: пользователь получает найденные данные без сгенерированного ответа.

### Цикл обработки запроса через ИИ-агента

1. Пользователь вводит запрос в веб-интерфейсе или отправляет сообщение боту. Например, в Telegram можно отправить голосовое сообщение.
2. Если нужна транскрибация, приложение отправляет аудио в core, который создаёт задачу в очереди выбранного agent_id. Результат приложение получает из core. Все агенты имеют одинаковый приоритет выше core: при следующем запросе `GET /api/task-sources` балансировщик может вытеснить работу core. Другой агент с равным приоритетом не вытесняется; порядок при равенстве задаётся по ID.
3. Приложение запускает ИИ-агента с текстом запроса. Тяжёлые задачи, которые понадобятся дальше (эмбеддинг запроса для семантического поиска, OCR присланной картинки), также отправляются в core и ставятся в очередь того же agent_id.
4. ИИ-агент ищет ответ с помощью инструментов (см. ниже).
5. Приложение возвращает ответ со ссылками в тот интерфейс, из которого пришёл запрос.

### API поиска и инструменты ИИ-агента

Оба режима поиска используют HTTP API core: `GET /api/search/schema`, `POST /api/search`, `POST /api/read`. Каждый запрос содержит `X-Agent-ID: <agent_id>` и `Authorization: Bearer <token агента>` выбранного режима. В режиме ИИ-агента параметры инструментов составляет LLM, а приложение выполняет HTTP-запросы; в ручном режиме приложение собирает параметры по условиям пользователя. Заголовки, параметры и примеры ответов закреплены в [HTTP API](docs/api.md). Произвольных SQL, Python, выражений и команд оболочки в этом языке нет. Приложение проверяет вызов и передаёт запрос в API core; доступов и паролей БД у модели и приложения нет. Поисковый API отделён от API приёма записей, очередей и административных операций; через него агент выполняет только поиск и чтение. Для удаления своей записи есть отдельная операция DELETE /api/records/{record_id} с обязательной серверной проверкой owner и trust_level (Core, 11.5); она не позволяет менять уровни доверия, пользователей или регистрации.

#### Что действительно можно прочитать

В БД остаются дерево объектов, их поля и метаданные, текст chunk'ов и эмбеддинги. Содержимое text читается из его chunk'ов в порядке `ord`; отдельной полной копии текста нет. Границы chunk'ов сохраняются в ответе: инструмент не обещает восстановить исходное форматирование документа.

Изображения photo, аудиодорожки audio и отрендеренные страницы не хранятся долговременно. Наличие строки element или fragment не означает наличие готового медиафайла. После завершения обработки `task_storage` очищается, и инструменты агента его не используют. Долговременно хранится исходный file, из которого потенциально можно заново извлечь данные по `meta` (Core, 3.3).

Обязательных `get_fragment` с рендерингом и `get_element` с возвратом медиа нет. В первой версии агент читает сохранённый текст и метаданные и даёт ссылку на источник. Повторное извлечение медиа из исходника — отдельная возможность на будущее: она потребует поддержки конкретного формата и ограничений на вычисления. Примеры извлечения в Core, 3.3 описывают механизм, а не обязательные инструменты агента.

#### `GET /api/search/schema` — узнать доступные поля

Необязательные query-параметры: `target` (тип объекта), `source_id` (источник). Без них возвращается вся схема. Ответ `200` содержит версию схемы языка, типы объектов, доступные поля, связи, типы значений, операции фильтрации и пределы запросов. Можно запросить описание целиком либо для конкретного типа объекта и источника. Метаданные источников и форматов описываются здесь же, а не зашиваются в промпт агента.

Поиск доступен по разрешённым схемой полям выбранного объекта и его предков, включая `record.metadata` и `file/fragment/element/text.meta`. Числовые массивы эмбеддингов не выдаются и не используются как обычные фильтры: для них есть семантический поиск; `embed_model` доступен как обычное поле. Поля record.owner, record.scrapper и record.trust_level описаны в схеме, но условия на них только сужают уже разрешённую область. Таблицы пользователей и регистраций агентов через search/read недоступны. Доступ к полям не даёт доступа к служебным таблицам задач, путям файловой системы или секретам. Метаданные схемы не включают значения из записей других пользователей.

Для JSONB путь задаётся массивом ключей, например `{"scope":"record","path":["metadata","chat_id"]}`. Зарегистрированные пути имеют тип в `schema`. Незарегистрированный путь тоже можно проверить на существование или сравнить с явно типизированным значением; это не возможность передать SQL. Отсутствующий ключ, JSON null и SQL NULL различаются отдельными операциями. Неподходящие типы не приводятся молча.

#### `POST /api/search` — поиск с фильтрами по всему пути к record

Параметры JSON-тела (обязателен только `target`):

- `target`: какой тип возвращать — `record`, `file`, `fragment`, `element`, `text` или `chunk`.
- `query`: необязательный объект с обязательными полями `embedding` (числовой вектор) и `embed_model` (имя модели). Текстовая строка вместо объекта не принимается. Агент получает эмбеддинг через собственную очередь и балансировщик и передаёт в core вектор и имя модели. Поиск идёт по совместимым эмбеддингам chunk'ов; другие модели не смешиваются. Если подходящего индекса нет, возвращается явная ошибка.
- `where`: дерево условий `all`, `any`, `not` и сравнений полей. Пустое условие означает отсутствие дополнительных фильтров.
- `select`: какие поля выбранного объекта и его предков вернуть. Обязательные идентификаторы и происхождение результата добавляются core.
- `order_by`: массив объектов с `scope`, `path`, `direction` (`asc` или `desc`), для fragment-предка также точная `depth`; для семантического поиска по умолчанию сначала самые близкие результаты.
- `limit`, `cursor`: размер страницы и непрозрачный курсор продолжения. По умолчанию `limit = 20`, `cursor = null`; верхние пределы задаёт core и публикует в `GET /api/search/schema`.

Без `query` инструмент выполняет обычную выборку по условиям и не требует эмбеддинга: например, «последние сообщения автора», «все PDF за неделю», «соседние chunk'и этого текста». Относительные даты агент переводит в абсолютные границы с учётом часового пояса пользователя; в core уходят даты со смещением UTC.

**Области полей (`scope`).** `self` — выбранный объект; остальные имена обозначают объекты на его фактическом пути вверх: `text`, `element`, `fragment`, `file`, `record`. Например, у chunk результата OCR путь проходит через text, photo, его fragment и file до record. У chunk собственного текста записи есть только text и record; отсутствующие связи не выдумываются. Несуществующая для типа связь — ошибка схемы; допустимая, но отсутствующая у конкретного объекта связь не удовлетворяет сравнению, кроме явной проверки отсутствия.

`fragment` обозначает ближайший fragment, включая сам объект, если `target = fragment`. Для вложенности есть условие `ancestor_fragment`: оно требует существования одного fragment выше ближайшего, удовлетворяющего вложенному `where`. Все сравнения внутри такого условия относятся к одному предку, а не к разным страницам или уровням. Можно указать точную глубину от ближайшего fragment (1 — его родитель). В результатах возвращается упорядоченный путь fragment с идентификаторами и запрошенными метаданными.

Поддерживаются равенство и неравенство, сравнение чисел и дат, принадлежность списку, буквальное вхождение подстроки, проверки NULL и наличия ключа, операции над JSON-массивами. Точный набор для каждого типа описан в `schema`; произвольных функций, регулярных выражений или SQL-фрагментов нет. Сортировка по предкам fragment требует точной глубины, чтобы поле имело однозначное значение.

Пример HTTP-тела: найти текстовые chunk'и из PDF, опубликованных в Telegram за октябрь, на странице с определённой меткой. Вектор в примере сокращён до трёх чисел; реальный запрос передаёт 2048 значений эмбеддинга текста «как работает asyncio», полученного через очередь агента. Ключ `page` здесь условный: использовать его можно, если он описан для этого формата в `schema`.

```json
{
  "target": "chunk",
  "query": {
    "embed_model": "Qwen3-VL-Embedding-2B",
    "embedding": [0.12, -0.34, 0.56]
  },
  "where": {
    "all": [
      {"scope": "record", "path": ["source_id"], "op": "eq", "value": "telegram"},
      {"scope": "record", "path": ["source_created_at"], "op": "gte", "value": "2026-10-01T00:00:00+03:00"},
      {"scope": "record", "path": ["source_created_at"], "op": "lt", "value": "2026-11-01T00:00:00+03:00"},
      {"scope": "file", "path": ["mime"], "op": "eq", "value": "application/pdf"},
      {"scope": "fragment", "path": ["meta", "page"], "op": "eq", "value_type": "integer", "value": 3}
    ]
  },
  "select": [
    {"scope": "self", "path": ["text"]},
    {"scope": "record", "path": ["title"]},
    {"scope": "file", "path": ["name"]},
    {"scope": "fragment", "path": ["meta"]}
  ],
  "limit": 20
}
```

**Семантика совпадения.** Если задан `query`, сначала условия проверяются на каждом кандидате chunk и его пути вверх, затем выполняется семантический поиск среди подходящих кандидатов. Для `target`, отличного от chunk, результат поднимается до выбранного объекта. Фильтры на `self` относятся к этому объекту. Поля ниже выбранного объекта в `where` недоступны: для условия на element нужно искать element или chunk, а не record. Если у одного объекта совпали несколько chunk'ов, он возвращается один раз, оценка — лучшая из оценок его подходящих chunk'ов. Ответ включает ограниченный список chunk'ов, подтверждающих совпадение. Дедупликация выполняется до применения лимита результата, чтобы одна большая запись не занимала всю страницу.

**Ответ `200`.** `items`, `next_cursor`, `schema_version`, `truncated`. Каждый результат содержит свой тип и ID, `record_id`, доступные ID объектов на пути, выбранные поля и сведения для ссылки: `source_id`, `source_url`, заголовок/автор/дата, доступная позиция в файле из метаданных. При семантическом поиске добавляются `score` (оценка близости) и `matches` (найденные chunk'и). Картинка без текста возвращается как совпадение по изображению с метаданными, а не как придуманное текстовое описание. Оценка близости не является вероятностью правильного ответа.

Обычная выборка имеет стабильную сортировку с ID в конце для разрешения равенств. При семантическом поиске core сохраняет ограниченную выдачу на время жизни курсора: продолжение не должно заново ранжировать первую страницу. При исчерпании бюджета или приблизительном поиске core явно сообщает, что выдача может быть неполной; отсутствие результатов не доказывает отсутствие данных. Истёкший курсор возвращает ошибку, после которой агент запускает поиск заново.

#### `POST /api/read` — дочитать найденное

JSON-тело: обязательные `target` (тип объекта), `id`, `mode` (`metadata`, `children` или `text`); необязательные `select` для metadata, `limit` (по умолчанию 20), `cursor` (по умолчанию null). Ответ `200` содержит `schema_version`, `items`, `next_cursor`, `truncated`. Читает только данные БД:

- `metadata` — поля объекта и путь предков, с той же схемой `select`, что у `search`.
- `children` — страница непосредственных детей в порядке дерева: у record — собственный text, затем file по `ord`; у file и fragment — fragment по `ord` либо содержащийся text/element; у photo/audio — существующий результирующий text; у text — chunk по `ord`. Служебные task не возвращаются. Равенства разрешаются по ID.
- `text` — сохранённые текстовые chunk'и объекта или его поддерева, с ID и границами каждого chunk, типом текста (собственный, извлечённый, OCR, транскрипция) и позицией в исходнике, если она известна. Обход следует тому же порядку дерева. Пустой ответ означает отсутствие сохранённого текста; OCR и транскрипция повторно не запускаются. Chunk-картинка текста не имеет; сохранённый OCR нужно читать через его photo или соответствующий text.

Все режимы имеют ограничения на число объектов и объём текста. Так агент может расширить контекст найденного chunk, прочитать соседние куски через `search` по `text_id` и `ord`, просмотреть структуру файла или постепенно прочитать запись целиком. Лимит одного вызова не означает молчаливого обрезания: ответ содержит курсор и признак усечения.

#### Границы доступа и выполнение

- Поиск и чтение доступны только для record в `done`. Условия пользователя этого не отменяют: фильтр готовности core добавляет самостоятельно ко всем операциям, включая чтение по ID. Внутри записи доступны метаданные сохранившегося file в `error`, но его содержимое отсутствует; упавший собственный text также не имеет chunk'ов.
- Core аутентифицирует отдельную регистрацию agent_id и сам добавляет record.owner = agent.owner и record.trust_level < agent.trust_level до поиска, ранжирования, подсчётов и чтения. Равные уровни доступа не дают. Owner и уровень из тела запроса не считаются полномочиями. То же условие проверяется при чтении по ID, переходе по курсору и выдаче из кеша; чужой или недоступный ID не отличим от отсутствующего. Роль администратора у владельца не расширяет права его агента (Core, 11).
- Core разбирает JSON в типизированное дерево запроса. Типы объектов, связи, поля, операции и сортировки выбираются из схемы; значения и JSON-пути передаются параметрами. Неизвестные конструкции отклоняются. Фильтрация строк по наличию слов `DROP` или `DELETE` не используется: эти слова могут быть обычным искомым текстом.
- Поисковые запросы выполняются отдельной ролью БД с чтением разрешённых таблиц/представлений, без владения объектами, прав записи, создания объектов, перехода к привилегированным ролям и выполнения опасных функций. Вызовы проходят в транзакциях только для чтения. Учётные данные приёма записей и административных операций не используются для поиска.
- Core ограничивает глубину и число условий, размер списков и строк, время выполнения, число одновременно выполняемых запросов, размер страницы и ответа. Приложение агента ограничивает число вызовов и общий бюджет одного пользовательского запроса. Произвольные JOIN, рекурсивный SQL и функции агент задать не может.
- Ошибки имеют машинный код и краткое объяснение: неверное поле/тип/операция, превышение лимита, истёкший курсор, недоступная модель эмбеддингов. Ответы не раскрывают SQL, внутренние пути и секреты. Содержимое найденных записей считается данными, а не инструкциями агенту и не может менять его права.

### Формат ответа ИИ-агента

В веб-интерфейсе ответ отображается в диалоге, в Telegram приходит одним сообщением: сам ответ на вопрос и список ссылок на источники. Ссылки берутся из `source_url` записей (record), на которых основан ответ. Для записей с псевдоссылкой `tg://chat/…` (личные диалоги и обычные группы Telegram) вместо ссылки показываются название чата и дата сообщения. Если найдены только метаданные или совпадение по картинке без доступного текста, ИИ-агент прямо сообщает об этом и не выдаёт догадку за прочитанное содержимое.

## HTTP API

Контракт запросов между скрапперами, core, агентами, балансировщиком и кабинетом core. Имена операций в путях — HTTP-эндпоинты, а не вызовы функций между процессами.

### Общие правила

- Пути начинаются от адреса соответствующего сервера. Для всех очередей это адрес core из конфига балансировщика.
- Тела запросов и ответов — JSON, кроме загрузки исходных файлов, входов агентских задач и скачивания данных задач. JSON-запросы передаются с `Content-Type: application/json`.
- Все даты — ISO 8601 со смещением UTC. ID объектов дерева — UUID v7.
- `owner` определяется сервером по сессии или регистрации с проверенной парой ID/token; клиент не может выбрать другого владельца. Поле `record.scrapper` сервер заполняет из scrapper_id этой регистрации, клиент его не назначает.
- У компонентов ID постоянен и задаётся при создании; token core генерирует автоматически и возвращает только при выдаче или перевыпуске. Обязательны оба значения; чужой token не подходит к ID. Правила выдачи — Core, 11.3.
- Числа `trust_level` — неотрицательные целые. `limit` — положительное целое; пределы поиска и чтения публикуются в `GET /api/search/schema`.
- Массивы эмбеддингов в примерах сокращены. Для Qwen3-VL-Embedding-2B передаются все 2048 чисел.
- Списки с пагинацией возвращают `items` и `next_cursor`; `null` означает конец выдачи. Для списков кабинета по умолчанию `limit = 20`, максимум 100. Следующая страница запрашивается с теми же фильтрами и полученным `cursor`.
- Ошибка возвращается в виде `{"error":{"code":"invalid_request","message":"Описание ошибки"}}`. `401` — нет действующего секрета или сессии, `403` — операция не разрешена, `404` — объект отсутствует или недоступен, `413` — превышен размер файла, `422` — неверные данные. Ошибки не содержат секретов, SQL и путей файловой системы.

### Скраппер → core

Каждый запрос содержит заголовки:

```http
X-Scrapper-ID: <scrapper_id>
Authorization: Bearer <token скраппера>
```

#### `GET /api/limits`

Без параметров. Ответ `200`:

```json
{"max_file_size":16106127360}
```

#### `GET /api/records/status`

Обязательные query-параметры: `source_id` и `source_url`. Значение `source_url` кодируется как URL-параметр.

```http
GET /api/records/status?source_id=youtube&source_url=https%3A%2F%2Fwww.youtube.com%2Fwatch%3Fv%3Dabc
```

#### `GET /api/records/{record_id}/status`

Альтернатива проверке по ссылке: обязательный `record_id` в пути, других параметров нет.

Оба эндпоинта отвечают `200`:

```json
{"record_id":"<UUID>","status":"processing"}
```

`status`: `unknown`, `processing`, `done`, `error`. Внешний `processing` объединяет внутренние `parsing` и `processing`. Если записи нет у владельца скраппера, ответ `{"record_id":null,"status":"unknown"}`; наличие чужой копии ничего не меняет.

#### `POST /api/records`

`Content-Type: multipart/form-data; boundary=...`. Первая часть `record` имеет тип `application/json`:

```json
{
  "source_id": "youtube",
  "source_url": "https://www.youtube.com/watch?v=abc",
  "source_created_at": "2026-10-31T12:00:00+03:00",
  "scraped_at": "2026-11-01T10:00:00+03:00",
  "title": "Название видео",
  "author": "Название канала",
  "parent_source_url": null,
  "metadata": {"duration": 120, "shorts": false},
  "trust_level": 2,
  "text": "Название и описание видео",
  "files": [{"name": "video.mp4", "mime": "video/mp4", "size": 12345678}]
}
```

Обязательны `source_id`, `source_url`, `scraped_at`, `trust_level`. Необязательны `source_created_at`, `title`, `author`, `parent_source_url`, `metadata`, `text`, `files`. Для отсутствующих `text` и `files` используются пустая строка и пустой массив; у записи должен быть непустой текст или хотя бы один файл. Для каждого файла обязательны `name`, `mime`, `size` (неотрицательное целое число байт). Неизвестная дата публикации — `null` или отсутствие поля. `source_id` должен совпадать с регистрацией скраппера.

За `record` идут части с именем `files`: бинарные данные в порядке массива `record.files`. Core проверяет метаданные, дубликат и заявленные размеры до чтения файловых частей; фактическое число частей и размеры также должны совпадать с описанием. `owner`, `scrapper`, `record_id`, `file_id` заполняет core, скраппер их не задаёт. `scrapper` равен scrapper_id проверенной регистрации; его owner должен совпадать с owner записи.

После сохранения всех файлов — `202 Accepted`:

```json
{
  "record_id": "<UUID>",
  "status": "processing",
  "files": [{"file_id": "<UUID>", "name": "video.mp4"}]
}
```

В ответе `files` сохраняет порядок загрузки. Разбор выполняется после ответа. Если запись уже есть у того же владельца, core не читает файловые части и отвечает `200`:

```json
{"record_id":"<UUID>","exists":true,"status":"done"}
```

Здесь `status` — текущий внешний статус записи. Повторная отправка, в том числе другим скраппером того же владельца, ничего не меняет, включая `trust_level` и `scrapper`. Пустая запись — `422`, превышение `max_file_size` — `413`. Прерванная или некорректная загрузка не оставляет зарегистрированной записи и её файлов.

### Балансировщик → core: очереди

Полный контракт шести вызовов (`task-sources`, `claim`, скачивание `input`, `result`, `fail`, `reset`) находится в [ТЗ балансировщика](docs/balancer/README.md#http-контракт-с-core). Там заданы заголовки, пути, тела запросов и ответов, ошибки и правила повторов. Это единственный источник форматов этого API; серверная реализация очередей описана в Core, 4.2.

### Агент → core: собственные задачи

Агент отправляет входные данные и получает результаты только через core, с заголовками `X-Agent-ID` и `Authorization: Bearer <token агента>`. Core определяет `agent_id` и владельца по проверенной регистрации; выбрать чужой источник нельзя. Общий сервер приложения может обслуживать несколько регистраций, но их задачи и результаты изолированы.

| Эндпоинт | Запрос и ответ |
|---|---|
| `POST /api/agent/tasks` | `multipart/form-data`: обязательные `type` (`transcribe`, `ocr`, `embed`) и файл `input`. Для текстового embed файл содержит байты UTF-8 с MIME `text/plain; charset=utf-8`. Core сохраняет вход и создаёт задачу в очереди авторизованного агента; `201`, JSON с `task_id`, `type`, `status: "wait"`. Параметров сложности, приоритета и выбора источника нет |
| `GET /api/agent/tasks/{task_id}` | `200`, JSON с `task_id`, `type`, `status` (`wait`, `processing`, `done`, `error`); при `done` — `payload` по формату результата соответствующего типа, при `error` — `error.message`. Только для задач этой регистрации; чужая и отсутствующая задача дают одинаковый `404` |

Core сам вычисляет сложность перед выдачей балансировщику. Эти самостоятельные задачи не создают record и дерево обработки скрапперских записей. Срок хранения входов и результатов, удаление и квоты агентских задач будут определены отдельно.

### Агент → core: поиск, чтение, удаление

Каждый запрос содержит:

```http
X-Agent-ID: <agent_id>
Authorization: Bearer <token агента>
```

Core проверяет пару `agent_id`/`token` и определяет регистрацию, `owner` и текущий `trust_level`. Для поиска и чтения обязательны совпадение владельца, `record.trust_level < agent.trust_level` и `record.status = done`. Для удаления статус записи может быть любым.

#### `GET /api/search/schema`

Необязательные query-параметры `target` и `source_id`. Без них возвращается вся схема. Например:

```http
GET /api/search/schema?target=chunk&source_id=telegram
```

Ответ `200`: версия схемы, типы объектов, поля, связи, операции фильтрации и ограничения. `target`: `record`, `file`, `fragment`, `element`, `text`, `chunk`.

#### `POST /api/search`

```json
{
  "target": "chunk",
  "where": {
    "all": [
      {"scope": "record", "path": ["source_id"], "op": "eq", "value": "telegram"},
      {"scope": "record", "path": ["source_created_at"], "op": "gte", "value": "2026-10-01T00:00:00+03:00"}
    ]
  },
  "select": [
    {"scope": "self", "path": ["text"]},
    {"scope": "record", "path": ["title"]}
  ],
  "order_by": [{"scope": "record", "path": ["source_created_at"], "direction": "desc"}],
  "limit": 20,
  "cursor": null
}
```

| Параметр | Обязателен | Значение |
|---|---|---|
| `target` | Да | Тип возвращаемого объекта из списка выше |
| `where` | Нет | Дерево условий; без него дополнительных фильтров нет |
| `select` | Нет | Поля объекта и предков; без него возвращаются ID и сведения об источнике |
| `query` | Нет | Объект с обязательными `embedding` и `embed_model` для семантического поиска |
| `order_by` | Нет | Список полей с `scope`, `path`, `direction` (`asc` или `desc`); для fragment-предка также точная `depth` |
| `limit` | Нет | По умолчанию 20, верхний предел публикуется в схеме |
| `cursor` | Нет | Непрозрачный курсор продолжения или `null` |

Для семантического поиска добавляется поле:

```json
{"query":{"embed_model":"Qwen3-VL-Embedding-2B","embedding":[0.12,-0.34,0.56]}}
```

Агент предварительно получает вектор через собственную очередь и балансировщик. Строка с текстом запроса вместо объекта `query` не принимается. Без `query` эмбеддинг не нужен. На следующих страницах сохраняются параметры исходного поиска и передаётся полученный `cursor`.

Ответ `200`:

```json
{
  "schema_version": 1,
  "items": [
    {
      "type": "chunk",
      "id": "<UUID>",
      "record_id": "<UUID>",
      "text": "Найденный текст",
      "source_id": "telegram",
      "source_url": "https://t.me/channel/123",
      "title": "Название записи"
    }
  ],
  "next_cursor": null,
  "truncated": false
}
```

Каждый результат включает ID и происхождение объекта, запрошенные поля, доступные ID предков и позицию в файле. При семантическом поиске добавляются `score` и `matches` — ограниченный список подтверждающих chunk'ов с ID, текстом при его наличии и позицией. Подробные правила `where`, `select`, обхода предков, сортировки, ранжирования и курсоров описаны в спецификации агента.

#### `POST /api/read`

```json
{"target":"record","id":"<UUID>","mode":"text","limit":20,"cursor":null}
```

Обязательны `target`, `id`, `mode`. Типы `target` те же, что у поиска. `mode`: `metadata`, `children`, `text`. Необязательны `select` (для `metadata`, как у поиска), `limit` (по умолчанию 20), `cursor`. На следующих страницах передаются те же `target`, `id`, `mode`, `select` и полученный курсор.

Ответ `200`:

```json
{"schema_version":1,"items":[],"next_cursor":null,"truncated":false}
```

`metadata` возвращает объект с полями и путём предков, `children` — непосредственных детей, `text` — сохранённые текстовые chunk'и объекта или его поддерева. Массив `items` содержит объекты выбранного режима. Для текстовых chunk'ов сохраняются ID, границы, вид текста и известная позиция в исходнике. Медиа заново не извлекаются, служебные task не возвращаются. Отсутствующий и недоступный объект дают одинаковый `404`.

#### `DELETE /api/records/{record_id}`

Обязательный `record_id` в пути, тела нет. Ответ `204 No Content` после удаления. Отсутствующий и недоступный объект дают одинаковый `404`. Проверка владельца и уровня и удаление выполняются одной транзакцией. Копии других владельцев сохраняются, поздние результаты удалённых задач игнорируются.

### Кабинет → core

После входа браузер передаёт cookie `session`. В изменяющих запросах под сессией также передаётся `X-CSRF-Token` из ответа входа. Для входа и регистрации сессия не нужна; они доступны только с допустимого origin интерфейса core. Поля `owner`, роли и чужие ID регистраций не позволяют расширить права пользователя.

| Эндпоинт | Параметры запроса | Успешный ответ |
|---|---|---|
| `POST /api/auth/register` | JSON: обязательные `login`, `password`; `invite_code` обязателен в режиме `invite` | `201`, `{"id":"<ID пользователя>","login":"<логин>"}`; затем отдельный вход |
| `POST /api/auth/login` | JSON: обязательные `login`, `password` | `200`, cookie `session` и `{"csrf_token":"<токен>"}` |
| `POST /api/auth/logout` | Без тела | `204`, сессия отозвана, cookie удалена |
| `GET /api/agents` | Query: необязательные `limit`, `cursor` | `200`, `items`, `next_cursor` |
| `POST /api/agents` | JSON: обязательные `agent_id` (UUID), `mode`, `trust_level` | `201`, регистрация и автоматически созданный `token` |
| `PATCH /api/agents/{agent_id}` | JSON: хотя бы одно из `trust_level`, `enabled` | `200`, обновлённая регистрация |
| `POST /api/agents/{agent_id}/rotate-token` | Без тела | `200`, `{"token":"<новый token>"}`; старый token отозван, agent_id сохранён |
| `DELETE /api/agents/{agent_id}` | Без тела | `204`, token отозван, источник исключён из списка задач балансировщика; ID сохраняется как удалённый и не переиспользуется |
| `GET /api/scrapers` | Query: необязательные `limit`, `cursor` | `200`, `items`, `next_cursor` |
| `POST /api/scrapers` | JSON: обязательные `scrapper_id` (UUID), `source_id` (`youtube` или `telegram`) | `201`, регистрация и автоматически созданный `token` |
| `PATCH /api/scrapers/{scrapper_id}` | JSON: обязательный `enabled` | `200`, обновлённая регистрация |
| `POST /api/scrapers/{scrapper_id}/rotate-token` | Без тела | `200`, `{"token":"<новый token>"}`; старый token отозван, scrapper_id сохранён |
| `DELETE /api/scrapers/{scrapper_id}` | Без тела | `204`, token отозван; регистрация сохранена для record.scrapper, записи сохраняются |
| `GET /api/records` | Query: необязательные `status`, `source_id`, `limit`, `cursor` | `200`, `items`, `next_cursor` |
| `GET /api/records/{record_id}` | Без дополнительных параметров | `200`, поля record и список file с их статусами, `error`, `error_detail` |
| `PATCH /api/records/{record_id}` | JSON: обязательный `trust_level` | `200`, обновлённая запись |
| `DELETE /api/records/{record_id}` | Без тела | `204` |

`agent_id` и `scrapper_id` — постоянные несекретные ID, заданные при создании. Повторный ID даёт `409 Conflict`. `mode`: `web_ai`, `web_manual`, `telegram_ai`, `telegram_manual` — отдельная регистрация для каждого используемого режима. Новые регистрации включены (`enabled = true`).

Обычный ответ с регистрацией агента содержит `agent_id`, `task_source_id`, `owner`, `mode`, `trust_level`, `enabled`; `task_source_id` совпадает с agent_id. Регистрация скраппера содержит `scrapper_id`, `owner`, `source_id`, `enabled`. Поле `token` добавляется только при создании и перевыпуске; секреты и их хеши не возвращаются в списках. При перевыпуске ID не меняется.

Поле `scrapper` возвращается вместе с остальными полями record и доступно в схеме поиска как UUID происхождения записи; доступ к нему не открывает регистрацию или token скраппера.

`GET /api/records` в кабинете принимает внутренние статусы `parsing`, `processing`, `done`, `error` и показывает только собственные записи. Эндпоинты изменения чужих регистраций и записей дают тот же `404`, что отсутствующие объекты. Отдельные file не удаляются. Сессионные операции кабинета не доступны по ID/token агента или скраппера; исключение — явно разрешённое агенту удаление записи по правилам выше.

### Административный раздел → core

Cookie `session` должна принадлежать администратору. Для изменяющих запросов обязателен `X-CSRF-Token`.

| Эндпоинт | Параметры запроса | Успешный ответ |
|---|---|---|
| `GET /api/admin/users` | Query: необязательные `limit`, `cursor` | `200`, `items`, `next_cursor` |
| `POST /api/admin/users` | JSON: обязательные `login`, `password` | `201`, `id`, `login`, `blocked = false` |
| `PATCH /api/admin/users/{user_id}` | JSON: обязательный `blocked` | `200`, `id`, `login`, `blocked` |
| `POST /api/admin/users/{user_id}/reset-password` | JSON: обязательный `password` | `204` |
| `GET /api/admin/settings` | Без параметров | `200`, `{"registration_mode":"closed"}` |
| `PATCH /api/admin/settings` | JSON: обязательный `registration_mode` (`closed`, `open`, `invite`) | `200`, обновлённая настройка |
| `POST /api/admin/invites` | Без тела | `201`, `{"id":"<ID>","code":"<одноразовый код>"}` |
| `DELETE /api/admin/invites/{id}` | Без тела | `204`, приглашение отозвано |
| `GET /api/admin/records` | Query: необязательные `owner`, `status`, `source_id`, `limit`, `cursor` | `200`, `items`, `next_cursor` |
| `GET /api/admin/records/{record_id}` | Без дополнительных параметров | `200`, запись и file со статусами и ошибками |
| `DELETE /api/admin/records/{record_id}` | Без тела | `204` |

Список пользователей содержит `id`, `login`, `blocked`, без паролей и хешей. Статусы и формат записей те же, что у кабинета, но администратору доступны все владельцы. Создание агентов и скрапперов остаётся в пользовательском кабинете.

### Воркеры и внешние сервисы

Контракт запуска воркеров и обмена через stdin/stdout описан в [ТЗ балансировщика](docs/balancer/README.md#контракт-запуска-воркера).

Telegram-скраппер читает историю через MTProto. Конкретный способ доступа к YouTube и провайдер LLM ещё не выбраны, поэтому их внешние эндпоинты здесь не задаются. Локальные сайты агентов и скрапперов настраивает владелец; этот контракт закрепляет их обращения к core и API очередей, а не устройство их собственных интерфейсов.
