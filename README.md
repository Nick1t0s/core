# Система сбора, индексации и поиска информации

Система состоит из четырёх частей:

- **скрапперы** собирают данные из внешних источников;
- **core** хранит, индексирует и выполняет поисковые запросы от клиентов;
- **балансировщик** распределяет тяжёлые задачи (транскрибация, OCR, эмбеддинги) между воркерами на GPU;
- **клиенты** обращаются к балансировщику для обработки запроса пользователя и к core для поиска.

Пример использования: спросить LLM «скинь ссылку, я вчера видел видео про asyncio» — модель находит его через SQL-запросы и семантический поиск.

## Модели (на сентябрь 2026)

| Задача | Модель |
|---|---|
| Эмбеддинги | Qwen3-VL-Embedding-2B (BF16) |
| Транскрибирование | whisper large-v3-turbo |
| OCR | PaddleOCR-VL + раскладка |

## Core

core — ядро системы сбора, индексации и поиска информации. Можно сказать, что core — цифровой мозг, который помнит всё, что вам писали.

Пример: LLM можно задать вопрос «скинь ссылку, я вчера видел видео, которое рассказывает про asyncio», и модель благодаря SQL-запросам и семантическому поиску быстро найдёт это видео.

Суть системы — перевод любого входного сообщения в мелкие неделимые части, которые можно обработать на GPU, проиндексировать и найти.

### Что делает core и чего не делает

Core делает:

- принимает записи от скрапперов, разбирает их на дерево и сохраняет его одной транзакцией;
- сохраняет исходные файлы записи в своём хранилище;
- хранит очереди задач (транскрибация, OCR, эмбеддинги) и отдаёт их балансировщику;
- принимает результаты задач и достраивает дерево;
- вычисляет статусы record, file, fragment, element и text;
- периодически (и при старте) проверяет дерево и распространяет вверх и `done`, и `error` (см. 4.5);
- отдаёт клиентам настройку `max_file_size`;
- выполняет поисковые запросы клиентов (раздел 5, пока в разработке).

Core не делает:

- не знает, что такое YouTube, Telegram или любой другой источник: он видит только record (универсальные поля и `metadata`);
- не исполняет тяжёлые задачи сам: это делают воркеры под управлением балансировщика;
- не хранит производные данные (аудиодорожки, кадры, отрендеренные страницы): только исходные файлы;

### Термины

| Термин | Значение |
|---|---|
| **record** | Наиболее крупная логическая часть информации: письмо, видео на YouTube, пост в канале. Корень дерева |
| **file** | Файл, прикреплённый к record (например для видео с YouTube — сам ролик) |
| **fragment** | Промежуточное состояние файла: страница PDF, лист в Word, кадр. Бывает вложенным |
| **element** | Наименьшая часть содержимого. Три типа: text, photo, audio |
| **chunk** | Часть text или photo, для которой считается эмбеддинг: кусок текста или картинка |
| **task** | Задача воркера, результат которой порождает новые записи в дереве: транскрибация (`transcribe`) и OCR (`ocr`) |
| **граница ошибки** | Место, где останавливается распространение ошибки: file либо собственный text записи (ребёнок record) |
| **метаданные (`metadata`)** | Данные, специфичные для источника, которым не нашлось места среди полей таблицы (длительность видео, признак shorts, оригинал пересланного сообщения и т. п.). Универсальные поля (`source`, даты, `title`, `author` и т. д.) метаданными не считаются |

### 1. Структура данных

#### 1.1. Дерево записи

Каждая запись представляется деревом. Корень — record. Путь от record до листа выглядит, например, так: `record → file → fragment → fragment → fragment → photo → chunk`.

Правила:

- **record** имеет n + 1 детей: n файлов (file) и не более одного собственного text (название и описание, склеенные; для YouTube-видео это склейка названия и описания). Если текста нет, text не создаётся. У записи должен быть хотя бы один ребёнок.
- **file** имеет сколько угодно детей fragment (минимум один).
- **fragment** имеет либо сколько угодно детей fragment, либо ровно один element (text, photo или audio). Смешивать fragment и element в одном родителе нельзя.
- **text** имеет сколько угодно детей chunk (минимум один). Сообщение нарезается на chunk'и в момент создания text.
- **photo** всегда имеет ровно один chunk с картинкой и ровно один `task_ocr`: картинка всегда и эмбедится, и отправляется на OCR. После получения результата OCR появляется ребёнок text, но только если распознан непустой текст. Отсутствие text у photo допустимо.
- **audio** содержит аудиоданные и имеет ребёнка `task_transcribe`. После получения транскрипции появляется ребёнок text (если транскрипция непуста).
- **chunk**, **task_transcribe**, **task_ocr** — листья, детей не имеют.

Видео — это набор фотографий (например, кадр каждые i секунд) и аудио.

Допустимые связи:

| Родитель | Дети | Количество |
|---|---|---|
| record | file, text | file: любое число; text: 0 или 1; в сумме не менее 1 |
| file | fragment | не менее 1 |
| fragment | fragment ИЛИ один element (text, photo, audio) | не менее 1 fragment, либо ровно 1 element |
| text | chunk | не менее 1 |
| photo | chunk (картинка); task_ocr; text | chunk: ровно 1; task_ocr: ровно 1; text: 0 или 1, появляется после OCR, если текст распознан |
| audio | task_transcribe; text | task_transcribe: ровно 1; text: 0 или 1, появляется после транскрибации |
| chunk, task_transcribe, task_ocr | — | листья |

Пример: видео с YouTube.

```
record
├─ text (название + описание)
│   └─ chunk, chunk, …
└─ file (видео)
    ├─ fragment (аудиодорожка)
    │   └─ audio
    │       ├─ task_transcribe
    │       └─ text                  ← появляется по результату транскрибации
    │            └─ chunk, chunk, …
    ├─ fragment (кадр, t = 0 с)
    │   └─ photo
    │       ├─ chunk                 ← картинка
    │       ├─ task_ocr              ← всегда
    │       └─ text                  ← появляется, только если OCR вернул текст
    │            └─ chunk, chunk, …
    └─ fragment (кадр, t = 5 с) …
```

#### 1.2. Chunk

Chunk — объект ровно с тремя полями:

- `text` — текст, максимум x символов (параметр конфигурации);
- `picture` — картинка;
- `embed` — эмбеддинг (список чисел).

`text` и `picture` взаимоисключающие: должно быть заполнено ровно одно. Если заполнены оба или ни одного, при создании должна возникать ошибка. Chunk в момент создания не имеет эмбеддинга (`embed` пуст): его считает воркер.

Картинка chunk'а отдельно не хранится: в БД у такого chunk'а стоит признак `is_picture`, а сама картинка получается из исходного файла по данным родительского photo (см. 6). Так как промежуточные данные не сохраняются, на уровне таблицы поле `picture` — это именно этот признак.

Внутри chunk'а текст больше не делится: это наименьшая часть, которая индексируется.

#### 1.3. Атрибуты record

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `id` | UUID (v7) | да | Суррогатный первичный ключ, выдаётся core |
| `source` | text | да | Имя источника: `youtube`, `telegram` |
| `source_url` | text | да | Каноническая ссылка на конкретную запись внутри источника |
| `source_created_at` | timestamptz | нет | Когда запись создана на оригинальном источнике; если источник не отдаёт дату — пусто |
| `scraped_at` | timestamptz | да | Когда скраппер получил запись |
| `registered_at` | timestamptz | да | Когда core зарегистрировал запись: момент коммита дерева, до окончания обработки |
| `processed_at` | timestamptz | нет | Когда обработка завершилась (record перешёл в `done` или `error`); пока идёт — `NULL` |
| `status` | enum | да | `processing`, `done`, `error` |
| `title` | text | нет | Заголовок, если есть |
| `author` | text | нет | Автор или канал |
| `parent_source_url` | text | нет | Запись, к которой относится эта (ответ, комментарий) |
| `metadata` | JSON | нет | Данные, специфичные для источника, которых нет среди полей таблицы (длительность видео, признак shorts, просмотры и т. п.) |
| `error` | text | нет | Текст единственной ошибки, если запись в статусе `error` |

Собственного текста записи в таблице нет: он хранится как дочерний text. Все даты хранятся в UTC. Изменения записей на источнике не отслеживаются.

#### 1.4. Первичный ключ и идентификация

- Первичный ключ — `id` (UUID, лучше v7, он сортируется по времени). Он нужен потому, что на record ссылаются другие таблицы, а тащить в каждую два длинных текстовых поля неудобно. `id` не зависит от правил нормализации ссылок.
- Пара `(source, source_url)` имеет ограничение `UNIQUE`, оба поля `NOT NULL`. Скраппер идентифицирует запись именно этой парой и `id` не генерирует.
- `source_url` каждый скраппер обязан приводить к каноническому виду (правила — в разделах скрапперов), иначе одна запись зарегистрируется дважды.
- Повторная отправка записи с уже существующим `(source, source_url)` ничего не меняет: core отвечает, что запись существует. Обновления записей не отслеживаются.

#### 1.5. Таблицы и их поля

Каждый тип объектов дерева лежит в своей таблице: `record`, `file`, `fragment`, `text`, `element`, `chunk`, `task`. Общих наборов полей нет: ниже для каждой таблицы перечислены все её поля. Поля record описаны в 1.3.

**Статусы в таблицах.** У `record`, `file`, `fragment`, `element` и `text` три статуса: `processing`, `done`, `error`. У листьев `chunk` и `task` четыре статуса: `wait`, `processing`, `done`, `error` (см. раздел 2).

**Таблица `file`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id` | Внешний ключ на record |
| `ord` | Порядок среди файлов записи |
| `status` | `processing`, `done`, `error` |
| `name`, `mime`, `size`, `sha256` | Имя, тип, размер и хэш исходного файла |
| `storage_path` | Путь в хранилище core; `NULL` только у пустышки |
| `error` | Текст ошибки file, если он в статусе `error` |
| `created_at` | Время создания |
| `finished_at` | Время перехода в `done` или `error` |
| `meta` | JSON с данными file, нужными для разбора |

**Таблица `fragment`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `file_id` | Внешний ключ на file (заполнен всегда) |
| `parent_fragment_id` | Внешний ключ на родительский fragment; пусто у фрагментов верхнего уровня |
| `ord` | Порядок среди соседей (номер страницы, порядковый номер кадра и т. п.) |
| `status` | `processing`, `done`, `error` |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |
| `meta` | JSON: номер страницы, время кадра `t_ms` и т. п. (то, из чего core получает входные данные для воркера) |

**Таблица `element`** (только photo и audio):

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `fragment_id` | Внешний ключ на fragment |
| `kind` | `photo` или `audio` |
| `ord` | Порядок среди соседей |
| `status` | `processing`, `done`, `error` |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |
| `meta` | JSON: `t_ms`, для audio ещё mime и длительность |

**Таблица `text`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `record_id`, `fragment_id`, `element_id` | Внешние ключи на родителя; заполнен ровно один: `record_id` — собственный text записи, `fragment_id` — text как element, `element_id` — результат OCR или транскрибации |
| `status` | `processing`, `done`, `error` |
| `error` | Текст ошибки; заполняется только у собственного text записи (он граница ошибки) |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |
| `meta` | JSON с данными text |

**Таблица `chunk`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `text_id`, `element_id` | Внешние ключи на родителя; заполнен ровно один: `text_id` — текстовый chunk, `element_id` — chunk-картинка photo |
| `ord` | Порядок среди соседей |
| `status` | `wait`, `processing`, `done`, `error` |
| `text` или `is_picture` | Текст chunk'а либо признак картинки (ровно одно из двух) |
| `embed`, `embed_model` | Эмбеддинг и название модели, которая его посчитала |
| `taken_at` | Когда chunk взяли в работу; `NULL` в статусе `wait` |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |

**Таблица `task`:**

| Поле | Описание |
|---|---|
| `id` | UUID (v7) |
| `element_id` | Внешний ключ на audio или photo |
| `type` | `transcribe` или `ocr` |
| `status` | `wait`, `processing`, `done`, `error` |
| `taken_at` | Когда задачу взяли в работу; `NULL` в статусе `wait` |
| `created_at`, `finished_at` | Время создания и время перехода в `done` или `error` |

Поле `error` заполняется только у file и собственного text записи, а также у пустышек: листья и промежуточные fragment, element, text ошибочного file (или собственного text записи) удаляются (см. 2.5), их текст ошибки хранить негде и не нужно.

В БД хранятся только пути и хэши исходных файлов. Хранилище принадлежит core, правила хранения — в разделе 3.

### 2. Статусы

#### 2.1. Значения статусов

**Листья chunk, task_transcribe, task_ocr** имеют четыре статуса:

| Статус | Значение |
|---|---|
| `wait` | Задача ждёт взятия: лежит в очереди, `taken_at IS NULL` |
| `processing` | Задача в работе: её взял воркер, `taken_at` заполнено |
| `done` | Задача успешно завершена |
| `error` | Задача завершена с ошибкой |

**Остальные объекты дерева** (record, file, fragment, element, text) имеют три статуса; `wait` у них не бывает:

| Статус | Значение |
|---|---|
| `processing` | Объект не завершён: не завершены его дети |
| `done` | Объект успешно завершён |
| `error` | Объект завершён с ошибкой |

`done` и `error` — терминальные: после перехода статус не меняется.

Переходы листьев: `wait → processing` (claim), `processing → done` (result), `processing → error` (fail), `processing → wait` (release, а также возврат по таймауту, см. 4.5).

#### 2.2. Вся работа сидит в листьях

Задачи воркеров привязаны только к листьям:

- эмбеддинг — chunk в статусе `wait` или `processing`;
- транскрибация — лист `task_transcribe`;
- OCR — лист `task_ocr`.

Все остальные объекты (record, file, fragment, audio, photo, text) не имеют собственной работы и являются контейнерами. Это закрывает проблему «пустого успеха»: у audio до завершения транскрибации всегда есть ребёнок `task_transcribe` не в статусе `done`, у photo — `task_ocr`, поэтому проверка «все дети готовы» не может ошибочно пометить контейнер готовым. Никаких дополнительных флагов «готов к обработке» не нужно.

#### 2.3. Правило готовности

Контейнер внутри file (или внутри собственного text записи) готов, когда число его готовых детей равно числу всех его детей, то есть когда у него нет ни одного ребёнка не в статусе `done`. Правило одинаково для всех контейнеров, включая «листовые» fragment (у которых единственный ребёнок — element): особых случаев нет.

#### 2.4. Граница ошибки и ошибки

- Границей ошибки является file либо собственный text записи (ребёнок record).
- Ошибка ребёнка — ошибка родителя, но только внутри file (или собственного text записи): ошибка листа делает ошибочными всех его предков вплоть до этого file (или text) включительно. После этого все дети file (или text) удаляются из БД (см. 2.6).
- На record ошибка file или собственного text не влияет: остальные файлы и текст записи обрабатываются дальше.
- Ошибка воркера всегда серьёзная: мелкие сбои (OOM и т. п.) воркер обрабатывает сам и возвращает задачу; ошибка в core приходит только после исчерпания ретраев.

#### 2.5. Готовность record

Record переходит в терминальный статус, когда у него нет ни одного ребёнка (file или text) в `processing` (все file и собственный text завершены: `done` или `error`). Тогда:

- `status` = `done`;
- `processed_at` = текущий момент.

Если все file и собственный text записи закончились ошибкой, record всё равно `done`, но искать в нём нечего.

Статус `error` у record бывает только у пустышки (см. 3.5).

#### 2.6. Обновление статусов

Статусы chunk и task (листья) меняются только по операциям балансировщика (см. 4.2): `claim` переводит лист из `wait` в `processing`, `result` — в `done`, `fail` — в `error`, `release` возвращает в `wait`. Статусы всех остальных объектов (element, fragment, text, file, record) вычисляются по каскаду ниже.

**Правило каскада:** каждое обновление статуса — отдельная транзакция со своим коммитом. Общей транзакции на весь путь вверх нет.

Успех. После коммита результата листа (см. 4.3) core проверяет его родителя:

1. Если у родителя нет ни одного ребёнка не в `done` (для record — ни одного в `processing`), родитель переводится в `done` (`finished_at = now()`), это отдельный коммит, и проверка повторяется для родителя родителя.
2. Если условие не выполнено, каскад останавливается.
3. Дойдя до record, при успешном обновлении заполняем `processed_at`.

Проверка родителя (пример для element):

```sql
UPDATE element e
SET status = 'done', finished_at = now()
WHERE e.id = :parent_id
  AND e.status = 'processing'
  AND NOT EXISTS (SELECT 1 FROM chunk c WHERE c.element_id = e.id AND c.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM task  t WHERE t.element_id = e.id AND t.status <> 'done')
  AND NOT EXISTS (SELECT 1 FROM text  x WHERE x.element_id = e.id AND x.status <> 'done');
```

Если обновилась одна строка, идём выше. Условие идемпотентно (`status = 'processing'`), поэтому дублирующий запуск ничего не портит. Явные блокировки не нужны: проверка запускается только после коммита собственного листа, значит, проверка последнего из одновременно завершающихся детей увидит все коммиты и переведёт родителя в `done`.

Ошибка. Распространяется тем же ходом, тоже по одному коммиту на шаг:

1. Лист (chunk или task) → `error`.
2. Каждый предок вплоть до file (или собственного text записи) → `error`, по одному коммиту.
3. На file (или собственном text записи): записывается текст ошибки в `error`, затем **все его дети удаляются из БД** (каскадным удалением: fragment, element, text, chunk, task, включая задачи в статусах `wait` и `processing`).
4. Проверка готовности record (см. 2.5).

Так ошибка хранится в единственном экземпляре — у file (или собственного text записи). Результат, пришедший позже для удалённого или уже не находящегося в `processing` объекта, игнорируется.

Оба каскада (успех и ошибка) не только запускаются событиями, но и периодически повторяются проверкой из 4.5: если core упал посреди каскада, недоделанное довершит эта проверка.

### 3. Приём записи

#### 3.1. Общая схема

1. Скраппер отправляет в core запись: метаданные (`source`, `source_url`, даты, `title`, `author`, `metadata`), текст и файлы.
2. Core берёт блокировку по `(source, source_url)` на всё время приёма и проверяет, нет ли уже такой записи. Если есть, отвечает, что запись существует, ничего не трогая.
3. Core проверяет размер каждого файла по `max_file_size` (см. 3.6). При превышении запись отклоняется статус-кодом ошибки, ничего не сохраняется.
4. Core создаёт служебную запись приёма и **разбирает** запись целиком: нарезает текст на chunk'и, раскладывает файлы на fragment и element (страницы PDF, листы Word, кадры и аудио видео и т. д.), определяя для каждого fragment и element в `meta`, как получить его данные из исходного файла (номер страницы, время кадра `t_ms` и т. п.). Исходные файлы сохраняются в хранилище (см. 3.3); производные (кадры, аудиодорожка, отрендеренные страницы) не сохраняются. На этом шаге в основной БД ничего не пишется.
5. Когда разбор завершён полностью, всё дерево записывается **одной транзакцией**: record, все его дети и их данные, задачи в очередях (chunk и task в статусе `wait`).
6. После коммита запись существует, статус `processing`, задачи доступны балансировщику.

Требования:

- В основной БД нет частично записанных деревьев: либо коммит прошёл и дерево целое, либо его нет.
- Очереди задач — таблицы той же БД (`task` и `chunk` в статусе `wait`), поэтому дерево и его задачи фиксируются атомарно.
- `registered_at` = момент коммита.
- Блокировка по `(source, source_url)` не даёт двум одновременным запросам на одну запись разбирать её параллельно: второй дожидается блокировки, видит, что запись уже существует (или что первая попытка провалилась, тогда разбирает сам).

#### 3.2. Состояние приёма

Пока идёт разбор, записи в основной БД нет, и скраппер по проверке статуса получил бы «нет такой записи» и отправил бы её повторно. Чтобы этого не было, core ведёт таблицу `ingest_job(source, source_url, state, accepted_at)`:

- запись создаётся при приёме, состояние `parsing`;
- удаляется при коммите дерева либо при неудаче разбора;
- запрос статуса сначала смотрит в `record`, затем в `ingest_job`; ответ для скраппера: `unknown`, `processing`, `done` или `error`. Состояние `parsing` отдаётся как `processing`.

Устаревшие записи в `parsing` (например, после падения core) удаляются по таймауту вместе с файлами этой записи в хранилище. Скраппер после этого увидит `unknown` и отправит запись заново.

#### 3.3. Хранение файлов

- Core сохраняет **либо исходный файл, либо ничего**. При приёме видео сохраняется само это видео; никаких аудиодорожек, кадров и других производных не сохраняется. Всё, что нужно воркеру или клиенту (аудио, кадр, страница), core получает из исходного файла на лету по `meta` соответствующего fragment или element.
- Временной области нет: файлы сразу кладутся в хранилище (storage) под именем, составленным из `source` и `source_url` записи (например, `<source>/<закодированный source_url>/<имя файла>`; `source_url` кодируется так, чтобы получалось допустимое имя каталога).
- Если транзакция с деревом откатилась или core упал, в хранилище остаётся мусор: путь однозначно определяется записью, поэтому повторная отправка перезаписывает те же файлы, а периодическая очистка удаляет каталоги записей, которых нет в БД и `ingest_job`, старше заданного срока.

#### 3.4. Ошибка file

При переходе file (или собственного text записи) в `error` все его дети удаляются из БД (см. 2.6), в том числе задачи из очередей. Задачи, которые уже выполняются на воркере, не прерываются, но их результат при получении игнорируется: объекта больше нет.

#### 3.5. Ошибки при приёме: пустышки

Скрапперы сами отвечают за целостность данных: если получить запись не удалось (например, нет интернета), запись в core не отправляется, и core пустышками не заполняется. Пустышки создаются только в таких случаях:

| Ситуация | Что записывается |
|---|---|
| Непредвиденная ошибка при разборе отдельного файла | Пустышка file: без детей, `status` = `error`, `error` с описанием. Файл пропускается, на record это не влияет, остальные файлы разбираются |
| Непредвиденная ошибка при разборе всей записи | Пустышка record с `status` = `error` |
| Запись целиком пуста (нет ни текста, ни файлов) | Пустышка record с `status` = `error`, ошибка «пустая запись» |

У пустышек `processed_at` равно `registered_at`. Пустышки — единственные контейнеры без детей.

Превышение `max_file_size` пустышкой не является: запись отклоняется целиком (см. 3.6).

#### 3.6. Ограничение размера файла

- В конфигурации core задаётся `max_file_size` — максимальный размер сохраняемого файла.
- Значение отдаётся по API по соответствующему запросу, скраппер может проверить его заранее.
- Если размер какого-либо файла записи больше, core отказывается записывать запись и возвращает ошибку в виде статус-кода (например, HTTP 413). Записи, пустышки и файлы при этом не создаются.

### 4. Задачи и очереди

#### 4.1. Очереди

Три очереди core соответствуют типам задач:

| Очередь (`type`) | Листья |
|---|---|
| `transcribe` | `task` с типом `transcribe` в статусе `wait` |
| `ocr` | `task` с типом `ocr` в статусе `wait` |
| `embed` | `chunk` в статусе `wait` |

Задача находится «в очереди», если `status = 'wait'`, и «на воркере», если `status = 'processing'` (тогда `taken_at` заполнено). Порядок внутри очереди — FIFO по `created_at`. Очередей для конкретных источников на стороне core не существует. Приоритеты очередей и источников хранит и применяет балансировщик, core их не знает.

#### 4.2. Операции для балансировщика

| Операция | Действие |
|---|---|
| `claim(type)` | `type` — `transcribe`, `ocr` или `embed`. Атомарно берёт следующую задачу очереди, переводит её из `wait` в `processing` и ставит `taken_at`. Реализуется как `UPDATE … SET status = 'processing', taken_at = now() WHERE id = (SELECT … WHERE status = 'wait' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING …`. Возвращает данные для воркера (аудио, картинку или текст chunk'а); аудио и картинку core получает из исходного файла на лету по `meta` fragment и element |
| `result(task_id, payload)` | Принимает результат задачи в статусе `processing` (см. 4.3) |
| `fail(task_id, error)` | Задача завершилась ошибкой после исчерпания ретраев: лист → `error`, каскад по 2.6 |
| `release(task_id)` | Задача была убита (вытеснение более приоритетным источником): `processing → wait`, `taken_at = NULL`, задача возвращается в очередь. Ошибкой это не считается |

`task_id` — идентификатор `task` либо chunk (для очереди `embed`).

Убитая и завершившаяся ошибкой задачи — разные события: убитую возвращаем в очередь (`wait`), ошибка помечает лист и его предков ошибочными. Любая операция над объектом, которого уже нет или который не в `processing`, игнорируется и не считается ошибкой.

#### 4.3. Обработка результата

Результат фиксируется **одной транзакцией вместе со всеми порождёнными записями**. Коммит происходит до ответа на запрос воркера, поэтому не бывает момента, когда задача завершена, а её дети ещё не созданы. После коммита запускается проверка родителя по 2.6 (отдельными коммитами).

**Эмбеддинг** (лист chunk): записываются `embed` и `embed_model`, chunk → `done`.

**Транскрибация** (лист `task_transcribe` под audio):

1. `task_transcribe` → `done`.
2. Если транскрипция непуста, создаётся text — ребёнок audio — со статусом `processing`. Текст сразу режется на chunk'и (дети text, статус `wait`, `embed` пуст).
3. Если транскрипция пуста, text не создаётся.

**OCR** (лист `task_ocr` под photo): то же самое, text становится ребёнком photo. Если OCR не вернул текст, text не создаётся; это не ошибка.

Пока созданные chunk'и не получат эмбеддинги, audio (или photo) остаётся в `processing`.

#### 4.4. OCR

OCR обязателен для каждой photo: `task_ocr` создаётся всегда, без настроек и политик. Photo с пустым результатом OCR завершается, не имея text.

#### 4.5. Восстановление и периодическая проверка

Возврат зависших задач:

- Листья в статусе `processing`, по которым не пришёл результат за заданное время (`taken_at` старше таймаута), возвращаются в очередь: `status = 'wait'`, `taken_at = NULL`. Это страховка на случай перезапуска балансировщика.

Проверка дерева. Так как каждое обновление статуса — отдельный коммит, core может упасть посреди каскада. Поэтому при старте core и затем каждые x минут (параметр конфигурации) выполняет проверку, которая распространяет и ошибки, и готовность:

1. **Распространение ошибок.** Для каждого листа в статусе `error`, чьи предки ещё не `error`, продолжается каскад ошибки по 2.6: предки вплоть до file (или собственного text записи) → `error`, запись текста ошибки, удаление детей.
2. **Распространение `done`.** Для каждого контейнера в статусе `processing` выполняется проверка готовности по 2.3: если нет ни одного ребёнка не в `done`, контейнер → `done`. Проверка идёт снизу вверх (element, затем fragment от самых вложенных к верхним, затем text, file, record) и повторяется, пока есть изменения. Для record условие — нет детей в `processing`; при переходе заполняется `processed_at`.
3. После обоих шагов проверяется готовность record (2.5).

Оба шага идемпотентны (условие `status = 'processing'`), поэтому безопасны при повторном и параллельном запуске.

Кроме того, при старте core проверяет `ingest_job` и хранилище (см. 3.2, 3.3).

### 6. Хранение и технологии

Рекомендуется PostgreSQL с расширением pgvector; СУБД пока не зафиксирована. Фрагменты SQL в этом разделе — эскизы для PostgreSQL.

- Типы `container_status`, `task_status`, `element_kind`, `task_type` — enum. Enum — тип поля, которое может принимать только одно значение из заданного списка. В SQLite enum нет, там используется `TEXT` с проверкой `CHECK`.
- Каждый тип объектов дерева лежит в своей таблице: `record`, `file`, `fragment`, `text`, `element`, `chunk`, `task`. Внешние ключи с `ON DELETE CASCADE`: удаление детей ошибочного file (или собственного text записи) выполняется удалением его потомков.
- Исходные файлы лежат в хранилище core, в БД — путь и хэш. Производные данные не хранятся.
- Индексы: внешние ключи дочерних таблиц (`file.record_id`, `fragment.file_id`, `fragment.parent_fragment_id`, `element.fragment_id`, `text.*_id`, `chunk.*_id`, `task.element_id`) для проверки готовности; частичные индексы очередей `task (type, created_at) WHERE status = 'wait'` и `chunk (created_at) WHERE status = 'wait'`; частичные индексы для возврата зависших задач `task (taken_at) WHERE status = 'processing'` и `chunk (taken_at) WHERE status = 'processing'`; уникальный индекс `record(source, source_url)`.
- Ограничения: у `chunk` заполнены ровно один родитель и ровно одно из `text` и `is_picture`, длина текста ограничена; у `text` ровно один родитель; в `wait` поле `taken_at` пусто, в `processing` заполнено; иерархические правила из 1.1 проверяются при построении дерева в коде (на уровне БД — при необходимости constraint-триггерами).
- Эмбеддинги лежат в столбце типа vector; размерность определяется моделью (см. таблицу моделей). В chunk хранится название модели (`embed_model`), чтобы при смене модели можно было пересчитать эмбеддинги.
- Эскиз таблиц:

```sql
CREATE TYPE container_status AS ENUM ('processing','done','error');          -- record, file, fragment, element, text
CREATE TYPE task_status      AS ENUM ('wait','processing','done','error');   -- chunk, task
CREATE TYPE element_kind     AS ENUM ('photo','audio');
CREATE TYPE task_type        AS ENUM ('transcribe','ocr');

CREATE TABLE record (
  id                 uuid PRIMARY KEY,
  source             text NOT NULL,
  source_url         text NOT NULL,
  source_created_at  timestamptz,
  scraped_at         timestamptz NOT NULL,
  registered_at      timestamptz NOT NULL,
  processed_at       timestamptz,
  status             container_status NOT NULL DEFAULT 'processing',
  title              text,
  author             text,
  parent_source_url  text,
  metadata           jsonb,
  error              text,
  UNIQUE (source, source_url)
);

CREATE TABLE file (
  id           uuid PRIMARY KEY,
  record_id    uuid NOT NULL REFERENCES record(id) ON DELETE CASCADE,
  ord          int  NOT NULL DEFAULT 0,
  status       container_status NOT NULL DEFAULT 'processing',
  error        text,
  name         text,
  mime         text,
  size         bigint,
  sha256       text,
  storage_path text,              -- NULL только у пустышки
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  meta         jsonb
);

CREATE TABLE fragment (
  id                 uuid PRIMARY KEY,
  file_id            uuid NOT NULL REFERENCES file(id) ON DELETE CASCADE,
  parent_fragment_id uuid REFERENCES fragment(id) ON DELETE CASCADE,  -- NULL на верхнем уровне
  ord                int  NOT NULL DEFAULT 0,
  status             container_status NOT NULL DEFAULT 'processing',
  created_at         timestamptz NOT NULL DEFAULT now(),
  finished_at        timestamptz,
  meta               jsonb
);

CREATE TABLE element (              -- photo и audio
  id           uuid PRIMARY KEY,
  fragment_id  uuid NOT NULL REFERENCES fragment(id) ON DELETE CASCADE,
  kind         element_kind NOT NULL,
  ord          int  NOT NULL DEFAULT 0,
  status       container_status NOT NULL DEFAULT 'processing',
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  meta         jsonb              -- t_ms, mime, длительность и т. п.
);

CREATE TABLE text (
  id           uuid PRIMARY KEY,
  record_id    uuid REFERENCES record(id)   ON DELETE CASCADE,  -- собственный текст записи
  fragment_id  uuid REFERENCES fragment(id) ON DELETE CASCADE,  -- text как element
  element_id   uuid REFERENCES element(id)  ON DELETE CASCADE,  -- результат OCR / транскрибации
  status       container_status NOT NULL DEFAULT 'processing',
  error        text,
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  meta         jsonb,
  CHECK (num_nonnulls(record_id, fragment_id, element_id) = 1)
);

CREATE TABLE chunk (
  id           uuid PRIMARY KEY,
  text_id      uuid REFERENCES text(id)    ON DELETE CASCADE,
  element_id   uuid REFERENCES element(id) ON DELETE CASCADE,   -- chunk-картинка photo
  ord          int  NOT NULL DEFAULT 0,
  status       task_status NOT NULL DEFAULT 'wait',
  text         text,
  is_picture   boolean NOT NULL DEFAULT false,
  embed        vector,
  embed_model  text,
  taken_at     timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  CHECK ((text_id    IS NOT NULL AND element_id IS NULL AND text IS NOT NULL AND NOT is_picture)
      OR (element_id IS NOT NULL AND text_id    IS NULL AND text IS NULL     AND is_picture)),
  CHECK (status <> 'wait' OR taken_at IS NULL),
  CHECK (status <> 'processing' OR taken_at IS NOT NULL)
);

CREATE TABLE task (
  id           uuid PRIMARY KEY,
  element_id   uuid NOT NULL REFERENCES element(id) ON DELETE CASCADE,
  type         task_type NOT NULL,
  status       task_status NOT NULL DEFAULT 'wait',
  taken_at     timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  CHECK (status <> 'wait' OR taken_at IS NULL),
  CHECK (status <> 'processing' OR taken_at IS NOT NULL)
);
```

### 7. Обработка отказов

| Ситуация | Поведение |
|---|---|
| Запись с таким `(source, source_url)` уже есть | Ответ «существует», ничего не меняется |
| Файл больше `max_file_size` | Запись отклоняется статус-кодом ошибки, ничего не сохраняется |
| core упал во время разбора | Дерева в БД нет; запись в `ingest_job` устаревает; скраппер получает `unknown` и отправляет запись повторно |
| Транзакция с деревом откатилась | Как выше; файлы в хранилище удаляются очисткой |
| core упал посреди каскада статусов | При старте и затем каждые x минут проверка (4.5) довершает и распространение `done`, и распространение `error` |
| Воркер убит (вытеснение) | `release`: задача из `processing` возвращается в `wait`, статус родителей не меняется |
| Воркер умер сам, ретраи исчерпаны | `fail`: лист → `error`, каскад вверх до file (или собственного text записи), тот → `error`, его дети удаляются, record продолжает обработку остальных file и text |
| Результат пришёл для объекта, которого нет или который не в `processing` | Игнорируется |
| Результат пришёл повторно | Игнорируется (идемпотентность по статусу) |
| Задача в `processing` дольше таймаута | Возвращается в `wait` (4.5) |
| Отправлена запись без содержимого | Пустышка record в статусе `error` |

### 8. Инварианты

1. Дерево записи появляется в БД целиком одной транзакцией; частичных деревьев не бывает.
2. Каждый контейнер имеет хотя бы одного ребёнка; исключение — пустышки со статусом `error`, а также file и собственный text записи, чьи дети удалены после ошибки.
3. Задачи привязаны только к листьям (chunk, `task_transcribe`, `task_ocr`).
4. Результат задачи фиксируется вместе со всеми порождёнными записями одной транзакцией и коммитится до ответа воркеру.
5. Каждый photo имеет ровно один chunk-картинку и ровно один `task_ocr` (пока его file не в `error`).
6. Контейнер внутри file (или собственного text записи) `done` только если все его дети `done`; ошибка ребёнка делает ошибочными всех предков вплоть до file (или собственного text записи) включительно, дети ошибочного file (или text) удаляются.
7. Статус `wait` бывает только у chunk, `task_transcribe` и `task_ocr`; у остальных объектов его нет.
8. Каждое обновление статуса — отдельный коммит.
9. Ошибка file или собственного text записи не влияет на record.
10. Терминальный статус (`done`, `error`) не меняется.
11. Пара `(source, source_url)` уникальна и обязательна.
12. Core хранит только исходные файлы: либо исходный файл, либо ничего.

### 9. Принятые допущения и открытые вопросы

Допущения, добавленные при составлении ТЗ (меняются локально):

1. Разбор записи до коммита выполняет сам core (разбиение PDF и Word на страницы и листы, определение кадров и аудио видео, нарезка текста); это не GPU-работа и в очереди балансировщика не входит. Сами кадры, аудио и рендер страниц не сохраняются, а строятся из исходного файла по `meta` при выдаче задачи воркеру и при запросах клиентов.
2. Границей распространения ошибки является file либо собственный text записи. Денормализованного идентификатора file в дочерних таблицах нет: при ошибке дети удаляются каскадом.
3. При ошибке file (или собственного text записи) его дети удаляются, а не дорабатываются (иначе работа GPU тратится на то, что нельзя найти).
4. OCR обязателен для каждой photo.
5. Одна аудиодорожка файла — один element audio; нарезка длинного аудио на части в ТЗ не описана.
6. `registered_at` — момент коммита дерева.
7. Параметры нарезки текста: максимум x символов на chunk, границы по абзацам и предложениям, перекрытие настраивается (по умолчанию 0).
8. Возврат «зависших» задач по таймауту (4.5), период проверки дерева (x минут), таймаут устаревшего `ingest_job` и срок очистки хранилища — параметры конфигурации.
9. Element хранится в двух таблицах: photo и audio — в `element`, text-элементы — в `text`. Так text как результат OCR, транскрибации, собственный текст записи и text-элемент фрагмента лежат в одной таблице.
10. Из-за отдельных коммитов на каждом шаге каскада статусов добавлена проверка при старте и периодическая проверка (4.5), которая распространяет и `done`, и `error`.
11. Статус `wait` есть только у листьев-задач (chunk, `task_transcribe`, `task_ocr`); у контейнеров «ожидания» нет, они с момента создания `processing`.

Открытые вопросы:

1. **Приоритеты источников.** `claim` принимает только тип очереди, а балансировщик описывает приоритеты источников. Как балансировщик узнаёт источник задачи (в ответе `claim`, отдельной операцией), не определено.
2. **Момент появления в поиске.** Зависит от раздела 5 (пока в разработке): можно искать только по записям в `done` или ослабить условие до «file в `done`».
3. **Запись, у которой все file и собственный text закончились ошибкой.** Сейчас `done` без содержимого; можно перевести в `error`.
4. **Задачи клиентов** (транскрибация голосовых запросов). Не входят в это ТЗ: у них нет записи, к которой можно привязать листья. Варианты: считать запрос клиента тоже record или завести отдельную таблицу задач.
5. **Повторная обработка** file и записей в `error` (ручной перезапуск) пока не описана; учтите, что дети ошибочного file удалены, поэтому перезапуск — это повторный разбор файла.

## Балансировщик

### Компоненты

- **Балансировщик** — один отдельный демон.
- **Три воркера-утилиты**: транскрибация, OCR, эмбеддинги. Каждый завершается после выполнения задачи.
- **Три очереди в core**: транскрибация, OCR, эмбеддинги.

### Воркеры

- Воркер получает задачи **пуллингом**: сам запрашивает очередную задачу у балансировщика и сам отправляет результат обратно. HTTP-сервера для API у воркера нет, входящих соединений он не принимает.
- У воркера есть **админка**, в которой можно управлять тем, выполняются ли сейчас задачи: пока выполнение выключено, воркер новые задачи не берёт.
- Так как входящих соединений нет, вытеснение (см. ниже) реализуется через завершение процесса воркера.

### Приоритеты

- У каждой очереди есть внутренний приоритет (по умолчанию транскрибация - 3, ocr - 2, эмбединги - 1).
- Каждый источник (комплект из очередей транскрибации, OCR и эмбеддингов) тоже имеет приоритет.
- По умолчанию клиенты - самые приоритетные
- Все приоритеты различны (для каждого источника, и внутри каждого источника), одинаковых нет.

### Цикл балансировщика

Цикл — это обход всех источников по убыванию приоритета, а внутри каждого источника — обход его очередей по убыванию приоритета.
1. Из очередной очереди берётся одна задача (`claim`: в core она переходит из `wait` в `processing`).
2. Балансировщик уведомляет core, что задача взята в работу.
3. Воркер выполняет задачу.
4. Результат отправляется в core.

Если воркер умер САМ(OOM, неправильный файл, непредвиденная ошибка) в лог пишется WARNING происходит x(настраивается в конфиге)
ретраев. Если это не помогло - отправляем в core то что произошла ошибка(не тоже самое что прервано)
Так как более приоритетные источники обходятся первыми, они вычищаются раньше остальных.

### Вытеснение

Если во время выполнения менее приоритетной задачи появилась задача более приоритетного **источника**:

1. воркер убивается(KILL);
2. core уведомляется, что задача больше не выполняется и была убита, и core возвращает её в очередь (`processing → wait`);
3. текущий цикл завершается и запускается новый.

Очередь отпускается только в двух случаях:

- она опустела;
- появилась задача более приоритетного источника.

Если более приоритетная очередь появилась внутри того же источника, ничего не происходит: цикл продолжается, а эта задача будет обработана в следующем цикле.

## Скрапперы

Скрапперы отвечают за сбор данных. Core не знает, что такое ютуб или любой другой источник: он получает только record: универсальные поля (ссылка на источник, дата публикации, дата скраппинга и т. п.) и `metadata` со специфичными для источника данными.

Каждый скраппер обязан заполнить `source` и `source_url` (вместе они образуют уникальный ключ записи) и привести `source_url` к каноническому виду.

Скрапперы сами отвечают за целостность данных: если получить запись целиком не удалось (например, нет интернета), она в core не отправляется. Размер каждого файла не должен превышать `max_file_size` core (значение отдаётся по API core); при превышении core отклоняет запись статус-кодом ошибки, а как поступить дальше, решает скраппер.

### YouTube

Скраппер YouTube — демон. У него несколько режимов работы, каждый включается отдельно в конфиге. Режимы выполняются последовательно, а не параллельно, чтобы не получить бан от YouTube.

#### Архитектура

Скраппер состоит из следующих частей:

- **Демон** — по очереди обходит включённые режимы, скачивает видео и кладёт их в очередь отправки в core.
- **Очередь загрузки** — хранится в памяти, не персистентна: после перезагрузки восстанавливается повторным сканированием.
- **Очередь отправки в core** — хранится в SQLite, персистентна (переживает перезагрузку).
- **Папка с файлами** — специальная папка внутри скраппера, где лежат файлы видео, ожидающих отправки в core.
- **API для core** — скраппер сам пушит задачи в core.
- **Админка** — веб-интерфейс на FastAPI, доступный только из локальной сети.

#### Идентификация записи

- `source` = `youtube`.
- `source_url` = ссылка на видео в каноническом виде: `https://www.youtube.com/watch?v=<video_id>`. Ссылки вида `youtu.be/…` и `/shorts/…` приводятся к этому виду, иначе одно и то же видео из разных режимов получило бы разные ключи.
- `text` = склейка названия и описания видео, `title` = название, `author` = канал.
- `source_created_at` = дата публикации видео, `scraped_at` = момент получения записи скраппером.
- В `metadata` кладутся длительность и признак shorts.

#### Режимы работы

- **Сканер каналов** — обходит список YouTube-каналов и выкачивает все их видео.
- **Сканер плейлистов** — обходит список плейлистов и выкачивает все видео из каждого.
- **Сканер истории** — получает доступ к аккаунту YouTube, читает историю просмотров и выкачивает просмотренные видео.
- **Telegram-бот источников** — принимает ссылки на видео, которые пользователь отправляет ему в чат, и ставит их на загрузку.

#### Устройство загрузчика

Скраппер работает с двумя очередями:

- **очередь загрузки** — содержит объекты `youtube_video`; изначально в них есть только ссылка;
- **очередь отправки в core** — содержит те же объекты после скачивания: с аудио-/видеофайлом (см. ниже) и метаданными.

Порядок работы:

1. Демон по очереди обходит режимы, включённые в конфиге: каждый режим сканирует свой источник и находит видео.
2. Перед добавлением видео в очередь загрузки проверяется, что его нет ни в одной из двух очередей и ни в core. Проверка в core выполняется по `source` и `source_url`.
3. Пока суммарный размер скачанных файлов меньше X ГБ, загрузчик берёт видео из очереди загрузки и скачивает его. Перед скачиванием ещё раз проверяется по `source` и `source_url`, что видео нет в core, и что его нет в очереди отправки в core.
4. Пока видео не загружено полностью, оно остаётся в очереди загрузки. Как только загрузка завершена, объект сразу переносится в очередь отправки в core.

#### Аудио или видео

Для каждого режима настраивается, что именно скачивать: только аудио или видео целиком.

- **Сканер каналов** хранит режим загрузки для каждого канала в списке каналов. В конфиге задаётся значение по умолчанию. Это значение по умолчанию именно для пользователя, а не для системы: оно соответствует положению переключателя при добавлении канала в админке, поэтому поле режима в списке каналов не может быть пустым.
- **Сканер плейлистов** работает так же, как сканер каналов.
- **Сканер истории** настраивается отдельно для shorts и для обычных видео.
- **Telegram-бот** запрашивает режим отдельно для каждого видео.

#### Очередь отправки в core

Очередь реализована на SQLite и работает по принципу FIFO.

#### Передача видео в core

Передача идёт прямым запросом со стороны скраппера. Задача остаётся в очереди скраппера, пока core не подтвердит, что она выполнена. Если вдруг core говорит что такой записи у него нет, мы передаем ему её.

1. Если очередь пуста - мы отправляем задачу, если не пуста - проверяем статус текущей задачи и ждем пока она не уйдет из статуса обработки.
2. Core регистрирует record у себя.
3. Пока core обрабатывает задачу, запись и её файлы остаются в очереди и в папке с файлами.
4. Когда core подтверждает выполнение, скраппер удаляет запись из очереди и файлы из папки. Следующая запись становится первой.

#### Админка

Админка написана на FastAPI и открывается только из локальной сети. В ней можно:

- смотреть статистику по очередям (загрузки и отправки в core);
- смотреть и редактировать списки каналов и плейлистов, в том числе выбирать режим загрузки (аудио или видео) при добавлении;
- включать и выключать режимы работы.

### Telegram

Скраппер Telegram — демон, устроенный так же, как скраппер YouTube: режимы выполняются последовательно, очередь отправки в core хранится в SQLite (FIFO, персистентна), скраппер сам пушит записи в core и удаляет их из очереди и папки с файлами только после подтверждения от core. Админка — на FastAPI, только из локальной сети.

#### Доступ к Telegram

История каналов и чатов читается через MTProto (например, Telethon или Pyrogram) от имени пользовательского аккаунта: Bot API не умеет читать историю каналов, в которых нет бота. Файл сессии — секрет, в репозиторий не попадает. При `FloodWait` скраппер ждёт указанное время и продолжает.

#### Идентификация записи

- Record — одно сообщение канала или чата. Альбом (сообщения с общим `grouped_id`) — один record с несколькими файлами.
- `source` = `telegram`.
- `source_url` в каноническом виде: для публичных каналов `https://t.me/<username>/<message_id>`, для приватных `https://t.me/c/<internal_id>/<message_id>`. Для альбома берётся ссылка на первое сообщение.
- `text` = текст или подпись, `author` = канал или отправитель, `source_created_at` = дата отправки сообщения.
- `parent_source_url` = сообщение, на которое это ответ. У пересланных сообщений оригинал записывается в `metadata`, а ключ строится по текущему сообщению.

#### Режимы работы

- **Сканер каналов** — обходит список каналов. Для каждого хранится `last_message_id`: скраппер читает только новые сообщения, а при первом запуске — всю историю.
- **Сканер чатов** — то же самое для групп и личных диалогов из явного списка.
- **Бот источников** — принимает пересланные сообщения и ссылки на посты и ставит их на скачивание.

Перед добавлением сообщения в очередь отправки проверяется, что его нет в очереди и в core (по `source` и `source_url`). Проверка в core нужна и при наличии `last_message_id`, на случай сброса состояния.

#### Что скачивать

Для каждого канала или чата настраивается глубина: только текст, текст и фото, или всё (включая видео и документы, с ограничением по размеру). Значение по умолчанию в конфиге задаётся для пользователя, а не для системы: оно соответствует положению переключателя при добавлении канала в админке, поэтому поле в списке каналов не бывает пустым. Голосовые сообщения и кружки идут как аудио на транскрибацию.

#### Ограничения

- Отредактированные сообщения не перечитываются.
- Удалённые на источнике сообщения не отслеживаются.

#### Админка

- статистика по очереди отправки в core;
- список каналов и чатов, в том числе выбор глубины скачивания при добавлении;
- включение и выключение режимов работы.

## Клиенты

Клиент — это ИИ-агент со своим интерфейсом (сейчас Telegram-бот). Клиент является источником задач для балансировщика с наивысшим приоритетом. К балансировщику он обращается за тяжёлыми задачами (например, транскрибацией), а к core — за поиском.

### Цикл обработки запроса

1. Пользователь отправляет боту голосовое сообщение.
2. Клиент кладёт задачу транскрибации в очередь своего источника. Клиенты самые приоритетные, поэтому воркеры обработают её раньше задач скрапперов.
3. Когда транскрипция готова, клиент запускает ИИ-агента с текстом запроса.
4. Агент ищет ответ с помощью инструментов (см. ниже).
5. Клиент отправляет пользователю одно сообщение с ответом и ссылками.

### Инструменты агента

- **Семантический поиск** по эмбеддингам в core.
- **SQL-запросы** по полям record и `metadata` (дата публикации, источник и т. д.).
- **Получение fragment** в отрендеренном виде (например, страница PDF как изображение).
- **Получение element** (текст, картинка, транскрипция аудио).

### Формат ответа

Ответ приходит одним сообщением: сам ответ на вопрос и список ссылок на источники. Ссылки берутся из `source_url` записей (record), на которых основан ответ.
